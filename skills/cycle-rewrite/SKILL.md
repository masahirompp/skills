# cycle-rewrite — サイクル型リライト開発ワークフロー

## 狙い

AI 開発ではコード生成速度が人間の理解速度を上回り、人間の頭の中の理論とコードが乖離していく(Naur "Programming as Theory Building")。この乖離=認知負荷は防げないので、発生を前提に定期的にリセットする。サイクルごとにコードをゼロから書き直し(Brooks「捨てるつもりで作れ」。AI でリライトの限界費用が激減したため再び成立する)、永続資産はコードではなく仕様と学びに置く。

中心原則は、永続層と使い捨て層をリポジトリ内で物理的に分離すること。

| 層 | 中身 | 扱い |
| --- | --- | --- |
| 永続層 | `docs/PRODUCT.md`、`docs/adr/`、`CONTEXT.md`、`.claude/skills/`、`CLAUDE.md` / `AGENTS.md`、cycle-end で昇格したコード | 厳格に維持し、サイクルを跨いで積み上げる |
| 使い捨て層 | `src/` とテストコード | 品質は「動けばOK」。サイクル末に全削除 |

コードは雑に、ドキュメントは厳格に。捨てていいのはコードだけで、学びを捨てるとサイクルが収束しない。

層の実パスは init で確定し、CLAUDE.md の規約ブロック「層の定義」に記録する。以降の全モード(特に cycle-end の削除対象)はそこを正とする。本スキルの `src/` はその略記。

前提: mattpocock-skills の grilling・domain-modeling(補助に prototype)と GitHub(issue・マイルストーン・gh CLI)。仕様詰めは grilling を domain-modeling と併用して行う(ユーザー起動の /grill-with-docs と同じ組み合わせ。/grill-with-docs は Claude からは起動できない)。本スキルは grilling を再実装せず、起動のタイミングと前提整備を担う。

## 現在地の把握

専用の状態ファイルは持たない。git タグとマイルストーンが正で、儀式の成果物そのものが状態になる。

- 現在のサイクル番号 N = `git tag -l 'cycle-*'` の最大番号 + 1(タグが無ければ 1)
- サイクル進行中か = マイルストーン `cycle-N` が open か、`src/` が存在するか

CLAUDE.md に cycle-rewrite 規約が無く、ユーザーが導入を求めてもいないプロジェクトには勝手に適用しない。方式を短く紹介し、導入の意思を確認してから init に進む。

## モード

各モードの手順は references にある。実行前に該当ファイルを読む。

| ユーザーの状況 | モード | 手順 |
| --- | --- | --- |
| 新規プロジェクトのセットアップ | init | [references/init.md](references/init.md) |
| サイクルを始める・仕様を詰め直す | cycle-start | [references/cycle-start.md](references/cycle-start.md) |
| 実装・動作確認中に学び/バグ/仕様変更/ハマりが出た | capture | 下記 [capture](#capture) |
| 実装完了後、前サイクルから失われた仕様・機能がないか点検したい | cycle-audit | [references/cycle-audit.md](references/cycle-audit.md) |
| サイクルを畳む・リセットする・作り直す | cycle-end | [references/cycle-end-ceremony.md](references/cycle-end-ceremony.md) |
| 次サイクルに行くべきか、通常開発に移るべきか、移行後に一部で再開するかの相談 | transition-check | [references/transition-check.md](references/transition-check.md) |

「リセットしたい」「作り直したい」は cycle-end(儀式を経てから次へ)。判別に迷えばユーザーに確認する。

## capture

実装・動作確認中の学びを、発見の都度 GitHub issue に起票する。issue は学びの受信箱であり、次サイクルのインプットには使わない。蒸留は cycle-end の棚卸しでまとめて行う(文脈が揃った境界で一括処理する方が矛盾も見つかる)。

- `gh issue create` にラベル(`bug` / `learning` / `spec-change` / `decision-log`)と現在サイクルのマイルストーンを付ける
- 対象: エッジケース、想定外挙動、暗黙の要件の発覚、ライブラリのハマり、仕様変更の申し送り、AI の内部設計判断
- 形式は雑でよいが、内容は正確に書く。未決の設計選択を確定済みとして書いたり、原因を推測で断定したりしない
- バグは、まず PRODUCT.md / CONTEXT.md にその挙動の仕様があるか照合する。無ければ暗黙の要件の発覚で、正しい挙動そのものが未決。期待動作を決め打ちせず、ドメイン語の選択肢(例: 重複は冪等に無視 / エラーで拒否)を併記して起票する
- 起票は可逆な受信箱への記録で、承認は要らない。人間の回答を待たずに起票してから報告し、作業を続ける。その場で docs を直したりスキルを作ったりしない。起票が人間の応答待ちになると捕捉が律速され、学びが漏れ始める

## 実装セッションの規律

実装は cycle-start が渡す指示文で起動される別セッションで行う。インプットは蒸留済み docs と指示文の完了条件だけ。

- **進め方**: 完了条件の形から決まる。受け入れシナリオ型なら直接実装、設計上の問い型なら /prototype。儀式コストはサイクル境界に集中させ、サイクル内は最小化する
- **prototype の後始末**: prototype スキルは試作物を main 外のブランチに残し、そのポインタを実装 issue に書くよう求める。本方式には実装 issue が無いので、ポインタは実装計画ジャーナルに追記し、得た答え(問いと判定)は capture で起票する。試作ブランチは作業ツリー外にあるので汚染防止の規律に反しない
- **実装計画ジャーナル**: 最初に実装順序を `decision-log` issue 1本に起票し、計画変更や中断時の現在地をそこへ追記する。再開セッションはこれと完了条件・コードの実態を突き合わせて続きから進む
- **分割・並列化はセッション内で自律に行う**(worktree サブエージェント等)。issue をタスクの媒介にしない。タスク issue は受信箱の意味論と衝突し、棚卸しを濁す。/to-spec → /to-tickets のチェーンは、PRODUCT.md が生きた spec を兼ねるため既定では使わない
- **停止条件**: 完了条件を満たすまで自律で進める。途中で人間に止めてよいのは下記の層2・層3のエスカレーションだけ

### AI の自律判断(3層)

init が CLAUDE.md に書き込むルール。

1. **内部設計の変更**(外から見える挙動が変わらない): 自律で進め、判断を `decision-log` issue に記録する(事前承認ではなく事後監査)。記録が無いと、動作確認で気づけなかった乖離が次サイクルで繰り返される
2. **観測可能な挙動・仕様の変更**: エスカレーションする。質問は「挙動 A と B のどちらが欲しいか」というドメイン語の二択にし、コード理解を要求しない。挙動の選択として表現できない変更は層1。仕様に無い挙動を変えるバグ修正もここに入る
3. **不可逆・外部影響**(課金、外部 API 契約、データ破壊等): 常に同期でエスカレーションする。サイクルリセットで取り消せない

## 全モード共通の規律

- **テスト**: 人間が手動確認できる規模の間は省略してよい。追いつかなくなったら PRODUCT.md の Testing Decisions から再生成する。使い捨て層のテストコードはサイクル間で流用しない(精査コストが再利用の利益を上回る)。昇格したコードのテストは例外で、持ち越して維持する
- **昇格したコード**: 依存は使い捨て層 → 昇格したコードの一方向のみ(逆依存があると src/ 削除で main が壊れる)
- **コンテキスト汚染防止**: 旧サイクルのコードを作業ツリーに置かない(AI が読んで流用する)。参照は `git show cycle-N:src/...` か作業ツリー外の `git worktree`
- **PR は使わない**: コード単位の人間レビューをしない本方式では PR は空のゲートで、PR コメントは issue → docs の捕捉経路の外に学びを漏らす。短命ブランチ(worktree)で作業し、ローカルチェック通過を条件にローカルで main にマージする。クラウドのリモートエージェント併用時のみ PR を統合点として許容する
- **不変条件は「main は常に起動する」のみ**
- サイクルの区切りはタグで行い、リポジトリ・ブランチ・サブフォルダでは分けない(資産の分断、マージしないブランチの履歴破壊、コンテキスト汚染のため)
