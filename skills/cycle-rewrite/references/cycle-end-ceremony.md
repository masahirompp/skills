# cycle-end 儀式の手順

サイクルを畳み、学びを永続 docs に蒸留してから使い捨て層を消す。順序に意味がある。棚卸しの前に issue を close するとルーティング漏れが起き、タグの前に `src/` を消すと復元手段が消える。

全体の流れ: 事前確認 → ふりかえり捕捉 → issue 棚卸し → ADR 遷移 → CONTEXT・Memory 剪定 → 全ファイル棚卸し → テストシナリオ更新 → 昇格(任意) → close → コミット+`git tag cycle-N` → 承認を経た src/ 削除 → 次へ

## 進め方の原則

- **分析は承認なしで先に済ませる**: ふりかえりの捕捉と、open issue 全件の宛先割当(台帳)は AI の分析作業。最初の応答で台帳まで出す。昇格の可否などの承認質問を台帳より先に単独で挟むと、人間が答えるまで棚卸し本体が始まらない
- **全体像を先に見せる**: 承認は複数ターンに渡る。承認に入る前に、上の流れ(タグが削除より先であること、昇格モジュールとそのテストは削除対象外であること、等)を人間に見せ、到達点を誤解したまま承認が進まないようにする
- **承認は1件ずつ**: docs への反映は issue ごとに具体的な反映案を示して確認し、合意したら反映して次へ進む。台帳全体や複数論点(台帳の妥当性・昇格・削除)をまとめて承認させると、確認ゲートが形骸化する。昇格と削除の承認はそれぞれの段で個別に取る

## 0. 事前確認

- N を確認し、作業ツリーが clean で main が起動することを確かめる
- サイクル2以降なら cycle-audit の実施有無を、監査台帳 issue の有無で判定する: `gh issue list --milestone "cycle-N" --state all --search "cycle-audit:"`。無ければ、任意である旨を添えて実行を提案する。src/ 削除後は現サイクルの実装漏れを検出できなくなるので、実行するなら儀式の前が最後の機会([cycle-audit.md](cycle-audit.md))

## 1. ふりかえりの捕捉

畳む動機と、何が覆ったかを人間から聞き取り、`spec-change` issue として起票する。会話で既に示されていれば聞き直さずに起票する。方向転換の判断は畳むと決めた瞬間に言語化されることが多く、受信箱にまだ無い。これが無いと ADR 遷移と CONTEXT 剪定の根拠が欠ける。聞き取るのは判決(何が死んだか)までで、次サイクルの新仕様は cycle-start の grilling に送る。

起票は capture と同じく承認不要。環境の制約で失敗したら、判決を台帳の1行として載せて続行する。

## 2. issue 棚卸し

サイクル中の受信箱を永続 docs に蒸留する。専用の学びファイル(LEARNINGS.md 等)は作らない。

1. **全件取得**: `gh issue list --milestone "cycle-N" --state open --limit 200`。`--limit` を超えた分は黙って切り捨てられるので、マイルストーンの `open_issues` 数と照合する
2. **台帳**: 全件を下表の宛先か「close(蒸留不要)」に割り当てる。1件が複数宛先を持つことがある(例: 機能廃止 → PRODUCT.md の Out of Scope + CONTEXT.md の用語剪定)。宛先は「ファイル+セクション+操作」の粒度で書く(例: 「PRODUCT.md: Out of Scope 追記 + User Stories の該当項目を削除」)。承認者は台帳の行だけで何が起きるか判断するため、「仕様更新」のような曖昧な書き方では割当として不完全。台帳の段階ではファイルを編集しない
3. **反映**: 1件ずつ具体的な反映案を示して確認し、合意したら反映する。保留した issue は最後に再訪し、最後にルーティング結果の一覧を示す

| 学びの種別 | 宛先 | 処理 |
| --- | --- | --- |
| 仕様: 判明した要件、やらないと決めた機能 | `docs/PRODUCT.md` | 該当セクションを更新。やらないことの正は Out of Scope |
| 設計判断: 採用しなかった案とその理由 | `docs/adr/` | 新規 ADR、または既存 ADR のステータス遷移(§3) |
| 実装・環境のハマり: コードを捨てても再発しうるもの | `.claude/skills/` | 対象単位で集約(下記) |
| プロセス: 進め方のルール | `CLAUDE.md` / `AGENTS.md` | 該当セクションに追記 |

判断基準は「コードを全部捨てた後も、この知見は真か」。偽なら close してよい(例: 捨てるコードに紐づく実装判断の decision-log)。ただし「既存 docs と矛盾しない」は close の理由にならない。ライブラリのハマりやプロセスの学びのように矛盾しない加算的な知見こそ新しい置き場を必要とし、落とすと次サイクルで同じ穴に落ちる。

**ADR 行きとスキル行きの区別**: どちらもライブラリの学びとして現れる。採用可否に関わる学び(例: 「Fuse.js は5000件超で破綻」)は設計判断なので ADR へ行き、その技術を採用した既存 ADR があればステータス遷移させる。使い方の罠(例: 「dexie はトランザクション内 await で即コミット」)は採用を覆さないのでスキルへ。issue の技術名は `docs/adr/` と突き合わせてから宛先を決める。採用可否の学びをスキル化すると、覆った ADR が Accepted のまま残って次サイクルで尊重され続ける。

**issue 以外の受信箱も見る**: パイプラインの実行ログなど issue 外のファイルや、Claude Code のセッション横断メモリ(Memory)に未蒸留の学びがあれば台帳に載せる。メモリはリポジトリの外にあり、プロジェクトの資産にならない。方針だけ決めて docs 反映前に close された issue も、見つけたら台帳に加える。

**プロジェクトスキルの集約**: 事象単位ではなく対象単位(ライブラリ/ツール/サブシステム。例: `working-with-dexie`)で集約する。スキルのメタデータは常時コンテキストに載るため、数を増やすと常駐コストが増える。既存があれば追記し、無ければ `.claude/skills/<対象名>/SKILL.md` に frontmatter(`name` と、いつ読むべきかを含む `description`)付きで作る(平置きの .md はスキルとして読み込まれない)。破ると環境が壊れる級の罠は、発火が確率的なスキルではなく CLAUDE.md に書く。

## 3. ADR ステータス遷移

覆った ADR は削除せずステータスを遷移させる(Nygard 式)。削除すると「なぜ捨てたか」が消え、同じ案が再採用される。遷移前に ADR 本文を読み、覆す issue と対応づける。対応づく issue の無い ADR には触らない。

- 新しい判断が置き換えた → `Status: Superseded by ADR-XXXX` と新 ADR
- 不採用と確定した → `Status: Rejected` と理由
- 注記を足して Accepted のまま残すのは遷移ではない。読み手は Status を見て尊重の要否を判断する

## 4. CONTEXT.md と Memory の剪定

CONTEXT.md は生きた用語集なので、失効した用語は削除・書き換えてよい(追記型の ADR とは扱いが違う)。PRODUCT.md 行きにした spec-change ごとに、消えた概念の用語が残っていないか照合する。残すと次の grilling が死んだ用語を前提にする。

Memory も同じ観点で剪定する(機能が無い環境ではスキップ)。src/ 削除でリセットされないため、使い捨て層のパスや廃止した概念を記したメモリが次サイクルの汚染源になる。未蒸留の学びを台帳に回収したうえで、失効分を削除・更新し、MEMORY.md の索引を同期する。承認は要らないが、変更一覧を報告する。

## 5. 全ファイル棚卸し

§2〜4 で確定した判決を、リポジトリに残る全ファイル(永続層 docs、CLAUDE.md、プロジェクトスキル、README、設定類、データ層の資産)に波及させ、「保持 / 書き直し / 削除」で分類する。基準は「このサイクルの判決を反映してもまだ真か、次サイクルでも使われるか」。次サイクルの新方向の先取りはしない(それは grilling 後の cycle-start が行う)。ここで失効分を落としきるほど、cycle-start の棚卸しは grilling 由来の差分だけで済む。

分類は承認不要の分析として示し、削除・書き直しは承認を得てから行う(復元手段は git 履歴)。使い捨て層とその付随成果物は §10 で扱う。

## 6. テストシナリオの更新

このサイクルで確立・変化した受け入れ条件(自然言語)を PRODUCT.md の Testing Decisions に反映する。テストコードは持ち越さず、必要になったらここから再生成する。

## 7. モジュール昇格(任意・要承認)

「次サイクルでもそのまま使いたい」モジュールは、削除の例外ではなく永続層への昇格として扱う。

基準は完成度ではなく仕様の収束。要望を受けたら AI が実際に点検し、結果を根拠として示して承認を得る。「検証済みでよく動く」という申告はきっかけであって根拠ではない。

- そのモジュールに触れる `spec-change` issue が直近サイクルに無い
- grilling がその領域で新発見・新用語を出していない
- インターフェースが切り出せ、使い捨て層への依存が無い
- 書き直しの費用が例外的に高い(実世界で経験的に検証されたコード。スクレイパー、外部 API アダプタ等)。「よく書けている」だけなら、知見をスキルに蒸留して書き直す方が方式に沿う

承認後は次の4点を1つの操作として行う。

1. `lib/` へ移動する(逆依存が残ると src/ 削除で main が壊れる)
2. テストを持ち越す(以後は厳格に維持する永続層なので、テストが品質ゲートになる)
3. インターフェース契約を永続 docs に書く(例: `docs/modules/<name>.md`)。次サイクルは契約経由で使い、中身を読まない
4. ADR に記録する。後で仕様が覆ったら ADR を遷移させて降格する

移動だけの「lib/ 置きっぱなし」は、削除の例外が名前を変えただけになる。昇格が数サイクル続くならプロジェクト全体の収束シグナルなので、transition-check を勧める。

## 8. close

棚卸し完了後、マイルストーンの open issue とマイルストーン自体を close する。

```bash
gh issue list --milestone "cycle-N" --state open --limit 200 --json number -q '.[].number' \
  | xargs -I{} gh issue close {} -c "cycle-N 棚卸し済み"
MS_NUM=$(gh api "repos/{owner}/{repo}/milestones" --jq '.[] | select(.title=="cycle-N") | .number')
gh api -X PATCH "repos/{owner}/{repo}/milestones/$MS_NUM" -f state=closed
```

## 9. コミットとタグ

docs と昇格の変更をコミットし(例: `docs: cycle N 棚卸し`)、`git tag cycle-N` を打つ。リモートがあれば push する。

## 10. src/ の削除(要承認)

破壊的操作なので、次を示して明示的な承認を得てから実行する。

- タグの存在(`git tag -l 'cycle-N'`)。タグがあれば `git show cycle-N:src/...` で全復元できる
- 削除対象: CLAUDE.md の層の定義にある使い捨て層、テストコード、テスト用フィクスチャ。さらに使い捨て層の付随成果物(削除するコードの運用手順書、そのコマンドを参照するプロジェクトスキル、実行ログ)も、`docs/` や `.claude/skills/` にあっても削除対象として点検する。残すと次サイクルが存在しないコマンドを前提に動く
- 残すもの: ルートの設定類、`.claude/`、`docs/`、`CONTEXT.md`、`CLAUDE.md`、昇格済みモジュールとそのテスト。迷うもの(package.json の依存等)は個別に確認する

削除してコミットしたら(例: `chore: cycle N end — reset disposable layer`)、コミットとフックが通ることを確かめる。パッケージ定義やフックが使い捨て層を参照していると、git コミット自体が壊れる(例: pre-commit がパッケージをビルドし、バージョン源の `src/<pkg>/__init__.py` が無くて全コミットが失敗する)。壊れたら最小の stub を置いて不変条件を回復する。

## 11. 次へ

次サイクル(cycle-start)か、収束していれば通常開発への移行(transition-check)を提案する。cycle-start は別セッションで始める前提で、起動用の短い指示文(使い捨て。コミットしない)を渡して終える。中身は「タグ `cycle-N` 済みという現在地」と「次の一手 = /cycle-rewrite cycle-start」だけにし、学びや仕様は docs にあるので重複させない。
