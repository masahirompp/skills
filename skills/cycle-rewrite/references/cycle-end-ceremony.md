# cycle-end 儀式の詳細手順

順序が重要である理由: 棚卸しの前に issue を close すると学びのルーティング漏れが起きる。タグを打つ前に `src/` を消すと復元手段が消える。必ずこの順で進める。

## 0. 事前確認

- 現在のサイクル番号 N を確認する(`git tag -l 'cycle-*'` の最大番号 + 1)
- 作業ツリーが clean か(`git status`)。未コミットの変更があれば先に main へ取り込む
- main が起動するか(不変条件の最終確認)
- サイクル2以降なら、cycle-audit(蒸留監査)の実施有無を確認する。判定は人間への質問ではなく**監査台帳 issue の有無**で行う: `gh issue list --milestone "cycle-N" --state all --search "cycle-audit:"`(監査は台帳を `decision-log` issue として必ず残す — [cycle-audit.md](cycle-audit.md) §4)。台帳 issue があれば実施済みとしてそのまま進む。無ければ未実施 — 任意である旨を添えて実行を提案する。必須ではないが、src/ 削除後は前サイクルとの挙動比較ができても現サイクルの実装漏れ検出が意味を失うため、実行するならこの儀式の前が最後の機会。実行するなら [cycle-audit.md](cycle-audit.md) を読み、儀式より先に監査を完了させる(監査が起票した issue はそのまま棚卸し(§2)に乗る)。見送るなら儀式を続行する

## 1. ふりかえりの聴取と捕捉

**棚卸しの前に、ふりかえりを捕捉する。** サイクルを畳む動機とふりかえり(何がうまくいかず、どの決定が覆ったか)を人間から聞き取り、`spec-change` issue として起票してから全件取得に進む(会話や起動時の引数で既に提示されていれば改めて聞かず、そのまま起票する)。方向転換の判断は畳むと決めた瞬間に言語化されることが多く、issue 受信箱にまだ無いことがある — この捕捉が無いと、§3 の ADR 遷移(覆す issue との対応づけ)と §4 の CONTEXT 剪定(失効判定)が駆動できない。聞き取るのは判決(何が死んだか・何を排除するか)まででよく、次サイクルの新仕様の中身は cycle-start の grilling に送る。

この起票は capture と同じく**受信箱への記録であり、人間の承認を要しない** — 起票の許可を求めて儀式を止めない。環境の制約で起票が失敗しても停止しない: ふりかえりの判決をそのまま台帳(§2)の1行として乗せて続行し、起票は儀式の締めに人間へ依頼すればよい。ここで止まると、承認を要しないはずの分析(台帳)まで人間の応答待ちに巻き込まれる。

## 2. issue 棚卸し(4宛先ルーティング)

サイクル中の issue 受信箱を永続 docs に蒸留する。専用の学びファイル(LEARNINGS.md 等)は作らない — 蒸留先は既存の永続ドキュメントのみ。棚卸しは3つの原則で動く。手順の細部で迷ったら原則に立ち返る:

- **分析は一括**: 全件を宛先に割り当てた台帳は、人間の承認を要しない AI の分析作業。儀式を開始する最初の応答に、ふりかえりの捕捉(§1)から台帳までを必ず含める。台帳より先に承認質問(昇格の可否等)を単独で挟まない — 人間が答えを返すまで棚卸し本体が始まらない。承認事項はすべて台帳提示後の承認ループと後続手順(§5・§10 の削除承認、§7 の昇格承認)に乗せる
- **全体像は先に見せる**: 反映の承認は複数ターンに渡る。台帳と同じ応答に儀式全体の正準ロードマップ(手順3)を転記し、タグが削除に先行する安全順序と最終到達点を、人間がループに入る前に見せる — 到達点を誤解したまま承認が進むことがなく、途中でセッションが切れても人間が儀式のどこにいるか分かる
- **承認は逐次**: 人間の認知負荷がかかるのは反映の承認。1件ずつ確認を取り、合意したらその場で反映して次へ。台帳全体への一括同意(「この方針でよければ進めます」等)を求めた時点で包括承認になり、確認ゲートが形骸化する。「確認事項: 1. 台帳の妥当性 2. 昇格の可否 3. 削除の承認」のような**複数論点の確認リストも形を変えた包括承認** — 昇格や削除の承認はそれぞれの手順(§5・§7・§10)の番になってから個別に取る。台帳を提示する応答の締めは常に「#X(1件目)の反映案 — この1件を反映してよいか」の形にする

手順:

1. **全件取得**: `gh issue list --milestone "cycle-N" --state open --limit 200`。取得件数がマイルストーンの open 数(`gh api` の `open_issues`)と一致することを照合する — `--limit` を超えた分は黙って切り捨てられ、台帳の「全件」が偽になる
2. **台帳作成**: 全件を下表の4宛先または「close(蒸留不要)」に割り当てる。issue 件数と割当件数の照合を台帳に付け、1件でも未割当が残っていれば棚卸しは未完。1つの issue が複数宛先を持つことがある(例: 機能廃止の spec-change → PRODUCT.md の Out of Scope + CONTEXT.md の用語剪定)。宛先欄は、後続の反映がそのまま実行できる粒度 — **ファイル+セクション+操作** — で書く(例: 「PRODUCT.md: Out of Scope 追記 + User Stories 該当項目の削除」)。承認者は台帳のその行だけを見て何が起きるかを判断する — 「仕様更新」「User Story 修正」のような操作の特定できない表現は割当として不完全で、項目を殺すなら「削除」まで台帳の時点で明示する。**台帳の段階ではファイルを一切編集しない** — 反映は承認ループで各 issue の承認を得た後にのみ行う
3. **ロードマップ転記**: 台帳と同じ応答で、次の正準文言を**そのまま転記**する(この文言の正はここにのみ置く):

   > ADR 遷移 → CONTEXT・Memory 剪定 → 承認を経た全ファイル棚卸し(失効 docs 等の削除) → テストシナリオ更新 → 昇格(lib/ 移動・テスト持ち越し・契約 docs・ADR 記録の4点) → close → `git tag cycle-N` → 承認を経た src/ 削除(昇格モジュールと**そのテスト**は除外)

   括弧内の構成要素は要約時に脱落しやすいが、省くと人間は到達点を誤解したまま承認ループに入る(例: テスト持ち越しを知らずに昇格を承認する、昇格モジュールのテストまで消えると誤解する)
4. **承認ループ**: 台帳に沿って issue を1件提示し(タイトル・要点・ラベル)、推奨宛先と**具体的な反映案**(どのファイルのどのセクションに何をするか)を添えて、この1件だけの確認を取る。台帳を提示する応答も、必ず**1件目の issue の反映案とその1件だけの確認**で締める。保留した issue は最後にまとめて再訪する
5. **締め**: 全件終了後、最終のルーティング結果一覧表(issue → 宛先)を提示する

| # | 学びの種別 | 宛先 | 処理 |
| --- | --- | --- | --- |
| 1 | 仕様レベル: 判明した要件、やらないと決めた機能 | `docs/PRODUCT.md` | 該当セクションを更新。「やらないことリスト」の正は Out of Scope セクション |
| 2 | 設計判断レベル: 採用しなかった案とその理由 | `docs/adr/` | 新規 ADR 起票、または既存 ADR のステータス遷移(→ §3) |
| 3 | 実装・環境レベルの個別ハマり: コードを捨てても再発しうるもの(ライブラリの罠等) | `.claude/skills/` | 対象単位で集約(→ 下記) |
| 4 | プロセスレベル: 進め方のルール(例:「並列度3以上でレビュー破綻」) | `CLAUDE.md` / `AGENTS.md` | 該当セクションに追記 |

どの宛先にも当てはまらない issue(単なる作業ログ、次サイクルには関係しない事象)はそのまま close してよい。判断基準: **「コードを全部捨てた後も、この知見は真か?」** — 偽なら蒸留不要。**「既存 docs と矛盾しない」は close の基準ではない** — 仕様変更や ADR を覆す知見は既存文書との矛盾として立ち上がるため拾いやすいが、矛盾しない加算的知見(ライブラリのハマり → プロジェクトスキル、プロセスの学び → CLAUDE.md)こそ**新しい住所を必要とする**。棚卸しの主目的は後者の回収にある — 落とすと次サイクルで同じ穴に落ちる。

**宛先2(ADR)と宛先3(プロジェクトスキル)の混同に注意。** どちらもライブラリの学びとして現れるが、性質が違う:

- **採用可否に関わる学び**(例: 「Fuse.js は5000件超で破綻 → 不採用にすべき」)は設計判断 — 宛先は ADR。既存 ADR がその技術を採用していれば、スキル化ではなく**その ADR のステータス遷移**(→ §3)+必要なら代替案の新 ADR が正しい処理。issue に出てくる技術名・ライブラリ名は `docs/adr/` を必ず突き合わせ、対応する ADR の有無を確認してから宛先を決める
- **使い方の罠**(例: 「dexie はトランザクション内 await で即コミットされる」)は、採用は覆さず次サイクルも使う前提の注意書き — 宛先はプロジェクトスキル

採用可否の学びをスキル化すると、覆った ADR が Accepted のまま残り、次サイクルの仕様詰め・実装がそれを尊重し続けてしまう。

**受信箱は issue だけとは限らない。** パイプラインの実行ログなど issue 外の受信箱ファイルがあれば、その未蒸留の気づきも台帳に乗せる(そのファイル自体は使い捨て層の付随成果物として src/ 削除(§10)で消える — 削除前が最後の回収機会)。Claude Code のセッション横断メモリ(Memory。memory ディレクトリと MEMORY.md 索引。機能が無い環境ではスキップ)も受信箱として点検する — サイクル中に書き込まれたメモリには、issue にならなかった学びが眠っていることがある。メモリは利用者個人のローカル資産でリポジトリの外にあるため、そこに留まった学びはプロジェクトの永続資産にならず、他の環境・他の作業者には届かない — 該当があれば台帳に乗せて docs へ蒸留する(メモリ自体の剪定は §4)。また「方針だけ決めて close した issue」はコメントに決定が眠ったまま棚卸し(open のみ)をすり抜ける — close 時に docs 反映まで済んでいない issue を見つけたら、その場で台帳に加える。

### 宛先3(プロジェクトスキル)の集約ルール

- 事象単位(1ハマり=1スキル)ではなく**対象単位**(ライブラリ/ツール/サブシステム。例: `working-with-mediapipe`)で集約する。スキルのメタデータ(name + description)は常時コンテキストに載るため、スキル数に比例して常駐コストが増える。対象単位なら「その対象を触る瞬間に発火する」という発火条件と集約単位が一致する
- `.claude/skills/` に同一対象の既存スキルがあれば追記、なければ新規作成。新規作成は **`.claude/skills/<対象名>/SKILL.md`** の形式で置き、frontmatter に `name` と `description`(どんな作業のときに読むべきかを含む)を書く。平置きの `.md` ファイルはスキルとして発見・ロードされず、受動知識として機能しない
- 破ると環境が壊れる級の致命的な罠は、スキルではなく CLAUDE.md に書く(格上げ)。スキルの発火は確率的(undertrigger 傾向)で、確実に毎セッション読まれるのは CLAUDE.md のみ

## 3. ADR ステータス遷移

覆った ADR は**削除せず**ステータスを遷移させる(Nygard 式)。削除すると「なぜ捨てたか」が消え、次サイクルで同じ案を再採用するリスクが生じる。superseded は ADR 解釈ルール(「Accepted な ADR を尊重せよ」)に対する「もう尊重不要」の標準的な信号になる。

遷移の前に、対象 ADR の**本文を読み**、どの issue がそれを覆すのかを対応づけてから遷移する。Status 行やタイトルだけで「覆った」と判断しない。対応づく issue の無い ADR には触らない。

- 新しい判断が旧 ADR を置き換えた → 旧 ADR に `Status: Superseded by ADR-XXXX` を記し、新 ADR を起票する
- 検討の結果、不採用と確定した案 → `Status: Rejected` + 理由
- 覆った ADR に制約や注記を追記して `Status: Accepted` のまま残すのは遷移ではない。覆ったと対応づいたら Status 行を必ず書き換える(ADR の読み手は Status を見て尊重の要否を判断するため、注記だけでは次サイクルでも尊重され続けてしまう)

## 4. CONTEXT.md と Claude Memory の剪定

失効した用語を削除・書き換える。CONTEXT.md は現在の共有言語を表す**生きた用語集**であり、自由に剪定してよい(追記型の ADR とは扱いが異なる)。

剪定の主な駆動源は §1〜2 の spec-change — 仕様から消えた概念(機能の廃止・一本化)は用語集からも死ぬ。PRODUCT.md 行きにした spec-change ごとに、その概念の用語が CONTEXT.md に残っていないかを照合する。残すと、次サイクルの grilling が死んだ用語を共有言語として再前提化する。

Claude Code のセッション横断メモリ(Memory)も同じ観点で剪定する(機能が無い環境ではスキップ)。メモリはリポジトリの外にあるため src/ 削除ではリセットされず、サイクルを跨いで生き残る — 使い捨て層のファイルパスやコマンド、廃止した概念を記したメモリを残すと、次サイクルのセッションが存在しない前提を思い出して動く(CONTEXT.md の死んだ用語が再前提化されるのと同じ機構)。未蒸留の学びが §2 で台帳に回収済みであることを確認したうえで、失効したメモリを削除し、まだ真である事実は現状に合わせて書き換え、MEMORY.md の索引行を同期する。剪定はメモリという AI 自身の作業記録の整理であり人間の承認を要しないが、削除・書き換えた一覧を報告に含める。

## 5. 全ファイル棚卸し(現サイクルまでの失効の削除)

§2〜4 は台帳に対応づいた文書(ADR・CONTEXT.md・Memory)だけを直す。この段では対象を**リポジトリに残る全ファイル**に広げ、「保持 / 書き直し / 削除」の三分類で点検する。対象は永続層 docs(運用ポリシー、技術メモ、UI メモ、モデル図)、CLAUDE.md、プロジェクトスキル、README、設定類(パッケージ定義、フック、CI)、データ層の資産まで(使い捨て層とその付随成果物はここでは扱わない — §10 の削除対象)。

判断基準は「**このサイクルで確定した判決を反映しても、まだ真か・次サイクルでも使われるか**」。台帳・ADR 遷移・剪定で確定した判決を残りの全ファイルに波及させる作業であり、次サイクルの新方向を先取りする作業ではない — 新方向による棚卸しは cycle-start が grilling 後に行う。ここで現サイクルまでの失効分を落としきるほど、cycle-start の棚卸しは grilling で新たに生じた差分だけで済む(cycle-start の負担軽減がこの段の目的)。

三分類の一覧は AI の分析として提示する(承認不要)。削除・書き直しは、その一覧への人間の承認を得てから実行する — この段はまだタグ前なので、復元手段は git 履歴(直前のコミット)である旨を添える。分類に迷うファイルは個別に確認する。

## 6. テストシナリオの更新

このサイクルで確立・変化した受け入れ条件(自然言語)を `docs/PRODUCT.md` の Testing Decisions セクションに反映する。テストコード自体は持ち越さない — 次サイクルで手動確認が追いつかなくなったら、このシナリオから再生成する。

## 7. モジュール昇格(任意・要承認)

使い捨て層の中に「次サイクルでもそのまま使いたい」モジュールがあれば、削除の例外ではなく**永続層への昇格**として扱う。該当がなければこの節はスキップする。

判断基準は完成度ではなく**仕様の収束**。昇格の要望を受けたら、以下を **AI が実際に点検して**(そのモジュールに触れる spec-change issue の検索、使い捨て層への import の確認)、点検結果を根拠として人間に提示し、明示的な承認を得る(AI は独断で昇格を実行しない)。人間の「検証済みでよく動いている」という申告はきっかけであって根拠にならない — 完成度は基準ではないため、申告をそのまま受けて昇格に応じない:

- そのモジュールに触れる `spec-change` issue が直近サイクルで出ていない
- grilling がその領域に新発見・新用語を出していない
- インターフェースが切り出せて、使い捨て層への依存が無い
- 書き直しの限界費用が例外的に高い(実世界への実行で経験的に検証されたコード — スクレイパー、外部 API アダプタ等)。**単に「よく書けている」は昇格理由にならない** — 残したいのが知見だけなら、プロジェクトスキルに蒸留して次サイクルで書き直す方が方式に沿う

承認後の手順:

1. モジュールを昇格置き場(既定 `lib/`。CLAUDE.md の層の定義が正)へ移動する。依存方向は使い捨て層 → 昇格モジュールの一方向のみ — 逆依存が残っていると src/ 削除(§10)で main が壊れる
2. テストを Testing Decisions のシナリオから整備し、**持ち越す**。テスト持ち越し禁止は使い捨て層のルールであり、昇格モジュールは以後厳格維持 — テストが品質ゲートになる
3. インターフェース契約を永続 docs に書く(例: `docs/modules/<name>.md`)。次サイクルの実装セッションはこの契約経由で使い、中身のコードは読まない(外部パッケージと同格)
4. 昇格を ADR に記録する — 「サイクルを跨いでも覆らない判断」の定義そのもの。後の grilling で仕様が覆ったら、ADR をステータス遷移させてモジュールを**降格**する(使い捨て層に戻すか削除)

この4手順は分割不可の1操作として扱い、昇格を提案・計画する時点で4つすべてを明示する。どれかを省くと、契約なしで中身のコードを読まれる(3の欠落)か、覆ったときの降格経路が無くなる(4の欠落)。移動だけ済ませた「lib/ 置きっぱなし」は昇格ではなく、削除の例外扱いが名前を変えただけになる。

昇格が数サイクル続けて発生するなら、リセット対象が縮小している = プロジェクト全体の収束シグナル。個別要望として処理せず、transition-check を回す契機として人間に伝える。

## 8. issue・マイルストーンの close

棚卸し(§2・§5)が終わってから実行する:

```bash
# マイルストーンの open issue を全て close(200件を超える場合は open が 0 になるまで繰り返す)
gh issue list --milestone "cycle-N" --state open --limit 200 --json number -q '.[].number' \
  | xargs -I{} gh issue close {} -c "cycle-N 棚卸し済み"

# マイルストーン自体を close
MS_NUM=$(gh api "repos/{owner}/{repo}/milestones" --jq '.[] | select(.title=="cycle-N") | .number')
gh api -X PATCH "repos/{owner}/{repo}/milestones/$MS_NUM" -f state=closed
```

## 9. docs コミットとタグ

1. §2〜7 の docs・昇格の変更をコミットする(例: `docs: cycle N 棚卸し`)
2. `git tag cycle-N` を打つ。リモートがあれば `git push && git push --tags`

## 10. src/ の削除(要・人間の承認)

破壊的操作。**実行前に必ず以下を提示して、人間の明示的な承認を得る**:

1. タグの存在確認を見せる: `git tag -l 'cycle-N'`(タグがあれば `git show cycle-N:src/...` でいつでも全復元できる=実質可逆であることを伝える)
2. 削除対象の一覧: 使い捨て層(CLAUDE.md の層の定義が正。既定は `src/` 全体)、テストコード(`tests/`、`*.test.*`、`e2e/` 等)、テスト用フィクスチャ。昇格済みモジュールのテストは削除しない
3. **使い捨て層の付随成果物も削除対象として点検する**: 削除するコードの運用手順ドキュメント(起動手順、cron/launchd 設定手順)、コードのコマンドを参照するプロジェクトスキル、パイプラインの実行ログ。これらは `docs/` や `.claude/skills/` に置かれていても実質は使い捨て層で、残すと次サイクルが存在しないコマンドを前提に動く。ログの未蒸留の気づきは §2 で回収済みであること
4. 残すもの: プロジェクトルートの設定類(フォーマッター、リンター、tsconfig、CI 設定)、`.claude/`、`docs/`、`CONTEXT.md`、`CLAUDE.md`、昇格済みモジュール(`lib/`)とそのテスト
5. 判断に迷うファイル(package.json の依存など次サイクルの足場になり得るもの)は個別に確認する

承認を得てから削除し、コミットする(例: `chore: cycle N end — reset disposable layer`)。

**削除後、コミットとフックが通ることを確認する。** パッケージ定義(pyproject / package.json)やコミットフックが使い捨て層を参照していると、削除の瞬間に「main は常に起動する」だけでなく **git コミット自体が壊れる**(例: pre-commit が `uv run` 経由でパッケージをビルドし、バージョン源の `src/<pkg>/__init__.py` が無くて全コミット失敗)。壊れたら、最小の stub(バージョン定数だけのパッケージと import 確認テスト)を次サイクルの種として置き、不変条件を回復してから次へ進む。

## 11. 次へ

transition-check の収束シグナルに軽く触れつつ、次サイクル(cycle-start)に進むか、収束していれば通常開発ワークフローへの移行を提案する。

cycle-start は別セッションで開始する前提とし、その起動用の指示文(使い捨て。コミットしない)をユーザーに渡して儀式を終える。
指示文は「儀式完了の現在地(タグ `cycle-N` 済み、マイルストーン close 済み)と、次の一手 = 新セッションで /cycle-rewrite cycle-start」だけに絞る。
学びと仕様はすべて docs に蒸留済みであり、指示文に内容を重複させると docs との同期ずれの種になる。
