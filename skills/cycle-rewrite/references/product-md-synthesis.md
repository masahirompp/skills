# docs/PRODUCT.md の合成と更新

PRODUCT.md はサイクルを跨ぐプロダクト全体の最新要件・仕様の集約 = 「プロダクト全体の生きた spec」。機能単位・サイクル内使い捨ての spec(/to-spec の成果物)とは異なり、サイクルを跨いで維持する。

**単一ファイル・固定名(`docs/PRODUCT.md`)を守る。** cycle-start が機械的に読む正のファイルはパスが決定的である必要があり、可変サフィックスや複数分割は仕様の散在を再導入する。

**プロダクト戦略も別ファイルに分けず、Further Notes に置く。** 顧客仮説、フェーズ設計、GTM 候補、戦略レベルの却下案は spec の要件セクションには入れないが、「プロダクト・ブリーフ」等の並行ファイルにもしない — 同じ目的のファイルが2つあると仕様転換のたびに片方が失効注記まみれになり、しかも cycle-start の読み取り対象から漏れて次の grilling の視界に入らない。詳細な運用ポリシー(編集方針、ソース選定、著作権等)だけは独立ファイルでよい(spec と目的が異なるため)。

セクション構成は to-spec スキルの spec テンプレートに準拠する(spec の標準的な語彙と揃えるため)。見出しは英語のまま、本文はプロジェクトの言語で書く。

## テンプレート

```markdown
# <プロダクト名>

<!-- last updated: cycle N -->

## Problem Statement

ユーザーが直面している課題を、ユーザー視点で。

## Solution

課題の解決策を、ユーザー視点で。

## User Stories

番号付きの網羅的なリスト。形式: As a <actor>, I want <feature>, so that <benefit>

## Implementation Decisions

サイクルを跨いで有効な実装判断のみ(モジュール構成、アーキテクチャ判断、スキーマ、API 契約等)。
ファイルパスや具体的なコードスニペットは書かない — サイクル末に消えるため即座に陳腐化する。
例外: プロトタイプ由来の schema / 型 / 状態機械など、散文より正確に判断を表すものは要点のみ引用可。

## Testing Decisions

自然言語のテストシナリオ(受け入れ条件のリスト)。テストコードはサイクル末に捨てるため、
ここが次サイクルでテストを再生成するときの正となる。
外部から観測できる振る舞いだけを書く(実装詳細のテストは書かない)。

## Out of Scope

やらないと決めたことのリスト。**「やらないことリスト」の正はここ。**
理由も添える — 理由がないと、次サイクルの grilling で同じ提案が繰り返される。

## Further Notes

その他の補足。
```

## サイクル1: 合成手順

この合成は cycle-rewrite の担当。

1. grilling が完了した直後に行う
2. **追加インタビューはしない** — 会話に既にある内容の合成に徹する(to-spec と同じ方針)。埋まらないセクションは推測で埋めず、空である旨を明記して人間に知らせる
3. grilling の会話全体から上記テンプレートの各セクションを埋め、`docs/PRODUCT.md` に書く。CONTEXT.md に確立したドメイン用語を本文で使う
4. 書き上げたら人間に提示し、認識齟齬がないか確認する
5. 確認後、cycle-start の残り手順([cycle-start.md](cycle-start.md))へ戻る

## サイクル2以降: 更新手順

0. 前サイクルで PRODUCT.md が未合成のまま(仕様が別ファイルに散在)なら、差分更新ではなく上記の合成手順で初回合成し、散在元のファイルは統合して削除する(参照の張り替えを忘れない)
1. cycle-start の grilling で判明した変更を反映する。全書き換えではなく差分更新 — ただし矛盾が残らないよう関連セクションは通読する
2. 消えた要件は削除してよい。ただし「やらないと決めた」ものは削除ではなく Out of Scope へ移す(理由付き)。設計判断レベルの不採用は ADR 側(削除禁止・ステータス遷移)が受け持つ
3. `<!-- last updated: cycle N -->` を更新する
