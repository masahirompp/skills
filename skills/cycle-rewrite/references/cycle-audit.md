# cycle-audit の手順(蒸留監査)

実装完了後、cycle-end の前に人間が呼び出す任意の点検。前サイクルの実装と現況を突き合わせ、蒸留の過程(capture → 棚卸し → grilling → 実装)で失われた仕様・機能を見つけて issue で回収する。本方式の中心の賭け「学びと仕様は docs に蒸留され、コードを捨てても失われない」を、実物どうしの比較で検証できる唯一の機会。

出口は issue 起票に一本化し、このモードでは docs を編集しない。直接編集すると issue → 棚卸し → docs の単一経路の外に第二の経路ができ、反映漏れと矛盾の温床になる。起票した issue は cycle-end の棚卸しに乗る。

## 0. 前提

- タグ `cycle-(N-1)` が必要。サイクル1は比較対象が無く対象外
- 実装がほぼ完了していること。途中で走らせると「まだ作っていない」と「実装漏れ」を区別できない
- 任意であり、cycle-end の前提条件ではない

## 1. 比較の単位は観測可能な挙動

ゼロから書き直す方式ではほぼ全行が差分になるので、コード diff は使わない。外から見える挙動(層2と同じ単位)をドメイン語で目録にする: 提供している操作、各操作の入出力と状態変化、扱っているエッジケース(重複・空入力・境界値)。モジュール構成・ライブラリ・アルゴリズムなど内部設計の違い(層1)は毎サイクル変わるのが正常なので対象外。

## 2. 挙動目録の抽出

前サイクルの実装は本体セッションで読まない(監査後に同じセッションで修正作業が続くと、旧コードを流用する)。サブエージェントに `git show cycle-(N-1):<使い捨て層パス>/...` か作業ツリー外の `git worktree` で旧実装(テストを含む)を読ませ、ドメイン語の挙動目録だけを返させる。worktree を作ったら抽出後に削除する。現サイクルの目録は本体で作ってよい。

## 3. 突合と4分類

前サイクルにあって現サイクルに無い挙動・変わった挙動を列挙し、推測ではなく証跡で分類する。証跡は安い順に取る: `git diff cycle-(N-1) HEAD -- docs/ CONTEXT.md`、遷移済み ADR の本文、前サイクルの closed `spec-change` issue(差分に対応する判決の特定に限って読む。cycle-start の「旧 issue を読まない」は grilling への生ログ混入を防ぐ規則で、この照合には当たらない)。

| 分類 | 判定条件 | 処理 |
| --- | --- | --- |
| A. 意図した変更・削除 | 証跡あり(遷移した ADR、spec-change issue、Out of Scope 等) | 報告のみ。復活を提案しない |
| B. 意図した先送り | 現 docs に仕様があるが、今サイクルの完了条件の範囲外 | 報告のみ。次以降の cycle-start が拾う |
| C. 実装漏れ | 現 docs に仕様があり、完了条件の範囲内なのに未実装・挙動が違う | 蒸留は成功し、実装が失敗した。人間に提示 |
| D. 蒸留漏れ | 前サイクルに挙動があり、現 docs にもどの証跡にも痕跡が無い | 監査の本命。起票する |

C は今サイクル内で直す問題、D は docs の欠落で次の grilling に送る問題。二値に潰すと対処の違いが消える。

## 4. 出口

- **台帳を issue として残す**: 全差分の分類(各行に証跡の出典)を示し、同じ内容を `decision-log` issue(マイルストーン `cycle-N`、タイトルは `cycle-audit:` で始める)として起票する。差分ゼロでも起票する。状態ファイルを持たない本方式では、この issue が「監査実施済み」の唯一の痕跡で、cycle-end の事前確認がこれで判定する
- **D は capture と同じ規律**: 「次サイクルで復活 / 廃止を確定」のドメイン語二択を併記した `spec-change` issue をまず起票し、それから人間に確認する
- **C は層2の二択で提示**: 「今サイクルで直す / 先送りを確定」。人間が決めるまでコードは直さない。先送りなら spec-change として捕捉する
- **A・B は報告だけで閉じる**: 「全部戻しますか」とは聞かない。意図的なスコープ削減は健全な蒸留
- 差分ゼロもそのまま報告する。パイプラインが機能している証拠であり、空振りではない
