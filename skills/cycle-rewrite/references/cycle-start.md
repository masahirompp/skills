# cycle-start の手順

サイクル N を始め、仕様を詰めて実装セッションに引き継ぐ。

1. **N を導出**し、マイルストーン `cycle-N` が無ければ作る。`src/` が存在し `cycle-N` に open issue が残っていればサイクル進行中なので、実装の続行か cycle-end かを確認する
2. **インプットは蒸留済み docs だけ**: `docs/`(PRODUCT.md・adr/・昇格モジュールの契約)、`CONTEXT.md`、`CLAUDE.md`。旧サイクルの issue とコードは読まない。issue は矛盾・失効の混じった生ログで、それを蒸留したのが docs だから
3. **grilling スキルを domain-modeling と併用して仕様を詰める**(用語は CONTEXT.md、判断は ADR にその場で残る)。このサイクルの業務的な完了条件(「何がどう動けば完成か」をドメイン語の受け入れシナリオ数件で表したもの)を、最初のラウンドで人間と合意する。完了条件が先に決まると以降の質問の要否と深さが定まり、後回しにすると設計パラメータの質問に埋もれて合意されないまま終わる。作り直しは過剰設計に走りがちなので(第二システム症候群)、最新の要件に絞る
4. **PRODUCT.md に反映**する。サイクル1は grilling の会話から合成し、2以降は差分更新する([product-md-synthesis.md](product-md-synthesis.md))。合意した完了条件は Testing Decisions に書き、ここを正本にする
5. **grilling 由来の棚卸し**: 方向や仕様が変わったなら、残存ファイルを「保持 / 書き直し / 削除」で点検する。前サイクルまでの失効分は cycle-end で削除済みの前提なので、見るのは grilling で新たに生じた差分の波及だけでよい(cycle-end を経ていない形跡があれば全ファイルに広げる)。旧方向の記述を残すと、docs だけを読んで始まる実装セッションが汚染される
6. **実装は別セッションで始める**。起動用の指示文(使い捨て。コミットしない)を渡して区切る。中身は「現在地 / 正の docs のありか / capture 規律の適用 / 完了条件」だけにする
   - 仕様の中身は書かない。実装セッションは docs を読んで判断し、docs の書き漏れは実装が詰まって表面化する(それ自体が capture 対象の学び)。grilling の会話の記憶で補えてしまうと docs の欠落に気づけない
   - 完了条件だけは Testing Decisions から指示文にそのまま転記する。実装セッションが自律で進むための停止条件だから。設計上の問いに答えるサイクルなら「問い X に答えが出て capture 済み」を完了条件にする。「open issue が 0」のような機械的条件は補助ゲートにとどめ、完了の定義にはしない
   - 実装の進め方(直接実装か prototype か、タスク分割)は指定しない。完了条件の形から決まり、実装セッションに委ねる(SKILL.md「実装セッションの規律」)。人間が進め方に制約を付けたいときだけ載せる
