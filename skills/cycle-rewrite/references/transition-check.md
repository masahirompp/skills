# transition-check の手順

サイクル型をいつまで続けるかの判断を支援する。最終判断は人間で、AI は材料を揃えて示す。

今のサイクルを畳むべきかの相談(大幅な見直しが要る、認知負荷が高く AI との意思疎通が困難)なら、cycle-end を提案する。サイクルは長引かせない。リライトの限界費用は低く、乖離を抱えて進むコストの方が高い。以下は、サイクル型そのものを終えるか(通常開発への移行)の判断。

## ハード境界

次を越える直前が、サイクル型を続けられる上限。

- 永続データ(本番 DB への実データ投入)
- 外部 API 契約(外部に公開・提供する API)
- 実ユーザー(知人への配布も含む)

越えると、安いリライトがマイグレーション費・調整費に変わり激増する。ユーザーが「本番 DB に」「公開したい」等と言ったら、境界越えの直前であることとこの機構を伝える。境界越えの実行自体は層3(不可逆)で、常に人間の同期承認を要する。

## 収束の材料

数値の閾値は設けない(規模で意味が変わる)。以下は AI の判定表ではなく、人間に示す観点。

- `spec-change` の比率や変更の半径が、直近サイクルで縮んでいる(骨格の見直しから表示の細部へ、など。複数サイクルの issue 履歴から読む)
- grilling で新しい発見・用語がほぼ出なくなった(人間の記憶。聞く)
- 次サイクルの動機が「見直し」ではなく「機能追加」になっている(人間の意図。聞く)
- PRODUCT.md の Out of Scope が安定している(過去タグとの diff で読む)

リポジトリと issue から読める材料は AI が自分で取得して示す。人間の記憶や意図に依存する項目だけを、推測で埋めずに質問として返す。

あわせて、越えようとする境界に直結する open issue(例: 本番データ保護に関わる未解決の認可・整合性の問題)を `gh issue list` で自分で読んで特定し、名指しで示す。件数の材料としてではなく、越える前に潰すべき障害物として扱う。

## 移行の作法(人間に選ばせる)

- **最後のサイクルを回す**: cycle-end で現行 `src/` を捨て、PRODUCT.md から本命実装を書き直して永続資産にする。「動けばOK」品質のコードを本番に持ち込まない
- **現行 `src/` を昇格する**: cycle-end の儀式を src/ 削除以外すべて行い(棚卸し・ADR 遷移・剪定・タグ)、学びを回収してから現行コードを永続資産にする。内側のロジックだけ仕様から書き直し、磨き込んだ層は残す、という部分的な書き直しとも組み合わせられる

どちらが良いかは一律に決まらない。次の2つを比べる材料を示す。

- **リセットの便益**: 人間と AI の認知の乖離が残っているか、内部が追えなくなっているか。乖離が無ければ、リライトの便益は薄い
- **リライトで失うもの**: 実機検証や実データ検証で磨き込んだ部分のように、docs には書けても再検証が人間律速になるもの。多いほど昇格に傾く

移行の判断は ADR に記録する。移行後は使い捨て層の扱いが反転する。`src/` とテストは永続資産になってサイクル末の削除をやめ、テストは Testing Decisions から生成して維持し、通常の品質ゲートを戻す。CLAUDE.md の規約ブロックも通常開発の規約に書き換える。

## 移行後の再開(部分適用)

移行した後でも、新しい領域(別プラットフォームへの展開、新しいサブシステム等)が霧の中にあるなら、その領域にだけサイクル型を再開してよい。

- 昇格済みの資産は永続層のまま残し、全削除の対象にしない
- 新しい領域の使い捨て層のパスを CLAUDE.md の層の定義に書き直す。cycle-end の削除対象はこの定義が正なので、ここが曖昧だと昇格済みの資産まで消える
- サイクル番号は既存タグの続きから数える
- 再開の判断と適用範囲を ADR に記録し、移行時の ADR を遷移させる

応答では、読める材料を先に全部示してから、人間にしか答えられない項目を質問し、最終判断を委ねる。AI が独断で「収束した」と結論しない。
