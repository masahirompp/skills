# next-issues — 次の本番リリースで出す issue を選んで片付ける

1回の呼び出しで、1回の本番リリースで出す issue を選び、PR にしてマージし、本番にリリースして本番で確かめるところまでを終わらせる。終わったら新しいセッションで再度呼び出すと、残りの issue から次を選ぶ。

引数で issue 番号が渡されたら、候補の先頭に置く（選定を省かず、他の候補と並べて評価する）。

## 方針

- **1回の本番リリースを単位にする。** 選ぶ量は、本番で異常が出たときに原因を切り分けて切り戻せ、本番での確認を1回で済ませられる分にする。迷ったら減らす（1件でもよい）。前回から残っている PR を加えるときも、この量に含める。
- **親（このセッション）は裁定役。** 親は判断する。実装、調査、動作確認のように手を動かす作業や出力の多い作業は、サブエージェントに任せ、結論と根拠だけを受け取る。親のコンテキストは、最後の報告まで判断のために空けておく。
- **人間に聞くことは最小限にし、まとめて聞く。** 途中で出た判断事項は溜めて、次の止まる場所でまとめて聞く。判断待ちの issue や PR は保留にし、何の判断を待っているかをその PR か issue に残して先へ進む（review-loop が尋ねたことも同じ）。ただし、権限の拒否のように環境に起因する失敗は、次の PR でも起きるので、全体を止めて人間に伝える。次の3か所では、必ず止まって人間の確認を得る。
  - 計画の承認（PR を作り始める前。着手前の判定を issue にコメントすることの承認を含む）
  - マージと、issue への書き込みの承認
  - 本番リリースの直前（マージがそのまま本番リリースになるリポジトリでは、マージの直前）。リリース作業を AI が行うと計画で決めていても、直前に確認を挟む
- **長い処理を流して待つのは親。** 数分以上かかるテスト（E2E など）と、CI やデプロイの待ちは、親が Bash のバックグラウンド実行で流す。出力はファイルに書き出し、結果は終了コードと要点だけを読む。
- **レビューは `masahirompp-skills:review-loop` に任せる。** review-loop は、サブエージェントに任せず、親が PR の worktree で回す。進め方は review-loop に従う。review-loop が人間に尋ねることも、上の方針どおり溜めてまとめて聞く。
- **記録は GitHub に残す。** 次の呼び出しは会話を引き継がない。要件、決めたこと、経緯、確認の結果は issue と PR に残す。
- **本番では読むだけ。** 本番での操作は、閲覧とデータを作らない・変えない操作にとどめ、それを超える確認は人間に頼む。本番の画面やログで見た顧客の個人情報、認証情報、内部の構成は、報告にも GitHub にも要約だけを書く（要るときは伏字にする）。認証情報はプロンプトにも書かない。確認を終えたら、ログインしたブラウザのセッションを閉じ、本番で撮った画像を消す。

## 流れ

工程ごとの責務と完了の条件。進め方と、誰に任せるかは親が決める。

### 1. 前提を確かめる

open な issue と PR を一覧にし、issue ごとに担当者と対応中の PR を把握する。前回このスキルで作った自分の PR（本文に `## マージとその後` の節があるもの）のうち、open のまま残っているものと、マージ済みで `## 本番での確認` のコメントが無いもの（前回が途中で終わった印）も控える。issue に `## 着手前の判定` で始まるコメントがあれば、その判定と、そのあとに本文の編集や別のコメントがあったかも控える。リポジトリの前提（基点ブランチ、各種の形式、テストとローカルでの起動、本番リリースまでの流れと各段階の担当、本番での確かめ方）を、実際に動くかを含めて把握する。

完了: 上のそれぞれを一言で言える。

### 2. 選んで計画する

候補は、担当者がいない issue、自分が担当の issue、前回から残っている自分の PR。他人が担当の issue と、他人の PR が対応中の issue は除く。ブロッカー、セキュリティ・データ破損・本番障害、明示された優先度、内容が明確なもの、の順に優先し、「1回の本番リリース」の量より少し多めに候補を絞る。

絞った候補の issue を、`masahirompp-skills:issue-check` で着手前に判定する。課題が本物か、issue の求める手段がそれを解くかを確かめ、前提の誤った issue を PR にしないためである。判定はサブエージェントに任せ、判定の結果だけを受け取る。前回から残っている PR の issue は判定しない。`## 着手前の判定` のコメントがあり、そのあとに本文の編集も別のコメントもない issue は、判定し直さずその判定を使う。判定ごとの扱いは次のとおり。

- 着手可: 候補に残す。
- 確認してから着手: 確認事項を計画の承認で一緒に聞く。答えが出るまでその issue は実装しない。
- 再定義が必要、やらない候補: 選ばず、判定を見送った理由として計画に書く。

判定は助言なので、人間は承認のときに覆せる。そのうえで「1回の本番リリース」の量に収める。同じ領域を触る issue は1本の PR にまとめ、どの PR も基点ブランチから出す。

PR ごとに、先に決めるべき判断、実装を止めて親に戻す条件、テストと動作確認（いつ・どこで・何を）を決める。全体について、前回から残っている PR の扱い（含めないなら、その旨を `## 本番での確認` のコメントに残し、次から拾わない）と、マージから本番での確認までの進め方（各段階を誰が行うか）を決める。

完了: 選んだ理由と見送った理由（着手前の判定を含む）、1回の本番リリースとして扱える理由を添えて計画を見せ、人間が承認した。今回判定した issue に、判定と承認での結論を `## 着手前の判定` で始まるコメントとして書いた（次の呼び出しが判定し直さないための目印になる）。

### 3. PR を作ってレビューする

計画の順に、PR ごとに実装し、draft PR を出し、review-loop を回し、計画で決めた動作確認を済ませる。PR 本文には、要件と計画で決めたことに加えて `## マージとその後` の節を書く（次の呼び出しが、このスキルで作った PR と見分ける目印になる）。画面を変える PR は、画面を実際に操作して確かめる。確かめたあとで挙動が変わったら、確かめ直す。

完了: 計画のすべての PR が、review-loop を終えて動作確認が通ったか、理由つきで保留になった。

### 4. 報告して判断を受ける

全 PR をまとめて1回で報告する。PR ごとの結果と保留の理由、溜めた判断事項、範囲外で見つかった問題と起票する issue の案、マージ後に閉じる issue を示す。判断を受けて PR を直したら、レビューと確認をやり直す。

完了: 判断事項がすべて解決し、人間がマージと issue への書き込みを承認した。承認された起票とコメントを行った。

### 5. マージする

承認された PR を、計画とリポジトリの慣習に沿ってマージし、基点ブランチを pull する。マージの前に PR に手を入れたら（衝突の解消など）、レビューと確認をやり直し、承認のときと中身が変わったら人間に聞き直す。マージがそのまま本番リリースになるリポジトリでは、手順6の「リリース前の状態を控える」と「人間の確認」を、マージの前に済ませる。

完了: 承認された PR がマージされ、手元の基点ブランチがそれを含んでいる。

### 6. 本番にリリースして確かめる

リリース前の状態（エラーやログ）を控え、人間の確認を得てから、計画どおりにリリースする。PR ごとの変更が本番で効いていることと、新しい異常が出ていないことを確かめる。異常があれば、切り戻すか、直すか、次回に回すかを人間と決め、本番と基点ブランチと issue の状態をそろえる。

完了: 対象のすべての PR に、`## 本番での確認` で始まるコメント（確認の結果、または止めた理由と人間と決めた対処）がある。

### 7. 締める

issue の状態をそろえ、対応した issue と PR、起票した issue、続きは新しいセッションでこのスキルを呼べば始まることを伝える。

完了: 対象にした issue のそれぞれについて、閉じたか、どこまで進んだかが issue 上で分かる。

## 既知の落とし穴

- サブエージェントは、このスキルを読まない。守らせたい方針（本番では読むだけ、長い処理は自分で流さず親に頼む、など）は、依頼に含める。着手前の判定を任せるときは、`masahirompp-skills:issue-check` を名指しで使うこと、issue にもほかの場所にも書き込まないこと（コメントは承認のあとに親が書く）、判定の出力をそのまま返すことを依頼に含める。
- サブエージェントが流した処理の終了通知は、そのサブエージェントにしか届かない。親は失敗にも完了にも気づけない。
- 親が worktree の中にいると、`EnterWorktree` で新しい worktree を作れない。呼び出し時に worktree の中にいたら `ExitWorktree` で抜け、抜けられなければ新しいセッションで呼び直してもらう。
- `EnterWorktree` は、`worktree-<name>` という名前のブランチを、既定の設定では origin の既定ブランチから切る（設定 `worktree.baseRef` が `head` なら、ローカルの HEAD から切る）。基点ブランチやブランチ名の形式が違うリポジトリでは、合わせてから作業する。
- サブエージェントを起動したあとに親が別の worktree に移ると、そのサブエージェントへの SendMessage が届かないことがある。PR は1本ずつ、その worktree の中で仕上げてから次へ移る。
- `gh pr edit --body` は本文全体を上書きする。書く直前に読み直し、ほかの書き手の節（review-loop の経緯など）を残す。
- PR 本文に閉じるキーワード（`Closes #N` など）が残っていると、マージで issue が閉じる。保留にした issue は、本文の要件と閉じるキーワードから外す。
- 同じ worktree で、長いテスト、review-loop、実装の修正、ローカルのアプリでの確認を同時に動かすと、作業ツリーが変わってどの結果も当てにならない。
- PR の上に PR を積むと、引数で比較の起点を取らないレビューに、下の PR の変更が混ざる。
- `gh issue list` と `gh pr list` は、既定で件数が制限される。`--limit` を大きくする。
- ローカルのアプリは、人間が動かしているものとポートを取り合う。起動・停止するのはこのセッションで起動したものだけにし、終えたら止める。
