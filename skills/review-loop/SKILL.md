# review-loop — 自分の PR のレビューループ

1反復は「修正をコミットして push する → スクリプトがレビューと判定と検証をする → 判定と検証の結果を読んで修正の方針を決める」。これを、リスクの高い指摘がなくなるまで回す(基準は「終了の判断」)。

スクリプト `scripts/review_loop.py` が受け持つのは、前提と安全上限の強制、観点別レビューと判定役と検証役の起動、PR の状態コメントの読み書きだけ。それ以外はすべて親の受け持ちになる。

**親**は、このループを回すただ1つのセッションで、ループ全体を管理する。この文書の「あなた」は親を指す。別のスキルから使うときは、ループを回す呼び出し元が親になる。親が責任を持つのは次の4つ。

- **スクリプトの起動**: 1つのループでスクリプトを起動するのは親だけ
- **順序**: 修正と push が終わってから起動し、実行中は worktree の編集も PR への push も起こさせない
- **反復をまたぐ文脈**: 過去の判定と、採らなかった指摘とその理由を持ち続け、採否と終了の判断に使う。スクリプトは独立性を保つため子に過去の判断を渡さないので、蒸し返しや振動を見分ける手がかりはここにしかない
- **利用者とのやり取り**: `--new-run` の確認、この文書で「利用者に報告する」とした失敗の報告、終了時の報告

## 前提

- 対象ブランチに PR がある。worktree の中で作業していて、`gh` が認証済み
- 観点スキルが使う `gh` や `git` の読み取り系コマンドが、許可ルールで許可されている。`-p` では、許可されていないツールの呼び出しは確認なしで拒否され、その試行は失敗になる。ただし、複合コマンドがサブコマンドごとの判定から拒否されたものでは、試行を止めず、記録して続ける(後述の「失敗したとき」)
- 観点スキルの既定の一覧は `scripts/review_loop.py` 冒頭の `PERSPECTIVES` にある。既定を変えるときはそこだけを書き換える。1つの PR だけで変えるときは、起動時のオプションで入れ替える(手順2)。各要素は「スキル名と引数」で、引数の `{pr}` は PR 番号に置き換わる(例: `code-review high {pr}` → `/code-review high 12`)。引数の意味はスキルごとに違うので、PR 番号は自動では足さない。たとえば `mattpocock-skills:code-review` は引数を比較の起点として読むので、数字だけでなく `PR #{pr}` と書く(スキルが PR のベースを起点に決め、PR 本文を仕様として使う)。組み込みの `code-review` は、レベルを指定しないと利用者が最後に使ったレベルを引き継ぐので、固定してある
- 制限時間・上限回数などの値は、同じファイル冒頭の定数(`REVIEW_TIMEOUT`、`VERIFY_TIMEOUT`、`BASH_TIMEOUT`、`STALE_LOCK_AFTER`、`SAFETY_MAX_ITER`、`MAX_CONSECUTIVE_FAILURES`)が正。この文書に書いた値は、その既定値

## 手順

### 1. コミットして push する

修正をコミットし、**毎回 push する**。スクリプトは、作業ツリーがクリーンで、ローカルの HEAD と PR の head が一致していなければ起動しない。コードを変えずに PR 本文だけを更新した場合は、同じ SHA のまま再実行してよい。

### 2. スクリプトを起動する

Bash ツールの**バックグラウンド実行**で、**制限時間を 90 分(`timeout: 5400000`。`BASH_TIMEOUT` と同じ値)と明示して**起動する。既定の制限時間では、レビューの途中で止められる。

```sh
python3 ${CLAUDE_SKILL_DIR}/scripts/review_loop.py iterate <worktree の絶対パス>
```

- コマンドは上の形のまま書き、パスを引用符で囲まない。sandbox の除外ルールなど、コマンドの文字列で照合する設定に合わせるため。スクリプトのパスか worktree のパスに空白が含まれるときだけ、そのパスを引用符で囲み、除外ルールもその形で登録する
- `--new-run` は、利用者から新しいシリーズを始めるよう明示的に指示されたときだけ付ける。直前のシリーズは run_id と反復回数だけに要約され、試行の記録は消える。状態コメントが手で編集されるなどして読めないときも、スクリプトは上限を黙って外さないよう終了コード2で止まる。そのときも `--new-run` は利用者に確認してから付ける
- `--no-verify` は、検証役(手順4)を回さない。利用者に指示されたときだけ付ける。付けた回の指摘は、どれも実行で確かめられていない
- 実行中は、誰も worktree を編集せず、PR に push しない。レビュー役は同じ worktree と PR を読んでいる。編集や push があると、試行は `contamination` か `head_changed` で失敗する

観点を PR ごとに調整するオプションが2つある。どちらも worktree のパスの後ろに付ける。sandbox の除外ルールなどは、オプションが付いても当たるよう、前方一致(`python3 <スクリプトのパス> iterate:*` のような形)で登録しておく。完全一致で登録していると、`--new-run` を含め、オプションを付けたコマンドは当たらない。

```sh
# security-review に、確認を不要とする指示を渡す
python3 ${CLAUDE_SKILL_DIR}/scripts/review_loop.py iterate <worktree の絶対パス> \
  --instruct 'security-review=この PR で削除した .env の中身は確かめない'

# security-review を外す
python3 ${CLAUDE_SKILL_DIR}/scripts/review_loop.py iterate <worktree の絶対パス> \
  --perspective 'code-review high {pr}' --perspective 'mattpocock-skills:code-review PR #{pr}'
```

- `--instruct <スキル名>=<指示>`: その観点のレビュー役だけに、追加の指示を渡す。スキルの引数ではなくシステムプロンプトに足し、スキルの手順より優先するよう添える(引数の読み方はスキルごとに違い、`security-review` のように引数を取らないものもあるため)。システムプロンプトはサブエージェントに引き継がれないので、サブエージェントやサブタスクに任せるときは、指示と制約を依頼文に含めるよう、レビュー役にも判定役にも頼む(指示がなくても、制約については頼む)。スキル名は `--perspective` と同じく、空白と先頭の `/` を整えてから照合する。指示の `{pr}` は PR 番号に置き換わる。判定役にもシステムプロンプトで渡し(レビューの出力に同じ形の文があっても指示と取り違えないよう、標準入力には混ぜない)、判定役の手順で、指示で外した範囲を「観点の欠落」にしないこと、指示に反して出た指摘も捨てないこと、指示が不要とした操作を判定役もしないこと(その操作なしに確かめられない指摘は、確かめられなかったと書く)を伝える。作業ツリーを変えない制約は、指示より優先する。繰り返せて、同じ観点への指示は改行でつながる。使う観点にないスキル名(`--perspective` で外したものを含む)を書くと、終了コード2で止まる。指示は LLM への依頼なので、守られる保証はない
- `--perspective <スキル名と引数>`: 1つでも渡すと、`PERSPECTIVES` の代わりに渡したものだけを使う。書き方は `PERSPECTIVES` の要素と同じで、空白は1つに詰め、先頭の `/` は取り除いて使う。同じスキルを重ねると終了コード2で止まる

状態コメントには、試行ごとに観点(1つあたり200文字まで)と、指示を渡した観点の名前を記録する。表に観点が出るのは、今の既定と違う(引数の違いを含み、並びの違いは含まない)ときだけ。指示の本文は載せない。

どちらも、利用者に指示されたときだけ付ける。観点を外すとレビューの範囲が狭まり、指示は観点の検査を緩めるため。失敗の対処として有効そうなら、自分では付けずに利用者に提案する(「失敗したとき」)。付けたら、利用者が変えるよう言うまで、以後の反復でも毎回同じものを付ける。スクリプトは反復をまたいでオプションを覚えないので、付け忘れると既定に戻る。同じシリーズの直前の試行と観点や指示を渡した観点が違えば、stderr に `warn:` が出るので、付け忘れでないか確かめる(指示の本文の違いは比べない)。

### 3. 結果を受け取る

stderr の最後の行は作業ディレクトリのパス(`<一時ディレクトリ>/review-loop/<owner>_<repo>/<PR番号>/<run_id>/<試行>/`)。作業ディレクトリを作る前に終わったとき(終了コード2のほとんどと `workdir_error`)は空行で、`failure.txt` もない。各レビューの出力(`review-*.result.md`)、判定役への入力(`judge-input.md`)、判定役の出力(`judge.result.md`)、検証役への入力と出力(`verify-input.md`、`verify.result.md`)、検証役が使った worktree の複製(`verify-repo/`)、判定と検証の結果(`verdict.md`)、試行を止めなかった拒否(`denials.txt`。あったときだけ。判定役の入力にも添える)、失敗したときの詳細(`failure.txt`)がそこに残る。子の stream の全体は `review-*.stdout.jsonl`、`judge.stdout.jsonl`、`verify.stdout.jsonl` にあるが、ツールの出力まで含んで大きいので、普段は読まない。

レビュー役の出力は、子の stream の最上位の `result` の行のうち、エラーでも空でもないものを出た順につないだもの。サブエージェントをバックグラウンドで動かす観点スキルでは、子がターンごとに `result` の行を出すので、「バックグラウンドで実行しています」のような途中経過の文も混ざる。判定役の出力は決めた形の文書1つなので、行をつながず、見出しを含む行のうち最後のものを判定として採る(`judge.result.md` はつないだもの)。

| 終了コード | 意味 | 次にすること |
| --- | --- | --- |
| 0 | 成功。標準出力は判定と検証の結果のテキストだけ(stderr に「記録できなかった」と出たときは、反復回数が進んでいない) | 手順4へ |
| 1 | 試行の失敗。状態コメントに記録済み(stderr に「記録できなかった」と出たときは記録されておらず、連続失敗にも数えられていない。同じ失敗が続くなら、上限を待たずに利用者に報告する) | stderr の理由を読む。後述の「失敗したとき」 |
| 2 | 試行を始めなかった(前提を満たさない、ロックを取れない、上限に達した、開始前に中断された)。試行は記録されない(ただし、残っていた古いロックを `interrupted` として片付けた記録は残る) | 理由を解消してから再実行するか、利用者に報告する |

失敗の種類は stderr の `failed:` の行の先頭にある: `permission_denied`(権限の拒否。複合コマンドがサブコマンドごとの判定から拒否されたものを除く)、`timeout`、`child_error`(子の異常終了)、`no_output`(空でない `result` の行が1つもない、判定が決めた形になっていない)、`contamination`(混入)、`head_changed`(試行中に PR に別の push があった)、`interrupted`(中断)、`spawn_error`(見張り役を起動できない。claude 自体が起動できないときは `child_error` になる)、`workdir_error`(作業ディレクトリを作れない)、`command_error` と `internal_error`(git・gh・スクリプト自身の失敗)。種類の正は `review_loop.py` の `AttemptFailed` と `classify`。PR の状態コメントには種類と対象だけを載せ、詳細(拒否されたコマンドなど)は載せない。

### 4. 判定と検証の結果を読んで方針を決める

判定と検証の結果は、作業ディレクトリの `verdict.md` から読む(Bash の出力ファイルには stderr の進捗が混ざる)。前半の「## 指摘」と「## 競合」が判定役の判定で、後半の「## 検証」が検証役の結果。判定の形と、影響・起きやすさの段階、範囲、再現の定義は `review_loop.py` の `JUDGE_PROMPT` が正で、検証の形と結論の定義は `VERIFY_PROMPT` が正。判定には、指摘ごとに次が書かれている。

- 影響(高 / 中 / 低 / なし)と、直さなかったら何が起きるか
- 起きやすさ(普通の使い方 / 特定の操作の組み合わせ / まれな条件)と、起きる操作の順
- 再指摘: 以前に採らなかった指摘と同じなら、その理由と、今回それを覆す事情があるか
- 範囲: 差分の内(PR の変更で起きるようになった。PR の目的の直し残しを含む)か、差分の外(PR の前から同じように起きる)か
- 再現: 分類が defect の指摘について、修正前のコードで失敗するはずのテストか実行の手順。実行では示せない種類なら、その理由
- 横展開: 指摘が破っている規則と、同じ規則に触れるほかの経路の候補
- 競合: 判定役が競合を裁定して直すことにした指摘なら、その競合の id

観点の欠落(影響の欄が「観点の欠落」の指摘)は、その観点がレビューになっていなかったことを表す。書き方が揺れていても、分類 other で、観点の出力がレビューになっていないとされた指摘は同じに扱う。その回の判定は欠けているので、原因(観点スキルの設定、対象の取り違えなど)を確かめてから回し直す。回し直した回も反復として数える。同じ観点が2回続けて欠けたら、利用者に報告する。

判定役もレビュー役も、コードを読んだだけで、実行して確かめてはいない。判定の指摘は仮説として読む。影響の段階も、実際に起きると確かめたものではない。

実行して確かめるのは検証役で、worktree の複製(作業ディレクトリの `verify-repo/`。リモートは外してある)の中で、分類が defect で範囲が差分の内の指摘を確かめる。「## 検証」には、指摘の id ごとに次が書かれている。

- 結論: 再現した / 起きなかった / 実行では示せない / 挙動に関わらない / 対象外(分類が defect でない、または範囲が差分の外)
- 実行: 実行したコマンドか、書いたテストの場所(`verify-repo/` の中の相対パス)
- 出力: 出力の要点
- 追跡: 結論が「実行では示せない」のとき、コードや文面を追って指摘が成り立つとしたか
- 根拠

検証役が結果を返さなかったとき(時間切れ、異常終了、決めた形でない出力)は、「## 検証」にそう書かれ、試行は成功のままになる。その回の指摘は実行で確かめられていないので、手順5の再現はあなたが行う。`--no-verify` を付けた回も同じ。

判定役の裁定や指摘は、PR の意図に照らして覆したり却下したりしてよい。判定役がレビューを取りこぼしていないか気になったら、作業ディレクトリにある各レビューの出力(`review-*.result.md`)を読む。

### 5. 修正し、判断の理由を残す

まず範囲を見る。範囲が「差分の外」の指摘は、この PR では直さず、再現もしない。直すと、PR が目的と関係のない変更で膨らみ、その変更がまた次の反復の指摘を呼ぶ。終了時に利用者に報告し、issue にするかを尋ねる(「終了の判断」)。ただし、PR の目的に含まれること(PR の本文やコミットが、直す・実現すると述べていること)の直し残しは、PR の前から同じように起きていても差分の内として扱う。判定役の範囲の判断も、読んだだけの仮説である。影響が高の指摘を差分の外として外すときは、PR のベースのコードで同じことが起きるかを確かめてから外す。それ以外でも、判断が疑わしければ同じように確かめて、自分で決め直す。

**差分の内で、分類が defect、かつ影響が高か、影響が中で普通の使い方で起きる指摘は、直す前に再現する。** PR が意図して変えた挙動を不具合とした指摘は、再現するまでもなく起きるので、再現の前に手順4で却下しておく。

再現は、検証役の結果から始める。結論が「再現した」なら、「実行」のコマンドやテストを自分で流し直し、同じ出力になるのを見る(`verify-repo/` は修正前のコードなので、そのまま流せる)。結論が「起きなかった」なら、検証役が試した条件が、指摘の言う条件と合っているかを「根拠」で確かめる。合っていなければ、自分で組み直して試す。検証役の結果が無い指摘(検証役が結果を返さなかった、対象外とされたがあなたが引き上げた)は、判定の「再現」を手がかりに、修正前のコードで失敗するテストを書くか、実際に実行して、指摘どおりのことが起きるのを見る。判定の手順が合っていなければ、自分で組み直す。

再現は、テストの中、fixture、一時ディレクトリに作ったリポジトリなど、隔離した場所で行う。利用者の作業中のリポジトリ、本物のデータ、外部のサービスに対して、消す・書き換える操作を実行しない(再現に成功した時点で、指摘された被害が実際に起きる)。隔離して再現する手段がなければ、「実行では示せない」として扱う。指摘が自分の環境とは違う条件(別の OS、ツールの別の実装など)で起きるとしていて、その条件を作れないときも同じに扱う。その条件を作らずに試して起きなかったことは、「起きなかった」に数えない。PR のベースのコードを確かめるときも、作業ツリーを切り替えず、`git show` や一時ディレクトリへの取り出しで行う。再現のために作ったファイルは、回帰テストとして残すもの以外、作業ツリーに残さない。

- 再現した: 採用して直す。同じテストや実行が、修正後に通ることを確かめる。書いたテストは、プロジェクトにテストの置き場があれば回帰テストとして残す
- 再現を試みたが、起きなかった(検証役の結論が「起きなかった」で、条件が指摘と合っているものを含む): 採らない。試した手順と結果を、採らなかった理由として残す。「起きうる」という推論だけでは採らない
- 実行では示せない(文書やプロンプトの書き方、外部のサービスの挙動、狙って起こせないタイミングなど): 起きる操作の順をコードで追って採否を決め、実行では確かめていないことを理由に残す。検証役の「追跡」は手がかりで、採否はあなたが決める。試さずにこの扱いにするのは、手段がないときだけにする(テストを書くのが手間、は理由にならない)

差分の内のそれ以外の指摘(分類が defect でないもの、影響が低か、中でも普通の使い方では起きないもの)は、再現なしで採否を決めてよい。

採用した指摘を修正する。横展開の候補は、範囲が差分の内になるものを、確かめたうえで同じ修正に含める。差分の外になる候補は直さず、差分の外の指摘と同じく終了時の報告に載せる。過去の判定と見比べて、同じ規則の破れが場所を変えて続いているなら、場所ごとに直すのをやめ、その規則を1か所で強制する形を検討する。

判定と異なる判断(指摘の却下、裁定の変更)をしたら、その理由を残す。

- レビュースキルは PR 本文を読むとは限らない。**次の反復で確実に伝えたい理由はコードコメントに書く**。ただし、コードの恒久的な説明として妥当なものに限る(「レビューで指摘されたが」のような経緯は書かない)
- レビューの経緯そのものは PR 本文に書く。PR 本文は**書く直前に読み直し**、該当する部分だけを追記・更新する。人間が編集した部分を上書きしない。リポジトリが公開なら、直していないセキュリティの指摘の悪用の手順は書かない

スクリプトは過去の判定を子に渡さない(独立性を保つため)。過去の判断を次の反復に伝える経路は、このコードコメントと PR 本文だけ。

修正したら手順1に戻る。

## 終了の判断

あなたが総合的に判断する。

- 観点の欠落がある判定では終えない
- 主な基準は、**リスクの高い指摘が残っていないか**。影響が高の指摘は、起きやすさに関係なく継続の理由になる。影響が中で、普通の使い方で起きる指摘も同じ
- ただし、範囲が「差分の外」の指摘と、再現を試みて起きなかった指摘は、影響の段階に関係なく継続の理由にしない
- 差分の内の指摘のうち、ここまでで継続の理由にならなかったもの(影響が低い指摘、テストの不足など)を、直すか、継続の理由にするかは、あなたが決める
- 直前の判定で、継続の理由になる指摘を採って直したとき、もう1回回すかは、その修正を何で確かめたかで決める。どの修正も、再現が修正前に失敗して修正後に通り、修正した箇所を通る既存のテストも通っているなら、回さずに終えてよい(共有している関数の変更や横展開の修正のように、再現が確かめた経路の外の挙動も変えているなら、修正の大きさに関係なく回す)。修正した箇所を通る既存のテストがない(テストのないプロジェクトを含む)なら、ほかの経路を壊していないことを確かめたものがないので、回す。実行で確かめていない修正が1つでもあれば、その修正はまだ誰にも確かめられていないので、終えずにもう1回回す。そのために5回の目安を超えるなら、残っている指摘と見通しを利用者に報告し、続けるかを決めてもらう
- 過去の判定と見比べ、同じ指摘の蒸し返しや、修正が行ったり来たりする振動が見えたら打ち切ってよい
- 反復は **5回を目安**にする。スクリプトの上限(シリーズあたり10回、連続失敗3回)は暴走を止めるためのもので、目安ではない

終了したら、利用者に次を報告する: 反復回数、残った指摘(採らなかったものはその理由も)、直した指摘のうち再現で確かめたものと実行では確かめていないもの、範囲が「差分の外」で直さなかった指摘と横展開の候補(影響の段階も)、最後に判定を受けた SHA(状態コメントの表で、最後に completed になった試行の SHA。`--new-run` のあとで表にまだなければ、あなたが持っている直前の判定の SHA)と終了時の HEAD の差(そのあとに入れた修正と、その影響の段階)、合計の入力・出力トークン数(状態コメントの表にある。失敗した試行の分は、途中で止めた子を含まない下限)。`--perspective` で観点を外したり、`--instruct` で範囲を絞ったりしたなら、最後の判定でレビューされなかった観点と範囲も報告する。

範囲が「差分の外」で直さなかった指摘や横展開の候補があれば、報告に続けて、issue にするかを利用者に尋ねる。どれを issue にするかは利用者が決め、言われたものだけを `gh issue create` で作る。尋ねずに作らない。作る前に、同じ不具合の issue が既にないかを探し、あれば作らずに利用者に伝える。本文には、場所、影響と起きやすさ、起きる操作の順、見つけた PR の番号と、レビューの指摘で実行では確かめていないことを書く。セキュリティに関わる指摘は、リポジトリが公開なら、悪用の手順が誰にでも読める形で残るので、起きる操作の順を書かず、公開の issue にしてよいか、非公開の経路で扱うかを利用者に尋ねる。反復をまたいで同じ指摘が出ていたら、1件にまとめる。影響が高のものは、尋ねるときに先頭に置く。

## 失敗したとき

- **同じ原因(同じ権限の拒否など)で2回続けて失敗したら、再実行せず利用者に報告する**
- 検証役の失敗: 試行は失敗にならない(判定は得られているため)。stderr に `warn: 検証役…` が出て、「## 検証」に結果を返さなかったと書かれる。権限の拒否も、検証役は再現の手段を選び直せるので止めず、stderr の `warn: verify:` の行に残すだけにする。2回続けて結果を返さなければ、stderr と `verify.result.md` を確かめ、利用者に報告する
- 権限の拒否(`permission_denied`): 拒否されたツールと入力が stderr に出る。子は拒否されても作業を続けるが、スクリプトは子の stream に拒否が出た時点で全体を止める。ただし、複合コマンド(`;`・`&&`・パイプなどでつないだもの)がサブコマンドごとの判定から拒否されたもの(イベントの `source` が `config` で、`reason_type` が `subcommandResults`)では止めない。読み取りの一部が `.env` 系のファイルの deny ルールに当たるといった形で普通に起き、子は該当部分を外して続けるため。スクリプトが見るのはこの2つの値だけで、拒否されたのが一部か全部か、deny ルールに当たったのか許可ルールに無かったのかは見分けない。この拒否は stderr の `warn:` の行と作業ディレクトリの `denials.txt` に残り、判定役の入力にも添えられる。判定を読むときは、`denials.txt` に、レビューに要るものを読めなかった跡がないかも確かめる。それ以外の拒否は止める。`source` が `config` でも、auto mode の分類器による拒否(`reason_type` が `classifier`)のように、子が読めないまま進みうるものは止める。`source` や `tool_use_id` がない拒否も、止める側に倒す。sandbox の中からこのスクリプトを起動し、子が sandbox を入れ子に起動できずに sandbox を外して再試行したときも、この失敗になる。許可ルールの追加は利用者が判断することなので、内容を伝えて止まる。拒否されたのが PR の目的に要らない確認(PR で削除した `.env` の中身を読もうとした、など)なら、その観点への `--instruct` で確認を不要と伝えるか、`--perspective` でその観点を外す案も添える。どちらを採るかは利用者が決める
- 混入(`contamination`): 子が作業ツリーやブランチを変えた。スクリプトは変更を元に戻さない。内容を確かめ、意図しない変更なら取り除いてから再実行する。子の変更を自分の修正と一緒にコミットしない。ほかの理由(権限の拒否など)で失敗した試行でも、混入があればこちらが優先して報告される
- `head_changed`: 試行中に PR のブランチへ push があった。実行中は誰も push しない決まりなので、誰の push でも決まりに反している。外からの push と、子がローカルを変えずに直接 push したもの(禁じている操作)は区別できない。新しいコミットの作者と内容を確かめ、出どころが分からなければ取り込まずに利用者に報告する。起動前に済ませるはずの push が遅れて届いただけなど、出どころが分かっていて内容が正当なら、取り込んで手順1からやり直す
- 事前確認の失敗(終了コード2で「事前確認」): 観点スキルの名前の誤りか未導入、または claude が起動しない(認証、sandbox、ネットワーク)。sandbox の外で実行する、権限の確認を飛ばすといった回避策は自分では取らず、利用者に伝える
- 「別の試行が実行中」: 二重起動の疑い。古いロック(`STALE_LOCK_AFTER` の95分を超えたもの)は次の起動で自動的に `interrupted` として片付く。スクリプトが SIGKILL されても、子とその子孫のうち同じプロセスグループにいるものは見張り役が止める(子孫が自分で別のセッションに切り離したものは止まらない)
- 「オープンではない」「作成者が自分ではない」: このスキルは自分のオープンな PR だけが対象

## 既知の制約

- `mattpocock-skills:code-review` は、PR のベースブランチ(ローカルの `main` か `origin/main`)を起点に差分を取る。ローカルのベースが古く、PR 側に新しいベースを取り込んでいると、ベース側の変更までレビュー対象に入りうる(対象が欠けることはない)
- 組み込みの `security-review` は引数を取らず、比較の起点を自分で決める(`origin/HEAD` と比べる可能性が高い)。PR のベースが既定ブランチでない、またはローカルの `origin/HEAD` が古いと、PR とは違う差分を見うる。既定ブランチ以外へ向けた PR では、その観点の出力が PR の差分に沿っているか確かめる
- 検証役の複製(`verify-repo/`)は、worktree を clone して同じコミットをチェックアウトし、ignored のファイルやディレクトリ(依存のディレクトリ、`.env` など)を写したもの。作業ディレクトリは自分だけが読める場所(0700)に作るが、試行ごとに複製が残る。容量が気になるときは、古い試行の作業ディレクトリを消してよい。サブモジュールは写さない
- 混入の検査は、作業ツリー、HEAD、ブランチ名だけを見る。stash のように ref だけを変える操作は検出しない。stash の積み場所は他の worktree やセッションと共有なので、比べると誤検知が出るため

## PR の状態コメント

スクリプトは PR にマーカー `<!-- review-loop-state -->` 付きのコメントを1つだけ置き、編集で更新する(人間のレビュアーに通知が飛ばないように)。載るのは run_id、反復回数、試行ごとの SHA・時刻・結果・入力と出力のトークン数・観点(引数を含めて200文字まで。表に出すのは既定と違うときだけで、80文字まで)・指示を渡した観点の名前、連続失敗回数、ロックだけで、指摘の内容や判断の理由、指示の本文は載せない。観点の引数は公開の PR コメントに載るので、公開したくないことは書かない。本文が上限を超えそうなときは、古い試行から観点の記録を外す。このコメントを書き換えるのはスクリプトだけ。あなたは編集しない。
