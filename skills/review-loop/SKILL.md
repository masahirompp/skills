# review-loop — 自分の PR のレビューループ

1反復は「修正を push する → スクリプトで試行を始める → レビュー役を呼び、出力を残す → スクリプトで試行を閉じる → 俯瞰の役が指摘を突き合わせ、規則ごとにまとめる → 直す対象を決め、再現してから直す」。これを、直近の反復の再現させる対象の扱いを全て決め終え(対象が無い場合を含む)、その反復で入れた修正がどれも、種類ごとの「回さずに終えてよい条件」を満たすまで回す(基準は手順5と「終了の判断」)。

スクリプト `scripts/review_loop.py` が受け持つのは、試行の前後の確認(前提、安全上限、試行中に作業ツリーや PR が変わっていないか)と、PR の状態コメントの読み書きだけ。レビュー役を呼ぶのは親で、観点スキルを Skill ツールで直接呼ぶか、文脈を引き継がないサブエージェントに呼ばせる(手順2)。指摘の俯瞰、修正、修正の差分のレビューも、親が起動するサブエージェントに任せる(手順4、5)。

モデル: レビュー役も、俯瞰の役、修正役、差分のレビュー役も、モデルを指定せずに起動する(親と同じモデルで動く)。モデルを変えたいときは、利用者が、ループを始める前に親のモデルを変える。指摘の数と質はモデルで変わるので、反復や PR の間で指摘の数を比べられるのは、親のモデルが同じときだけ。既定の観点を選んだ根拠(bench の結果)は、Opus で測ったもの。

**親**は、このループを回すただ1つのセッションで、ループ全体を管理する。この文書の「あなた」は親を指す。別のスキルから使うときは、ループを回す呼び出し元が親になる。親が責任を持つのは次の5つ。

- **試行の開始と終了**: 1つのループでスクリプトとレビュー役を呼ぶのは親だけ。`begin` で始めた試行は、必ず `end` で閉じる
- **順序**: 修正と push が終わってから試行を始め、`begin` から `end` までの間は worktree の編集も PR への push も起こさせない
- **反復をまたぐ文脈**: 過去の俯瞰の役の出力と、採らなかった指摘とその理由を持ち続け、採否と終了の判断に使う。レビュー役には過去の判断を渡さない。俯瞰の役には過去の出力と修正の差分を渡す(手順4)が、蒸し返しや振動を最後に見分けるのはあなた
- **修正の受け渡し**: 修正は修正役(手順5)に任せるが、何を採るかを決め、修正役の結果を自分で流して確かめ、push するのは親
- **利用者とのやり取り**: `--new-run` の確認、この文書で「利用者に報告する」とした失敗の報告、俯瞰の役が方針や範囲の見直しを挙げたときの確認(手順4)、終了時の報告

## 前提

- 対象ブランチに PR がある。worktree の中で作業していて(あなたの作業ディレクトリが、その worktree のトップ)、`gh` が認証済み。レビュー役はあなたの作業ディレクトリで動くので、ほかの場所から呼ぶと、対象でないリポジトリをレビューする。`begin` は、作業ディレクトリが worktree のトップでなければ始めない。そのときは、コマンドの前に `cd` を付けて通さない(スクリプトは通るが、レビュー役は元の場所で動く)。セッションの作業ディレクトリを worktree にしてから始める
- 既定の観点は、`code-review high <PR番号>` を2つと、`security-review` を1つ(レビュー役の名前は `code-review`、`code-review-2`、`security-review`。`scripts/review_loop.py` 冒頭の `ROLES`)。`code-review` は同じ差分でも回ごとに見つける不具合が変わるので、2回分を合わせる(根拠は、このスキルのリポジトリの `skill-dev/review-loop/bench/README.md`。プラグインには含まれない)。組み込みの `code-review` は、レベルを指定しないと利用者が最後に使ったレベルを引き継ぐので、`high` を毎回書く
- 上限回数などの値は、`scripts/review_loop.py` 冒頭の定数(`STALE_LOCK_AFTER`、`LEGACY_STALE_LOCK_AFTER`、`SAFETY_MAX_ITER`、`MAX_CONSECUTIVE_FAILURES`)が正。この文書に書いた値は、その既定値

## 手順

### 1. コミットして push する

修正をコミットし、**毎回 push する**。スクリプトは、作業ツリーがクリーンで、ローカルの HEAD と PR の head が一致していなければ試行を始めない。コードを変えずに PR 本文だけを更新した場合は、同じ SHA のまま再実行してよい。

### 2. 試行を始め、レビュー役を呼ぶ

まず、スクリプトで試行を始める。

```sh
python3 ${CLAUDE_SKILL_DIR}/scripts/review_loop.py begin <worktree の絶対パス>
```

- 終了コードが0なら、標準出力に `pr=<PR番号>`、`sha=<試行の SHA>`、`attempt=<試行の番号>`、`workdir=<作業ディレクトリ>` と、レビュー役ごとの `out.<レビュー役の名前>=<出力のファイル>` の行が出る。作業ディレクトリは `<一時ディレクトリ>/review-loop/<owner>_<repo>/<PR番号>/<run_id>/<試行>/`。出力のファイルは、役ごとに別の、作業ディレクトリの外の場所にある(レビュー役が、ほかの役の出力や過去の試行の記録を、渡されたパスの隣で見つけないように)
- スクリプトは、この試行の記録(PR 番号、SHA、ブランチ、作業ディレクトリ、役ごとの出力のファイル)を git の管理ディレクトリに置き、`end` がそれを読む。`end` は、作業ディレクトリとレビュー役の名前をもう一度出すので、`begin` の出力を覚えていなくても先へ進める
- 0でなければ、レビュー役を呼ばない。1は、作業ディレクトリを作れなかった(`workdir_error`。失敗として記録済み)。2は、試行を始めなかった(前提を満たさない、ロックを取れない、上限に達した)。stderr の理由を読み、解消してから再実行するか、利用者に報告する(「失敗したとき」)
- `--new-run` は、利用者から新しいシリーズを始めるよう明示的に指示されたときだけ付ける。直前のシリーズは run_id と反復回数だけに要約され、試行の記録は消える。状態コメントが手で編集されるなどして読めないときも、スクリプトは上限を黙って外さないよう終了コード2で止まる。そのときも `--new-run` は利用者に確認してから付ける
- `begin` から `end`(手順3)までの間は、誰も worktree を編集せず、PR に push しない。レビュー役は同じ worktree と PR を読んでいる。編集や push があると、`end` が試行を `contamination` か `head_changed` で失敗にする

次に、**レビュー役を、同じターンで全て呼ぶ**。レビュー役は、あなたの会話を引き継がない別の文脈で動かす(過去の指摘や採否を知らないまま読ませるため)。呼び方は、観点スキルがフォークで動くかどうかで2つに分かれる。

| レビュー役の名前 | 呼び方 |
| --- | --- |
| `code-review`、`code-review-2` | あなたが Skill ツールで `code-review` を直接呼ぶ。同じターンで2回 |
| `security-review` | 文脈を引き継がないサブエージェントに、Skill ツールで呼ばせる |

**どのレビュー役にも、自分の出力を、`begin` が示したその役のファイル(`out.<レビュー役の名前>=` の値)に書かせる。** 役には、その役のファイルのパスだけを渡し、作業ディレクトリのパスは渡さない。`end` が、全ての役のファイルを作業ディレクトリに集め、役の名前の区切りでつないで `reviews.md` を作る。あなたが出力を書き写すと、過去の採否を知っているあなたの手が入りうるうえ、出力の分だけ余計に時間がかかるため。

**フォークで動くスキル(`code-review`)は、あなたが Skill ツールで直接呼ぶ。** 引数は次の形にする。1行目がレベルと PR 番号、空行のあとが制約と、出力の置き場。

```text
high <PR番号>

(他のレビューと並列に、同じworktreeで実行しています。ファイルの編集、checkout、commit、stash、pushなど、作業ツリーやブランチを変える操作をしないでください。サブエージェントやサブタスクに作業を任せるときは、この制約をその依頼文にも含めてください。
レビューの結果を返す前に、返すものと同じ内容を `<その役の出力のファイル>` に書いてください。書いてよいのは、このファイルだけです。)
```

Skill ツールの結果が「forked execution」と返れば、スキルは別の文脈で動いている。同じターンで2つ呼ぶと、片方はバックグラウンドで起動されて結果が完了の通知で届き、もう片方はその場で結果が返ることがある。どちらも、そのスキルの出力として扱う。

**フォークで動かないスキル(`security-review`)は、あなたが直接呼ばない。** Skill ツールで呼ぶと、手順の本文があなたの文脈に読み込まれ、過去の指摘を知っているあなた自身がレビュー役になる。代わりに、Agent ツールで、あなたの文脈を引き継がないサブエージェント(fork ではない種類)を起動し、次の依頼文を渡す。`<...>` を埋め、ほかは変えない。

```text
git の worktree `<worktree の絶対パス>` にある PR #<PR番号> の変更をレビューしてください。

Skill ツールで `<スキル名>` を、引数 `<引数。無ければ「なし」>` で呼び、読み込まれた手順にそのまま従ってください。手順がサブエージェントやサブタスクの起動を求めていれば、そのとおりに起動します。

他のレビューと並列に、同じworktreeで実行しています。ファイルの編集、checkout、commit、stash、pushなど、作業ツリーやブランチを変える操作をしないでください。サブエージェントやサブタスクに作業を任せるときは、この制約をその依頼文にも含めてください。

最後の出力は、スキルの手順が求める形のレビューの結果を、そのまま返してください(要約しない、指摘を省かない)。返す前に、返すものと同じ内容を `<その役の出力のファイル>` に書いてください。書いてよいのは、このファイルだけです。スキルを呼べなかった、対象が上の PR でなかった、手順の一部を実行できなかったときは、自分の判断でレビューを代わりに行わず、ファイルも書かず、何が起きたかだけを返してください。
```

- ここに無いスキルを観点に使うときは、サブエージェントに呼ばせる(フォークで動くと確かめていないスキルを直接呼ばない)。直接呼んだ結果が「forked execution」でなく、手順の本文が読み込まれたときは、その手順に従わず、サブエージェントに呼ばせ直す
- 引数の意味はスキルごとに違う。`security-review` は引数を取らない。`mattpocock-skills:code-review` は引数を比較の起点として読むので、数字だけでなく `PR #<PR番号>` と書く(スキルが PR のベースを起点に決め、PR 本文を仕様として使う)

観点は、利用者に指示されたときだけ、次のように変える。レビュー役の名前を変える(足す、外す、入れ替える)ときは、`begin` に `--roles <名前>,<名前>,...` を付けて、その試行で呼ぶ役の名前を全て渡す(例: `--roles code-review,code-review-2,security-review,focus-1`)。`end` は、渡した役の出力が全てそろっていなければ、試行を完了にしない。

- **観点を足す**(利用者が、見てほしい観点を言葉で指定した): スキルを使わないレビュー役を1つ足す。文脈を引き継がないサブエージェントに、「PR #<PR番号> の差分を、次の観点でレビューし、具体的な指摘を file:line 付きの箇条書きで出してください。観点: <観点>」と、上の依頼文と同じ制約の段落、出力をファイルに書く文を渡す。レビュー役の名前は `focus-1`、`focus-2`…
- **観点に指示を渡す**(確認を不要とする、範囲を絞る、など): `code-review` には、引数の制約の括弧の中に、指示と「サブエージェントやサブタスクに作業を任せるときは、この指示もその依頼文に含めてください。作業ツリーやブランチを変えない制約は、この指示よりも優先します」を書き足す。サブエージェントに呼ばせる観点には、依頼文の制約の段落のあとに、同じものを書き足す。指示の本文は、レビュー役の出力のファイルにも `reviews.md` にも混ぜない(レビューの出力に同じ形の文があっても、指示と取り違えないため)。俯瞰の役には、あなたが依頼文の「利用者が観点に渡した指示」の節で渡す([references/overview.md](references/overview.md))。そこで、指示で外した範囲を「観点の欠落」にしないこと、指示に反して出た指摘も捨てないこと、指示が不要とした操作を俯瞰の役もしないことを伝える。指示は LLM への依頼なので、守られる保証はない
- **観点を外す、入れ替える**: 呼ぶスキルを変える。同じスキルを重ねたら、レビュー役の名前は2つ目から `<スキル名>-2` のように番号を付ける。名前に使えるのは、英数字と `_` `.` `:` `-`

観点を外すとレビューの範囲が狭まり、指示は観点の検査を緩め、観点を足すと時間と指摘が増えるので、自分の判断では変えない。失敗の対処として有効そうなら、利用者に提案する(「失敗したとき」)。変えたら、利用者が戻すよう言うまで、以後の反復でも毎回同じにする(`--roles` を付け忘れると、既定の役に戻る)。`end` は、直前の試行とレビュー役の名前が違えば stderr に `warn:` を出すので、付け忘れでないか確かめる。観点に渡した指示は、どこにも記録されない(「既知の制約」)。

### 3. 出力を確かめ、試行を閉じる

**呼んだレビュー役の結果が全て届くまで待つ。** バックグラウンドで動いているレビュー役の結果は、完了の通知で届く。待つ間は、worktree を編集せず、push せず、俯瞰の役も起動しない。届かないレビュー役があるまま先へ進まない。

あなたは、通知が来るまで起こされない。レビュー役が止まったまま終わらないと、ループはそこで黙って止まる。利用者に声を掛けられるなどして、結果が届いていないことに気づいたら、試行の開始時刻(PR の状態コメントの「実行中(開始 …)」)を見る。40分を過ぎていれば、動いているレビュー役を止めてから(バックグラウンドのタスクを止める手段を使う。止められなければ、利用者に伝える)、失敗として閉じる(下の `--failed`)。止めずに閉じると、そのレビュー役が、次の試行の最中に worktree を読み、遅れて届いた結果が次の試行の出力に紛れうる。

結果が全て届いたら、届いた結果を役ごとに見る。

- 届いた結果が、スキルを呼べなかった、手順を実行できなかった、対象が PR でなかった、という報告だった役: レビュー役の失敗(下の `--failed`)
- レビューの結果は届いているのに、その役の出力のファイルが無い役(下の `end` が「出力の無いレビュー役がある」と、役の名前とファイルのパスを出す): 届いた結果を、あなたが Write ツールで**そのまま**そのファイルに書いてから(要約しない、指摘を省かない、並べ替えない、言い回しを直さない)、もう一度 `end` を呼ぶ
- レビュー役が「権限が無くて読めなかった」「実行できなかった」と書いていても、レビューの結果が出ていれば、出力の一部として残す(俯瞰の役が見る)

スクリプトで試行を閉じる。`end` は、全ての役の出力を作業ディレクトリに写し(`review-<レビュー役の名前>.md`)、役の名前の順に、行頭から始まる `===== 観点: <レビュー役の名前> =====` の行で区切ってつないで、`reviews.md` を作る。本文に区切りと同じ形の行があれば、行頭に空白を足す(行頭から始まる区切りの行を数えれば、役を数えられる)。終了コードが0なら、標準出力に `workdir=<作業ディレクトリ>` と `roles=<レビュー役の名前の一覧>` の行が出る。

```sh
python3 ${CLAUDE_SKILL_DIR}/scripts/review_loop.py end <worktree の絶対パス>
```

レビュー役のどれかが失敗したとき(エラーで終わった、結果が届かない、出力が空、対象が PR でなかった、スキルを呼べなかったと返った)は、その回のレビューは欠けている。出力を俯瞰の役に渡さず、理由を付けて閉じる。理由は PR の状態コメントに載る(100文字まで)ので、どの役が、どう失敗したかだけを書き、指摘の内容や公開したくないことは書かない。

```sh
python3 ${CLAUDE_SKILL_DIR}/scripts/review_loop.py end <worktree の絶対パス> --failed 'security-review: スキルを呼べなかった'
```

| 終了コード | 意味 | 次にすること |
| --- | --- | --- |
| 0 | 試行を completed として記録した。反復回数が進んだ | 手順4へ |
| 1 | 試行を失敗として記録した。`--failed` を付けたとき(`reviewer_failed`)か、`begin` のあとに作業ツリー、HEAD、ブランチが変わっていたとき(`contamination`)、PR の head が動いていたとき(`head_changed`) | stderr の理由を読む。後述の「失敗したとき」 |
| 2 | 何も記録していない。stderr の理由で、次にすることが分かれる(下) | 下の一覧 |

終了コード2の理由:

- 「出力の無いレビュー役がある」(ファイルが無いか、空): 試行は開いたまま。上の一覧のとおり、届いた結果を置くか、`--failed` を付けて、もう一度 `end` を呼ぶ
- gh や git の失敗、状態コメントへの書き込みの失敗: 試行は開いたまま。原因を除いて、もう一度 `end` を呼ぶ。閉じないままにすると、次の `begin` が止まる
- 「閉じる試行が無い」「この試行のロックが、状態コメントに無い」: 閉じるものが無い。もう一度呼んでも同じ結果になる。PR の状態コメントの表で、最後の試行の SHA と結果を見る。この試行が記録済み(前の `end` が、書き込みには成功していた)なら、その結果に従って進む。記録が無ければ、この試行は無かったものとして、手順1からやり直す。stderr に「この試行の間に、次の変更があった」と出ていれば、レビュー役が作業ツリーやブランチを変えている。やり直す前に、混入(「失敗したとき」)と同じに扱う
- 「試行の記録 … を読めない」「begin の書いた形をしていない」: 試行の記録が壊れている。メッセージにあるファイルを消してから、手順1からやり直す

失敗の種類は stderr の `failed:` の行の先頭にあり、PR の状態コメントにも載る。詳細は stderr と、作業ディレクトリの `failure.txt` に残る。

### 4. 俯瞰の役に、指摘を突き合わせてまとめさせる

**毎反復、直す対象を決める前に、レビュー役の出力を俯瞰の役に渡す。** 俯瞰の役は、あなたの文脈を引き継がないサブエージェントで、1反復に1つ。レビュー役の出力を突き合わせて、根拠を確かめ、当たらない指摘を理由付きで外し、役どうしの食い違いを裁き、以前に採らなかった指摘の扱いを決めて、1つの表にする。そのうえで、指摘を規則ごとにまとめ、横展開の箇所を探し、規則ごとの直し方(箇所ごとに直す / 方式を変える / 別の課題にする)と、PR の方針への判断を返す。指摘を1件ずつ直すと、同じ規則の破れに反復ごとに継ぎを当てることになり、「この PR で直すべきか」を問う場所もないため。材料の用意と依頼文は [references/overview.md](references/overview.md) にある。サブエージェントを使えないときは、依頼文の「頼みたいこと」と「出力の決まり」に、あなた自身が従う。

受け取った出力は、その試行の作業ディレクトリに `overview.md` として保存する。次の反復で、俯瞰の役に過去の出力として渡す。

俯瞰の役の表には、指摘ごとに次が書かれている。段階の定義は依頼文の「段階の決め方」が正。

- 挙げた役: `reviews.md` の区切りの名前。`code-review` と `code-review-2` のように、同じスキルを重ねた役どうしの一致は、別の観点どうしの一致ほど強い裏づけではない
- 分類(defect / test_gap / naming_or_comment / style / other)
- 影響(高 / 中 / 低 / なし)と、起きやすさ(普通の使い方 / 特定の操作の組み合わせ / まれな条件)
- 範囲: 差分の内(PR の変更で起きるようになった。PR の目的の直し残しを含む)か、差分の外(PR の前から同じように起きる)か
- 扱い: 規則の番号、その他、外した(理由)、観点の欠落。以前に採らなかった指摘なら、覆す事情の有無

規則ごとには、当たる指摘、指摘ごとの症状と起きる条件、横展開で見つけた箇所、直し方の選択が書かれている。

表を読むときに、あなたが確かめること:

- **指摘が落ちていないか。** 表の行は、レビュー役の生の出力をまとめたもの。行が疑わしいとき、外した理由に納得できないとき、別の指摘が1行に畳まれていそうなときは、`<作業ディレクトリ>/reviews.md` を読み比べる。畳まれていた指摘は、別の行として扱う。分類が defect で扱いが「外した」の行は、疑わしくなくても、`reviews.md` の元の指摘と読み比べる(外した行は再現させる対象に入らないので、俯瞰の役が読み違えて外すと、実行で確かめられないまま消える)
- **観点の欠落。** 扱いが「観点の欠落」の行は、その観点がレビューになっていなかったことを表す。その回のレビューは欠けているので、原因(観点スキルの設定、対象の取り違えなど)を確かめてから回し直す。回し直した回も反復として数える。同じ観点が2回続けて欠けたら、利用者に報告する
- **読めなかった跡。** `reviews.md` に、レビュー役が、レビューに要るものを読めなかった、実行できなかったと書いた跡がないか(権限の設定で拒否された、など)。あれば、その役のレビューはその分だけ欠けている
- **表と役の対応。** 機械的に確かめる。俯瞰の役の出力に表がある。`reviews.md` の全ての区切りの名前(`===== 観点: <名前> =====`)が、表の「挙げた役」の列か、「観点の欠落」の行か、指摘が無かった役として、1回以上出る。区切りとして数えるのは、行頭から始まる `===== 観点: <名前> =====` の行だけにする(レビュー役の本文が、区切りと同じ形の文字列を引用することがある)。照らすときは、セルや一覧を区切り(読点、カンマ、空白)で名前に分け、名前の完全一致で見る(部分一致では、`code-review` が抜けていても `code-review-2` や `mattpocock-skills:code-review` に当たってすり抜ける)。欠けていれば、その役の出力を `reviews.md` で読み比べる

レビュー役も俯瞰の役も、指摘を仮説として出している。俯瞰の役は根拠を確かめるが、影響の段階は、実際に起きると確かめたものではない。実行で確かめるのは手順5になる。俯瞰の役の判断(外した、裁いた、段階)は、PR の意図に照らして覆してよい。覆したら理由を残す。

**次のどちらかなら、直し始めずに、その部分を利用者に見せて決めてもらう。** PR の方針への判断が「このまま進める」でない。手順5の再現させる対象の行(一覧の「別の課題にする」で外す前のもの)を含む規則に、「別の課題にする」が付いた。見せるのは、俯瞰の役の理由(起きる条件の広さ、失うもの)と、あなたの考え。範囲を狭めるか、同じ PR で直すかは、安全と PR の膨らみのどちらを重く見るかの判断で、利用者のもの。

「方式を変える」は、あなたが採否を決めてよい。採るなら、その規則の指摘は方式の変更として1回で直す。

### 5. 直す対象を決め、再現してから直す

まず範囲を見る。範囲が「差分の外」の指摘は、この PR では直さず、再現もさせない。直すと、PR が目的と関係のない変更で膨らみ、その変更がまた次の反復の指摘を呼ぶ。終了時に利用者に報告し、issue にするかを尋ねる(「終了の判断」)。ただし、PR の目的に含まれること(PR の本文やコミットが、直す・実現すると述べていること)の直し残しは、PR の前から同じように起きていても差分の内として扱う。俯瞰の役の範囲の判断も仮説である。影響が高の指摘を差分の外として外すときは、PR のベースのコードで同じことが起きるかを確かめてから外す。それ以外でも、判断が疑わしければ同じように確かめて、自分で決め直す。ベースのコードを確かめるときは、作業ツリーを切り替えず、一時ディレクトリへの取り出しで行う(手順は references/fix.md)。

**再現させる対象は、差分の内で、分類が defect、影響が中以上の指摘のうち、文書への指摘(後述)でなく、下の一覧にも当たらないもの。** 指摘の出どころは3つあり、どれも同じ基準で扱う。俯瞰の役の表の行、修正の差分のレビューの指摘(後述)、前の反復で扱いが決まらずに持ち越したもの(「終了の判断」)。俯瞰の役の表では、単位は行で、扱いが「規則N」か「その他」かを問わない(規則にまとめられなかった行も、ここで対象になる)。扱いが「外した」(手順4であなたが覆したものを除く)と「観点の欠落」の行は、指摘として残っていないので含まない。俯瞰の役が対象の行に「直さない」「再現させない」と書いていても、対象のまま(外すなら、下の一覧のどれかに当て、理由を残す)。起きやすさは問わない(表には残るが、この境目には使わない)。この文書のほかの箇所で「再現させる対象」と言うときは、この定義を指す。次は、この対象から外す。

- 範囲が差分の外の指摘
- 以前に採らなかった指摘で、覆す事情が無いもの
- PR が意図して変えた挙動を不具合とした指摘(再現するまでもなく起きる。理由を残して却下する)
- 俯瞰の役が「別の課題にする」、または PR の方針を「範囲を変える」とした部分(手順4で利用者に見せ、利用者が決めたとおりにする)

**再現させる対象は、修正役に、再現してから直させる。** 修正役は、あなたの文脈を引き継がないサブエージェントで、1反復に1つ。規則ごとに、修正前のコードで失敗する再現のコマンドを作り、失敗を見てから直し、コミットする。あなたが自分で直さないのは、指摘を読んだ時点の見込みに引きずられ、修正が見込んだ例に閉じるため。材料の用意、依頼文、返ってきたあとに確かめることは [references/fix.md](references/fix.md) にある。

- 規則は、修正役に渡す単位にとどめる(対象を決めるのは上の定義)。渡すのは、指摘ではなく、指摘が破っている規則。対象の行を含む規則は、俯瞰の役がまとめた規則をそのまま使う。どの規則にも入っていない対象の行は、それだけで1つの規則として渡す。1つの例だけを捉える再現では、修正がその例に閉じる
- 再現は、一時ディレクトリの中など、隔離した場所で行わせる。利用者の作業中のリポジトリ、本物のデータ、外部のサービスに対して、消す・書き換える操作を実行させない(再現に成功した時点で、指摘された被害が実際に起きる)
- 横展開で見つけた箇所のうち、範囲が差分の内になるものは同じ依頼に含める。差分の外になる箇所は直させず、差分の外の指摘と同じく終了時の報告に載せる
- 過去の反復と見比べて、同じ規則の破れが場所を変えて続いているなら、場所ごとに直させるのをやめ、その規則を1か所で強制する形を依頼する

修正役が返す結果は、箇所ごとに次の3つ。どれも、あなたが確かめてから扱いを決める。

- **再現できた**(現実に起こせる入力や操作で、指摘の症状を見た): あなたが再現のコマンドを読み、修正前と修正後のコードの写しに流して、失敗と成功を見たら、**必ず直す**(採否をあなたの裁量にしない)。修正役の報告だけでは「再現できた」に数えない
- **起きなかった**: 直さない。試した手順と結果を、採らなかった理由として残す。「起きうる」という推論だけでは直さない。指摘が自分の環境とは違う条件(別の OS、ツールの別の実装など)で起きるとしていて、その条件を作れなかったときは、ここに数えず、次の扱いにする
- **実行では確かめていない**(外部のサービスの挙動、狙って起こせないタイミング、未確認の前提に立つ入力など): 修正役がコードを追った結果を読んで、あなたが採否を決め、理由を残す。採った修正は、まだ実行で確かめられていないので、もう1回回す(「終了の判断」)。この扱いにするのは、手段がないときだけにする(再現を作るのが手間、は理由にならない)

**再現で作った入力や状態が、外部の挙動についての未確認の前提に立つなら、「再現できた」に数えない。** たとえば、ツールや外部のサービスが出すイベントの形を、一度も観測しないまま作り物で与えた再現。症状は見えても、その入力が現実に起きるかは確かめられていない。修正役には、どの前提が未確認かを添えて「実行では確かめていない」と返させる(依頼文にある)。あなたも、再現のコマンドを読む段で、入力が現実に起こせるかを見る。作り物の入力を前提に直すと、その修正がまた次の反復の指摘を呼ぶ。

差分の内の指摘のうち、分類か影響の段階で再現させる対象(上の定義)に入らないものは、再現なしで採否を決めてよい。直すなら、同じ修正役への依頼の「再現なしで直すもの」に入れる。ただし、反復の途中で直すのは、修正が指摘された箇所に閉じるときだけにする。共有している関数、出力の形、既定値、子に渡すもの(プロンプト)を変える修正が要るなら、直さずに終了時の報告に載せる。修正のたびに、まだ誰もレビューしていないコードが増え、次の反復の指摘を呼ぶため(影響の広い修正の費用は、中以上の指摘にだけ払う)。箇所に閉じるものに限るので、再現なしで直したものは、修正の差分のレビュー(後述)を受けていれば、それだけではもう1回回す理由にならない(「終了の判断」)。

**文書への指摘は、再現させず、ループを回す理由にもしない。** 文書への指摘とは、指摘された箇所が文書やプロンプト(SKILL.md、README、子に渡す依頼文、コメントなど、読んで従うもの)で、症状が読み手の読み方に依るもの(決まりの穴、曖昧さ、文面どうしの食い違い)。次の2つは、流せば合否が出るので、文書への指摘にせず、上の再現させる対象の定義で扱う。

- 文書が述べる事実が実物と合わない、という指摘(書いてあるコマンドが動かない、パスやオプションが無い、出力の形が違うなど)。再現は、書いてあるとおりに流して失敗を見る
- プロンプトの文面を合否で確かめる既存の手段(テスト、eval)がリポジトリにあるもの

文書への指摘をループから外すのは、読み方に依る穴は読むたびに見つかり、直しても実行で確かめられないので、ループが止まる根拠にならないため。扱いは次のとおり。

- 差分の内で、分類が defect、影響が中以上のものは、あなたが採否を決め、理由を残す。直すなら、修正役への依頼の「再現なしで直すもの」に入れて、1回だけ直す(箇所に閉じない修正でもよい)
- そのうち影響が高のものは、採否を決める前に利用者に見せ、決めてもらう(消す操作の手順の誤りのように、文面の誤りが実害に直結することがある)
- 分類か影響の段階がそれに満たないものは、上の段落の、再現なしで採否を決めるものと同じに扱う
- 修正の差分のレビューが挙げた文書への指摘は、直さずに終了時の報告に載せる。直すと、その修正にまた、読むだけのレビューが要るため。影響が高のものだけは、終了を待たずに利用者に見せる

サブエージェントを使えないときは、references/fix.md の依頼文の「進め方」に、あなた自身が従う。

**push の前に、修正の差分を、あなたの文脈も修正役の文脈も引き継がない、別のサブエージェントにレビューさせる。** 修正役は自分が確かめた例に、あなたは依頼に書いた規則に引きずられるので、どちらも読み直しの役にしない。渡すのは、修正の差分(最後にレビューを受けた SHA から作業ツリーまで)と、直した規則だけ。修正役の報告や、確かめた例は渡さない。頼むのは次の2つで、読むだけにさせる(作業ツリーを変えさせない)。

- 直し残し: 修正後のコードで、規則をまだ破る入力や環境(利用者の設定、リポジトリの構成の違いを含む)
- 修正が持ち込んだ問題: 修正によって変わった、ほかの挙動や出力の読み方

指摘ごとに、分類、影響、範囲を、[references/overview.md](references/overview.md) の「段階の決め方」に従って、1つの値で付けさせる(その節を依頼に写す)。「中〜低」のような幅で返ったら、高いほうで読む。

出た指摘は、俯瞰の役の表の行と同じ基準で扱う(読んだだけの仮説なので、再現させる対象の定義に当たるものは、再現させる対象にする。同じ修正役に続きを頼んでよい。文書への指摘は、上の扱いに従い、直さない)。続きを頼むときは、修正前の写しを、その時点の HEAD から作り直す。この差分のレビューは、1回の修正につき1回だけ行う。その結果を受けた修正のレビューは、次の反復に任せる(そのため、差分のレビューの指摘を受けて直したら、もう1回回す。「終了の判断」)。もう1回回すと既に決まっているとき(「終了の判断」。共有している関数を変えた、コードを変える修正で実行では確かめていないものがある、など)は、この差分のレビューを省いてよい。次の反復のレビュー役が、同じ差分を見る。サブエージェントを使えないときは、規則ごとに、横展開の箇所に無い入力や環境を自分で挙げて確かめる。差分の外との食い違いは見ないので、次の反復の代わりにはならない。

俯瞰の役と異なる判断(指摘の却下、段階や裁きの変更)をしたら、その判断と理由を PR 本文の経緯に書く。次の反復の俯瞰の役に届くのは、PR 本文、`src/` のコード(コードコメントを含む)、`history/` にある自分の過去の出力と修正の差分(`fixes.diff`)。このうち却下の理由を書けるのは PR 本文とコードコメントで、コードコメントには恒久的な説明として妥当なものしか書かない(次の項目)ので、判断と理由は必ず PR 本文に書く(レビュー役に伝える経路は次の項目)。

- レビュースキルは PR 本文を読むとは限らない。**次の反復で確実に伝えたい理由はコードコメントに書く**。ただし、コードの恒久的な説明として妥当なものに限る(「レビューで指摘されたが」のような経緯は書かない)。このコメントも、修正役の結果を確かめる途中の手直しも、修正の差分のレビューの前にコミットし、そのレビューに含める(「終了の判断」)
- レビューの経緯そのものは PR 本文に書く。PR 本文は**書く直前に読み直し**、該当する部分だけを追記・更新する。人間が編集した部分を上書きしない。リポジトリが公開なら、直していないセキュリティの指摘の悪用の手順は書かない

レビュー役には過去の判断を渡さない(別の文脈で動かすのは、そのため)。過去の判断を次の反復のレビュー役に伝える経路は、このコードコメントと PR 本文だけ。俯瞰の役には、これに加えて、過去の俯瞰の出力と修正の差分(`history/`)も届く。

修正したら手順1に戻る。

## 終了の判断

- 観点の欠落がある反復では終えない
- **終えるのは、次のどちらか。** 差分の内で、分類が defect、影響が中以上の指摘が、出どころ(俯瞰の役の表、修正の差分のレビュー、前の反復からの持ち越し)を問わず、どれも下の扱いのどれかに決まり(そういう指摘が無い場合を含む)、次の項目で、もう1回回さなくてよいとなった。または、俯瞰の役の判断で止まり(手順4)、利用者が終えると決めた
  - 決まった扱いに数えるもの: 再現して直した。起きなかった(試した手順を残した)。実行では確かめずに、採否を決めた(理由を残した)。手順5の一覧に当てて、対象から外した(理由を残した)。文書への指摘として、直したか、報告に回した。利用者が決めた
  - どれにも当たらない指摘は、扱いが決まっていない。確かめられない修正を `git revert` で戻して次の反復に任せたもの、修正役が決められずに返したものなど。次の反復の俯瞰の役の表に無くても、再現させる対象として持ち越し、持ち越しがある間は終えない
- もう1回回すかは、直近の反復で入れた全てのコミット(最後にレビューを受けた SHA から HEAD まで)を、次の種類に分けて決める。修正役のコミットだけでなく、あなたが入れたもの(却下の理由のコードコメント、修正役の結果を確かめる途中の手直しなど)も含め、どれも、いずれかの種類に入る。コミットが1つも無ければ、回さずに終えてよい。あれば、全てのコミットが自分の種類の「回さずに終えてよい条件」を満たすときだけ、回さずに終えてよい。1つでも満たさなければ、もう1回回す。そのために3回の目安を超えるなら、回す前に、残っている指摘と見通しを利用者に報告し、続けるかを決めてもらう(目安の項目)
  - 再現させる対象への修正(再現して直したもの): 修正の差分のレビュー(手順5)を受け、再現が修正前に失敗して修正後に通り、修正した箇所を通る既存のテストも通っている。共有している関数の変更や横展開の修正のように、再現が確かめた経路の外の挙動も変えているなら、修正の大きさに関係なく満たさない。修正した箇所を通る既存のテストがない(テストのないプロジェクトを含む)ときも、ほかの経路を壊していないことを確かめたものがないので満たさない
  - 再現なしで直したもの(箇所に閉じる修正、文書への指摘の修正、あなたが入れた、箇所に閉じるコメントや手直し): 修正の差分のレビューを受けている。箇所に閉じるか、合否で確かめる手段が無いものなので、差分のレビューを受けていれば、それだけでは回す理由にしない。差分のレビューのあとに入れたコミットは、そのレビューを受けていないので満たさない(そのため、あなたのコミットは差分のレビューの前に入れる)
  - 修正の差分のレビューの指摘を受けた修正(文書への指摘は直さないので、ここに入らない): 満たす条件は無い(回す)。そのレビューを次の反復に任せる(手順5)ので、再現と既存のテストが通っていても回す
  - 実行では確かめていない修正(手順5で採ったもの。あなたが入れた手直しのうち、箇所に閉じないものも含む。文書と一緒に変えたものも含む): 満たす条件は無い(回す)。その修正はまだ誰にも確かめられていないため
  - 採らずに `git revert` で戻したコミットと、その revert のコミットは、差し引きで変更が無いので、種類に分けず、数えない
- 過去の反復と見比べ、同じ指摘の蒸し返しや、修正が行ったり来たりする振動が見えたら、回数に関係なく、そこで回すのを止める。残っている指摘と見通しを利用者に報告し、続けるかを決めてもらう
- 反復は **3回を目安**にする。数えるのは、状態コメントの反復回数(completed になった試行)で、観点の欠落で回し直した回も含む。3回目の反復のあと、まだ回す理由が残っていれば、打ち切らずに、残っている指摘と見通しを利用者に報告し、続けるかを決めてもらう。スクリプトの上限(シリーズあたり10回、連続失敗3回)は暴走を止めるためのもので、目安ではない

終了したら、利用者に次を報告する: 反復回数、残った指摘(採らなかったものはその理由も)、直した指摘のうち再現で確かめたものと実行では確かめていないもの、範囲が「差分の外」で直さなかった指摘と横展開の箇所(影響の段階も)、直さずに報告に回した文書への指摘(影響の段階も)、最後にレビューを受けた SHA(状態コメントの表で、最後に completed になった試行の SHA。`--new-run` のあとで表にまだなければ、あなたが持っている直前の試行の SHA)と終了時の HEAD の差(そのあとに入れた修正と、その影響の段階)。観点を外したり、観点への指示で範囲を絞ったりしたなら、最後の反復でレビューされなかった観点と範囲も報告する。レビュー役のトークン数は記録していない(バックグラウンドで動いた役の分は完了の通知に付くが、その場で結果が返った役の分は分からない)。

範囲が「差分の外」で直さなかった指摘や横展開の候補、報告に回した文書への指摘があれば、報告に続けて、issue にするかを利用者に尋ねる。どれを issue にするかは利用者が決め、言われたものだけを `gh issue create` で作る。尋ねずに作らない。作る前に、同じ不具合の issue が既にないかを探し、あれば作らずに利用者に伝える。本文には、場所、影響と起きやすさ、起きる操作の順、見つけた PR の番号と、レビューの指摘で実行では確かめていないことを書く。セキュリティに関わる指摘は、リポジトリが公開なら、悪用の手順が誰にでも読める形で残るので、起きる操作の順を書かず、公開の issue にしてよいか、非公開の経路で扱うかを利用者に尋ねる。反復をまたいで同じ指摘が出ていたら、1件にまとめる。影響が高のものは、尋ねるときに先頭に置く。

## 失敗したとき

- **同じ原因で2回続けて失敗したら、再実行せず利用者に報告する**
- レビュー役の失敗(`reviewer_failed`。あなたが `end --failed` で記録したもの): 原因を確かめる。スキルの名前の誤りか未導入、対象の取り違え(あなたの作業ディレクトリが worktree のトップでない)、権限の設定による拒否、モデルや API のエラーなど。権限の設定を変える、sandbox の外で実行するといった回避策は自分では取らず、内容を利用者に伝える。拒否されたのが PR の目的に要らない確認(PR で削除した `.env` の中身を読もうとした、など)なら、その観点に確認を不要と伝える指示を渡すか、その観点を外す案も添える(手順2)。どちらを採るかは利用者が決める
- レビュー役が、スキルを呼ばずに自分でレビューした、手順の一部を飛ばしたと返したとき: その出力は観点スキルのレビューではないので、`reviews.md` に入れず、レビュー役の失敗として閉じる
- 混入(`contamination`): `begin` から `end` までの間に、作業ツリー、HEAD、ブランチのどれかが変わった。レビュー役が変えたか、あなたが `end` の前に編集した。スクリプトは変更を元に戻さない。内容を確かめ、意図しない変更なら取り除いてから、手順1からやり直す。レビュー役の変更を自分の修正と一緒にコミットしない。`--failed` を付けて閉じたときも、混入があればこちらが優先して記録される
- `head_changed`: `begin` から `end` までの間に、PR のブランチへ push があった。その間は誰も push しない決まりなので、誰の push でも決まりに反している。外からの push と、レビュー役がローカルを変えずに直接 push したもの(禁じている操作)は区別できない。新しいコミットの作者と内容を確かめ、出どころが分からなければ取り込まずに利用者に報告する。`begin` の前に済ませるはずの push が遅れて届いただけなど、出どころが分かっていて内容が正当なら、取り込んで手順1からやり直す
- 「前の試行を end で閉じていない」: この worktree で `begin` した試行が開いたまま。`end` を呼んで閉じる(レビュー役の結果を受け取れていなければ `--failed` を付ける)
- 「別の試行が実行中」: ほかのセッションが、同じ PR で試行中の可能性がある。`end` は、この worktree で `begin` した試行しか閉じない(ほかの試行のロックは閉じない)。終わるのを待つか、利用者に報告する。古いロック(`STALE_LOCK_AFTER` の55分を超えたもの。この長さをロックに記録していない旧版のロックは、旧版が持ちうる75分(`LEGACY_STALE_LOCK_AFTER`)を超えたもの)は、次の `begin` で自動的に `interrupted` として片付き、連続失敗に数えられる
- 「オープンではない」「作成者が自分ではない」: このスキルは自分のオープンな PR だけが対象

## 既知の制約

- スキルがフォークで動くかどうかは、スキルの作りと Claude Code の版で決まる。`code-review` がフォークで動き、`security-review` と `mattpocock-skills:code-review` が動かないのは、2026-11-17 に確かめた結果。変わっていれば、Skill ツールの結果で分かる(手順2)
- レビュー役が試行中に何を読み、何を実行したかは、出力に書かれたことしか分からない。スクリプトが確かめるのは、試行の前後で作業ツリー、HEAD、ブランチ、PR の head が同じことだけ。レビュー役に制限時間は無く、止まったレビュー役をスクリプトは止めない(手順3)
- レビュー役の出力のファイルは、レビュー役自身が書く。返した結果と同じ内容を書いたかは、確かめていない。疑わしければ、届いた結果と、作業ディレクトリの `review-<レビュー役の名前>.md` を読み比べる
- レビュー役の出力のファイルは、役ごとに別の場所に置くが、同じ利用者の権限で読める。レビュー役が一時ディレクトリを探せば、ほかの役の出力や過去の試行の記録を読める。渡すパスの隣に置かない、という程度の隔離
- ロックは、55分(`STALE_LOCK_AFTER`)たつと古いとみなされる。レビュー役に制限時間は無いので、それより長引いた試行のロックは、同じ PR で始めたほかのセッションの `begin` に奪われうる。奪われた試行の `end` は、「この試行のロックが、状態コメントに無い」で止まる
- `begin` は、スクリプトのプロセスの作業ディレクトリが worktree のトップかを確かめるが、あなたのセッションの作業ディレクトリ(レビュー役が動く場所)を直接は確かめられない
- `begin` は、試行の記録を git の管理ディレクトリに書く。リンクされた worktree では、そこは worktree の外(本体の `.git/worktrees/<名前>/`)になる。sandbox などで書き込み先を絞っている環境で書けるかは、確かめていない(`git commit` が通る環境なら書ける)
- 観点に渡した指示は、どこにも記録されない(公開の PR コメントに本文を載せないため)。反復をまたいで同じ指示を渡し続けるのは、あなたの受け持ち。文脈が圧縮されても失わないよう、指示を渡したら、その本文を PR 本文の経緯に書いておく
- `mattpocock-skills:code-review`(既定には無い。観点に足したとき)は、PR のベースブランチ(ローカルの `main` か `origin/main`)を起点に差分を取る。ローカルのベースが古く、PR 側に新しいベースを取り込んでいると、ベース側の変更までレビュー対象に入りうる(対象が欠けることはない)
- 組み込みの `security-review` は引数を取らず、比較の起点を自分で決める(`origin/HEAD` と比べる可能性が高い)。PR のベースが既定ブランチでない、またはローカルの `origin/HEAD` が古いと、PR とは違う差分を見うる。既定ブランチ以外へ向けた PR では、その観点の出力が PR の差分に沿っているか確かめる
- 混入の検査は、作業ツリー、HEAD、ブランチ名だけを見る。stash のように ref だけを変える操作は検出しない。stash の積み場所は他の worktree やセッションと共有なので、比べると誤検知が出るため

## PR の状態コメント

スクリプトは PR にマーカー `<!-- review-loop-state -->` 付きのコメントを1つだけ置き、編集で更新する(人間のレビュアーに通知が飛ばないように)。載るのは run_id、反復回数、試行ごとの SHA・時刻・結果(失敗なら種類と、`--failed` に渡した理由)・レビュー役の名前、連続失敗回数、ロックだけで、指摘の内容や判断の理由は載せない。`--failed` の理由は公開の PR コメントに載るので、公開したくないことは書かない。このコメントを書き換えるのはスクリプトだけ。あなたは編集しない。
