# review-loop — 自分の PR のレビューループ

1反復は「修正をコミットして push する → スクリプトがレビューと判定をする → 判定を読んで修正の方針を決める」。これを、リスクの高い指摘がなくなるまで回す(基準は「終了の判断」)。

スクリプト `scripts/review_loop.py` が受け持つのは、前提と安全上限の強制、観点別レビューと判定役の起動、PR の状態コメントの読み書きだけ。それ以外はすべて親の受け持ちになる。

**親**は、このループを回すただ1つのセッションで、ループ全体を管理する。この文書の「あなた」は親を指す。別のスキルから使うときは、ループを回す呼び出し元が親になる。親が責任を持つのは次の4つ。

- **スクリプトの起動**: 1つのループでスクリプトを起動するのは親だけ
- **順序**: 修正と push が終わってから起動し、実行中は worktree の編集も PR への push も起こさせない
- **反復をまたぐ文脈**: 過去の判定と、採らなかった指摘とその理由を持ち続け、採否と終了の判断に使う。スクリプトは独立性を保つため子に過去の判断を渡さないので、蒸し返しや振動を見分ける手がかりはここにしかない
- **利用者とのやり取り**: `--new-run` の確認、この文書で「利用者に報告する」とした失敗の報告、終了時の報告

## 前提

- 対象ブランチに PR がある。worktree の中で作業していて、`gh` が認証済み
- 観点スキルが使う `gh` や `git` の読み取り系コマンドが、許可ルールで許可されている。`-p` では、許可されていないツールの呼び出しは確認なしで拒否され、その試行は失敗になる
- 観点スキルの一覧は `scripts/review_loop.py` 冒頭の `PERSPECTIVES` にある。変えるときはそこだけを書き換える。各要素は「スキル名と引数」で、引数の `{pr}` は PR 番号に置き換わる(例: `code-review high {pr}` → `/code-review high 12`)。引数の意味はスキルごとに違うので、PR 番号は自動では足さない。たとえば `mattpocock-skills:code-review` は引数を比較の起点として読むので、数字だけでなく `PR #{pr}` と書く(スキルが PR のベースを起点に決め、PR 本文を仕様として使う)。組み込みの `code-review` は、レベルを指定しないと利用者が最後に使ったレベルを引き継ぐので、固定してある
- 制限時間・上限回数などの値は、同じファイル冒頭の定数(`REVIEW_TIMEOUT`、`BASH_TIMEOUT`、`STALE_LOCK_AFTER`、`SAFETY_MAX_ITER`、`MAX_CONSECUTIVE_FAILURES`)が正。この文書に書いた値は、その既定値

## 手順

### 1. コミットして push する

修正をコミットし、**毎回 push する**。スクリプトは、作業ツリーがクリーンで、ローカルの HEAD と PR の head が一致していなければ起動しない。コードを変えずに PR 本文だけを更新した場合は、同じ SHA のまま再実行してよい。

### 2. スクリプトを起動する

Bash ツールの**バックグラウンド実行**で、**制限時間を 90 分(`timeout: 5400000`。`BASH_TIMEOUT` と同じ値)と明示して**起動する。既定の制限時間では、レビューの途中で止められる。

```sh
python3 ${CLAUDE_SKILL_DIR}/scripts/review_loop.py iterate <worktree の絶対パス>
```

- コマンドは上の形のまま書き、パスを引用符で囲まない。sandbox の除外ルールなど、コマンドの文字列で照合する設定に合わせるため。ただし、パスに空白が含まれる環境では引用符で囲み、除外ルールもその形で登録する
- `--new-run` は、利用者から新しいシリーズを始めるよう明示的に指示されたときだけ付ける。直前のシリーズは run_id と反復回数だけに要約され、試行の記録は消える。状態コメントが手で編集されるなどして読めないときも、スクリプトは上限を黙って外さないよう終了コード2で止まる。そのときも `--new-run` は利用者に確認してから付ける
- 実行中は、誰も worktree を編集せず、PR に push しない。レビュー役は同じ worktree と PR を読んでいる。編集や push があると、試行は `contamination` か `head_changed` で失敗する

### 3. 結果を受け取る

stderr の最後の行は作業ディレクトリのパス(`<一時ディレクトリ>/review-loop/<owner>_<repo>/<PR番号>/<run_id>/<試行>/`)。作業ディレクトリを作る前に終わったとき(終了コード2のほとんどと `workdir_error`)は空行で、`failure.txt` もない。各レビューの出力(`review-*.stdout.json` の `result`)、判定役への入力(`judge-input.md`)、判定(`verdict.md`)、失敗したときの詳細(`failure.txt`)がそこに残る。

| 終了コード | 意味 | 次にすること |
| --- | --- | --- |
| 0 | 成功。標準出力は判定のテキストだけ(stderr に「記録できなかった」と出たときは、反復回数が進んでいない) | 手順4へ |
| 1 | 試行の失敗。状態コメントに記録済み(stderr に「記録できなかった」と出たときは記録されておらず、連続失敗にも数えられていない。同じ失敗が続くなら、上限を待たずに利用者に報告する) | stderr の理由を読む。後述の「失敗したとき」 |
| 2 | 試行を始めなかった(前提を満たさない、ロックを取れない、上限に達した、開始前に中断された)。試行は記録されない(ただし、残っていた古いロックを `interrupted` として片付けた記録は残る) | 理由を解消してから再実行するか、利用者に報告する |

失敗の種類は stderr の `failed:` の行の先頭にある: `permission_denied`(権限の拒否)、`timeout`、`child_error`(子の異常終了)、`no_output`(結果が空、判定が決めた形になっていない)、`contamination`(混入)、`head_changed`(試行中に PR に別の push があった)、`interrupted`(中断)、`spawn_error`(見張り役を起動できない。claude 自体が起動できないときは `child_error` になる)、`workdir_error`(作業ディレクトリを作れない)、`command_error` と `internal_error`(git・gh・スクリプト自身の失敗)。種類の正は `review_loop.py` の `AttemptFailed` と `classify`。PR の状態コメントには種類と対象だけを載せ、詳細(拒否されたコマンドなど)は載せない。

### 4. 判定を読んで方針を決める

判定は作業ディレクトリの `verdict.md` から読む(Bash の出力ファイルには stderr の進捗が混ざる)。形と、影響・起きやすさの段階の定義は `review_loop.py` の `JUDGE_PROMPT` が正。指摘ごとに次が書かれている。

- 影響(高 / 中 / 低 / なし)と、直さなかったら何が起きるか
- 起きやすさ(普通の使い方 / 特定の操作の組み合わせ / まれな条件)と、起きる操作の順
- 再指摘: 以前に採らなかった指摘と同じなら、その理由と、今回それを覆す事情があるか
- 横展開: 指摘が破っている規則と、同じ規則に触れるほかの経路の候補
- 競合: 判定役が競合を裁定して直すことにした指摘なら、その競合の id

観点の欠落(影響の欄が「観点の欠落」の指摘)は、その観点がレビューになっていなかったことを表す。書き方が揺れていても、分類 other で、観点の出力がレビューになっていないとされた指摘は同じに扱う。その回の判定は欠けているので、原因(観点スキルの設定、対象の取り違えなど)を確かめてから回し直す。回し直した回も反復として数える。同じ観点が2回続けて欠けたら、利用者に報告する。

判定役の裁定や指摘は、PR の意図に照らして覆したり却下したりしてよい。判定役がレビューを取りこぼしていないか気になったら、作業ディレクトリにある各レビューの出力を読む。

### 5. 修正し、判断の理由を残す

採用した指摘を修正する。横展開の候補は、確かめたうえで同じ修正に含める。過去の判定と見比べて、同じ規則の破れが場所を変えて続いているなら、場所ごとに直すのをやめ、その規則を1か所で強制する形を検討する。

判定と異なる判断(指摘の却下、裁定の変更)をしたら、その理由を残す。

- レビュースキルは PR 本文を読むとは限らない。**次の反復で確実に伝えたい理由はコードコメントに書く**。ただし、コードの恒久的な説明として妥当なものに限る(「レビューで指摘されたが」のような経緯は書かない)
- レビューの経緯そのものは PR 本文に書く。PR 本文は**書く直前に読み直し**、該当する部分だけを追記・更新する。人間が編集した部分を上書きしない

スクリプトは過去の判定を子に渡さない(独立性を保つため)。過去の判断を次の反復に伝える経路は、このコードコメントと PR 本文だけ。

修正したら手順1に戻る。

## 終了の判断

あなたが総合的に判断する。

- 観点の欠落がある判定では終えない
- 主な基準は、**リスクの高い指摘が残っていないか**。影響が高の指摘は、起きやすさに関係なく継続の理由になる。影響が中で、普通の使い方で起きる指摘も同じ
- それ以外の指摘(テストの不足などを含む)を、直すか、継続の理由にするかは、あなたが決める
- 直前の判定で、上の基準に当たる指摘を採って直したなら、その修正はまだレビューされていないので、終えずにもう1回回す。そのために5回の目安を超えるなら、残っている指摘と見通しを利用者に報告し、続けるかを決めてもらう
- 過去の判定と見比べ、同じ指摘の蒸し返しや、修正が行ったり来たりする振動が見えたら打ち切ってよい
- 反復は **5回を目安**にする。スクリプトの上限(シリーズあたり10回、連続失敗3回)は暴走を止めるためのもので、目安ではない

終了したら、利用者に次を報告する: 反復回数、残った指摘(採らなかったものはその理由も)、最後に判定を受けた SHA(状態コメントの表で、最後に completed になった試行の SHA。`--new-run` のあとで表にまだなければ、あなたが持っている直前の判定の SHA)と終了時の HEAD の差(そのあとに入れた修正と、その影響の段階)、合計の入力・出力トークン数(状態コメントの表にある。失敗した試行の分は、途中で止めた子を含まない下限)。

## 失敗したとき

- **同じ原因(同じ権限の拒否など)で2回続けて失敗したら、再実行せず利用者に報告する**
- 権限の拒否(`permission_denied`): 拒否されたツールと入力が stderr に出る。許可ルールの追加は利用者が判断することなので、内容を伝えて止まる
- 混入(`contamination`): 子が作業ツリーやブランチを変えた。スクリプトは変更を元に戻さない。内容を確かめ、意図しない変更なら取り除いてから再実行する。子の変更を自分の修正と一緒にコミットしない。ほかの理由(権限の拒否など)で失敗した試行でも、混入があればこちらが優先して報告される
- `head_changed`: 試行中に PR のブランチへ push があった。実行中は誰も push しない決まりなので、誰の push でも決まりに反している。外からの push と、子がローカルを変えずに直接 push したもの(禁じている操作)は区別できない。新しいコミットの作者と内容を確かめ、出どころが分からなければ取り込まずに利用者に報告する。起動前に済ませるはずの push が遅れて届いただけなど、出どころが分かっていて内容が正当なら、取り込んで手順1からやり直す
- 事前確認の失敗(終了コード2で「事前確認」): 事前確認では、子の claude を1回起動し、Bash で `pwd` を実行させて結果まで確かめる(API を最大3回呼ぶ。そのトークン数は試行の記録に含まれる)。失敗の原因は、観点スキルの名前の誤りか未導入、claude が起動しないか応答しない(認証、sandbox、ネットワーク)、子の Bash が失敗する(sandbox の中からこのスクリプトを起動し、子が sandbox を入れ子に起動できないなど)、Bash が許可ルールで拒否される、のどれか。sandbox の外で実行する、権限の確認を飛ばすといった回避策は自分では取らず、利用者に伝える。子が Bash を呼ばなかったとき(または結果を読めなかったとき)は失敗にせず、stderr に「確かめていない」と出して続ける。事前確認の子が作業ツリー、ブランチ、PR の head を変えたときも、レビューを始めずに止まる
- 「別の試行が実行中」: 二重起動の疑い。古いロック(`STALE_LOCK_AFTER` の75分を超えたもの)は次の起動で自動的に `interrupted` として片付く。スクリプトが SIGKILL されても、子とその子孫のうち同じプロセスグループにいるものは見張り役が止める(子孫が自分で別のセッションに切り離したものは止まらない)
- 「オープンではない」「作成者が自分ではない」: このスキルは自分のオープンな PR だけが対象

## 既知の制約

- `mattpocock-skills:code-review` は、PR のベースブランチ(ローカルの `main` か `origin/main`)を起点に差分を取る。ローカルのベースが古く、PR 側に新しいベースを取り込んでいると、ベース側の変更までレビュー対象に入りうる(対象が欠けることはない)
- 組み込みの `security-review` は引数を取らず、比較の起点を自分で決める(`origin/HEAD` と比べる可能性が高い)。PR のベースが既定ブランチでない、またはローカルの `origin/HEAD` が古いと、PR とは違う差分を見うる。既定ブランチ以外へ向けた PR では、その観点の出力が PR の差分に沿っているか確かめる
- 混入の検査は、作業ツリー、HEAD、ブランチ名だけを見る。stash のように ref だけを変える操作は検出しない。stash の積み場所は他の worktree やセッションと共有なので、比べると誤検知が出るため

## PR の状態コメント

スクリプトは PR にマーカー `<!-- review-loop-state -->` 付きのコメントを1つだけ置き、編集で更新する(人間のレビュアーに通知が飛ばないように)。載るのは run_id、反復回数、試行ごとの SHA・時刻・結果・入力と出力のトークン数、連続失敗回数、ロックだけで、指摘の内容や判断の理由は載せない。このコメントを書き換えるのはスクリプトだけ。あなたは編集しない。
