# review-loop — 自分の PR のレビューループ

1反復は「修正をコミットして push する → スクリプトがレビューと判定をする → 判定を読んで修正の方針を決める」。これを、挙動が変わる修正を要する指摘がなくなるまで回す。

スクリプト `scripts/review_loop.py` が受け持つのは、前提と安全上限の強制、観点別レビューと判定役の起動、PR の状態コメントの読み書きだけ。修正、push、裁定の採否、終了の判断はあなた(親)が行う。修正をエージェントに任せてもよいが、push と判断は任せない。

## 前提

- 対象ブランチに PR がある。worktree の中で作業していて、`gh` が認証済み
- 観点スキルが使う `gh` や `git` の読み取り系コマンドが、許可ルールで許可されている。`-p` では、許可されていないツールの呼び出しは確認なしで拒否され、その試行は失敗になる
- 観点スキルの一覧は `scripts/review_loop.py` 冒頭の `PERSPECTIVES` にある。変えるときはそこだけを書き換える

## 手順

### 1. コミットして push する

修正をコミットし、**毎回 push する**。スクリプトは、作業ツリーがクリーンで、ローカルの HEAD と PR の head が一致していなければ起動しない。コードを変えずに PR 本文だけを更新した場合は、同じ SHA のまま再実行してよい。

### 2. スクリプトを起動する

Bash ツールの**バックグラウンド実行**で、**制限時間を 90 分(`timeout: 5400000`)と明示して**起動する。既定の制限時間では、レビューの途中で止められる。

```sh
python3 "${CLAUDE_SKILL_DIR}/scripts/review_loop.py" iterate <worktree の絶対パス>
```

- `--new-run` は、利用者から新しいシリーズを始めるよう明示的に指示されたときだけ付ける。直前のシリーズは run_id と反復回数だけに要約され、試行の記録は消える
- 実行中は、あなたも、あなたが起動したエージェントも worktree を編集しない。レビュー役は同じ worktree を読んでいる

### 3. 結果を受け取る

stderr の最後の行は作業ディレクトリのパス。各レビューの出力(`review-*.stdout.json` の `result`)、判定役への入力(`judge-input.md`)、判定(`verdict.json`)がそこに残る。

| 終了コード | 意味 | 次にすること |
| --- | --- | --- |
| 0 | 成功。標準出力は判定 JSON だけ | 手順4へ |
| 1 | 試行の失敗(レビュー役・判定役の失敗、権限の拒否、タイムアウト、作業ツリーやブランチへの混入、中断)。状態コメントに記録済み | stderr の理由を読む。後述の「失敗したとき」 |
| 2 | 前提を満たさない、ロックを取れない、上限に達した。試行としては記録されない | 理由を解消してから再実行するか、利用者に報告する |

### 4. 判定を読んで方針を決める

判定 JSON の構造は `scripts/verdict.schema.json` にある。要点は次のとおり。

- `findings[]`: 指摘。`behavior_change` はその指摘に従って修正したときに挙動が変わるか、`category` は `defect` / `test_gap` / `naming_or_comment` / `style` / `other`
- `conflicts[]`: 観点どうしの競合と、判定役の裁定(`ruling.action` が `fix` のものは `findings` にも `conflict` で参照される形で載る)
- `recommendation`: 継続の推奨。参考情報で、決めるのはあなた

判定役の裁定や指摘は、PR の意図に照らして覆したり却下したりしてよい。判定役がレビューを取りこぼしていないか気になったら、作業ディレクトリにある各レビューの出力を読む。

### 5. 修正し、判断の理由を残す

採用した指摘を修正する。判定と異なる判断(指摘の却下、裁定の変更)をしたら、その理由を残す。

- レビュースキルは PR 本文を読むとは限らない。**次の反復で確実に伝えたい理由はコードコメントに書く**。ただし、コードの恒久的な説明として妥当なものに限る(「レビューで指摘されたが」のような経緯は書かない)
- レビューの経緯そのものは PR 本文に書く。PR 本文は**書く直前に読み直し**、該当する部分だけを追記・更新する。人間が編集した部分を上書きしない

スクリプトは過去の判定を子に渡さない(独立性を保つため)。過去の判断を次の反復に伝える経路は、このコードコメントと PR 本文だけ。

修正したら手順1に戻る。

## 終了の判断

あなたが総合的に判断する。

- 主な基準は、**挙動が変わる修正を要する指摘が残っていないか**
- 挙動は変えないが重要な指摘(テストの不足など)を継続の理由にするかは、あなたが決める
- 過去の判定と見比べ、同じ指摘の蒸し返しや、修正が行ったり来たりする振動が見えたら打ち切ってよい
- 反復は **5回を目安**にする。スクリプトの上限(シリーズあたり10回、連続失敗3回)は暴走を止めるためのもので、目安ではない

終了したら、利用者に次を報告する: 反復回数、残った指摘(採らなかったものはその理由も)、合計の費用(状態コメントの表にある)。

## 失敗したとき

- **同じ原因(同じ権限の拒否など)で2回続けて失敗したら、再実行せず利用者に報告する**
- 権限の拒否(`permission_denied`): 拒否されたツールと入力が stderr に出る。許可ルールの追加は利用者が判断することなので、内容を伝えて止まる
- 混入(`contamination`): 子が作業ツリーやブランチを変えた。スクリプトは変更を元に戻さない。内容を確かめ、意図しない変更なら取り除いてから再実行する
- 事前確認の失敗(終了コード2で「事前確認」): 観点スキルの名前の誤りか未導入、または claude が起動しない(認証、sandbox、ネットワーク)。sandbox の外で実行する、権限の確認を飛ばすといった回避策は自分では取らず、利用者に伝える
- 「別の試行が実行中」: 二重起動の疑い。古いロック(65分を超えたもの)は次の起動で自動的に `interrupted` として片付く

## PR の状態コメント

スクリプトは PR にマーカー `<!-- review-loop-state -->` 付きのコメントを1つだけ置き、編集で更新する(人間のレビュアーに通知が飛ばないように)。載るのは run_id、反復回数、試行ごとの SHA・時刻・結果・費用、連続失敗回数、ロックだけで、指摘の内容や判断の理由は載せない。このコメントを書き換えるのはスクリプトだけ。あなたは編集しない。
