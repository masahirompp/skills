# 修正役: 材料の用意、依頼、返ってきたあとに確かめること

SKILL.md の手順5で、再現させる対象と直すものを決めたあとに読む。どの指摘を採るか、どこで利用者に見せて止まるかは SKILL.md にある。

修正役は、あなたの文脈を引き継がないサブエージェント。1反復に1つだけ起動する(同じ作業ツリーを並列に編集させない)。規則ごとに、修正前のコードで失敗する再現のコマンドを作り、失敗を見てから直し、コミットする。push はあなたが行う。

## 材料を用意する

修正役のために、新しい一時ディレクトリを作る。俯瞰の材料のディレクトリは使い回さない(レビュー役の出力の全文や過去の反復が置いてあり、修正役に渡さないと決めたものまで読めてしまう)。作業ツリーの中から、1行ずつ別のコマンドとして実行する。

```sh
mktemp -d                                   # 出たパスを <F> として、以下に書き写す
mkdir <F>/before <F>/work
git rev-parse HEAD                          # 出た SHA を <修正前の SHA> として控える
git archive HEAD | tar -x -C <F>/before
```

`<F>/before` が、修正前のコードの写しになる。差分のレビューで出た指摘の続きを頼むときも、その時点の HEAD から新しく作り直す(修正が持ち込んだ問題は、レビューを受けた SHA の写しでは再現しない)。

## 依頼文

`<...>` を埋め、ほかは変えない。書くのは、規則、箇所、症状、起きる条件、俯瞰の役が選んだ直し方、変えてはいけないものだけ。あなたが考えた修正の中身、レビュー役の出力にある具体的な再現の手順や入力は書かない(修正役が、その例に合わせた再現と修正を作るため)。

- 規則は、俯瞰の役の出力の規則を1文のまま写す。どの規則にも入っていない再現させる対象の行(SKILL.md の手順5)は、それだけで1つの規則にし、その指摘が破っている規則をあなたが1文で書く
- 「症状」と「起きる条件」は、指摘された箇所ごとに書く。1つの規則に、症状の違う箇所が複数入るため。「症状」には、規則が破れたときにその箇所で何が起きるかを書く。「起きる条件」には、起きる環境や操作の組み合わせを書く(別の OS、特定の引数の組み合わせなど)。どちらも、俯瞰の役が規則ごとに書いた、指摘ごとの症状と起きる条件から写す(規則に入っていない行は、「その他」に添えられたものから写す)。条件が無ければ「無い」。どの箇所も同じなら、1行にまとめてよい
- 「直し方」には、俯瞰の役が選んだ直し方を写す。あなたが一部だけを採ったなら、採らなかった部分を書き添える
- 「横展開の候補」には、俯瞰の役が横展開で見つけた箇所のうち、範囲が差分の内になるものだけを書く。差分の外の候補は「直さない箇所」に書く。ただし、規則を1か所で守る直し方で同時に塞がるものは、候補に書いてよい
- 「再現なしで直すもの」には、再現の対象でない指摘のうち、直すと決めたものを書く(文書への指摘で、直すと決めたものを含む)。無ければ「無い」
- 「変えてはいけないもの」には、PR が意図して変えた挙動と、以前に採らなかった指摘とその理由を書く。修正役は反復をまたぐ文脈を持たないので、ここに無いことは知らない

## 進め方
`mattpocock-skills:diagnosing-bugs` のスキルを使えるなら、呼び出して、その手順で進めてください。使えなければ、下の決まりだけで進めてください。どちらの場合も、下の決まりをスキルの手順より優先します。

1. 規則ごとに、直す前に、再現のコマンドを1つ作る。`<F>/work/repro-<規則の番号>/` の下に置き、対象のルートを引数に取る形にする(例: `sh <F>/work/repro-1/run.sh <ルート>`)。終了コードは3通りに分ける。規則が守られていれば 0。指摘された症状を見たら 1(見たものを出力する)。実行できなかった(依存が足りない、前提のファイルが無いなど、症状とは別の理由で失敗した)なら 2。指摘された症状そのものを見る(「落ちずに動く」や、関数や文言があるかどうかでは足りない)。何度流しても同じ結果で、数秒で終わる。対象のルートの中には書き込まない(要るなら `<F>/work/` に写してから動かす)
   - 写しには、追跡されていない依存物(`node_modules`、ビルドの生成物など)が無い。それが無くて動かせないときは、作業ツリーの依存物を借りてよい(絶対パスで参照する、`<F>/work/` に写した側からリンクを張る、など。作業ツリーの依存物は書き換えない)。修正前と修正後の写しで、同じ依存物を使う形にする。借りたら、何をどこから借りたかを返す
2. 再現の対象は、1つの例ではなく規則。指摘された箇所と、横展開の候補のそれぞれを、同じコマンドの中で1件ずつ確かめ、箇所ごとに結果を出す。規則が守られている入力を、断ったり壊したりしていないことを見る対照も、入れられるなら入れる
3. 直す前に、`<F>/before` に向けて流し、終了コード 1 で終わるのを見る。症状が出なかった箇所は「起きなかった」として、直さない。「起きうる」という推論だけでは直さない。ただし、「起きる条件」にある環境を作れなかったときは、「起きなかった」ではなく「実行では確かめていない」にする
4. 再現を作れないとき(文書やプロンプトの書き方、外部のサービスの挙動、狙って起こせないタイミング、作れない環境)は、利用者に尋ねず、代わりの実験(作り物のスクリプトで文書の主張を確かめる、など)も作らない。コードや文面を追って、成り立つと判断したものだけを直し、「実行では確かめていない」と理由を付けて返す。作るのが手間、は理由にならない
   - 再現の入力や状態が、外部の挙動についての未確認の前提に立つとき(ツールや外部のサービスが出すイベントの形、外部のコマンドの出力などを、実物で一度も観測しないまま作り物で与えた)は、症状を見ても「再現して直した」にしない。どの前提が未確認かを書いて、「実行では確かめていない」と返す。実物で観測できるなら、観測してから作る
5. 原因が指摘のとおりで、再現がそれを裏づけたら、仮説の列挙と計測(スキルのフェーズ3〜4)は省いてよい
6. 直すのは規則。再現が通るだけの継ぎを当てない。「方式を変える」とある規則は、1か所で守る形に直す。「直さない箇所」と「変えてはいけないもの」には手を付けない
7. 再現のコマンドの判定を、修正に合わせて変えない。コマンドの側が誤っていたと分かって直したら、変えた点と理由を返す
8. プロジェクトにテストの置き場があれば、再現を回帰テストとしてそこへ足す(規則が破れる経路を通せる継ぎ目が無ければ、足さずに、そう返す)。既存のテストを流し、通るのを見る(既存のテストは、数秒で終わらなくてよい)。全体を流すのに数分以上かかるテスト(e2e など)は、規則ごとには、修正した箇所を通るものに絞って流し、全体は全ての規則を直し終えてから1回だけ流す。そこで落ちたら、直したあとは落ちたテストだけを流し直す(全体は、親が修正後にもう1回流す)
9. 直したら、作業ツリーに向けて再現のコマンドを流し、終了コード 0 で終わるのを見る。調べるために足した出力や一時ファイルを、作業ツリーに残さない
10. コミットは、規則ごとに分ける。「再現なしで直すもの」と、実行では確かめていない修正は、再現して直したものと別のコミットにする(親が、規則ごとに採るか戻すかを決めるため)。コードコメントには、コードの恒久的な説明として妥当なことだけを書く(レビューで指摘された、といった経緯は書かない)

迷ったこと、あなたでは決められないことは、推し進めずに、直さないまま返してください。

- 箇所ごとの結果: 再現して直した / 起きなかった(試した手順)/ 実行では確かめていない(理由と、追った結果。未確認の前提に立つ入力なら、どの前提が未確認か)

- 直さなかったものと理由、親に決めてほしいこと

最後に、「再現なしで直すもの」のコミットの SHA と、流した既存のテストのコマンドと結果を書いてください。

## 返ってきたあとに確かめる

修正役の報告も、仮説として読む。次を、あなたが自分で行う。

1. **再現のコマンドを、流す前に読む。** LLM が作ったコマンドなので、書き込み先が `<F>/work/` と一時ディレクトリに収まっていること(ツールが既定で作る一時ファイルやソケットの置き場を含む)、ネットワークや本物のデータに触れないことを見る。あわせて、依頼に書いた症状と起きる条件と読み比べ、指摘の症状を、指摘の条件で見ているかを確かめる。修正で足した関数や文言の有無を見るだけの再現、条件を作っていない再現は、症状を見ていないものとして扱う。入力が現実に起こせるかも見る。ツールや外部のサービスの出力を作り物で与えている再現は、その形が実物で観測されたものか(プロジェクトのテストや記録、実物の出力に根拠があるか)を確かめ、根拠が無ければ、修正役が申告していなくても「実行では確かめていない」として扱う
2. 修正後のコードの写しを作る。作業ツリーではなく写しに流すのは、修正の有無のほかの条件(未追跡の依存物、ビルドの生成物)を、修正前の写しと揃えるため

   ```sh
   mkdir <F>/after
   git archive HEAD | tar -x -C <F>/after
   ```

3. 規則ごとの再現のコマンドを `<F>/before` に流し、終了コード 1 で終わるのを見る。次に `<F>/after` に流し、0 で終わるのを見る
4. プロジェクトの既存のテストを流す
5. 再現のコマンドが作業ツリーの依存物を借りているなら、修正が依存物の定義(`package.json`、ロックファイル、`requirements.txt` など)を変えていないことを、`git diff --stat <修正前の SHA> HEAD` で見る。変えていれば、修正前の写しを修正後の依存物で動かしたことになるので、その規則は、3 の結果にかかわらず実行では確かめていない修正として扱う
6. 修正役が、禁じた操作をしていないことを見る。`git status` で作業ツリーに残り物が無い。`git branch --show-current` でブランチが変わっていない。`git merge-base --is-ancestor <修正前の SHA> HEAD` が 0 で終わる(履歴が書き換えられず、コミットが足されただけ)

3 の結果ごとの扱い:

- 修正前が 1、修正後が 0: 再現で確かめた修正(1 で入力が未確認の前提に立つと分かったもの、5 で依存物の定義が変わっていたものを除く)
- どちらかが 2(実行できなかった): 写しに依存物が足りないなど。実行では確かめていない修正として扱う。作業ツリーでだけ通ることは、根拠にしない
- それ以外(修正前が 0、修正後が 1 など): 確かめられていない修正。原因を調べ、修正役に差し戻す(同じ修正役に続きを頼む)か、その規則のコミットを `git revert` で戻して、次の反復に任せる。戻した対象は扱いが決まっていないので、次の反復の表に無くても、再現させる対象として持ち越す(SKILL.md の「終了の判断」)

修正役が返した結果は、SKILL.md の採否の扱いに読み替える。

- 再現して直した: 1 と 3 を通ったものは、必ず採用する。再現のコマンドと、あなたが流した結果を、PR 本文に残す
- 起きなかった: 試した手順を読み、指摘の条件で試していれば採らない。試した手順と結果を、採らなかった理由として残す。条件を作っていなければ、実行では確かめていないものとして、次の扱いにする
- 実行では確かめていない(1 で未確認の前提に立つと分かったもの、5 で依存物の定義が変わっていたものを含む): 修正役が追った結果を読み、採否をあなたが決める。採らないなら、そのコミットを `git revert` で戻す。採るなら、実行では確かめていないことを理由に残す(「終了の判断」で、もう1回回す理由になる。文書への指摘の修正は「再現なしで直すもの」として頼むので、ここには入らない)
- 親に決めてほしいこと: あなたが決められなければ、利用者に尋ねる

影響が高の指摘を「差分の外」として外すか迷うときは、差分の内として依頼に入れ、返ってきた再現のコマンドを PR のベースの写しに流す。1 で終われば、PR の前から起きているので、その規則のコミットを `git revert` で戻し、差分の外として扱う。

```sh
mkdir <F>/base
git merge-base origin/<PR のベースブランチ> HEAD   # 出た SHA を <BASE> として書き写す
git archive <BASE> | tar -x -C <F>/base
```

そのあと、SKILL.md の手順5に戻り、修正の差分のレビューを行う。

## この依頼文で分かっていること

- 実際の PR で1回使った(この手順を入れる前の版の依頼文で、規則2つ)。再現は、指摘の症状(失われた出力の数)を見る作りで、横展開の候補と、断ってはいけない場合の対照も同じコマンドに入れた。親が流し直した結果は、報告と一致した。`diagnosing-bugs` は実際に呼び出された。所要は約7分
- 症状と起きる条件の欄、終了コードの3通り、修正後の写しに流す確認、コミットを規則ごとに分ける決まりは、bench の題材から作った PR 2本で1回ずつ使った(記録は、このスキルのリポジトリの `skill-dev/review-loop/bench/trials/2026-11-16-bench-prs/`。プラグインには含まれない)。2回とも、症状を見る再現、終了コードの使い分け、規則ごとのコミットを守った。所要は約19分と約28分
- そのときに、規則1つに症状の違う箇所が複数入り、修正役が箇所ごとに書き分けた。症状と起きる条件を箇所ごとに書く形は、そのあとに変えたもので、まだ使っていない
- `node_modules` の無い写しでも、修正役が作業ツリーの依存物を借りて、修正前と修正後を同じ依存物で動かした。依存物を借りるのを認める決まりと、依存物の定義の確認は、そのあとに足したもので、まだ使っていない
- 約28分かかった回(e2e のある TypeScript の PR)では、テストの待ちが約17分で、そのうち約14.5分は全体のテスト(単体と e2e)を2回流した分だった。全体を最後に1回だけ流す決まりは、そのあとに足したもので、まだ使っていない
- tmux を使う再現が、ソケットを既定の置き場(`/tmp/tmux-<uid>/`)に作った。一時ファイルやソケットを作業場所の下に向ける決まりは、そのあとに足したもので、まだ使っていない
- 修正役は、反復をまたぐ文脈を持たない。「変えてはいけないもの」に書き漏らした意図は、壊されうる。修正の差分のレビューと、次の反復のレビューが、その受け皿になる
- 再現と修正を同じ役が行うので、再現が修正の形に引きずられうる。そのために、あなたが再現を読み、修正前の写しで症状を流し直す
- 対象は自分の PR だけ。他人のコードを含む PR では、PR の内容が再現のコマンドに影響しうるので、この手順をそのまま使わない
