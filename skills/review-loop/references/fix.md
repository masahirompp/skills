# 修正役: 材料の用意、依頼、返ってきたあとに確かめること

SKILL.md の手順5で、採る指摘を決めたあとに読む。どの指摘を採るか、どこで利用者に見せて止まるかは SKILL.md にある。

修正役は、あなたの文脈を引き継がないサブエージェント。1反復に1つだけ起動する(同じ作業ツリーを並列に編集させない)。規則ごとに、修正前のコードで失敗する再現のコマンドを作り、失敗を見てから直し、コミットする。push はあなたが行う。

## 材料を用意する

俯瞰を行った反復では、俯瞰の材料の一時ディレクトリ `<D>` をそのまま使う。`<D>/src` が修正前のコード(判定を受けた SHA)で、`<D>/work` が作業場所になる。

俯瞰を省いた反復では、作業ツリーの中から、1行ずつ別のコマンドとして実行して作る。

```sh
mktemp -d                                   # 出たパスを <D> として、以下に書き写す
mkdir <D>/src <D>/work
git archive HEAD | tar -x -C <D>/src
```

## 依頼文

`<...>` を埋め、ほかは変えない。書くのは、規則、箇所、俯瞰の役が選んだ直し方、変えてはいけないものだけ。あなたが考えた修正の中身や、起きると見込んだ例は書かない(修正役が、その例に合わせた再現と修正を作るため)。

- 規則は、俯瞰の役の出力の規則を1文のまま写す。俯瞰を省いた反復では、判定の「横展開」にある規則を使う
- 「横展開の候補」には、範囲が差分の内になるものだけを書く。差分の外の候補は「直さない箇所」に書く
- 「再現なしで直すもの」には、再現の対象でない指摘のうち、直すと決めたものを書く。無ければ「無い」
- 「変えてはいけないもの」には、PR が意図して変えた挙動と、以前に採らなかった指摘とその理由を書く。修正役は反復をまたぐ文脈を持たないので、ここに無いことは知らない

```text
ある PR のレビューで出た指摘を、再現してから直す役を頼みます。日本語で答えてください。

## 場所
- 作業ツリー: <worktree の絶対パス>(ここを直して、コミットする)
- 修正前のコードの写し: <D>/src/(読むだけ。書き換えない)
- 作業場所: <D>/work/(再現のコマンドや一時ファイルは、ここに置く)

書き込みは、作業ツリーと `<D>/work/` の下だけにしてください。ネットワークには出ないでください。本物のデータや外部のサービスに対して、消す・書き換える操作を実行しないでください。`claude` コマンドは起動しないでください。git は、作業ツリーの中から1行ずつ実行し、コミットを足すだけにしてください(push、ブランチの切り替え、履歴の書き換え、stash はしない)。

## 何の PR か
<2〜3文>

## 直すもの

### 規則1: <規則を1文で>
- 指摘された箇所: <ファイルと関数、または行>
- 横展開の候補: <ファイルと関数。確かめたか、読んだだけか> / 無い
- 直し方: 箇所ごとに直す / 方式を変える(<どう変えるか>)

(規則ごとに繰り返す)

### 再現なしで直すもの
- <箇所と、直す内容> / 無い

### 直さない箇所
- <差分の外の箇所など。理由> / 無い

## 変えてはいけないもの
<PR が意図して変えた挙動、以前に採らなかった指摘とその理由> / 無い

## 進め方
`mattpocock-skills:diagnosing-bugs` のスキルを使えるなら、呼び出して、その手順で進めてください。使えなければ、下の決まりだけで進めてください。どちらの場合も、下の決まりをスキルの手順より優先します。

1. 規則ごとに、直す前に、再現のコマンドを1つ作る。`<D>/work/repro-<規則の番号>/` の下に置き、対象のルートを引数に取る形にする(例: `sh <D>/work/repro-1/run.sh <ルート>`)。規則が破れていれば 0 以外、守られていれば 0 で終わる。指摘された症状そのものを見る(「落ちずに動く」では足りない)。何度流しても同じ結果で、数秒で終わる。対象のルートの中には書き込まない(要るなら `<D>/work/` に写してから動かす)
2. 再現の対象は、1つの例ではなく規則。指摘された箇所と、横展開の候補のそれぞれを、同じコマンドの中で1件ずつ確かめ、箇所ごとに結果を出す
3. 直す前に、`<D>/src` に向けて流し、失敗するのを見る。失敗しなかった箇所は「起きなかった」として、直さない。「起きうる」という推論だけでは直さない
4. 再現を作れないとき(文書やプロンプトの書き方、外部のサービスの挙動、狙って起こせないタイミング、作れない環境)は、利用者に尋ねず、代わりの実験(作り物のスクリプトで文書の主張を確かめる、など)も作らない。コードや文面を追って、成り立つと判断したものだけを直し、「実行では確かめていない」と理由を付けて返す。作るのが手間、は理由にならない
5. 原因が指摘のとおりで、再現がそれを裏づけたら、仮説の列挙と計測(スキルのフェーズ3〜4)は省いてよい
6. 直すのは規則。再現が通るだけの継ぎを当てない。「方式を変える」とある規則は、1か所で守る形に直す。「直さない箇所」と「変えてはいけないもの」には手を付けない
7. 再現のコマンドの判定を、修正に合わせて変えない。コマンドの側が誤っていたと分かって直したら、変えた点と理由を返す
8. プロジェクトにテストの置き場があれば、再現を回帰テストとしてそこへ足す(規則が破れる経路を通せる継ぎ目が無ければ、足さずに、そう返す)。既存のテストを流し、通るのを見る
9. 直したら、作業ツリーに向けて再現のコマンドを流し、成功するのを見る。調べるために足した出力や一時ファイルを、作業ツリーに残さない
10. コミットする。コードコメントには、コードの恒久的な説明として妥当なことだけを書く(レビューで指摘された、といった経緯は書かない)

迷ったこと、あなたでは決められないことは、推し進めずに、直さないまま返してください。

## 返すもの
規則ごとに、次を書いてください。
- 再現のコマンド(そのまま流せる1行)と、修正前(`<D>/src`)と修正後(作業ツリー)の出力
- 箇所ごとの結果: 再現して直した / 起きなかった(試した手順)/ 実行では確かめていない(理由と、追った結果)
- 直した内容(ファイルと要点)、足した回帰テスト(足さなかったなら理由)
- 直さなかったものと理由、親に決めてほしいこと

最後に、足したコミットの SHA と、流した既存のテストのコマンドと結果を書いてください。
```

## 返ってきたあとに確かめる

修正役の報告も、仮説として読む。次を、あなたが自分で実行して確かめる。

1. 規則ごとの再現のコマンドを、`<D>/src` に向けて流し、失敗するのを見る
2. 同じコマンドを、作業ツリーに向けて流し、成功するのを見る
3. プロジェクトの既存のテストを流す
4. `git status` で作業ツリーに残り物が無いこと、`git log <判定を受けた SHA>..HEAD` でコミットが足されただけであることを見る

1 か 2 が報告と食い違う規則は、確かめられていない修正として扱う。原因を調べ、修正役に差し戻す(同じ修正役に続きを頼む)か、その規則のコミットを `git revert` で戻して、次の反復に任せる。

修正役が返した結果は、SKILL.md の採否の扱いに読み替える。

- 再現して直した: 採用。再現のコマンドと、あなたが流した結果を、PR 本文に残す
- 起きなかった: 採らない。試した手順と結果を、採らなかった理由として残す
- 実行では確かめていない: 修正役が追った結果を読み、採否をあなたが決める。採るなら、実行では確かめていないことを理由に残す(「終了の判断」で、もう1回回す理由になる)
- 親に決めてほしいこと: あなたが決められなければ、利用者に尋ねる

影響が高の指摘を「差分の外」として外すか迷うときは、再現のコマンドを PR のベースのコードに向けて流せば、PR の前から起きるかを実行で確かめられる(俯瞰の材料の `<D>/base`)。

そのあと、SKILL.md の手順5に戻り、修正の差分のレビューを行う。

## この依頼文で分かっていること

- 入れる前に、過去の PR で試していない。初めて使ったのは、この手順を入れた PR 自身のレビュー
- 修正役は、反復をまたぐ文脈を持たない。「変えてはいけないもの」に書き漏らした意図は、壊されうる。修正の差分のレビューと、次の反復のレビューが、その受け皿になる
- 再現と修正を同じ役が行うので、再現が修正の形に引きずられうる。そのために、あなたが修正前のコードで失敗を流し直す
