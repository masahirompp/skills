# 指摘の俯瞰: 材料の用意と、俯瞰の役への依頼

SKILL.md の手順4で、毎反復読む。俯瞰の役の出力の扱い(どれを直すか、どこで利用者に見せて止まるか)は SKILL.md にある。

俯瞰の役は、あなたの文脈を引き継がないサブエージェント。レビュー役の出力を突き合わせて確かめ、指摘を規則ごとにまとめ、直し方と PR の方針への判断を返す。あなたの修正の意図や、採否の見込みは渡さない。渡すのは、下の材料と依頼文だけ。

## 材料を用意する

履歴を持たない一時ディレクトリに取り出す。俯瞰の役はこの中だけで動くので、作業ツリーは変わらない。worktree の中から、1行ずつ別のコマンドとして実行する(`git -C` や `$(...)` で1つにまとめると、worktree に隔離されたセッションでは、git の対象を確かめられないとして拒否されることがある)。

```sh
mktemp -d                                   # 出たパスを <D> として、以下に書き写す
mkdir <D>/src <D>/base <D>/work
git merge-base origin/<PR のベースブランチ> HEAD   # 出た SHA を <BASE> として書き写す
git archive HEAD | tar -x -C <D>/src
git archive <BASE> | tar -x -C <D>/base
git diff <BASE> HEAD > <D>/pr.diff
gh pr view <PR 番号> --json body -q .body > <D>/pr-body.md
cp <今回の試行の作業ディレクトリ>/reviews.md <D>/reviews.md
```

リポジトリが大きければ、`archive` と `diff` の末尾に `-- <PR が触れたディレクトリ...>` を付けて絞る。

2反復目以降は、過去の反復も渡す。同じ規則の破れは、反復をまたいで1件ずつ出るので、今回の指摘だけでは繰り返しが見えない。俯瞰の役の出力は、受け取るたびに、その試行の作業ディレクトリに `overview.md` として保存しておく(SKILL.md の手順4)。

```sh
mkdir <D>/history
cp <反復 N の作業ディレクトリ>/overview.md <D>/history/overview-N.md   # 過去の反復ごと
git diff <最初にレビューを受けた SHA> HEAD > <D>/history/fixes.diff
```

## 依頼文

`<...>` を埋め、ほかは変えない。「何の PR か」には、対象が何をするもので、この PR が何を足す・変えるかだけを書く。評価、問題点、あなたの修正の方針は書かない。`history/` を作らなかったときは、その行を消す。「利用者が観点に渡した指示」は、スクリプトを `--instruct` 付きで起動したときだけ、レビュー役の名前(同じスキルを重ねていれば、その全て)と指示の本文を書く。付けていなければ、その節を見出しごと消す。

```text
ある PR に、複数のレビュー役が指摘を出しました。指摘を1件ずつ直し始める前に、指摘を突き合わせて確かめ、全体を見て、どう直すかの方針を決める役を頼みます。日本語で答えてください。

## 材料(このディレクトリの中だけを使う)
<一時ディレクトリの絶対パス>/

- `pr-body.md`: PR の本文(作者が書いた意図、測った結果、限界、以前のレビューで採らなかった指摘とその理由)
- `pr.diff`: PR の差分
- `src/`: PR を当てた後のファイル
- `base/`: PR を当てる前のファイル
- `reviews.md`: レビュー役の出力。役ごとに `===== 観点: <役の名前> =====` で区切ってある。コードを読んで出した仮説で、誰も確かめていない。末尾に、レビュー中に権限の設定で拒否された呼び出しが添えてあれば、その役はそれを実行できていない
- `history/`: 過去の反復で、この役が返した出力(`overview-N.md`)と、そのあとに入れた修正の差分(`fixes.diff`)
- `work/`: あなたが自由に使ってよい作業場所

このディレクトリの外のファイルは読まないでください(元のリポジトリ、GitHub、`gh` コマンド、Web を含む)。書き込みは `work/` と、`mktemp -d` で作った一時ディレクトリだけにしてください。本物のデータや外部のサービスに対して、消す・書き換える操作を実行しないでください。`claude` コマンドは起動しないでください。`src/` と `base/` は書き換えないでください(修正はしません。方針を決めるだけです)。

## 何の PR か
<2〜3文>
詳しくは `pr-body.md` を読んでください。

## 利用者が観点に渡した指示
<レビュー役の名前>: <指示>

これは、利用者がそのレビュー役に渡した指示です。指示で外した範囲をその役が見ていないことは、観点の欠落にしません。指示に反して出た指摘も、捨てずに表に載せます。指示が避けるよう求めた操作のうち、権限の設定で拒否されうるもの(秘密を含むファイルの読み取りなど)は、あなたもしません。その操作なしに確かめられない指摘は、確かめられなかったと書きます。範囲を絞るだけの指示(「テストは見ない」など)は、そのレビュー役に向けたもので、あなたは縛られません。

## 頼みたいこと
0. `reviews.md` の指摘を突き合わせて、1つの表にする
   - 同じ問題への指摘は1件にまとめ、挙げた役を全て、区切りの名前のまま書く。名前が `-2`、`-3` で終わる役は、番号の無い同じ名前のスキルをもう1回流したもの。同じスキルどうしの一致は、別のスキルどうしの一致ほど強い裏づけに数えない
   - 別の指摘として挙がったものは、同じ箇所や同じ規則に関わっていても、畳まずに別の行にする(実装の不具合と、それを見逃したテストの不備は、別の行)。1行にまとめてよいのは、同じ問題を指していて、直す内容も同じものだけ
   - 指摘を黙って捨てない。根拠をコードで読むか、`work/` で動かして確かめる。当たらないと確かめたものは、「外した」として理由を書く。確かめられなかったものは、外さずに、確かめられなかったと書く
   - 役どうしで食い違う指摘(一方に従うと他方が悪化する、事実の認識が違う)は、コードで確かめて、どちらを採るかを裁く
   - `pr-body.md` やコードコメント、`history/` に、以前のレビューで採らなかった指摘とその理由があれば、同じ指摘にはそう書き、今回の指摘がその理由を覆す事情を持つかを書く
   - 役の出力がレビューになっていない(セットアップの案内や利用者への質問で終わっている、対象を取り違えているなど)ときは、その役が欠けたことを、要約の先頭に「観点の欠落」と書いた1行にする
1. 表の指摘を、それぞれが破っている規則(不変条件、安全の前提、利用者への約束)ごとにまとめる。規則に関わらない指摘(命名、重複、テストの書き方など)は「その他」に寄せる。`history/` があれば、過去の反復で同じ規則の指摘が出て、修正が入っているかも見る
2. 規則ごとに横展開する。指摘された箇所のほかに、同じ規則に頼っている箇所、同じ形で破れる箇所を、差分の外も含めて `src/` から探す。見つけた箇所は、動かして確かめたか、読んだだけかを分けて書く
3. 規則ごとに、直し方を選ぶ。指摘された箇所を1つずつ直せば規則を守りきれるか。守りきれないなら、規則を1か所で守る方式は何か
4. 指摘の全体から見て、PR の方針そのものを見直すべき兆候があるかを判断する(PR の結論が根拠から導けない、目的に対してもっと単純な道がある、範囲を狭める・分けるべき、など)

## 段階の決め方
- 分類: defect(挙動の不具合)/ test_gap / naming_or_comment / style / other
- 影響は、直さなかったときに起きることで決める。`src/` の CLAUDE.md などに影響の具体例があれば、それに従う
  - 高: 取り返しがつかない(データの消失、消すべきでないものを消す、セキュリティ)
  - 中: 機能が使えない、誤った表示で利用者が判断を誤る
  - 低: 表示の乱れなど、利用者がすぐ気づいてやり直せる
  - なし: 挙動に関わらない(命名、コメント、書き方)
- 起きやすさ: 普通の使い方 / 特定の操作の組み合わせ / まれな条件(競合やタイミング)
- 範囲は、その問題が PR の変更で起きるようになったかで決める。場所が PR の変えていない行でも、PR の変更が原因で起きるなら「差分の内」。PR の前から同じように起きるなら「差分の外」とし、根拠(`base/` でも同じ操作の順で起きる、など)を書く。ただし、PR の目的に含まれること(PR の本文やコミットが、直す・実現すると述べていること)の直し残しは、PR の前から起きていても「差分の内」。どちらか確かめられなければ「差分の内」とし、確かめられなかったと書く

## 出力の決まり
- 先頭に、突き合わせた指摘の表を置く。`reviews.md` の指摘を全て載せる(外したもの、観点の欠落も)。列は、番号(F1、F2…)、要約、場所(ファイル:行)、挙げた役、分類、影響、起きやすさ、範囲、扱い
  - 扱いは「規則N」「その他」「外した(理由)」「観点の欠落」のどれか。以前に採らなかった指摘なら、そのことと、覆す事情の有無を添える
- 表のあとに、指摘が1件も無かった役の名前を挙げる(無ければ「無い」)。続けて、外した指摘と、裁いた食い違いの根拠を、1件ずつ短く書く
- 規則は5つまで。重い順。規則に入れなかった指摘も、表の行として必ず残す(扱いは「その他」でよい)。分類が defect で影響が中以上の指摘を、規則に関わらないとして、または規則が5つを超えるために規則に入れなかったときも、表から消さない(直す対象は、規則ではなく表の行から決まる)。規則ごとに次を書く
  - 規則(1文)と、当たる指摘(表の番号)
  - 当たる指摘ごとの、症状(規則が破れたときに何が起きるか)と、起きる条件(操作の順や環境。無ければ「無い」)。1件1行
  - 横展開で見つけた箇所(ファイルと関数。確かめたか、読んだだけか)。見つからなければ「無い」
  - 直し方の選択: 「箇所ごとに直す」「方式を変える(どう変えるか)」「この PR では直さず、別の課題にする」のどれかと、理由、失うもの
- 「その他」の指摘は、番号と、直す・直さないを1行ずつ。分類が defect で影響が中以上のものは、症状と起きる条件も添える
- 最後に、PR の方針への判断(このまま進める / 方針を変える / 範囲を変える)と理由、修正の順序
- 指摘が互いに無関係で、箇所ごとに直せば足りるなら、そう書く。無理に規則にまとめたり、方式の変更を提案したりしない
- 表を除いて、全体で2000字〜4000字程度
```

## この依頼文で分かっていること

- 前の版(突き合わせを含まない形)を、過去の PR 2本に3回(入力はレビュー役の出力)、bench の題材から作った PR 2本に3回(入力は、当時あった判定役の判定)流した。横展開で挙げる箇所は当てになる(あとの反復が実際に直した箇所を、1回目の時点で挙げた)。直し方と範囲の選択は、回によって割れる(同じ PR に2回流して、判断が食い違った)。直してみて初めて出る問題は、挙げられない
- 突き合わせを足した形(この版の手順0と表のもとになったもの)を、bench の題材の PR 2本の反復2に1回ずつ流した(記録は、このスキルのリポジトリの `skill-dev/review-loop/bench/trials/2026-11-16-bench-prs/no-judge.md`。プラグインには含まれない)。判定役の判定と比べて、落とした指摘は無く、挙げた役の記録も一致した。一方で、別の指摘として挙がったテストの不備を元の指摘に畳み、消した。手順0の「畳まずに別の行にする」は、そのあとに足した
- 「畳まずに別の行にする」を足した形(この版)を、反復1(`history/` が無く、指摘が最も多い回)を含めて使った。bench の題材の sk-12 の反復1と、この依頼文を足した PR の反復1〜3(記録は `skill-dev/review-loop/bench/trials/2026-11-17-no-judge/README.md`。プラグインには含まれない)。親が `reviews.md` と表を読み比べ、落とした指摘は無かった。別の指摘として挙がったものは分けて載せた(sk-12 では、判定役が1件にまとめていた3組を分けた)。この試しは、全ての役を Opus に固定して行った。本番の既定では俯瞰の役のモデルを指定しない(親と同じモデルで動く)ので、親が別のモデルなら結果は変わりうる
- 影響の段階は、付ける役によって変わる(上の試しでは、判定役と3件違った)。直す対象の境目(SKILL.md の手順5)はこの段階で決まるので、境目の指摘は、あなたも根拠を読む
