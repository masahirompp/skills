# 指摘の俯瞰: 材料の用意と、俯瞰の役への依頼

SKILL.md の手順5で、指摘の俯瞰を行うと決めたときに読む。結果の扱い(どこで利用者に見せて止まるか)は SKILL.md にある。

俯瞰の役は、あなたの文脈を引き継がないサブエージェント。あなたの修正の意図や、採否の見込みは渡さない。渡すのは、下の材料と依頼文だけ。

## 材料を用意する

履歴を持たない一時ディレクトリに取り出す。俯瞰の役はこの中だけで動くので、作業ツリーは変わらない。

```sh
D=$(mktemp -d); mkdir "$D/src" "$D/base" "$D/work"
BASE=$(git -C <worktree> merge-base origin/<PR のベースブランチ> HEAD)
git -C <worktree> archive HEAD | tar -x -C "$D/src"
git -C <worktree> archive "$BASE" | tar -x -C "$D/base"
git -C <worktree> diff "$BASE" HEAD > "$D/pr.diff"
gh pr view <PR 番号> --json body -q .body > "$D/pr-body.md"
cp <今回の試行の作業ディレクトリ>/verdict.md "$D/findings.md"
```

リポジトリが大きければ、`archive` と `diff` の末尾に `-- <PR が触れたディレクトリ...>` を付けて絞る。

2反復目以降は、過去の反復も渡す。同じ規則の破れは、反復をまたいで1件ずつ出るので、今回の判定だけでは繰り返しが見えない。

```sh
mkdir "$D/history"
cp <反復 N の作業ディレクトリ>/verdict.md "$D/history/verdict-N.md"   # 過去の反復ごと
git -C <worktree> diff <最初に判定を受けた SHA> HEAD > "$D/history/fixes.diff"
```

## 依頼文

`<...>` の3か所だけを埋め、ほかは変えない。「何の PR か」には、対象が何をするもので、この PR が何を足す・変えるかだけを書く。評価、問題点、あなたの修正の方針は書かない。`history/` を作らなかったときは、その行を消す。

```text
ある PR にレビューの指摘が出ました。指摘を1件ずつ直し始める前に、指摘の全体を見て、どう直すかの方針を決める役を頼みます。日本語で答えてください。

## 材料(このディレクトリの中だけを使う)
<一時ディレクトリの絶対パス>/

- `pr-body.md`: PR の本文(作者が書いた意図、測った結果、限界)
- `pr.diff`: PR の差分
- `src/`: PR を当てた後のファイル
- `base/`: PR を当てる前のファイル
- `findings.md`: レビューの判定。コードを読んで出した仮説で、誰も確かめていない
- `history/`: 過去の反復の判定(`verdict-N.md`)と、そのあとに入れた修正の差分(`fixes.diff`)
- `work/`: あなたが自由に使ってよい作業場所

このディレクトリの外のファイルは読まないでください(元のリポジトリ、GitHub、`gh` コマンド、Web を含む)。書き込みは `work/` と、`mktemp -d` で作った一時ディレクトリだけにしてください。本物のデータや外部のサービスに対して、消す・書き換える操作を実行しないでください。`claude` コマンドは起動しないでください。`src/` と `base/` は書き換えないでください(修正はしません。方針を決めるだけです)。

## 何の PR か
<2〜3文>
詳しくは `pr-body.md` を読んでください。

## 頼みたいこと
1. `findings.md` の指摘を、それぞれが破っている規則(不変条件、安全の前提、利用者への約束)ごとにまとめる。規則に関わらない指摘(命名、重複、テストの書き方など)は「その他」に寄せる。`history/` があれば、過去の反復で同じ規則の指摘が出て、修正が入っているかも見る
2. 規則ごとに横展開する。指摘された箇所のほかに、同じ規則に頼っている箇所、同じ形で破れる箇所を、差分の外も含めて `src/` から探す。見つけた箇所は、動かして確かめたか、読んだだけかを分けて書く
3. 規則ごとに、直し方を選ぶ。指摘された箇所を1つずつ直せば規則を守りきれるか。守りきれないなら、規則を1か所で守る方式は何か
4. 指摘の全体から見て、PR の方針そのものを見直すべき兆候があるかを判断する(PR の結論が根拠から導けない、目的に対してもっと単純な道がある、範囲を狭める・分けるべき、など)

## 出力の決まり
- 規則は5つまで。重い順。規則ごとに次を書く
  - 規則(1文)と、当たる指摘(`findings.md` の id)
  - 横展開で見つけた箇所(ファイルと関数。確かめたか、読んだだけか)。見つからなければ「無い」
  - 直し方の選択: 「箇所ごとに直す」「方式を変える(どう変えるか)」「この PR では直さず、別の課題にする」のどれかと、理由、失うもの
- 「その他」の指摘は、id と、直す・直さないを1行ずつ
- 最後に、PR の方針への判断(このまま進める / 方針を変える / 範囲を変える)と理由、修正の順序
- 指摘が互いに無関係で、箇所ごとに直せば足りるなら、そう書く。無理に規則にまとめたり、方式の変更を提案したりしない
- 全体で1500字〜3000字程度
```

## この依頼文で分かっていること

過去の PR 2本(レビューを受ける前のコミット)に3回流し、あとの修正の経緯と照合した結果による。

- 横展開で挙げる箇所は当てになる。あとの反復が実際に直した箇所を、1回目の時点で挙げた
- 直し方と範囲の選択は、回によって割れる。同じ PR に2回流して、判断が食い違った。提案として読み、決めるのはあなたと利用者
- 直してみて初めて出る問題は、挙げられない
- `history/` を渡した形と、入力を判定(`verdict.md`)にした形は、試していない(試したのは、レビュー役の出力を1回分だけ渡した形)
