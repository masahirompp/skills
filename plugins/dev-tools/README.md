# dev-tools

どのリポジトリでも使う開発作業のスキル集。
各スキルの概要は、リポジトリの README の[スキル一覧](../../README.md#スキル一覧)にある。
この文書は、issue を片付けるスキル（`issue-triage`、`issue-check`、`next-issues`、`review-loop`）を、どの順で、どのセッションで使うかを定める。

## issue を片付ける流れ

open な issue は、振り分ける、詰める、片付ける、の3つの工程を通る。
着手できる状態に持っていくまで(振り分ける、詰める)を `issue-triage` が、片付けるのを `next-issues` が受け持つ。
3つは別のセッションで回す。
工程ごとに人間の関わり方と回す頻度が違い、1つのセッションに混ぜると、考えて決めるべき問いが、まとめての承認の中で浅く決まってしまうためである。

| 工程 | スキル | 人間の関わり方 | 1回の単位 | 回すとき |
|---|---|---|---|---|
| 振り分ける | `/dev-tools:issue-triage`(引数なし) | 振り分けの表をまとめて承認する | open な issue 全体 | 振り分けていない issue が溜まったとき、着手できる issue が無くなったとき |
| 詰める | `/dev-tools:issue-triage #番号`(中で `issue-check` と grilling を使う) | 問いに1つずつ答えて決める | issue 1件 | 「詰める」に振り分けた issue のうち、価値の高いものから |
| 片付ける | `/dev-tools:next-issues`（中で `issue-check` と `review-loop` を使う） | 計画、マージ、本番リリースの直前に承認する | 本番リリース1回 | 着手できる issue があるとき |

```
新しい issue（人間の起票、next-issues が範囲外で見つけた問題、review-loop で直さなかった指摘）
  │
  ▼
振り分ける（issue-triage）
  ├─ 着手できる → 片付ける
  ├─ 詰める     → 詰める（1件ずつ）→ 振り分け直して「着手できる」→ 片付ける
  ├─ 待つ       → 見直すきっかけが来たら、次の振り分けで付け直す
  └─ やらない   → 閉じる

詰める（issue-triage #番号）
  issue-check → 観測 → grilling → 本文に反映して振り分け直す

片付ける（next-issues）
  issue-check → 実装 → review-loop → マージ → 本番リリース → 本番での確認
  └─ 範囲外で見つけた問題を起票する → 新しい issue
```

工程は一方向に1回ずつ流れるのではなく、振り分けが issue ごとの行き先を決める。
詰めると片付けるは別の issue を扱うので、並行して回せる（例: `next-issues` で1件を片付けている間に、別のセッションで別の issue を詰める）。

### 振り分ける

`/dev-tools:issue-triage` を引数なしで呼ぶと、open な issue を見比べ、解く価値（高、中、低）と準備の度合いで4つに振り分ける。
価値と準備の付け方は [issue-triage の SKILL.md](skills/issue-triage/SKILL.md) が定める。

| 振り分け | 状態のラベル | 次に扱うもの |
|---|---|---|
| 着手できる | `ready-for-agent` | 片付ける（`next-issues`） |
| 着手できる（人間の判断や手作業が要る） | `ready-for-human` | 人間 |
| 詰める | `needs-triage` | 詰める |
| 待つ | `needs-info` | 次の振り分け（見直すきっかけが来たかを確かめる） |
| やらない | `wontfix` | 閉じる |

価値は `priority:high` / `priority:medium` / `priority:low` のラベルで残す。
状態のラベルは mattpocock/skills の triage と同じ役割の名前を使い、`docs/agents/triage-labels.md` があればその対応表に従う。

振り分けは、`next-issues` の前に毎回は回さない。
新しい issue が無い回に振り分けても行き先は変わらず、人間の承認の手間だけがかかる。

### 詰める

`/dev-tools:issue-triage #番号` で、「詰める」に振り分けた issue を1件、着手できる状態にする。
終わりの条件は、人間が決めることが残っておらず、何ができたら終わりかを issue の本文から読み取れること。

1. `issue-check` で、課題が本物か、issue の求める手段が課題を解くかを確かめる。返ってくる確認事項と推奨の答え、まず確かめることが、続く手順の議題になる。
2. 読むだけでは分からない事実（実機での挙動など）を、AI が観測する。
3. grilling で、決めることを人間に問い、決める。grilling は mattpocock/skills のプラグインに入っている。入れていなければ、同じ進め方（前提の決まった問いから順に、推奨の答えを添えて聞く）で対話する。
4. 決めたことを issue の本文に反映し、振り分け直す。本文の案、ラベル、コメントは、まとめて承認してから書き込む。

手順の詳細は [issue-triage の SKILL.md](skills/issue-triage/SKILL.md) が定める。
1回の呼び出しで扱うのは1件にする。
詰める作業は人間の集中が要り、1件ずつ終わりの条件まで持っていくほうが、半端に決まった issue が残らない。

### 片付ける

`next-issues` が、着手できる issue を選び、1回の本番リリースまでを終える。
`next-issues` は振り分けのラベルを人間の決定として扱い、`ready-for-human` と `needs-info` を候補から外し、`needs-triage` には `issue-triage <番号>` を勧める。
価値の順には並べないので、振り分けで次に片付けると決めた issue があれば、番号を引数で渡す（例: `/dev-tools:next-issues 53`）。
`next-issues` は、着手前の判定で詰める必要がある issue のうち優先の高いものと、着手できる候補が無いときの次の一手として、`issue-triage` を勧める。
範囲外で見つけた問題は起票し、次の振り分けに回る。

## issue-check を呼ぶ場所

`issue-check` は1件を深く確かめるスキルで、詰める前（`issue-triage #番号` の中）と、片付ける前（`next-issues` の中）の2か所で呼ぶ。

- 詰める前: 議題を作る。前提の誤った issue に、詰める時間をかけずに済む。
- 片付ける前: 詰めてから実装するまでの間に、コードやほかの issue が変わっていないかを確かめ直す。申し送り（まず確かめること、未検証の前提）は、実装役がそのまま確認の項目に使う。

全体の振り分けでは呼ばない。
全体の振り分けは open な issue を見比べる工程で、1件ずつ深く確かめると、issue の数に比例して時間とトークンがかかる。
振り分けは、行き先と価値が決まる深さで止める。

## issue に残すもの

工程をまたぐ記録は、GitHub の issue と PR に残す。
次のセッションは会話を引き継がないためである。

- 残すもの: 調べた事実（`## 着手前の調査`、`## 振り分け` のコメント）、人間が決めたこと、人間が承認した振り分けと価値のラベル
- 残さないもの: AI の判定の言葉（`issue-check` の「着手可」など）。残すと、次の判定がそれに引きずられる
