# review-loop — 自分の PR のレビューループ

1反復は「レビューする → 対象を選ぶ → 再現してから直す → 確かめて push する」。レビューして対象が1つも無くなるまで回す。

**ループが入れる変更は、修正前に失敗し、修正後に通る再現を持つものだけ。** それ以外の指摘は、直さずに報告する。レビュー役は指摘を出すだけで、真偽を確かめるのは修正役の再現になる。

この文書の「あなた」は、ループを回すセッション。

## 用語

- **対象**: その反復で直そうとする指摘。差分の内で、分類が defect、影響が中以上のもの(手順2)
- **再現**: 対象のルートを引数に取り、指摘の症状を見たら終了コード 1、症状が無ければ 0 で終わるコマンド。入力は、実物で観測した形だけを使う
- **経緯**: PR 本文の末尾の `## レビューループの経緯` の節。反復をまたぐ記録は、ここだけに置く(あなたの文脈は、圧縮や呼び直しで失われる)。PR 本文に、別の見出しの経緯(以前の版のループの記録など)が既にあれば、その節をこの見出しに改めて引き継ぎ、反復の番号も続きから数える
- **判断を仰ぐ**: 直さずに止まり、決めてほしいことと、選べる道、あなたの考えを示す。利用者に尋ねる。利用者と話せない形で動いているなら(ほかのセッションから呼ばれた、など)、未決の判断を経緯に書いてから、質問を最後の出力として返す

## 前提

- 対象は、自分が作成した、オープンな PR
- セッションの作業ディレクトリが、PR のブランチの worktree のトップ(レビュー役はそこで動くので、ほかの場所から呼ぶと別のリポジトリをレビューする)
- 既定のレビュー役は、`code-review high <PR番号>` を2回と、`security-review` を1回。`code-review` は回ごとに見つける不具合が変わるので、2回分を合わせる。レベルは毎回書く(書かないと、利用者が最後に使ったレベルを引き継ぐ)。利用者が別の構成を指示したら、それに従う

## 手順

### 1. レビューする

1. 作業ツリーがクリーンで、HEAD が PR の head と同じことを確かめる(`git status --short` が空、`gh pr view <PR番号> --json headRefOid,state,author`)。経緯を読み、これが何回目の反復かと、以前に採らなかった指摘を把握する
2. レビュー役を、同じターンで全て、Skill ツールで呼ぶ。引数は `high <PR番号>`(`security-review` は引数なし)。過去の指摘や採否は、引数に書かない
3. `security-review` は、手順の本文があなたの文脈に読み込まれる。その手順に、段を省かずに従う(サブタスクの起動を求めていれば、そのとおりに起動する)。従うあいだは、経緯にある以前の採否を使わない(候補を落とす理由にしない)。採否は手順2で決める。その手順が「最後の返答はレポートだけ」と求めていても、レポートを出したら、このループの手順を続ける
4. 完了の通知で届く分も含めて、全ての結果がそろうまで待つ。そろったら、`git status --short` が空で、HEAD が変わっていないことを確かめる。変わっていれば、変更を取り除いて、この手順をやり直す

レビュー役が失敗したら(エラー、対象の取り違え)、1回だけやり直す。同じ原因で2回続けて失敗したら、判断を仰ぐ。

**完了**: 全てのレビュー役の結果が手元にあり、作業ツリーと HEAD がレビューの前と同じ。

### 2. 対象を選ぶ

指摘を、同じ問題どうしでまとめ、1件ずつ次を付ける。

- **範囲**: 差分の内(PR の変更で起きるようになった。PR が直す・実現すると述べたことの直し残しを含む)か、差分の外(PR の前から同じように起きる)か
- **分類**: defect(挙動の不具合)/ test_gap / doc(文書やプロンプトの読み方に依るもの。決まりの穴、曖昧さ、文面どうしの食い違い)/ style。文書が述べる事実が実物と合わない指摘(書いてあるコマンドや例を、そのとおりに流すと失敗する)は、流せば合否が出るので、doc ではなく defect
- **影響**: 高(取り返しがつかない。データの消失、セキュリティ)/ 中(機能が使えない、誤った表示で利用者が判断を誤る)/ 低(すぐ気づいてやり直せる)/ なし。起きたときの結果で決め、起きやすさは入れない
- **目的との関わり**: この指摘のとおりなら、PR が本文で述べた目的が果たせなくなるか。当たるなら、果たせなくなる目的を述べた本文の文を1つ引く。引けなければ、当たらない。分類や、再現できるかとは別に付ける

**対象は、差分の内で、分類が defect、影響が中以上の指摘。** ただし、以前に採らなかった指摘で、今回の指摘に新しい事情が無いものは、対象にしない(経緯の理由をそのまま使う)。対象でない指摘は、直さずに経緯に1行で残す。そのうち、目的に関わるものは、経緯の「目的に関わるが、直していない」に、折りたたまずに残す(直す範囲は広げない。利用者が読み落とさないように、前に出すだけ)。

対象を修正役に渡す前に、次の2つを見る。どちらかに当たれば、**直さずに判断を仰ぐ**(当たる対象だけを止め、関わりのない対象は先へ進めてよい)。

- **対象を直しても、PR が成り立たない。** 対象を直しても PR の目的が果たせない(前提が誤っている)。または、直すには PR の範囲を超える変更が要る。または、経緯と見比べて、同じ決まりの破れが場所を変えて続いている。レビュー役が設計の代案を挙げただけでは、当たらない。今の設計の中で直せる対象は直し、代案は経緯の「未決」に残して、終了時に報告する
- **対象が、観測していない外部の挙動に懸かっている。** ツールや外部のサービスが出すものの形を、誰も実物で見ていない。既にある記録や文書で確かめられるなら、ここであなたが確かめる。確かめた結果、直し方まで決まるなら、結果を修正役に渡す。確かめた形では症状が起きないと分かった対象は、修正役に渡さず、「起きなかった」として経緯に残す。PR の前提が実物と合わないと分かったら、1つ目に当たる。実物を動かさないと確かめられないなら、判断を仰ぐ

**完了**: 全ての指摘に範囲、分類、影響、目的との関わりが付き、対象と、対象でないものに分かれている。上の2つのどちらにも当たらない。対象が無ければ「終了」へ。

### 3. 再現してから直す

修正は、あなたの文脈を引き継がないサブエージェント(修正役)に任せる。1反復に1つ。あなたが直すと、修正の試行錯誤で文脈が尽きる。

修正前の写しを用意する。

```sh
mktemp -d                              # 出たパスを <F> とする
mkdir <F>/before <F>/work
git archive -o <F>/before.tar HEAD
tar -xf <F>/before.tar -C <F>/before
```

修正役への依頼に書くこと。

- 場所: 作業ツリー(直してコミットする)、`<F>/before/`(修正前の写し。読むだけ)、`<F>/work/`(再現を置く)。読むのも書くのも、この3つの中だけ
- 対象ごとに: 破られている決まり(1文)、指摘された箇所、症状、起きる条件。レビュー役が書いた再現の手順や入力は写さない(修正が、その例に閉じる)
- 手順2であなたが実物で確かめたこと(外部の挙動の形)
- 変えてはいけないもの: PR が意図して変えた挙動、以前に採らなかった指摘とその理由
- 進め方: `mattpocock-skills:diagnosing-bugs` を使えるなら、その手順で進める。次の決まりを、スキルの手順より優先する
  1. 直す前に、対象ごとに再現を1つ作り、`<F>/before` に流して終了コード 1 を見る。見られなかった対象は、直さずに返す(「起きなかった」と、試した手順。または「再現を作れなかった」と、足りないもの)
  2. 再現の入力は、実物で観測した形だけを使う。観測していない形を作り物で与えるしかないなら、直さずに、何の観測が要るかを返す。リポジトリのテストが使う偽物(外部のコマンドの代わり)は、対象のコードを動かす足場として使ってよい。偽物が出す形そのものが症状を左右するなら、その形は観測したものに限る
  3. 再現は `<F>/work/` の中で動かす。本物のデータや外部のサービスに、消す・書き換える操作をしない
  4. 直すのは、例ではなく決まり。同じ決まりに頼る箇所を差分の内から探し、同じ再現の中で確かめて、一緒に直す
  5. 直したら、作業ツリーに流して終了コード 0 を見る。テストの置き場があれば、再現を回帰テストとして足す。既存のテストを流す
  6. コミットは対象ごとに分ける。push、ブランチの切り替え、履歴の書き換えはしない
  7. 返る前に、自分が始めた仕事(再現、テスト)が全て終わっているのを見る。バックグラウンドに回した仕事を残して返らない
- 返すもの: 対象ごとに、再現のコマンド(そのまま流せる1行)、修正前と修正後の終了コード、コミットの SHA。直さなかった対象と、その理由

**完了**: 修正役が、全ての対象について、直した(SHA つき)か、直さなかった(理由つき)かを返した。

### 4. 確かめて push する

1. 再現のコマンドを読む。指摘の症状を、指摘の条件で見ているか。入力は、実物で観測した形か。書き込み先は `<F>/work/` に収まっているか
2. 再現を `<F>/before` と作業ツリー(この反復のコミットが全て入った状態)に流し、対象ごとに 1 と 0 を見る。既存のテストを流し、通るのを見る
3. この反復のコミットの差分を読む。対象の修正、その回帰テスト、変えた挙動に合わせた文書の直しのほかに、変更が無いのを見る(対象でない指摘の修正が、再現を持たないまま紛れ込む)
4. 1 と 0 のどちらかが期待と違うコミットと、ほかの変更を含むコミットは、push しない。修正役に続きを頼むか、そのコミットを外す(push の前なので、PR の履歴には残らない)。外した対象は、「再現を作れなかった」として経緯に残す
5. 経緯に、この反復を書く(下の形)。PR 本文は書く直前に読み直し、経緯の節を書き換える。経緯の外は、この反復のコミットで挙動が変わった箇所の説明だけを、実物に合わせて直してよい。PR の目的や範囲を述べた文は変えない(レビュー役は、PR が述べたことを基準に直し残しを判定する。基準を動かすと、指摘が直らないまま消える)。直したら、どの記述をどのコミットに合わせたかを、経緯に残す。判断を仰いで止まった反復を、答えを受けて続けたときは、その反復の「未決」の行を、決まった扱いに書き換える
6. push する。コミットを足したら、手順1に戻る(push の直後は、`gh pr view` の head が古いままのことがある。数秒おいて読み直す)

**完了**: PR の head にあるこの反復のコミットは、どれも、あなたが 1 と 0 を見た再現を持ち、その対象のほかの変更を含まない。経緯に、全ての指摘の扱いが載っている。

## 経緯の形

```markdown
## レビューループの経緯

### 反復 2(レビューした SHA: f5acefd)
- 直した: <指摘の要約>(<コミットの SHA>。再現: <1行>)
- 直さなかった: <対象だった指摘の要約> — <起きなかった / 再現を作れなかった / 以前に採らなかった / 利用者の判断>と、理由
- 未決: <判断を仰いでいること>
- 目的に関わるが、直していない: <要約>(<doc / 差分の外 / test_gap など>。果たせなくなる目的: <本文の引用>)
- 本文を直した: <直した記述の要約>(<コミットの SHA> に合わせた)

<details><summary>対象でない指摘</summary>

- <要約>(<差分の外 / test_gap / doc / style / 影響が低い defect>)

</details>
```

リポジトリが公開なら、直していないセキュリティの指摘は、悪用の手順を書かずに要約だけを載せる。

## 終了

- **レビューして、対象が1つも無ければ終える。** 修正を push した反復では終えない(その修正を、まだ誰もレビューしていない)
- 3回目の反復のあとも対象が残っていれば、残っている指摘と見通しを示して、判断を仰ぐ
- 直したはずの指摘が、次の反復でまた対象になったら(修正が行ったり来たりしている)、そこで止めて判断を仰ぐ。採らないと決めた指摘がまた挙がるのは、これに当たらない(手順2で外す)
- 判断を仰いだ結果、利用者が終えると決めたら終える

終えたら、次を報告する: 先頭に、目的に関わるが直していない指摘(引いた本文の文と一緒に。無ければ、無いと書く)。続けて、反復回数、直した指摘と再現、直さなかった指摘と理由、対象でなかった指摘(差分の外、影響が低いもの、文書への指摘)、判断を仰いだ結果として採らなかった案、最後にレビューした SHA。続けて、issue にするかを尋ねる。尋ねるのは、直していない指摘のうち、影響が中以上のものと、目的に関わるものだけにする(起きなかったものと、採らないと決めたものは除く。当たるものが無ければ、尋ねない)。言われたものだけを作る。影響の低い指摘は、経緯に残っていて、そのコードを次にレビューするときにまた挙がるので、issue の候補にしない。
