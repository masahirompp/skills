# next-issues — 次の本番リリースで出す issue を選んで片付ける

1回の呼び出しで、1回の本番リリースで出す issue を選び、PR にしてマージし、本番にリリースして本番で確かめるところまでを終わらせる。着手できる issue も、前回から残っている PR も無ければ、計画の段階でリリースせずに終える。終わったら新しいセッションで再度呼び出すと、残りの issue から次を選ぶ。

引数で issue 番号が渡されたら、候補の先頭に置く（選定を省かず、他の候補と並べて評価する）。人間がはっきり指示したものなので、振り分けのラベル（手順2）より優先し、ラベルにかかわらず候補にする（`needs-info` や open のままの `wontfix` も、issue-check で判定する）。ただし `ready-for-human`（作業そのものに人間が要る）なら、人間が担う作業を計画に書き、その部分を人間が行うと承認されたときだけ選ぶ。

## 方針

- **1回の本番リリースを単位にする。** 選ぶ量は、本番で異常が出たときに原因を切り分けて切り戻せ、本番での確認を1回で済ませられる分にする。迷ったら減らす（1件でもよい）。前回から残っている PR を加えるときも、この量に含める。マージがそのまま本番リリースになるリポジトリでは、PR 1本のマージが1回の本番リリースになるので、選ぶ PR は1本にする。
- **親（このセッション）は裁定役。** 親は判断する。実装、調査、動作確認のように手を動かす作業や出力の多い作業は、サブエージェントに任せ、結論と根拠だけを受け取る。親のコンテキストは、最後の報告まで判断のために空けておく。
- **人間に聞くことは最小限にし、まとめて聞く。** 途中で出た判断事項は溜めて、次の止まる場所でまとめて聞く。判断待ちの issue や PR は保留にし、何の判断を待っているかをその PR に残して先へ進む（review-loop が尋ねたことも同じ）。ただし、権限の拒否のように環境に起因する失敗は、次の PR でも起きるので、全体を止めて人間に伝える。まとめて聞く問いは素早く答えられるものに限り、選択肢にはそれぞれを選んだあと何が起きるか（次の呼び出しでどう扱われるか）を書く。issue の本文をどう絞るかのように考えて決める問いは、まとめて聞く中に入れず、計画の前に `dev-tools:issue-triage` で1問ずつ詰める（手順2）。まとめての承認の中では、考えて決めるべき問いも浅く決まるためである。計画の承認のあとに出たときは、その issue を保留にし、`/dev-tools:issue-triage <番号>` で詰めることを勧める。次の3か所では、必ず止まって人間の確認を得る。
  - 計画の承認（PR を作り始める前。着手前の調査を issue にコメントすることの承認を含む）
  - マージと、issue への書き込みの承認
  - 本番リリースの直前（マージがそのまま本番リリースになるリポジトリでは、マージの直前）。リリース作業を AI が行うと計画で決めていても、直前に確認を挟む
- **長い処理を流して待つのは親。** 数分以上かかるテスト（E2E など）と、CI やデプロイの待ちは、親が Bash のバックグラウンド実行で流す。出力はファイルに書き出し、結果は終了コードと要点だけを読む。
- **レビューは `dev-tools:review-loop` に任せる。** review-loop は、サブエージェントに任せず、親が PR の worktree で回す。進め方は review-loop に従う。review-loop が人間に尋ねることも、上の方針どおり溜めてまとめて聞く。
- **見つけた問題は、このセッションで片付ける。** 範囲外で見つけた問題と、review-loop が直さなかった指摘は、親が裁定して、直すか、残さないかに決める。起票は最後の手段にする（[見つけた問題の扱い](#見つけた問題の扱い)）。
- **記録は GitHub に残す。** 次の呼び出しは会話を引き継がない。要件、決めたこと、経緯、確認の結果は issue と PR に残す。
- **本番では読むだけ。** 本番での操作は、閲覧とデータを作らない・変えない操作にとどめ、それを超える確認は人間に頼む。本番の画面やログで見た顧客の個人情報、認証情報、内部の構成は、報告にも GitHub にも要約だけを書く（要るときは伏字にする）。認証情報はプロンプトにも書かない。E2E テストのようにデータを作る処理は、本番に向けて流さない。確認を終えたら、ログインしたブラウザのセッションを閉じ、本番で撮った画像を消す。

## 見つけた問題の扱い

実装役が範囲外で見つけた問題と、review-loop が直さなかった指摘（対象でなかった指摘を含む）は、親が1件ずつ裁定する。扱いは「直す」「残さない」「起票する」の3つ。review-loop が終了時に尋ねる issue の問いも、人間に回さず、ここで親が裁定する。人間には、裁定した結果を手順4の報告で見せる。

**起票が1件も無いのが、通常の結果である。** issue は、閉じるまで、振り分け、承認、着手前の判定の手間を人間にかけ続ける。影響の低い指摘は、そのコードを次に触るときのレビューでまた挙がるので、issue にして覚えておく必要がない。

裁定は、次の2つで決める。

- **影響**: review-loop と同じ尺度で付ける。高（取り返しがつかない。データの消失、セキュリティ）、中（機能が使えない、誤った表示で利用者が判断を誤る）、低（すぐ気づいてやり直せる）。
- **確かめた**: 再現したか、起きる経路をコードで示せる。レビュー役や実装役の指摘は、確かめるまでは推測として扱う。

| 問題 | 扱い |
|---|---|
| PR の変更で起きるようになった（テストや文書の不足を含む） | 確かめて、その PR で直す。影響が低くても直す（自分の PR の直し残しを issue にして先送りしない）。確かめて起きなかったものと、好みの問題（style など）は、残さない |
| PR の前からあり、影響が中以上で、確かめた | その PR と同じ領域にあり、足しても「1回の本番リリース」の量に収まるなら、その PR で直す。収まらなければ、起票する |
| PR の前からあり、影響が低い、または確かめられなかった | 残さない |

- **直す**: 直すものは PR ごとに1回にまとめてサブエージェントに任せ、defect は再現してから直させる。直したら、review-loop と動作確認をやり直す。やり直しの review-loop で新しく挙がった影響の低い指摘は、残さない（レビュー役は回ごとに違う指摘を出すので、追い続けると終わらない）。PR の前からある問題を足して直したら、PR 本文の要件に足す。
- **残さない**: issue にも PR にも書き足さない（review-loop の指摘は、すでに PR の経緯に残っている）。報告に、件数と1行ずつの要約だけを出す。
- **起票する**: 案に、確かめた事実（再現か、起きる経路）、影響、このセッションで直せなかった理由を書く。同じ原因の問題は1件にまとめる。open な issue と重なるものは、新しく作らず、その issue へのコメントの案にする。
- **人間の判断に回す**: 直し方を人間が決める必要があるもの（仕様の選択、PR の範囲を超える変更）と、影響が高になりうるのに確かめられなかったものは、起票の案にせず、判断事項として溜める。

## 流れ

工程ごとの責務と完了の条件。進め方と、誰に任せるかは親が決める。

### 1. 前提を確かめる

open な issue と PR を一覧にし、issue ごとに担当者と対応中の PR を把握する。前回このスキルで作った自分の PR（本文に `## マージとその後` の節があるもの）のうち、open のまま残っているものと、マージ済みで本番での確認が済んでいないもの（PR のコメントで分かる）も控える。issue に `## 着手前の調査` で始まるコメント（前回までの判定の材料）があれば控える。リポジトリの前提（基点ブランチ、各種の形式、テストとローカルでの起動、本番リリースまでの流れと各段階の担当、本番での確かめ方、本番のログやエラーの見方）を、実際に動くかを含めて把握する。E2E テストは、有無と、どこで流せるか（ローカル、デプロイした STG など）と流し方を把握するにとどめ、ここでは流さない。流すかは手順2で決める。

完了: 上のそれぞれを一言で言える。

### 2. 選んで計画する

候補は、担当者がいない issue、自分が担当の issue、前回から残っている自分の PR。他人が担当の issue と、他人の PR が対応中の issue は除く。`dev-tools:issue-triage` の振り分けのラベル（役割の名前。実際のラベル名は issue-triage の決まりに従う）は、読むだけで書き換えない（書き換えるのは issue-triage と人間）。準備の度合いは選ぶ条件にしない。詰める必要のある issue も優先の順で選び、選んだあとで詰める。

- 状態のラベルが無い issue（`bug` などだけが付いたものを含む）と `ready-for-agent`: 候補にし、issue-check で判定する
- `needs-triage`: 候補にし、絞った中に入ったら、計画の前に詰める
- それ以外（`needs-info`、`ready-for-human`、open のままの `wontfix`）: 候補にせず、計画に名前と状態だけ出す（`needs-info` はきっかけを待っているので、詰めても進まない）

`needs-triage` のうち `## 振り分け` のコメントが無い（まだ評価していない）issue が2件以上あれば、`/dev-tools:issue-triage` で全体を振り分けることを計画に添える（価値が付いていないと、優先の順に並べられないため）。

ブロッカー、セキュリティ・データ破損・本番障害、明示された優先度、内容が明確なもの、の順に優先し、「1回の本番リリース」の量より少し多めに候補を絞る。明示された優先度には、価値のラベル（`priority:high`、`priority:medium` の順。`docs/agents/triage-labels.md` で既存のラベルに対応させたものを含む）を数える。`priority:low` は、内容が明確なものより後に置く。価値のラベルが無い `needs-triage` は、`priority:low` より後に置く。

絞った候補のうち `needs-triage` でない issue を、`dev-tools:issue-check` で着手前に判定する。課題が本物か、issue の求める手段がそれを解くかを確かめ、前提の誤った issue を PR にしないためである。前回から残っている PR の issue は判定しない。前回の判定は使い回さず、毎回判定する（issue が変わっていなくても、コードやほかの issue が変われば結論も変わる）。`## 着手前の調査` のコメントがあれば、判定の材料にする。issue-check に頼むときは、対象の issue と、読むだけで書き込まないことだけを伝え、判定の観点（1回の本番リリースに収まるか、優先度など）や仮説は足さない。足すと、量や優先の判断が課題の妥当性の判定に混ざり、親の仮説がそのまま判定になりやすい。量と優先は、判定を受けてから親が決める。判定ごとの扱いは次のとおり。

- 着手可: 候補に残す。
- 確認してから着手: 確認事項を計画の承認で一緒に聞く。答えが出るまでその issue は実装しない。確認事項が素早く答えられないもの（範囲や手段を考えて決める必要があるもの）なら、詰める。
- 再定義が必要、やらない候補: 詰める（再定義が必要なものは範囲や手段を決めるため、やらない候補は閉じるかを決めるため）。

**詰める。** 絞った候補のうち `needs-triage` の issue と、上の判定で詰めるとした issue は、計画の前に、親が `dev-tools:issue-triage` を issue 番号を渡す呼び方（1件を詰める）で呼んで詰める。優先の高いものから1件ずつ行い、着手できる候補（着手可と、詰めて着手できるようになったもの）が「1回の本番リリース」の量に達したら、そこで止める。残りは詰めず、計画に名前と状態だけ出す（今回出さない issue まで詰めると、人間の時間を使ううえ、次に選ばれるまでに決めたことが古くなる）。進め方、人間への問い、issue への書き込みとその承認は issue-triage に従う（問いは人間との対話なので、サブエージェントに任せない）。このセッションで issue-check にかけたばかりの issue は、その判定を issue-triage の手順1の判定として使う。詰めて `ready-for-agent` になった issue は候補に残し、issue-check はやり直さない（issue-triage の中で判定したばかりのため）。`ready-for-human` になった issue は、引数で渡された issue と同じ条件で選ぶ。ほかの振り分けになった issue は選ばず、その理由を計画に書く。詰めた結果、issue が新しい issue に書き直されるか分けられたら、元の issue の代わりに、新しい issue を同じ扱いで候補にする。人間が詰めを断るか途中でやめたら、その issue は選ばず、理由を計画に書く。

判定と詰めを終えて、着手可の候補も、詰めて着手できるようになった候補も、素早く答えられる確認事項だけが残る「確認してから着手」の候補も1件も無ければ、無理に選ばない。前回から残っている自分の PR（open のもの、マージ済みで本番での確認が済んでいないもの）があれば、それだけで計画を立てる。それも無ければ、計画の承認で、今回はリリースせずに終えることと、次の一手（`/dev-tools:issue-triage` での全体の振り分けなど）を示し、承認されたら調査のコメントを書いて終える。

判定は助言なので、人間は承認のときに覆せる。そのうえで「1回の本番リリース」の量に収める。同じ領域を触る issue は1本の PR にまとめ、どの PR も基点ブランチから出す。

PR ごとに、先に決めるべき判断、実装を止めて親に戻す条件、テストと動作確認（いつ・どこで・何を）を決める。E2E テストがあれば、どこで（リポジトリで流せる場所）、どの段階で（マージ前、マージ後で本番リリース前など）、どの範囲を流すかを決める。流さないなら、その理由を計画に書く。全体について、前回から残っている PR の扱い（マージ済みのものは基点ブランチに入っているので、次の本番リリースで必ず出る）と、マージから本番での確認までの進め方（各段階を誰が行うか）を決める。

完了: 選んだ理由と見送った理由（着手前の判定を含む）、1回の本番リリースとして扱える理由を添えて計画を見せ、人間が承認した。今回判定した issue に、調査の結果（調べたこと、確認できたこと、確認できなかったこと）と、承認で人間が答えた確認事項を、`## 着手前の調査` で始まるコメントとして書いた（issue-triage がすでに書いた issue には重ねない。詰めを途中でやめた issue には、そこまでに調べたことをここで書く）。判定そのもの（着手可など）は書かない。次の呼び出しは、これを材料に判定し直す。前回の結論が残っていると、次の判定がそれに引きずられるためである。

### 3. PR を作ってレビューする

計画の順に、PR ごとに実装し、draft PR を出し、review-loop を回し、見つけた問題を裁定して直し（[見つけた問題の扱い](#見つけた問題の扱い)）、計画で決めた動作確認を済ませる。PR 本文には、要件と計画で決めたことに加えて `## マージとその後` の節を書く（次の呼び出しが、このスキルで作った PR と見分ける目印になる）。画面を変える PR は、画面を実際に操作して確かめる。確かめたあとで挙動が変わったら、確かめ直す。

完了: 計画のすべての PR が、review-loop を終え、見つけた問題のすべてに扱いが付き、動作確認が通ったか、理由つきで保留になった。

### 4. 報告して判断を受ける

全 PR をまとめて1回で報告する。PR ごとの結果と保留の理由、溜めた判断事項、見つけた問題の扱い（直したもの。計画に無かった修正はそう示す。残さなかったものの件数と要約。起票の案は、あるときだけ）、マージ後に閉じる issue を示す。判断を受けて PR を直したら、レビューと確認をやり直す。

完了: 判断事項がすべて解決し、人間がマージと issue への書き込みを承認した。承認された書き込み（コメントと、あれば起票）を行った。

### 5. マージする

承認された PR を、計画とリポジトリの慣習に沿ってマージし、基点ブランチを pull する。マージの前に PR に手を入れたら（衝突の解消など）、レビューと確認をやり直し、承認のときと中身が変わったら人間に聞き直す。マージがそのまま本番リリースになるリポジトリでは、手順6の「E2E テストが通ったことを確かめる」「リリース前の状態を控える」「人間の確認」を、マージの前に済ませる。

完了: 承認された PR がマージされ、手元の基点ブランチがそれを含んでいる。

### 6. 本番にリリースして確かめる

リリースの前に、計画で決めた E2E テストがすべて通ったことを確かめる。まだ流していないものがあれば、ここで流す。通らなければリリースしない。落ちた原因の PR を直すか、基点ブランチから外す（revert する）かを人間と決め、E2E テストが通ってからリリースする。落ちた変更を基点ブランチに残したまま次回に回さない（次の本番リリースでそのまま出るため）。リリース前の状態（エラー、ログ、見られる指標）を控え、人間の確認を得てから、計画どおりにリリースする。PR ごとの変更が本番で効いていることと、新しい異常が出ていないことを確かめる。異常があれば、切り戻すか、直すか、次回に回すかを人間と決め、本番と基点ブランチと issue の状態をそろえる。

完了: 対象のすべての PR に、本番での確認の結果、または止めた理由と人間と決めた対処がコメントされている。

### 7. 本番を監視する

本番に出た変更とその危険の大きさから、監視するか、何を見るか（ログ、エラー、指標）、何を異常とみなすか、いつ見るかを、ここで決める。リリースしなかったときと、監視するものが無いときは、この手順を飛ばす。

決めた時点ごとに、決めたものを見て、手順6で控えたリリース前の状態と比べる。時点は、リリースの5分後、10分後、30分後を目安にする。時点の間は、親が `sleep` を Bash のバックグラウンド実行で流し、その終了で次の時点に移る。各時点で見る作業は、出力が多ければサブエージェントに任せ、異常の有無と根拠だけを受け取る。AI から見られないログや指標があるときだけ、その部分を人間に頼む。監視の間に本番で動かない経路（日に1回のバッチなど）は確かめず、確かめていないことを PR のコメントに残す。異常があれば、手順6と同じく、切り戻すか、直すか、次回に回すかを人間と決め、本番と基点ブランチと issue の状態をそろえる。

完了: 対象のすべての PR に、監視の結果（確かめていない経路を含む）、または止めた理由と人間と決めた対処がコメントされている。

### 8. 締める

issue の状態をそろえ、対応した issue と PR、起票した issue（あれば）、続きは新しいセッションでこのスキルを呼べば始まることを伝える。

完了: 対象にした issue のそれぞれについて、閉じたか、どこまで進んだかが issue 上で分かる。

## 既知の落とし穴

- サブエージェントは、このスキルを読まない。守らせたい方針（本番では読むだけ、長い処理は自分で流さず親に頼む、など）は、依頼に含める。
- サブエージェントが流した処理の終了通知は、そのサブエージェントにしか届かない。親は失敗にも完了にも気づけない。
- 親が worktree の中にいると、`EnterWorktree` で新しい worktree を作れない。呼び出し時に worktree の中にいたら `ExitWorktree` で抜け、抜けられなければ新しいセッションで呼び直してもらう。
- `EnterWorktree` は、`worktree-<name>` という名前のブランチを、既定の設定では origin の既定ブランチから切る（設定 `worktree.baseRef` が `head` なら、ローカルの HEAD から切る）。基点ブランチやブランチ名の形式が違うリポジトリでは、合わせてから作業する。
- サブエージェントを起動したあとに親が別の worktree に移ると、そのサブエージェントへの SendMessage が届かないことがある。PR は1本ずつ、その worktree の中で仕上げてから次へ移る。
- `gh pr edit --body` は本文全体を上書きする。書く直前に読み直し、ほかの書き手の節（review-loop の経緯など）を残す。
- PR 本文に閉じるキーワード（`Closes #N` など）が残っていると、マージで issue が閉じる。保留にした issue は、本文の要件と閉じるキーワードから外す。
- 同じ worktree で、長いテスト、review-loop、実装の修正、ローカルのアプリでの確認を同時に動かすと、作業ツリーが変わってどの結果も当てにならない。
- PR の上に PR を積むと、引数で比較の起点を取らないレビューに、下の PR の変更が混ざる。
- `gh issue list` と `gh pr list` は、既定で件数が制限される。`--limit` を大きくする。
- ローカルのアプリは、人間が動かしているものとポートを取り合う。起動・停止するのはこのセッションで起動したものだけにし、終えたら止める。
