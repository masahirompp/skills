# issue-triage — open な issue を価値と準備で振り分ける

next-issues のような実装役は、準備のできた issue しか片付けられない。準備のできていない issue を誰も詰めないと、価値が高くても残り続ける。このスキルは、open な issue を見比べて、次に片付けるもの、次に詰めるもの、きっかけを待つもの、やらないものを決める。

引数で issue 番号が渡されたら、それだけを振り分ける。ただし価値は、ほかの open な issue と見比べて付ける。

## 振り分け

| 振り分け | 条件 | ラベル(役割) |
|---|---|---|
| 着手できる | 新しい判断なしに、PR にして終えられる | `ready-for-agent`。人間の判断・手作業での確認・AI が持たない権限が要るなら `ready-for-human` |
| 詰める | 人間が決めること、または取りに行ける観測(実機で見比べる、など)が残っていて、手段や範囲が定まらない | `needs-triage` |
| 待つ | 自分たちでは起こせないきっかけ(事例が出る、ほかの issue の結論が出る)が来るまで、詰める材料が無い | `needs-info` |
| やらない | 価値が低い、困る人がいない、すでに解けている | `wontfix`(閉じる) |

**ラベルは役割の名前で扱う。** 実際のラベル名は、リポジトリに `docs/agents/triage-labels.md`(mattpocock/skills の setup が書く対応表)があればそれに従い、無ければ役割の名前をそのまま使う。1つの issue に付ける役割は1つにし、付け替えるときはほかの役割のラベルを外す。状態と価値の役割以外のラベル(`bug` など)には触れない。

ラベルとして残すのは、人間が承認した振り分けと価値だけである。issue-check の結果のコメント(`## 着手前の調査`)は材料として読み、そこにある事実は根拠に引いてよい。判定の言葉(着手可など)は、ラベルにもコメントにも書かない。

## 価値

価値は、**起きたときの結果と、起きやすさの両方**で、高・中・低の3段階に付ける。結果が重くても、手元の環境で引き金がほぼ無いものは高にしない。点数は付けない。根拠を事実で1〜2行添える(何が起きるか、誰が困るか、どの条件で起きるか、起きた事例があるか)。

**依存で価値が変わる。** ほかの issue の前提や確かめ役になる issue は、その issue の価値まで上げる(例: 直すときの再現に使うテストが壊れている issue)。依存される側が「詰める」や「待つ」でも上げ、「やらない」なら上げない。上げたときは、根拠にそう書く。

**価値はラベルでも残す。** 役割は `priority:high` / `priority:medium` / `priority:low` の3つで、値はラベル、根拠はコメントに置く。付ける価値は1つにし、付け替えるときはほかの2つを外す。やらないものには付けない(閉じるときに外す)。リポジトリにすでに優先度を表すラベル(`P0`〜`P3`、`priority/high` など)があれば、新しく作らず、承認のときにどれを3つの役割に対応させるかを人間に聞く。決まった対応は、人間の承認を得て `docs/agents/triage-labels.md` に表として足すよう提案し、次の振り分けではそれに従う。

## 準備

着手できると言えるのは、次がすべて満たされるときである。

- 何ができたら終わりかが、本文とコメントから読み取れる
- 手段や範囲について、人間が決めていないことが残っていない
- 前提が今のコードやほかの issue・PR と合っている(閉じた PR で方針が変わったのに本文が古いまま、などは「詰める」)

性質の違う項目が1つの issue に混ざっていて振り分けが分かれるときは、項目ごとに振り分け、issue を分ける案を出す。

## 手順

### 1. 集める

open な issue と PR、リポジトリにあるラベルを一覧にする(状態と価値の役割に当たるラベルが、すでにあるかを見る)。issue ごとに、本文とコメント、付いているラベル、対応中の PR を読む。前回の振り分けのコメント(`## 振り分け` で始まる)、`## 着手前の調査` のコメント、mattpocock/skills の triage のメモがあれば、材料として読む。前回の振り分けと価値は使い回さず、今の状態で付け直す。一方、コメントに残る人間の決定(承認で答えたこと)は、その後に事情が変わっていなければ前提として引き継ぐ。「待つ」だった issue は、書いてある見直すきっかけが起きたかを確かめる。他人が担当している issue と、対応中の PR がある issue は、振り分けずに一覧に名前だけ出す。

**完了**: 振り分ける issue と、除いた issue とその理由を一言で言える。

### 2. 下調べする

issue ごとに、価値と準備を付けるのに足りる事実を読んで確かめる。関係するコード、閉じた PR とその理由、手元の状態(残っている一時ファイル、設定の値など)を見る。調べるのは読むことだけにする。原因の特定や再現のように、作らないと分からないことは確かめず、「詰める」や「着手できる」の申し送りとして書く。1件を深く判定するのは issue-check の役目で、ここでは振り分けと価値が決まる深さで止める。以前の調査のコメントがある issue は、その日付のあとに関係するコードやほかの issue・PR が変わったかと、振り分けを変えうる事実だけを確かめ直す。読むだけで本文の見立てや直し方の誤りが分かったら、申し送りに書く。その誤りで手段が成り立たなくなるなら、振り分けも変える。

**完了**: issue ごとに、課題(1行)、価値とその根拠、準備の欠け(あれば)、依存する issue を書ける。

### 3. 見比べて振り分ける

依存をたどって価値を直し、振り分けを決める。振り分けごとに次を添える。

- 着手できる: 価値の順と、先に片付けるべき依存
- 詰める: 人間が決めること(最大3つ。それぞれ推奨の答え)。詰める作業そのものはしない
- 待つ: 見直すきっかけ(何が起きたら、または何が分かったら振り分け直すか)
- やらない: 理由。閉じるかどうか

**完了**: すべての issue に振り分けが1つ付き、上の添えるものがそろっている。

### 4. 承認を得る

振り分けを、価値の高い順の表で人間に見せ、まとめて承認を得る。表には、次に片付ける issue と、次に詰める issue を1つずつ挙げる。行う書き込み(付け替える状態と価値のラベル、作るラベル、既存の優先度ラベルとの対応、コメント、閉じる issue、分けて作る issue)も一緒に見せる。人間は振り分けも価値も覆せる。

詰めることへの答えを人間がその場で出し、決めることが残らなくなった issue は、振り分けを「着手できる」に変える。答えはコメントの「決めたこと」に書く。書き込みは、承認されたものだけ行う。

**完了**: 人間が、振り分けと書き込みを承認した。

### 5. 記録する

承認された issue に、状態と価値のラベルを付け替え、次のコメントを書く。リポジトリに無いラベルは作る。

```markdown
## 振り分け(YYYY-MM-DD)

- 振り分け: 着手できる / 詰める / 待つ / やらない
- 価値: 高・中・低。根拠(事実で1〜2行)
- 依存: #番号(あれば)
- 決めたこと: 承認で人間が答えたこと(あれば)
- 詰めること / 見直すきっかけ / やらない理由(振り分けに応じて)
- 申し送り: 下調べで分かったことのうち、次に手を付ける人が使うもの
```

やらないものは、承認されていれば閉じる。issue を分ける案が承認されていれば、新しい issue を作り、元の issue から参照する。

**完了**: 承認されたすべての issue に、状態と価値のラベル(やらないものは状態だけ)とコメントが付いた。

### 6. 報告する

振り分けの表と、次の一手を返す。次の一手は、着手できるもののうち最も価値が高いもの(next-issues に渡す)と、詰めるもののうち最も価値が高いもの(別のセッションで、人間と詰める)を挙げる。
