# issue-triage — issue を着手できる状態に持っていく

next-issues のような実装役は、準備のできた issue しか片付けられない。準備のできていない issue を誰も詰めないと、価値が高くても残り続ける。このスキルは、issue を着手できる状態に持っていくところまでを受け持つ。

- **引数なし**: open な issue を見比べて振り分け、次に片付けるもの、次に詰めるもの、きっかけを待つもの、やらないものを決める([全体を振り分ける](#全体を振り分ける))。詰める作業はしない。
- **issue 番号を渡す**: その1件を、着手できる状態まで詰める([1件を詰める](#1件を詰める))。同じ決定を共有する issue があれば、人間が選んだものを一緒に詰める([一緒に詰める組](#一緒に詰める組))。番号を複数渡すと、先頭を詰める issue とし、残りを組の候補として扱う。

2つを別の呼び出しにするのは、人間の関わり方が違うためである。全体の振り分けは表をまとめて承認し、詰める作業は問いに1つずつ答えて決める。混ぜると、考えて決めるべき問いが、まとめての承認の中で浅く決まる。

## 振り分け

| 振り分け | 条件 | ラベル(役割) |
|---|---|---|
| 着手できる | 新しい判断なしに、PR にして終えられる | `ready-for-agent`。決めることは無いが、作業そのものに人間が要る(手作業での確認、AI が持たない権限)なら `ready-for-human` |
| 詰める | 人間が決めること、または取りに行ける観測(AI が調べる、人間が実機で操作して見比べる、など)が残っていて、手段や範囲が定まらない | `needs-triage`(mattpocock/skills では「まだ評価していない」issue にも付く。どちらも、人間が関わらないと着手できるにならない) |
| 待つ | 自分たちでは起こせないきっかけ(事例が出る、ほかの issue の結論が出る)が来るまで、詰める材料が無い | `needs-info` |
| やらない | 価値が低い、困る人がいない、すでに解けている | `wontfix`(閉じる) |

**ラベルは役割の名前で扱う。** 実際のラベル名は、リポジトリに `docs/agents/triage-labels.md`(mattpocock/skills の setup が書く対応表)があればそれに従い、無ければ役割の名前をそのまま使う。1つの issue に付ける状態の役割は1つにし、付け替えるときはほかの状態の役割のラベルを外す(価値のラベルは別に1つ付ける)。状態と価値の役割以外のラベル(`bug` など)には触れない。

ラベルとして残すのは、人間が承認した振り分けと価値だけである。誰がいつ付け替えるかは[ラベルの移り変わり](#ラベルの移り変わり)が定める。issue-check の結果のコメント(`## 着手前の調査`)は材料として読み、そこにある事実は根拠に引いてよい。判定の言葉(着手可など)は、ラベルにもコメントにも書かない。

## ラベルの移り変わり

状態のラベルを付け替えるのは、このスキルと人間だけである。next-issues はラベルを読むだけで、書き換えない。mattpocock/skills の triage や人間が付け替えたラベルも、同じ意味として読む。

| 呼び方 | 受ける issue | 付け替えてよい先 |
|---|---|---|
| 全体の振り分け | open な issue すべて(状態のラベルが無いもの、`bug` などだけのもの、open のままの `wontfix` を含む) | 4つのどれか。ただし「着手できる」にするのは、issue の記述と下調べだけで[準備](#準備)の条件を満たすときだけ。`needs-info` は、見直すきっかけが来ていなければ据え置く。きっかけが書かれていない `needs-info`(mattpocock/skills の triage や人間が付けたもの)は、付いたあとに返事や新しい情報が来ていれば振り分け直す |
| 1件を詰める | 渡された issue(状態を問わない)と、手順0で人間が組に選んだ issue | 4つのどれか |

人間の答えが要る issue を「着手できる」に変えるのは、1件を詰める呼び方だけにする。まとめての承認の中では答えが浅く決まりやすく、観測が残っていることもあるためである。人間は、作業を終えた `ready-for-human` を閉じるなど、いつでも付け替えられる。

## 価値

価値は、**起きたときの結果と、起きやすさの両方**で、高・中・低の3段階に付ける。結果が重くても、手元の環境で引き金がほぼ無いものは高にしない。点数は付けない。根拠を事実で1〜2行添える(何が起きるか、誰が困るか、どの条件で起きるか、起きた事例があるか)。

**依存で価値が変わる。** ほかの issue の前提や確かめ役になる issue は、その issue の価値まで上げる(例: 直すときの再現に使うテストが壊れている issue)。依存する側(価値を借りる元の issue)が「やらない」なら上げず、それ以外の振り分けなら上げる。上げたときは、根拠にそう書く。

**価値はラベルでも残す。** 役割は `priority:high` / `priority:medium` / `priority:low` の3つで、値はラベル、根拠はコメントに置く。付ける価値は1つにし、付け替えるときはほかの2つを外す(状態のラベルはそのまま)。やらないものには付けない(閉じるときに外す)。リポジトリにすでに優先度を表すラベル(`P0`〜`P3`、`priority/high` など)があれば、新しく作らず、承認のときにどれを3つの役割に対応させるかを人間に聞く。決まった対応は、人間の承認を得て `docs/agents/triage-labels.md` に表として足すよう提案し、次からはそれに従う。

## 準備

着手できると言えるのは、次がすべて満たされるときである。

- 何ができたら終わりかが、本文とコメントから読み取れる
- 手段や範囲について、人間が決めていないことが残っていない
- 前提が今のコードやほかの issue・PR と合っている(閉じた PR で方針が変わったのに本文が古いまま、などは「詰める」)

性質の違う項目が1つの issue に混ざっていて振り分けが分かれるときは、項目ごとに振り分け、issue を分ける案を出す。

## 記録の形

振り分けを書き込むときは、状態と価値のラベルを付け替え(リポジトリに無いラベルは作る)、次のコメントを書く。書き込みは、人間が承認したものだけ行う。

```markdown
## 振り分け(YYYY-MM-DD)

- 振り分け: 着手できる / 詰める / 待つ / やらない
- 価値: 高・中・低。根拠(事実で1〜2行)
- 依存: `#<番号>`(あれば)
- 一緒に詰める: `#<番号>`、共有する決定(1行。「止めるか読み飛ばすか」のように問いの形で書き、答えは書かない)(あれば。全体の振り分けで承認された組、または1件を詰める呼び方で一緒に詰めた組)
- 決めたこと: 1件を詰める呼び方で、人間が決めたこと(あれば)
- 承認の場での答え: 全体の振り分けの承認で、人間がその場で答えたこと(あれば)。決めたことではなく、詰めるときの推奨の答えとして扱う
- 詰めること / 見直すきっかけ / やらない理由(振り分けに応じて)
- 申し送り: 調べて分かったことのうち、次に手を付ける人が使うもの
```

やらないものは、状態を `wontfix` にして閉じ、価値のラベルを外す(本文は直さない)。issue を分けるときは、新しい issue を作り、元の issue から参照する。

## 一緒に詰める組

別々の issue でも、片方の答えがもう片方の手段や範囲を決めることがある(例: 「入力を読めないときは止めるか読み飛ばすか」を、2つの issue がそれぞれ前提にしている)。別々のセッションで詰めると、同じ問いに2回答えることになり、答えが食い違うこともある。片方を詰めた結果で、もう片方の前提が古くなることもある。こうした issue は、一緒に詰める組にする。

- **組にする基準は、同じ決定を共有することだけにする。** 同じプラグインに属する、同じファイルに触る、という近さでは組にしない。近さで束ねると grilling の問いが混ざり、1件ずつ深く決める意味が失われる。片方がもう片方の前提になっているだけ(依存)なら、先に詰めるほうを決めれば足りるので、組にしない。
- **組に入れるのは「詰める」の issue だけにする。** 「待つ」は詰める材料が無く、きっかけがほかの issue の結論なら依存に当たる。状態のラベルが無い issue と「着手できる」は next-issues の候補で、並行して実装されることがある。他人が担当している issue と、対応中の PR がある issue も入れない。
- **組は3件までにする。** 基準を満たす issue が4件以上あるとき、または共有する決定が各 issue の決めることの大半を占めるときは、組を示さず、1つの issue に書き直して元を閉じる案だけを出す。
- **組を決めるのは人間である。** AI は候補と共有する決定を示し、人間が含めるものを選ぶ。

組は、[全体を振り分ける](#全体を振り分ける)の手順3で候補を見つけ、手順4で承認を得て、手順5で記録しておく。[1件を詰める](#1件を詰める)の手順0で、記録された組を確かめてから使う。

## 全体を振り分ける

### 1. 集める

open な issue と PR、リポジトリにあるラベルを、件数の上限で切れないようにすべて一覧にする(`gh issue list` と `gh label list` は既定で件数が限られるので、`--limit` を大きくする)。状態と価値の役割に当たるラベルが、すでにあるかを見る。issue ごとに、本文とコメント、付いているラベル、対応中の PR を読む。前回の振り分けのコメント(`## 振り分け` で始まる)、`## 着手前の調査` のコメント、mattpocock/skills の triage のメモがあれば、材料として読む。前回の振り分けと価値は前提にせず、手順2で確かめ直す。確かめて変わらなければ据え置き、その issue には書き込まない(同じ中身のコメントを重ねない)。ただし、一緒に詰める組が新しく承認された、または変わった issue は、振り分けと価値が同じでも書き込む。一方、コメントの「決めたこと」は、その後に事情が変わっていなければ前提として引き継ぐ。「承認の場での答え」は、決めたこととして扱わない。「待つ」だった issue は、書いてある見直すきっかけが起きたかを確かめる。他人が担当している issue と、対応中の PR がある issue は、振り分けずに一覧に名前だけ出す。

**完了**: 振り分ける issue と、除いた issue とその理由を一言で言える。

### 2. 下調べする

issue ごとに、価値と準備を付けるのに足りる事実を読んで確かめる。関係するコード、閉じた PR とその理由、手元の状態(残っている一時ファイル、設定の値など)を見る。調べるのは読むことだけにする。原因の特定や再現のように、作らないと分からないことは確かめず、申し送りとして書く。1件を深く判定するのは issue-check の役目で、ここでは振り分けと価値が決まる深さで止める。以前の振り分けや調査のコメントがある issue は、振り分けと価値を変えうる事実(その日付のあとの、関係するコードやほかの issue・PR の変化を含む)に絞って確かめ直す。読むだけで本文の見立てや直し方の誤りが分かったら、申し送りに書く。その誤りで手段が成り立たなくなるなら、振り分けも変える。

**完了**: issue ごとに、課題(1行)、価値とその根拠、準備の欠け(あれば)、依存する issue を書ける。

### 3. 見比べて振り分ける

依存をたどって価値を直し、振り分けを決める。振り分けごとに次を添える。

- 着手できる: 価値の順と、先に片付けるべき依存
- 詰める: 人間が決めること(最大3つ。それぞれ推奨の答え)。ほかの「詰める」の issue と決めることが重なっていれば、[一緒に詰める組](#一緒に詰める組)の候補と、共有する決定(問いの形)
- 待つ: 見直すきっかけ(何が起きたら、または何が分かったら振り分け直すか)
- やらない: 理由。閉じるかどうか

**完了**: すべての issue に振り分けが1つ付き、上の添えるものがそろっている。

### 4. 承認を得る

振り分けを、価値の高い順の表で人間に見せ、まとめて承認を得る。表には、次に片付ける issue と、次に詰める issue を1つずつ挙げる(次に詰める issue が組に入っていれば、組の issue も並べる)。一緒に詰める組の候補は、表とは別に、組ごとに共有する決定を添えて見せ、組にするかを承認してもらう。行う書き込み(付け替える状態と価値のラベル、作るラベル、既存の優先度ラベルとの対応、コメント、閉じる issue、分けて作る issue)も一緒に見せる。人間は振り分けも価値も覆せる。

詰めることへの答えを人間がその場で出したときは、コメントの「承認の場での答え」に書き、振り分けは「詰める」のままにする([ラベルの移り変わり](#ラベルの移り変わり))。

**完了**: 人間が、振り分けと書き込みを承認した。

### 5. 記録する

承認された issue に、[記録の形](#記録の形)で書き込む。

**完了**: 書き込むと承認されたすべての issue に、状態と価値のラベル(やらないものは状態だけ)とコメントが付いた。承認された組は、組のすべての issue のコメントに「一緒に詰める」として載っている。据え置いた issue(組も変わらないもの)には書き込んでいない。

### 6. 報告する

振り分けの表と、次の一手を返す。次の一手は、`ready-for-agent` のうち最も価値が高いもの(next-issues に渡す)と、詰めるもののうち最も価値が高いもの(別のセッションで `/dev-tools:issue-triage <番号>` で詰める。組に入っていれば、組の issue も一緒に詰まることを添える)を挙げる。`ready-for-human` があれば、人間の作業として別に挙げる。

## 1件を詰める

渡された issue を、[準備](#準備)の条件がすべて満たされるまで詰める。手順0で人間が組を選んだときは、組の issue すべてを同じ手順で一緒に詰める。番号が複数渡されたら、先頭を渡された issue とし、残りを手順0の候補として扱う。

### 0. 一緒に詰める組を決める

渡された issue と[一緒に詰める組](#一緒に詰める組)になる候補を探す。前回の振り分けのコメントに「一緒に詰める」があれば、その組を起点にする。加えて、[組に入れてよい](#一緒に詰める組) open な issue を読み、渡された issue と同じ決定を共有するものを探す。ここで読むのは、決めることが重なるかを判断できる深さまでにする。記録された組も、その後に片方が閉じた、詰めて前提が変わった、などで組でなくなっていないかを確かめる。

候補があれば、issue ごとに共有する決定を問いの形で1行添えて人間に見せ、含めるものを選んでもらう。番号で渡されたのに組に入れられない issue は、黙って外さず、理由を添えて見せ、どれを詰めるかを1問だけ聞く。基準を満たす issue が4件以上ある、または共有する決定が大半を占めるなら、組は示さず、1つの issue に書き直す案だけを出す。採られたら、元の issue の本文とコメントを、新しい決定を足さずに1つの issue にまとめる案を作り、承認を得てから作って元を閉じ(元からは新しい issue を参照する)、その issue を渡された issue として手順1へ進む。候補が無ければ、渡された1件だけで手順1へ進む。

**完了**: 詰める issue(1件、または人間が選んだ組)が決まった。

### 1. 確かめる

issue の本文とコメント(前回の振り分け、`## 着手前の調査`、人間の決定を含む)を読み、`dev-tools:issue-check` で判定する。issue-check への依頼には、対象の issue と、読むだけで書き込まないことだけを書き、振り分けや価値、自分の仮説は足さない(足すと、それがそのまま判定になりやすい)。組のときは、issue ごとに別々に判定し、依頼に次の2つを足す。人間が選んだ組と共有する決定(問いの形。答えは書かない)。判定するのはその issue だけで、共有する決定がその issue に当てはまらない、または要らないと分かれば、そう報告すること。組は人間が選んだものなので、AI の仮説とは違い、伝えてよい。ほかの issue の判定は伝えない。判定の確認事項と推奨の答え、申し送りの「最初に確かめること」が、続く手順の議題になる。

- 決めることも観測も残っていなければ、手順4に進む
- 判定が「やらない候補」なら、やらないへの振り分け直しを人間に提案する。承認されれば、[記録の形](#記録の形)のやらないものの書き込みだけを行って手順5へ進む。却下されたら、判定の確認事項と申し送りを議題にして手順2へ進む
- 「承認の場での答え」があれば、手順3の推奨の答えとして使う
- 組のときは、上の分岐を issue ごとに行うが、手順4へ進むのは組のすべての issue が手順3を終えてからにする(共有する決定がまだ決まっていない間は、本文の案を作れないため)。やらないへの振り分け直しが承認された issue と、共有する決定が当てはまらないと分かった issue は、組から外すことを人間に提案する。外した issue のうち、渡された issue はこの呼び出しで単独で続けて詰め、それ以外はこの呼び出しでは書き込まず、手順5の報告で別の呼び出しを勧める(やらないが承認されたものは、その書き込みだけを行う)

**完了**: 観測すること、人間が決めること、すでに分かっていることを分けて言える。組のときは、そのうち組で共有する決定と、issue ごとに固有の決定を分けて言える。

### 2. 観測する

読むだけでは分からない事実(実機での挙動、イベントの値、再現するか)を観測する。AI が取れる観測は AI が取り、実機での操作のように人間が要るものは、操作の手順と見るものを示して人間に頼む。観測のための一時的な変更は、作業用の worktree か一時ディレクトリで行い、コミットしない。観測は結果だけを持ち帰り、決めることに効く形で人間に示す。

**完了**: 手順1で挙げた観測が、結果か、観測できなかった理由とともにそろった。

### 3. 決める

`grilling` スキルがあれば呼び、無ければ同じ進め方で、決めることを人間に問う。進め方は、前提の決まった問いから順に、推奨の答えを添えて聞き、答えで変わった次の問いを続ける。手順1の確認事項を最初の問いにする。事実は AI が調べ、決定は人間に委ねる。組のときは、共有する決定を先に1回だけ問い、その答えを前提にして、issue ごとに固有の問いへ進む。

**完了**: 決めることが残っておらず、何ができたら終わりか、範囲外は何かについて、人間が「理解がそろった」と認めた(組のときは issue ごとに)。

### 4. 反映して振り分け直す

決めたことを issue の本文に反映する案を作る(課題、要件、何ができたら終わりか、範囲外、決めたこと)。追記やコメントが重なっていて、本文を直すより書き直したほうが読みやすいときは、新しい issue に書き直して元を閉じる案にする。

[準備](#準備)の条件で振り分け直し、価値も付け直す。価値が付いていれば、それを起点に、詰めて範囲や前提が変わった分だけ直す。付いていなければ、ほかの open な issue に付いた価値のラベルと見比べて付け、issue やコメントに書かれた依存があれば[価値](#価値)の決まりで上げる。

本文の案、振り分けと価値、`## 着手前の調査` のコメント(next-issues と同じ形で、issue-check と観測で調べたこと、確認できたこと、確認できなかったこと、人間が答えたことを書く。判定の言葉は書かない)、[記録の形](#記録の形)のコメントを人間に見せ、まとめて承認を得てから書き込む。組のときは、本文の案、振り分けと価値、コメントを issue ごとに作り、共有した決定はそれぞれの本文に書く(片方だけを読んで着手する人がいるため)。コメントの「一緒に詰める」には、一緒に詰めた issue を書く。承認は組でまとめて得る。

**完了**: 承認された本文、ラベル、コメントが issue に入った。

### 5. 報告する

振り分け直した結果と、次の一手を返す(組のときは issue ごとに。組から外して詰めなかった issue があれば、`/dev-tools:issue-triage <番号>` で別に詰めることを勧める)。`ready-for-agent` になったなら `/dev-tools:next-issues <番号>` に渡せることを、`ready-for-human` なら人間の作業として何が要るかを、ほかの振り分けになったならその理由を書く。
