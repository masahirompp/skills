# 着手前の課題判定

依頼を額面どおりに受け取って作業を始めると、間違った問いに対するもっともらしい成果物ができる。このスキルは、着手前に「解く課題は本物か」「提案された手段はその課題を解くか」を、依頼の重さに見合った深さで確かめ、着手してよいかの判定を返す。

## このスキルの範囲

**見るもの: 課題の妥当性。** 不具合修正、機能追加、企画、施策のどれも同じ枠で見る。

- 不具合: 現状が望む状態からずれている
- 機能追加・企画: 望む状態が新しくなった
- 施策: 指標に差がある

どれも「その差は本物か。提案された手段はその差を埋めるか」を判定する。

**見ないもの: 技術面。** 実装方法、設計の良し悪し、影響範囲、性能、セキュリティは評価しない。コードや仕様を読むのは「何を直すべきか、何を作るべきか」を知るためであり、「どう実装するか」を決めるためではない。M以上の判定には必ず「技術面は未評価」と書く。

**判定で止まる。** 依頼された作業そのもの(実装、資料作成、施策の実行)には入らない。判定を返したら止まり、着手するかどうかはユーザー(他のスキルの手順から呼ばれたときは呼び出し元)が決める。判定は助言であり、関門ではない。未解決の点を承知で進む判断は正当である。

**起動は名指しの指示だけ。** 利用者の依頼、スキルの手順、CLAUDE.md などで issue-check を名指しして使うよう指示されたときだけ使う。依頼を受けたことや、「よく確かめて」のような名指しのない指示だけでは使わない。

小さな依頼を重く扱うと使われなくなる。大きな依頼を軽く扱うと手戻りになる。深さの調整がこのスキルの中心である。

## 0. 対象の特定

判定する依頼を最初に決める。

- 名指しと一緒に渡されたもの(依頼文、issue の番号や URL、資料)があれば、それを対象にする。なければ、会話の中で直前に出た依頼を対象にする。
- issue やチケットは、本文だけでなくコメントまで読む。目的や再現条件がコメントにしか書かれていないことがある。GitHub なら `gh issue view <番号> --comments` で読む。
- 対象が見つからない、または候補が複数あって決められないときは、どれを判定するかだけを1問聞く。推測で選ばない。

## 1. トリアージ(対象を決めたらすぐ、数秒で)

次の3軸で S / M / L を決める。ユーザーは上書きできる。

| 軸 | 軽い | 重い |
|---|---|---|
| 間違えたときのコスト | 30分以内でやり直せる | 数日以上の工数、または他者・顧客・本番に影響 |
| 可逆性 | すぐ戻せる | 公開・送信・データ変更・対外約束など戻しにくい |
| 曖昧さ | 目的と完了条件が依頼から読み取れる | 目的が書かれていない、解決策だけが指定されている |

- **S**: 3軸すべて軽い
- **M**: いずれか1軸が重い、または作業が数時間から数日
- **L**: 2軸以上が重い、複数の関係者がいる、新規の企画・施策

迷ったら重い方にする。調査中に想定より重いと分かったら格上げする。

危険信号が1つでもあれば、Sに見えてもMにする。

- 解決策の形で依頼が来ている(「Xを作って」「Yを直して」)のに、目的が書かれていない
- 「とりあえず」「念のため」「一応」が付いている
- 期限はあるが成功基準がない
- 依頼者と、実際に結果を使う人が別である
- 同じような依頼が過去にやり直しになっている

## 2. 判定の種類

必ず次の4つのどれか1つを返す。

- **着手可**: 課題設定は妥当。そのまま進めてよい。
- **確認してから着手**: 方向は妥当だが、答えによってやることが変わる未確定事項がある。
- **再定義が必要**: 提案された手段が本来の課題を解かない可能性が高い、解く課題が特定できない、または成否を確かめる手段がない。
- **やらない候補**: 結果がどちらでも次の行動が変わらない、または困る人が特定できない。

妥当な依頼には「着手可」とはっきり返す。指摘を無理に作らない。

優先順位や費用対効果は判定しない。それは他の依頼との比較で決まるもので、1件の依頼からは見えない。影響の大きさは事実として報告するが、判定の理由には使わない。issue に付いた価値や優先度(`priority:*` などのラベル、振り分けのコメントにある価値と根拠)も、判定の材料にしない。コメントにある事実は材料にしてよい。

## 3. チェック項目

1. **誰の問題か**: 依頼者と受益者は同じか。この課題が解かれないと、誰がどう困るのか。誰も困らないなら「やらない候補」。
2. **課題は本物か**: 現状と望む状態の差を言葉にする。その差は事実として確認できるか。不具合なら、仕様どおりの挙動ではないか、誰の期待と食い違っているのか。報告された現象は課題の全体か、症状の一部か。
3. **手段は課題を解くか**: 依頼された修正・機能・施策は、その差を埋めるか。原因に効くのか、回避策にとどまるのか。機能要望なら、対象の人は今その課題をどう凌いでいるか、すでにある手段で解けないか。解かないなら「再定義が必要」。
4. **答えを出す価値があるか**: この結果によって次の行動や判断が変わるか。どちらの結果でも行動が変わらないなら「やらない候補」。
5. **仮説**: 現時点で最も確からしい答えは何か。それが間違いなら、どの事実がどうなっているはずか。M以上では4章に従って確かめる。
6. **完了条件とやらないこと**: 何ができたら終わりか。成否を何で確かめるか。範囲に含めないものは何か。施策なら、動かしたい指標と現在の値、判断する時期、やめる基準。
7. **(Lのみ)代替案と副作用**: やらない、小さくやる、別の手段でやる、を比べる。この解決で、今の状態に頼っている別の人が困らないか。

## 4. 下調べ

判定は依頼文の読解だけで出さない。使えるデータ、コード、資料に当たり、仮説を確かめてから判定する。

**読めば分かることは調べる。作らないと分からないことは後続に渡す。**

- 調べる: コードや仕様を読む、ログを見る、BigQueryやGAなどで数字を確認する、過去の資料や経緯を読む
- 後続に渡す: テストコードを書く、再現環境を作る、不具合を再現させる、試作する

調査は読み取りに限る。データ、環境、元資料を変更しない。大量のデータを走査するクエリは、実行前に走査量を確認する。

**深さは規模に連動させる**
- **S**: 3章の項目2・3だけを、依頼文と、関係するコードや資料を少し読んで確かめる。反証探しや数字の確認はしない。
- **M**: 仮説の成否を分ける主要な事実を確認する。
- **L**: 反証を含めて検証する。複数の切り口、期間やセグメントの比較、計測定義の確認まで行う。

**反証を先に探す**
調べる前に「この仮説が間違いなら、どの事実がどうなっているはずか」を決める。仮説を支持する証拠が見つかった時点で止めず、仮説を崩す証拠を探す。崩す証拠が見つかったら、仮説を直してから判定する。

**止めどき**
これ以上調べても判定が変わらないなら止める。読むだけでは確定しないこと(不具合の原因など)は確定させようとせず、「未確定」として申し送りに書く。成否を確かめる手段がそもそも見つからない場合は、「再定義が必要」の材料として扱う。

**根拠を残す**
何を調べ、何が確認でき、何が確認できなかったかを判定に添え、確信度を高・中・低で示す。アクセスできないデータは推測で埋めず、「確認できなかったこと」に書く。

## 5. 深さごとの出力

### S: 3行

```
判定: 着手可(S)
理解: ○○のために△△を行い、□□になれば完了。
根拠: 読んだもの/確信度
```

質問や補足は付けない。着手可以外の判定になりそうなら、Sのまま返さない。Mに格上げし、Mの深さで調べてMの形で返す。

### M: 10行程度

チェック項目1から6を確認する。自分で答えられる項目は答えを書く。

```
判定: (4種のいずれか)(M)/技術面は未評価
解く課題: 現状と望む状態の差を1文で
誰の問題か: 依頼者/受益者
手段の妥当性: 依頼された手段がその差を埋めるか
仮説: 仮説と、調べて分かった成否
影響の大きさ: 対象人数や頻度の概算(報告のみ)
完了条件: 何ができたら終わりか/やらないこと
確認事項: 最大3つ。それぞれ推奨回答と「誰に聞くか」を添える
根拠: 調べたこと/確認できたこと/確認できなかったこと/確信度
申し送り: 未検証の仮説/最初に確かめること/懸念
```

### L: 短いメモ

チェック項目をすべて確認し、次の構成で書く。

- 判定とその理由(技術面は未評価と明記)
- 解く課題(現状、望む状態、その差)
- 誰の問題か、解かないと誰がどう困るか
- 手段の妥当性
- 仮説と、その検証結果(反証を探した結果を含む)
- 影響の大きさ(報告のみ)
- 代替案(やらない案、もっと小さい案を含めて2つか3つ)と副作用
- 完了条件と、やらないこと
- 確認事項(推奨回答と「誰に聞くか」を添える)
- 根拠(調べたこと、確認できたこと、確認できなかったこと、確信度)
- 後続への申し送り

### 後続への申し送りに書くこと

着手する人(または次のターン)がそのまま使える形で書く。

- 未検証の仮説と、未確定の原因
- 最初に確かめること。不具合なら先頭に「まず再現確認」を置く
- 懸念(再現しない可能性、計測の信頼性など)
- 未解決のまま進む場合に置いている前提

## 6. 原則

- **判定で止まる**: 判定を返したあと、作業に進まない。「続けて着手しますか」といった申し出もしない。
- **確認事項は絞る**: 答えによってやることが変わるものだけを挙げる。依頼者が第三者の場合に備え、そのまま転送できる文面で書く。
- **観察と推測を分ける**: 確認済みの事実と、置いた前提を区別して書く。
- **埋めることを目的にしない**: 該当しない項目は「該当なし」と書き、内容を捻り出さない。
