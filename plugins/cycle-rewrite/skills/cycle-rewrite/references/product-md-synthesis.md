# docs/PRODUCT.md の合成と更新

PRODUCT.md はプロダクト全体の最新要件・仕様の集約 = 「プロダクト全体の生きた spec」。機能単位の使い捨ての spec とは異なり、作り直しを跨いで維持する。

設計(Implementation Decisions に当たる内容)は `docs/` 配下の別ファイルに分け、PRODUCT.md を要件に絞ってもよい。

見出しは英語のまま、本文はプロジェクトの言語で書く。

## テンプレート

```markdown
# <プロダクト名>

## Problem Statement

ユーザーが直面している課題を、ユーザー視点で。

## Solution

課題の解決策を、ユーザー視点で。

## User Stories

番号付きの網羅的なリスト。形式: As a <actor>, I want <feature>, so that <benefit>

## Implementation Decisions

作り直しても有効な実装判断のみ(モジュール構成、アーキテクチャ判断、スキーマ、API 契約等)。
ファイルパスや具体的なコードスニペットは書かない — 作り直しで消えるため陳腐化する。
例外: schema / 型 / 状態機械など、散文より正確に判断を表すものは要点のみ引用可。

## Testing Decisions

自然言語のテストシナリオ(受け入れ条件のリスト)。実装の完了条件であり、
テストコードを生成し直すときの正でもある。
外部から観測できる振る舞いだけを書く(実装詳細のテストは書かない)。

## Out of Scope

やらないと決めたことのリスト。**「やらないことリスト」の正はここ。**
理由も添える — 理由がないと、次の仕様詰めで同じ提案が繰り返される。

## Further Notes

その他の補足。
```

## 初回: 合成手順

1. 最初の仕様詰めが終わった直後に行う
2. **追加インタビューはしない** — 会話に既にある内容の合成に徹する。埋まらないセクションは推測で埋めず、空である旨を明記して人間に知らせる
3. 仕様詰めの会話全体から上記テンプレートの各セクションを埋め、`docs/PRODUCT.md` に書く。GLOSSARY.md に確立したドメイン用語を本文で使う
4. 書き上げたら人間に提示し、認識齟齬がないか確認する

## 以降: 更新手順

棚卸しで人間が決めた仕様と、作り直しの仕様詰めで判明した変更を反映する。

1. 全書き換えではなく差分更新 — ただし矛盾が残らないよう関連セクションは通読する
2. 消えた要件は削除してよい。ただし「やらないと決めた」ものは削除ではなく Out of Scope へ移す(理由付き)。設計判断レベルの不採用は ADR 側(削除禁止・ステータス遷移)が受け持つ
