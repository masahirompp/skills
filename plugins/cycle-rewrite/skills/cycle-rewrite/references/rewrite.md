# rewrite の手順(作り直し)

使い捨て層を消し、docs を正にゼロから実装し直す。最初の仕様を詰めるときも同じ手順で、消すものが無いだけ(1〜3を飛ばす)。使い捨て層が無く、PRODUCT.md があり、人間が変えたいことも述べていないなら、この手順でやることは残っていない。新しいセッションへの案内を繰り返さず、そのまま実装する(SKILL.md「実装の規律」)。

人間が頼んだときだけ行う。頼まれたこと自体が削除の承認なので、改めて承認は取らない。作り直す理由や次の目的も聞かない。守る順序は2つだけ: 受信箱を空にしてからタグを打つ、タグを打ってから消す。前者を破ると学びが、後者を破ると復元手段が失われる。

1. **受信箱を空にする**: open が残っていれば棚卸しをする(SKILL.md「棚卸し」)。人間の回答待ちの issue が残る間は消さない。docs に書かれていない挙動がコードに残っていないかは、手順としては確かめない(確かめたい人間が、消す前に docs と実装の突き合わせを頼む。消した後では、docs にも新しい実装にも無い挙動は見つけられない)
2. **タグを打つ**: 作業ツリーが clean で、作業がタグを打つブランチに統合されていることを確かめ、`git tag rewrite-YYYY-MM-DD`(同じ日に2回目なら `-2` を付ける)。リモートがあれば push する。未統合のブランチがあれば、統合するか捨てるかだけ聞く(削除後に統合すると旧コードが作業ツリーに戻る)
3. **消す**: 対象を一覧で示してから削除し、コミットする(例: `chore: reset disposable layer`)。リモートがあれば push する
   - 対象: CLAUDE.md の層の定義にある使い捨て層。その付随成果物(消すコードの運用手順、そのコマンドを前提にしたスキルの記述、実行ログ、使い捨て層のパスを記した Memory)も落とす
   - 「これは残す」「ここだけ作り直す」と言われたら、その範囲に合わせる。残すコードは、そのテストと一緒に残し、CLAUDE.md の層の定義から外して、次の作り直しでも消えないようにする
   - 迷うもの(package.json の依存等)は消さずに残し、扱いを最後に聞く。その確認のために削除を止めない
   - コミットとフックが通ることを確かめる。パッケージ定義やフックが使い捨て層を参照していて壊れたら、最小の stub を置く
4. **仕様を詰める(必要なときだけ)**: 人間が変えたいことを述べているとき、または PRODUCT.md がまだ無いときだけ、grilling を domain-modeling と併用して詰める。今の仕様のまま作り直すなら、この段は飛ばす
   - インプットは docs と人間の要望だけ。閉じた issue と消したコードは読まない
   - 何がどう動けば完成かを、ドメイン語の受け入れシナリオ数件で最初に合意し、PRODUCT.md の Testing Decisions に書く。作り直しは過剰設計に走りがちなので(第二システム症候群)、最新の要件に絞る
   - 結果を PRODUCT.md に反映する([product-md-synthesis.md](product-md-synthesis.md))。方向が変わったら、旧方向の記述を docs・スキルから落とす
5. **新しいセッションで実装する**: 作り直す前のコードや grilling の会話を覚えているセッションで実装すると、docs の欠落を記憶で補えてしまい、docs が正にならない。人間には「新しいセッションで、docs を正に実装を始める」ことだけ伝える。今回の範囲が Testing Decisions の一部なら、その範囲を添える。仕様の中身や進め方は書かない
