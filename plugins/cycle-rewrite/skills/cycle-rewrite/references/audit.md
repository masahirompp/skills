# audit の手順(蒸留監査)

作り直した実装がほぼできた後に、人間が呼び出す任意の点検。作り直す前の実装と現況を突き合わせ、docs に書かれないまま失われた仕様・機能を見つけて issue で回収する。「学びと仕様は docs に蒸留され、コードを捨てても失われない」という前提を、実物どうしの比較で確かめる。

このモードでは docs を編集しない。出口は issue の起票だけで、反映は棚卸しが行う。

## 前提

- 比較対象は直近のタグ: `git tag -l 'rewrite-*' 'cycle-*' --sort=-creatordate | head -1`。タグが無ければ対象外
- 実装がほぼ完了していること。途中で走らせると「まだ作っていない」と「実装漏れ」を区別できない

## 1. 比較の単位は観測可能な挙動

ゼロから書き直すとほぼ全行が差分になるので、コード diff は使わない。外から見える挙動をドメイン語で目録にする: 提供している操作、各操作の入出力と状態変化、扱っているエッジケース(重複・空入力・境界値)。モジュール構成・ライブラリ・アルゴリズムなど内部設計の違いは対象外。

前の実装は本体セッションで読まない(同じセッションで修正が続くと旧コードを流用する)。サブエージェントに `git show <タグ>:<使い捨て層パス>/...` か作業ツリー外の `git worktree` で旧実装(テストを含む)を読ませ、ドメイン語の挙動目録だけを返させる。worktree を作ったら抽出後に削除する。

## 2. 突合と4分類

前にあって今は無い挙動・変わった挙動を列挙し、推測ではなく証跡で分類する。証跡は `git diff <タグ> HEAD -- docs/ CONTEXT.md`、遷移済み ADR、閉じた `spec-change` issue。

| 分類 | 判定条件 | 処理 |
| --- | --- | --- |
| A. 意図した変更・削除 | 証跡あり(遷移した ADR、spec-change issue、Out of Scope 等) | 報告のみ。復活を提案しない |
| B. 意図した先送り | 現 docs に仕様があるが、今回の完了条件の範囲外 | 報告のみ |
| C. 実装漏れ | 現 docs に仕様があり、完了条件の範囲内なのに未実装・挙動が違う | 「今直す / 先送りを確定」を人間に聞く。決まるまで直さない |
| D. 蒸留漏れ | 前に挙動があり、現 docs にもどの証跡にも痕跡が無い | 監査の本命。「復活 / 廃止を確定」の二択を併記した `spec-change` issue を起票する |

全差分を分類と証跡の出典つきで報告する。A・B について「全部戻しますか」とは聞かない(意図的なスコープ削減は健全な蒸留)。差分ゼロもそのまま報告する。
