# cycle-rewrite — サイクル型リライト開発ワークフロー

## 狙い

AI 開発ではコード生成速度が人間の理解速度を上回り、人間の頭の中の理論とコードが乖離していく(Naur "Programming as Theory Building")。この乖離は防げないので、コードをゼロから書き直してリセットする(Brooks「捨てるつもりで作れ」。AI でリライトの限界費用が激減したため再び成立する)。永続資産はコードではなく仕様と学びに置く。

| 層 | 中身 | 扱い |
| --- | --- | --- |
| 永続層 | `docs/PRODUCT.md`、`docs/adr/`、`GLOSSARY.md`、`.claude/skills/`、`CLAUDE.md` / `AGENTS.md` | 厳格に維持し、積み上げる |
| 使い捨て層 | `src/` とテストコード | いつ消してもよい。品質は「動けばOK」 |

コードは雑に、ドキュメントは厳格に。docs が常に最新なら、コードはいつでも捨てられる。そのために、学びは溜めずに、分かった時点で docs に書く。

作り直すかどうかと、いつ作り直すかは人間が決める。回数は数えない。作り直さなければ、docs を最新に保つ習慣が付いた通常の開発としてそのまま続く。

層の実パスは init で確定し、CLAUDE.md の規約ブロック「層の定義」に記録する。作り直しの削除対象はそこを正とする。本スキルの `src/` はその略記。

仕様を詰める対話に使えるスキル(mattpocock-skills の grilling・domain-modeling など)が入っていれば使い、無ければ同じ進め方で対話する。docs のファイル名(用語集の `GLOSSARY.md` など)は、プロジェクトに既にあるものがあればそれに合わせる。

CLAUDE.md に cycle-rewrite 規約が無く、ユーザーが導入を求めてもいないプロジェクトには勝手に適用しない。方式を短く紹介し、導入の意思を確認してから init に進む。

## モード

| ユーザーの状況 | 手順 |
| --- | --- |
| 新規プロジェクトのセットアップ | init: [references/init.md](references/init.md) |
| リセットしたい・作り直したい・最初の仕様を詰めたい | rewrite: [references/rewrite.md](references/rewrite.md) |
| docs を正に実装を始める・続ける | 下記 [実装の規律](#実装の規律)(作り直しの手順は通らない) |
| 実装・動作確認中に学び/バグ/仕様の未決/ハマりが出た | 下記 [学びの反映](#学びの反映) |
| 作業を終えて報告する | 下記 [完了報告](#完了報告) |
| 溜まった issue を整理して docs に反映したい | 下記 [issue の整理](#issue-の整理) |

状態ファイルも、学びを溜める置き場も持たない。学びは docs に直接書き、人間が決めることは完了報告で聞く。issue を作るのは、人間が残すと決めたときだけ。

## 学びの反映

作業中に得た学びを、issue を経由せずに宛先へ直接書く。判断基準は「コードを全部捨てた後も、この知見は真か」。

| 学びの種別 | 宛先 | 誰が決めるか |
| --- | --- | --- |
| 実装・環境のハマり | `.claude/skills/`(ライブラリ・ツール単位で1スキルに集約。既存があれば追記) | 聞かずに書く |
| プロセス: 進め方のルール | `CLAUDE.md` / `AGENTS.md` | 聞かずに書く |
| 仕様: 判明した要件、やらないと決めた機能 | `docs/PRODUCT.md`(やらないことは Out of Scope に理由付きで。受け入れ条件は Testing Decisions) | 人間 |
| 用語: ドメインの言葉の追加・変更・廃止 | `GLOSSARY.md` | 人間 |
| 設計判断: 作り直しても覆らない判断、採用しなかった案とその理由 | `docs/adr/`(新規、または既存 ADR のステータス遷移) | 人間 |
| 捨てるコードに紐づくだけの判断 | 残さない(コミットメッセージで足りる) | — |

- 聞かずに書くものは、原因が分かった時点で書いてコミットする。最初の疑いの段階では書かない(後で誤りと分かると docs を直すことになる)。最後にまとめて書くこともしない(セッションが途中で切れると失われる)
- 人間が決めるものは、その場では docs に書かず、作業も止めない。完了報告で聞く(作業の途中で止めてよい場合は「実装の規律」)
- バグは、まず PRODUCT.md・ADR・GLOSSARY.md にその挙動の仕様があるか照合する。無ければ暗黙の要件の発覚で、正しい挙動そのものが未決。期待動作を決め打ちせず、ドメイン語の選択肢(例: 重複は冪等に無視 / エラーで拒否)を完了報告で示す。作業を進めるために暫定の挙動で直したなら、採った案をコミットメッセージに書く(層2)
- 「既存 docs と矛盾しない」は書かない理由にならない。ライブラリのハマりのような加算的な知見こそ置き場を必要とする
- 採用可否に関わるライブラリの学び(例: 「Fuse.js は5000件超で破綻」)は ADR へ、使い方の罠(例: 「dexie はトランザクション内 await で即コミット」)はスキルへ。前者をスキルにすると、覆った ADR が accepted のまま尊重され続ける
- 覆った ADR は削除せず、frontmatter の `status` を `superseded by ADR-NNNN` か `deprecated` に変える(既存の ADR が本文の `Status:` 行を使っていれば、その書式に合わせる)。削除すると「なぜ捨てたか」が消え、同じ案が再採用される
- 仕様が変わったら、旧方向の記述(GLOSSARY.md の用語、スキル、README 等)も一緒に落とす。残すと docs だけを読む次のセッションが汚染される

## 完了報告

頼まれた作業を終えて人間に応答を返すときに行う。バグの報告を受けて調べただけの短いやり取りでも同じ。

1. **聞かずに書いた学び**を、何をどこへ書いたかで報告する
2. **人間が決めること**(仕様、用語、ADR、暫定で採った挙動)を、1件ずつドメイン語の選択肢で示す。暫定で進めたものは、どの案を採ったかも示す。コードの理解を要求する聞き方はしない
3. それぞれについて、**いま決めるか、issue に残すか**を聞く
   - 決まったもの: docs に反映してコミットする
   - issue に残すと言われたもの: 選択肢と、暫定で採った案を本文に書いて起票する
   - 答えの無いもの: 何もしない。勝手に起票も反映もしない

## issue の整理

人間に頼まれたときだけ行う。対象は、人間が指した issue。指定が無ければ open な issue を見て、docs に反映すべき学びや未決の問いを含むものを選び、一覧で示してから進める。直す作業そのものを頼む issue(バグ修正の依頼など)は対象にしない。

宛先と、誰が決めるかは「学びの反映」の表と同じ。聞かずに書くものは反映して閉じ、人間が決めるものは完了報告と同じ形で聞いて、決まってから反映して閉じる。

- issue に結論らしいことが書いてあっても、仕様は反映の前に人間に確かめる(書いたのが人間か AI かを、本文からは見分けられない)
- 反映はコミットしてから閉じ、反映先を1行コメントで残す
- 1件が複数の宛先を持つことがある(例: 環境のハマりが、新しい要件も含む)。聞かずに済む分は先に反映し、人間が決める分が残る間は open のままにする
- 捨てるコードに紐づくだけの判断は、反映せずに閉じる

## 実装の規律

- **インプットは docs**: 仕様は PRODUCT.md・ADR・GLOSSARY.md を正とする。完了条件は PRODUCT.md の Testing Decisions。docs の書き漏れで詰まったら、それ自体が学び
- **停止条件**: 完了条件を満たすまで自律で進める。途中で人間に止めてよいのは、層2のうち docs に定めた挙動の変更と、層3だけ
- **終わり方**: 完了報告で終える

### AI の自律判断(3層)

層1(内部設計の変更)は自律で進めてコミットメッセージに残し、層2(観測可能な挙動・仕様の変更)は docs に定めがあればドメイン語の二択で聞き、無ければ暫定で進めて完了報告で確かめ、層3(不可逆・外部影響)は常に同期で聞く。init が CLAUDE.md に書き込むルールで、全文は [references/init.md](references/init.md) の規約ブロックにある。

## 作り直す前のコード

作り直す前のコードを作業ツリーに置かない(AI が読んで流用する)。参照は `git show <タグ>:src/...` か作業ツリー外の `git worktree`。
