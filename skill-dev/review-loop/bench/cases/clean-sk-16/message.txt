review-loop: 指摘を仮説として扱い、再現で確かめてから直す

## 背景

判定役もレビュー役もコードを読むだけで、指摘を実行して確かめていない。それでも影響が「高」の指摘は起きやすさに関係なく継続の理由になり、直すたびにもう1回回していた。その結果、反復が伸び、PR が目的の外へ膨らんでいた。

過去の状態コメントの実績:

| PR | 反復 | 入力トークン | 備考 |
|---|---|---|---|
| #14 | 6 | 991万 | mktemp の修正が、65分かけて +234/-55 行になった |
| #13 | 5 | 949万 | |
| #9 | 3 | 460万 | |
| #11 | 3 | 368万 | |

きっかけは https://zenn.dev/karamage/articles/5c3f8370b2b370 の「指摘は仮説、検証が判定」。

## 変更

1. **再現を採用の条件にする**: 分類が defect で、終了の基準に当たる指摘は、親が直す前に再現する(修正前に失敗するテストか、実際の実行)。再現を試みて起きなければ採らない。実行では示せない種類(文書、プロンプト、外部のサービス、狙って起こせないタイミング)は、コードを追って採否を決め、実行では確かめていないと残す
2. **再レビューの条件を絞る**: どの修正も再現で確かめてあり、修正した箇所を通る既存のテストも通るなら、その修正のためのもう1回は回さない(修正が大きく、再現が確かめた範囲を超えて挙動を変えているなら回す)。そういうテストがなければ回す。再現に書いたテストは、置き場があれば回帰テストとして残す。実行で確かめていない修正が1つでもあれば、これまでどおり回す
3. **差分の外を分ける**: PR の前から同じように起きる指摘は、この PR では直さず、継続の理由にもしない。終了時に影響の段階と合わせて利用者に報告する。報告に続けて issue にするかを尋ね、言われたものだけを作る

判定役のプロンプトには「範囲」(差分の内 / 外)と「再現」(修正前に失敗するはずのテストか実行の手順)の欄を足した。判定役は作業ツリーを変えられないので、実行して確かめるのは親の受け持ちのままにしている。

## 確かめていないこと

- この変更で反復や時間が実際に減るかは、まだ測っていない。実際の PR で回して確かめる必要がある
- 判定役が「範囲」を正しく見分けられるかも未確認。確かめられないときは「差分の内」に倒すよう書き、親が PR のベースで確かめて決め直せるようにしてある
- 差分の外にある重大な不具合は、直さずに報告だけになる。#14 の反復3で見つかった「無い ref があると全ブランチが delete になる」がこれに当たるなら、これからは同じ PR では直らない(報告と、issue にするかの確認には載る)
- 観点スキルの構成(`PERSPECTIVES`)は変えていない。不具合を埋め込んだコードで検出率と誤検出を測ってから、別の PR で決める

## テスト

`python3 skill-dev/review-loop/test.py` は全て成功。スクリプトが確かめるのは判定の見出しだけなので、欄の追加で挙動は変わらない。
