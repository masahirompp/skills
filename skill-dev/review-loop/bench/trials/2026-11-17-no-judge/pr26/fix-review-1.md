## 結論
直し残しが3件、修正が持ち込んだ問題が4件あります。いちばん重いのは、ロックに足した `stale_after` を検査していないことです(規則3)。手で編集されて真偽値や負の値になると、実行中のロックを奪います。逆に大きな値になると、`--new-run` を付けても永久に止まります。

既存のテスト(`python3 skill-dev/review-loop/test.py`)は、作業ツリーを一時ディレクトリに写して流し、全て成功しました。下の項目にはそれぞれ、試したか、読んだだけかを書いています。

## 指摘(影響の大きい順)

**1. `stale_after` を型しか見ていない。手で編集されると、実行中のロックを奪うか、永久に止まる(規則3の直し残しで、修正が持ち込んだもの)。動かして確かめた。**
- 場所: `skills/review-loop/scripts/review_loop.py:624`(`isinstance(lock.get("stale_after", 0), int)`)と `:802`(`age < state["lock"].get("stale_after", ...)`)。
- 試したこと: 写しの test.py の末尾に試しを足して流した。`started_at` が1分前の、実行中のロックを置いた。
  - `"stale_after": true` のとき: Python の bool は int なので検査を通る。値は1秒として扱われ、終了コード0でロックを奪った。`attempts` に `stale_lock` が足された。
  - `"stale_after": -1` のとき: 同じくロックを奪った。0でも同じになる(読んだだけ)。
  - `"stale_after": 1000000000` のとき: `started_at` を10時間前にしても「別の試行が実行中」で止まった。`--new-run` を付けても、終了コード2で同じ文言になる。ロックの検査が `new_run` の分岐より前にあるため。SKILL.md の「古いロックは次の起動で自動的に片付く」と食い違い、状態コメントを手で直すほかに抜ける方法がない。
  - `"stale_after": 3300.0`(小数。将来の版や手の編集で起きうる)のとき: 状態コメントが「読めない」扱いになり、終了コード2。ここで利用者が `--new-run` を付けると、生きているロックごと上書きされる。
- 直す案: bool を外し、`0 < v <= 上限`(たとえば `BASH_TIMEOUT_MAX`)の範囲に収めるか、範囲外なら旧版の75分に倒す。

**2. 事前確認のエラーは、原因によらず「モデルの名前の誤りか、使えないモデル」と表示される。一時的な API の失敗でもループが止まる(修正が持ち込んだもの)。読んだだけ。**
- 場所: `review_loop.py:598-602`。
- 何が起きるか: 事前確認が API を呼ぶようになったので、次のような失敗も事前確認で `is_error` になる。
  - 429 のレート制限、529 の過負荷
  - クレジット不足、API キーの失効
  - Bedrock や Vertex の権限不足
- これらも全部「名前の誤りか、使えないモデル」と表示されるので、親が原因を取り違える。
- 挙動も変わる。修正前は、こうした失敗はレビュー役の `child_error` として試行の失敗になり、連続失敗3回まで回し直せた。修正後は終了コード2で止まる。SKILL.md の「失敗したとき」は、事前確認の失敗では「利用者に伝える」としているので、一時的な過負荷でもループが利用者の判断待ちで止まる。
- 試していないこと: 本物の claude が、モデル以外のエラーで `is_error` をどの形で返すか。認証方式ごとに形が違うかもしれない。
- 直す案: 文言を「応答を得られなかった。モデルの誤り、認証、レート制限など」に広げ、`result` の本文を必ず見せる。

**3. 「終了の判断」に、終え方の読み方がまだ2通りある(規則1の直し残し)。読んだだけ。**
- 場所: `skills/review-loop/SKILL.md:169`(「対象を1つも直していない…回さずに終えてよい」)。手順5の「再現なしで直すもの」(:136付近)と、差分のレビューの結果を受けた修正(:146付近の「その結果を受けた修正のレビューは、次の反復に任せる」)とつき合わせた。
- 起きる順:
  - ある反復で、対象が全て「起きなかった」になる。一方で、defect でない指摘や影響が低の指摘を、再現なしで直した。この場合、新しい文言だと誰もレビューしていない修正を残したまま終えてよいと読める。
  - 差分のレビューが defect・中の指摘を出し、修正役が再現して直した。手順5は「次の反復に任せる」と言うが、終了の判断では、再現と既存のテストが通っていれば終えてよいと読める。
- 前者は、修正前の文言でもあいまいだった。ただ、今回の追記で「終えてよい」がはっきり書かれたので、強まった。

**4. 事前確認の費用と所要が増えたのに、文書には「短い応答を1回」とだけあり、記録にも報告にも出ない(修正が持ち込んだもの)。読んだだけ。**
- 場所: `review_loop.py:537-540`、SKILL.md:71。
- 費用: 事前確認は、既定の `opus` で、ツールの定義・CLAUDE.md・スキルの一覧を含むシステムプロンプト全体を毎回送る。これが起動するたびにかかる(入力が数万トークン規模という見込みで、測ってはいない)。この分は状態コメントのトークン数に入らず、終了時の報告(SKILL.md の「レビュー役の分だけ」)にも出ない。
- 時間: 次の失敗は、修正前は init の直後に分かった。今は `result` を待つので、API を1回呼んだあと、最長2分後に分かる。
  - 観点スキルが無い
  - cwd が合わない
- 反復の上限や連続失敗の上限で止まる起動でも、事前確認がロックより前に走るので、毎回この1回分を払う(`:971` が `:978` より前にある)。
- フックへの影響: 事前確認の子が、プロンプトの送信から応答の終わりまで1ターン走るようになった。そのため、利用者の UserPromptSubmit と Stop のフック(通知やセッションの記録など)が、毎回の起動で1回余分に動く。
- 直す案: init の検査を先に済ませ、それが通ってから `result` を待つ。文書に「事前確認の分はトークン数の記録に入らない」と書く。

**5. 「表と役の対応」の機械的な確かめを部分一致で行うと、すり抜ける(修正が持ち込んだもの)。読んだだけ。**
