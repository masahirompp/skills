## PR の方針への判断: 範囲を変える(拒否の扱いを分ける)ことを勧める

- **result 行をつなぐ側は根拠がある。** whatnext #308 の実物の stream で再現し、直ったことを確かめている。判定役だけ「見出しを持つ最後の行」に直せば、このまま進めてよい。
- **拒否の側は、前提が実物で確かめられていない。** 前提は「config の拒否は deny ルールの一部に当たったものだけ」というもの。PR 本文が頼る緩和策(判定役が欠落を拾う)も、判定役に拒否が渡らないので働かない(F6)。安全の向きは security-review の言うとおり問題ない。ただし「許可されていない呼び出しは試行が失敗」という利用者への約束が、黙って崩れうる。
- **反対の見方。** .env の deny ルールを持つ利用者には、今の挙動では毎回失敗するという実害がある。分けるとその解消が遅れる。実物の拒否イベントを1回取れるなら、このまま同じ PR で、規則1 と規則4 を入れて進めるのが妥当です。
- **自分で検討するための問い。** 許可ルールの無い Bash を -p で呼んだとき、イベントに source が付くか。付くなら値は何か。F5 の裁定はこの一点で決まります。

**修正の順序**: 規則1(分類の集約、id の無いものは止める、リスト化。F3・F4・F12・F15 とテスト F10)→ 規則4(判定役の入力に拒否を添える)→ 規則2(判定役は最後の有効な行を使う。F1)→ 規則3(F2・F7)→ F9 の文言 → 余力があれば F14。
