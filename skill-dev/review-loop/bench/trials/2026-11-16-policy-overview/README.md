# 方針のレビューと、指摘の俯瞰の試し(2026-11-16)

review-loop に「設計の誤りを優先して見る段」を足すための試し。2つの形を、過去の PR で比べた。結果をもとに、指摘の俯瞰を `skills/review-loop/SKILL.md` の手順5に入れた。

モデルは Fable 5.2(対照の `code-review high` だけ、bench の既存の結果で Opus 5.5)。どの役も、文脈を引き継がないサブエージェントで動かした。

## 1. 方針のレビュー(差分だけを見て、方針と設計を問う)

`policy-review/prompt.txt` を、題材の説明だけ差し替えて流した。題材は、PR #13・#14・#16 のレビューを受ける前のコミット(bench の `sk-13` `sk-14` `sk-16`)、#14・#16 のマージ時点(`clean-sk-14` `clean-sk-16`)、PR #2。

採点の基準(`policy-review/criteria/`)は、レビュー役とは別の役が、PR の修正コミット、本文の編集履歴、マージ後の経緯から、設計・方針の水準の問題を拾って作った。採点も別の役(`policy-review/score/`。`key.txt` は、順不同に並べたレビューの対応)。対照は、bench の `results/pr/<題材>/code-review/{1,2,3}/result.md`。

| 題材 | 基準 | 方針のレビュー | `code-review high`(3回) |
|---|---|---|---|
| sk-13 | 6件 | ○2 △3 | ○3、○4、○2 |
| sk-14 | 6件 | ○2 △4 | ○2、○1、○3 |
| sk-16 | 6件 | ○3 △0 | ○5、○4、○4 |

- 設計上の問題を挙げる数は、既存のレビューを上回らなかった
- 挙げた指摘の反例は、流し直した範囲で全て再現した。マージ時点の状態からは、issue #15 に無い実在の経路を挙げた(issue #15 に追記した)
- 指摘なしで終えた題材は無い。設計上の問題が無い PR を用意できなかったので、捻り出さないかは確かめられていない(bench の `clean-*` は、行単位の不具合が無い題材で、設計上の問題は残っていた)
- 「実行した反例を2つ以上」の決まりは、文書の題材で、代理の実験(作り物のスクリプト、変異テスト)を生んだ

## 2. 指摘の俯瞰(指摘の一覧を受け取り、直し方を決める)

`overview/prompt.txt` を先に固定して流した。入力の指摘は、bench の `code-review high` の出力(sk-13 は試行1、sk-14 は試行1と試行2。試行2にはヒアドキュメントの指摘が無い)。出力は `overview/plans/`、後の修正コミットとの照合は `overview/score/result.md`。

- 横展開で挙げた箇所(入力に無かったもの)のうち、後の反復が実際に直した箇所: sk-14 の1回目は3/3、2回目は4/6、sk-13 は2/6
- 入力に無かった問題にも届いた。大きな作り直しの提案は無かった
- 後の反復が採った方式を言い当てたのは、18項目中2つ。同じ PR の2回で、直し方と範囲の判断は割れた
- sk-14 では、起きる条件の狭さを確かめたうえで「別の課題にする」寄りの判断で、実際の経緯(同じ PR で直した)と逆だった

## 限界

- 方針のレビューは各題材1回、俯瞰は3回。題材はこのリポジトリの PR だけ
- 基準は、過去の review-loop が見つけて直したものから作っている(既存のレビューに有利)。方針のレビューは指摘5件まで、`code-review high` は10件前後。モデルも違う
- 採点は LLM の判断。俯瞰の採点役は、どれが俯瞰の出力かを知っている
- レビュー役が材料の外を読まないことは、依頼文で頼んだだけ

## 置いてあるもの

| 場所 | 中身 |
|---|---|
| `scoring-rules.txt` | 結果を見る前に固定した、採点の採り方 |
| `policy-review/` | 依頼文、基準、レビューの原文、採点 |
| `overview/` | 依頼文、俯瞰の役の出力、採点 |
| `repro/housekeeping/` | issue #15 に追記した経路の再現。`setup.sh <空のディレクトリ>` で使い捨てのリポジトリを作り、`fb/` を `PATH` の先頭に置いて `FAULT=jq-stacked`(ほかに `git-gitpath`、`git-ignored`)か `HIDE_PID=<pid>` を付けて、`HOUSEKEEPING_PR_JSON=<root>/prs.json` で `scan.sh` を流す。`fb/` の包みは、本物の `git`・`jq` を `/opt/homebrew/bin` に、`lsof` を `/usr/sbin` に決め打ちしている。`heredoc.sh <scripts のディレクトリ>` は、ヒアドキュメントの失敗で保護の判定が素通りになる条件の確認(`sandbox-exec` で一時領域への書き込みを禁じ、カレントディレクトリが書ける場合と書けない場合で流す) |
| `repro/review-loop/sk-13-exp.py` | sk-13 の方針のレビューの反例。材料のディレクトリ(`src/` に当時のファイル)の `work/` に置いて流す形 |

原文の中の手元の絶対パスは、`<材料>` と `<tmp>` に置き換えてある。レビュー役に渡した材料(履歴の無い一時ディレクトリ)と、ここに無い反例のスクリプトは残していない。
