ある PR の「方針のレビュー」を頼みます。日本語で答えてください。

## 材料(このディレクトリの中だけを使う)
@@DIR@@/

- `pr-body.md`: PR の本文(作者が書いた意図、測った結果、限界)
- `pr.diff`: PR の差分(主要なファイルだけ。生成物とデータは除いてある)
- `src/`: PR を当てた後のファイル
- `base/`: PR を当てる前のファイル
- `work/`: あなたが自由に使ってよい作業場所

このディレクトリの外のファイルは読まないでください(元のリポジトリ、GitHub、`gh` コマンド、Web を含む。後の経緯が書いてあり、見ると試しになりません)。書き込みは `work/` と、`mktemp -d` で作った一時ディレクトリだけにしてください。`claude` コマンドは起動しないでください。

## 何の PR か
@@WHAT@@
詳しくは `pr-body.md` を読んでください。

## 頼みたいこと
行単位の不具合探しではありません。この PR の方針と設計が妥当かを見てください。問いは次のとおりです。

1. この PR が足した・変えた仕組みは、それぞれどんな規則(不変条件、安全の前提、利用者への約束)を守ろうとしているか
2. その規則の守り方は、構造として成り立つか。個別の場合を1つずつ塞ぐ方式になっていて、塞ぎきれない種類のものはないか。前提にしている環境(利用者の設定、リポジトリの構成、ツールの挙動)が、文書に書いた前提と合っているか
3. PR の結論(何を既定にし、何を外したか)は、PR 自身が示した根拠から本当に導けるか。根拠が測っているものと、結論が必要とするものは一致しているか
4. PR の目的に対して、この方針は最も筋のよい道か。もっと単純な、または構造的に安全な別の方針はないか

## 出力の決まり
- 指摘は5件まで。重い順。命名、コメント、個別の例外処理、テストの不足のような行単位の指摘は書かない
- 各指摘に、次を書く
  - 何の規則・結論についてか
  - なぜ構造として成り立たないか(または根拠から導けないか)
  - 反例: 実際に実行して確かめたもの。`src/` のコードを `work/` や一時ディレクトリから呼ぶ、一時ディレクトリにリポジトリを作る、などで、規則が破れる具体例を2つ以上動かして見せる(1つだけなら個別の不具合で、設計の問題とは言えないため)。コマンドと出力の要点を書く。数字の根拠についての指摘は、`pr-body.md` と `src/` の文書からの引用でよい
  - 実行で示せなかった場合は、そう明記し、コードのどこからそう読んだかを書く。反例の無い一般論は書かない
  - 代わりの方針(1〜2案)と、それぞれが失うもの
- 妥当だと判断した方針があれば、最後に1〜3行で挙げる(無理に弱点を捻り出さない)
- 全体で1500字〜3000字程度
