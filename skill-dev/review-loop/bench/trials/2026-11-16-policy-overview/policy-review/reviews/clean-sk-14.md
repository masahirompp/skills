# 方針のレビュー: housekeeping「mktemp の失敗で止まり、一時ディレクトリを TMPDIR に従わせる」

結論: 「一時ディレクトリを作れなければ止まる」という中心の方針は妥当です。ただし「判定の入力が読めなければ残す」という規則は、経路を1つずつ塞ぐ方式で、塞いでいない経路が3つ残っています。指摘は4件です。

反例は、一時ディレクトリに使い捨てリポジトリを作り(`work/setup.sh`)、`src/` の scan.sh / apply.sh を `HOUSEKEEPING_PR_JSON` 付きで実行して確かめました。失敗の注入は `work/fb/` の `git`・`jq`・`lsof` の包みで行っています。PR 自身のテスト(`lsof` を `exit 1` にする、`git config` を失敗させる)と同じ水準の模擬で、自然に起きる引き金までは特定できていません。

## 1. 「読めなければ残す」は拒否型の判定5つのうち2つにしか効いていない(重)

- **規則**: 判定の入力が読めないときは残す側に倒す(PR 本文「削除側に倒れていた経路を塞ぐ」、lib.sh 冒頭のコメント)。
- **成り立たない理由**: 削除の根拠(PR が MERGED で先端が head に含まれる、git 上で取り込み済み)は「証拠があるときだけ delete」で、ここは堅い。一方、削除を止める拒否型の判定は「出力が空なら問題なし」と読む作りです。この PR は保護名と使用中プロセスの2つだけを「空は確かめられない」に変えました。スタックした PR、進行中の操作、ignored ファイルの警告は空のまま通ります。`hk_parse_action` は出力の形しか見ないので、形の正しい誤った delete は通します。
- **反例**(平常時は `stack-base` が keep、`wt-bisect` が keep、`wt-env` が「一緒に消える ignored ファイル: .env」付きの delete):
  - `open_pr_based_on` の jq だけ失敗させる(`FAULT=jq-stacked`): `delete branch stack-base PR #1 マージ済み` と `delete remote stack-base` が出る。オープン PR #2 のベースがローカルとリモートの両方で候補になる。
  - `hk_in_progress_op` の `git rev-parse --git-path` だけ失敗させる(`FAULT=git-gitpath`): bisect 中の worktree が `delete worktree wt-bisect PR #3 マージ済み` になり、ブランチも「一緒に消す」になる。
  - `git status --ignored` だけ失敗させる(`FAULT=git-ignored`): `delete worktree wt-env PR #4 マージ済み` となり、`.env` の警告が黙って消える。SKILL.md の「必ず添える」が守れない。
- **代わりの方針**:
  - 拒否型の判定をすべて「該当あり / 該当なし / 確かめられない」の3値にして、1か所で「確かめられない」を keep にする。失うのは、判定関数の書き直しの手間と、一時的な失敗で keep が増えること。
  - 拒否型の判定のコマンドが1つでも非ゼロで終わったら走査全体を止める。単純だが、1つの壊れた worktree で全体が使えなくなる。

## 2. 「自分が lsof に出れば、プロセスを見られる」は推論として成り立たない(中)

- **規則**: lsof で自分自身すら見えなければ「確かめられない」として残す。裏を返すと、自分が見えれば「使用中でない」と断定している。
- **成り立たない理由**: 自分が見えることは、ほかのプロセスが見えることを保証しません。この仕組みが検出できるのは「まったく見えない」場合だけです。
- **反例**:
  - この macOS での実測。lsof に自分の pid は出るが、`ps` との突き合わせでは自ユーザーが 630 件中 620 件見え、root の 190 件を含む他ユーザーの 312 件は 0 件だった。
  - worktree を cwd にした `sleep` を、その pid だけ見えない lsof(`HIDE_PID`、他ユーザーや別の pid 名前空間の模擬)で走査: `delete worktree wt-env …` となり、apply.sh も `done worktree <root>/wt-env` で実際に削除した。プロセスは消えた cwd に残った。
- **重さの留保**: 未コミットの変更は `git worktree remove` が拒否するので、失うのは ignored ファイルと、動作中プロセスの足場です。
- **代わりの方針**:
  - cwd の確認を「分かる範囲の確認」と文書に書き、keep の理由も「確かめた」と読めない文にする。失うものはほぼ無い。
  - 見えないプロセスがあるときは worktree を ask にする。macOS では常に root のプロセスが見えないので、worktree の行がすべて ask になり、実用性を失う。

## 3. 確認が模擬だけで、動機である本物のサンドボックスを測っていない(中)

- **結論**: サンドボックスで安全に止まり、案内どおり `!` で進められる。
- **導けない理由**: PR 本文の「確認」は「`skill-dev/housekeeping/test.sh` 全件成功」の1行だけで、限界の記述もありません。test.sh の lsof は `printf '#!/bin/sh\nexit 1\n'` の偽物で、Seatbelt の中で lsof が実際に何を返すかは測っていません。指摘2のとおり、自分だけ見える返り方なら仕組みは働きません。SKILL.md の「`!` の結果では終了コードが見えない」「ユーザーのシェルの `$TMPDIR` は、エージェントのものと違うことがある」も Claude Code の挙動についての主張で、根拠が示されていません。ヒアドキュメントの禁止は `<<` の grep で確かめており、測っているのは書き方です。必要な性質(入力が空でも delete に倒れない)は指摘1のとおり満たされていません。
- **確かめられた主張**: 「macOS の mktemp はテンプレートなしだと TMPDIR を見ない」は手元で再現した(`TMPDIR=<別の場所> mktemp -d` が `/var/folders/...` を返す)。
- **代わりの方針**: サンドボックスの中で scan.sh と apply.sh を1回ずつ実行した記録(lsof の出力、止まった場所)を PR に残す。自動化できないので、手作業の記録になる。

## 4. サンドボックス対応が3つの縮退動作と文章の手順に分散している(中〜軽)

- **対象**: 目的に対する道筋。
- **理由**: 制限の現れ方ごとに動作が違います。mktemp の失敗は停止、fetch の失敗は警告だけで続行、lsof が見えなければ worktree を全部 keep、書き込みや push の拒否は行ごとの skipped です。その継ぎ目を SKILL.md の文章が埋めています(stderr に `error:` が無いことを目で確かめる、`done` の行を条件から外す、外で走査して中で適用すると skipped になる)。機械で検査できる約束が、エージェントの読解に移っています。
- **反例**: 実行では示していません。SKILL.md 37行・70行・72行の記述と、scan.sh 27〜29行(fetch の失敗で続行)からの読みです。
- **代わりの方針**:
  - scan.sh と apply.sh の先頭に環境の事前検査を1つ置く(一時ディレクトリ、プロセスの可視性、git ディレクトリへの書き込み)。足りなければ、何もせず1種類のメッセージで止まる。失うのは、サンドボックスの中でブランチだけ片付けられる部分的な動作。
  - 走査の出力に「環境が制限されていた」という行を入れ、apply.sh がそれを見て拒否する。TSV の形式が変わる。

## 妥当と判断した方針

- `hk_mktemp_dir` で場所を明示し、作れなければ fetch より前に止まる。空のパスで `/prs.json` に書きに行く元の不具合を、原因の位置で断っている。
- 削除の根拠を証拠があるときだけに限る骨格と、apply.sh の削除直前の sha 照合・`--force-with-lease`。PR 一覧が欠けても「PR なし」の経路は git の取り込み確認に落ちるので、消しすぎになりにくい。
- 保護パターンの取得失敗を「保護対象」とみなすことと、first-parent に存在する ref だけを渡すこと。
