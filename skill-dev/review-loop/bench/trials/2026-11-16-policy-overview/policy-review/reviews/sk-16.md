## 方針のレビュー結果(指摘4件、重い順)

結論: 「指摘は仮説、確かめるのは親」という分担は妥当です。ただし3つの規則のうち、再レビューの省略と差分の外の扱いは、確かめているものと規則が必要とするものがずれています。

実験はすべて `<材料>/work/` にあります(`drv.py` と `exp1.py`〜`exp4.py`)。`src/` の写しを偽の claude と gh で動かしました。

### 1. 再レビューの省略条件は、再レビューが見ていたものを測っていない
- **規則**: 「再現が修正前に失敗、修正後に通り、既存のテストも通るなら回さずに終えてよい」。
- **成り立たない理由**: 再現と既存テストが確かめるのは「指摘された症状が消えたか」です。再レビューが見ていたのは「修正が新しい問題を持ち込んでいないか」でした。ただし書きの「修正が大きいなら回す」は直した本人の自己判断で、数行の修正には効きません。
- **反例**(`exp1.py`、`exp1b.py`): どちらも8行ほどの修正で、再現は赤から緑になり、`test.py` は131件すべて成功します。
  - **修正S(stash の比較を足す)**: 再現は `rc=0` から `failed: contamination` に変わります。しかし別の worktree で `git stash` されただけで、修正前は `rc=0` の試行が `failed: contamination` になります。これは `SKILL.md` の「既知の制約」が誤検知として警告しているそのものです。
  - **修正I(無視対象ファイルの増減を比べる)**: 再現は同じく赤から緑です。しかし試行中に `.DS_Store` が置かれただけで `failed: contamination` になります(修正前は `rc=0`)。
- **代案**:
  - (a) 省略せず、最後に判定を受けた SHA からの差分だけを1観点で見る軽い回を足す。1回分の費用がかかり、PR 全体との相互作用は見られません。
  - (b) 省略の条件を、スクリプトが出す差分量など機械的に測れるものにする。柔軟さを失い、(a) より粗くなります。

### 2. 「差分の外」は基準が欠陥ではなく操作の順の選び方で決まり、約束は親の記憶にしかない
- **規則**: 差分の外は直さず、影響が高でも継続の理由にせず、終了時に報告する。
- **成り立たない理由**: 「PR の前から同じように起きるか」は、どの操作の順で試すかで答えが変わります。また報告の約束を支える記録が、スクリプト側にありません。
- **反例**:
  - **作り物のリポジトリ**(`exp4.py`): `--prune` を付けると base でも PR でも `delete: ['feat-a', 'feat-b']` で、差分の外になります。引数なしだと base は `delete: []`、PR は全削除で、差分の内になります。同じ欠陥が両方に分類できます。
  - **この PR 自身**(`exp4.py`): 範囲と再現の欄がない判定は、base でも src でも `rc=0` です。基準どおりなら差分の外ですが、その欄に重みを持たせたのはこの PR です。
  - **記録の不在**(`exp3.py`): 影響が高の defect を、根拠なしの「差分の外」とした判定でも `rc=0` で反復1になります。状態コメントに指摘の語はなく、`verdict.md` は一時ディレクトリにしかありません。
- **代案**:
  - (a) 影響が高の差分の外は、終了時まで持ち越さず、その場で止めて利用者に尋ねる。自動で回り切る性質を失います。
  - (b) スクリプトが範囲の欄を拾い、件数を状態コメントに残す。「見るのは見出しだけ」という単純さを失います。

### 3. 「再現しなければ採らない」は、手順と環境の出来を欠陥の不在と読む
- **規則**: 再現を試みて起きなければ採らず、影響の段階に関係なく継続の理由にもしない。
- **成り立たない理由**: 手順は実行していない判定役が書きます。成否を決めるのは、早く終えたい側の親です。「組み直す」とは書いてありますが、どこまで試すかの下限がありません。
- **反例**(`exp2.py`): 同じ種類の見逃し(子の変更を検出しない)が、手順と利用者の設定で分かれます。
  - **手順の違い**: 子が `git stash` するだけだと `rc=0` で stash もなく、「起きなかった」になります。編集してから stash すると `rc=0` で `stash@{0}` が残り、見逃しが起きています。
  - **設定の違い**: 子が `stray.txt` を書くと、通常は `failed: contamination` です。グローバル gitignore に同じ名前があると `rc=0` で、ファイルは残ります。
- **代案**:
  - (a) 再現できなかった影響が高の指摘は、却下ではなく「未確認」として終了報告に必ず載せる。報告が長くなります。
  - (b) 再現を、worktree の写しで実行できる独立の検証役に任せる。費用が増え、削減効果の一部を失います。

### 4. 根拠は反復数と子のトークンだけで、3つの仕組みを既定にする結論は導けない
- **根拠が測っているもの**: `pr-body.md` の表は、反復数と入力トークンだけです。反復が伸びた原因(誤検出、修正への新しい指摘、差分の外)の内訳がありません。
- **結論が必要とするもの**: #14 の「+234/-55 行」が修正への正しい指摘の積み重ねなら、規則2はそれを見逃す側に働きます。本文も「まだ測っていない」と認めています。
- **測り方の問題**:
  - トークンは `add_tokens` が子の `modelUsage` だけを数えます。再現の作業は親に移るので、同じ表では減って見えます。
  - 試行の記録のキーは `at, iter, perspectives, result, sha, tokens` だけです(`exp3.py`)。再現で採否が変わった件数も、再レビューを省いた事実も残りません。
  - 修正を push して終えると、PR head は `d936b2c`、最後の completed は `090e812` のままです。省略と打ち切りが区別できず、「実際の PR で回して確かめる」ための材料が残りません。
- **代案**:
  - (a) 過去4件の判定を原因別に分類してから、既定を決める。時間がかかります。
  - (b) 3つを一度に入れず、終了報告に理由別の件数と親の費用の欄を先に足す。効果が出るのが遅れます。

### 妥当と判断した方針
- 判定役には実行させず、確かめるのは親とする分担。作業ツリーを変えない制約と整合しています。
- 範囲を確かめられないときは「差分の内」に倒すこと。
- issue は尋ねてから作ること。
- 未計測の点を本文に明記していること。
