## 方針のレビュー結果

指摘は4件。実行はすべて `work/` の写しと `mktemp` の一時リポジトリで行い、子は同梱の偽 `claude`/`gh` を使った(本物の `claude` は起動していない)。

### 1.(最重)再レビューを省く条件は、再レビューが守っていたものを測っていない

- **規則**: 「再現が修正前に失敗・修正後に通り、修正箇所を通る既存テストも通るなら、もう1回は回さない」(終了の判断)。
- **成り立たない理由**: この条件が確かめるのは「指摘された不具合が直った」と「既にテストが見ている挙動が壊れていない」だけ。再レビューの役目は「修正が持ち込んだ、テストの見ていない新しい不具合」を見つけることで、そこは空白のまま。「テストが修正箇所を通る」ことと「その挙動を検査している」ことは別。しかも確かめるのも終了を決めるのも、修正した親自身になる。
- **反例(実行)**: `review_loop.py` の、全テストが通る行を1行ずつ変え、`python3 skill-dev/review-loop/test.py` を回した(`work/mut.py`)。4つとも「131 ok / FAIL 0 / 全て成功」。
  - A: `git_status` から `--untracked-files=all` を外す。`status.showUntrackedFiles=no` の環境で未追跡ファイルの混入を見落とす(`work/exp2.py`: src は `'?? stray.txt\n'`、変異は `''`)。
  - B: `render` の `>` のエスケープを外す。観点に `-->` があると状態コメントを読み直せなくなる(src は True、変異は False)。
  - C: `kill_group` の SIGKILL を外す。D: `STRIP_ENV` から `CLAUDE_CODE_SESSION_KIND` を外す。この2つは挙動の差までは実行で示していない。
  - これは「こうした変更を含む修正でも条件を満たす」ことの代理実験で、ループが実際に作った修正ではない。
- **PR 自身の記述**: #14 の「全ブランチが delete になる」は反復3、つまり後の回で見つかっている。後の回に価値があった例で、省いてよい根拠にはならない。
- **代案**:
  - (a) 省くのではなく安くする。修正コミットの差分だけを1観点で見る軽い回を用意する。失うのは、反復が0にはならないこと。
  - (b) 省く条件を「修正が再現テストの対象関数に閉じ、公開の挙動を変えない」に絞り、それ以外は回す。失うのは削減の幅。

### 2. 根拠の表は、結論が必要とするものを測っていない

- **結論**: 3つの仕組みを既定にすれば、反復と膨らみが減る。
- **導けない理由**(`pr-body.md` と `src/` からの引用):
  - 表は反復数と入力トークンだけで、後半の反復の指摘が「誤検出」「修正が生んだ本物の不具合」「差分の外」のどれだったかの内訳がない。3つの仕組みはそれぞれ別の原因を前提にしている。
  - 唯一の具体例(#14 反復3)は、本物で影響が高の指摘。新しい方針では直らなくなる側の例である。
  - 表のトークンは子の分だけ(`add_tokens` は子の `modelUsage` を足す)。再現の作業は親に移るので、総費用が増えてもこの指標は改善して見える。
  - 本文も「まだ測っていない」と認めている。
  - この PR 自身の差分は SKILL.md、プロンプト、偽 `claude` だけで、指摘はほぼ「実行では示せない」になり、規則2は働かない。文書が中心のリポジトリでは効果が出にくい。
- **代案**: 過去4件の `verdict.md` を3分類で数えてから、既定を決める。失うのは時間。または、まず「差分の外」だけを入れる(効果が見えやすく、失うものが報告で補える)。失うのは一括で入れる手軽さ。

### 3.「再現を試みて起きなければ採らない」は、影響が高の指摘で偽陰性を通す

- **規則**: 起きなかった指摘は採らず、影響の段階に関係なく継続の理由にもしない。
- **成り立たない理由**: 文書は「別の OS、ツールの別の実装」を例外にしているが、これは指摘が条件を名指ししている場合だけ。読むだけのレビュー役が知らない前提(利用者の設定、リポジトリに固有の状態)は、隔離した一時リポジトリには持ち込まれず、列挙では塞げない。安全のための「隔離」が、そのまま偽陰性の原因になる。
- **反例(実行、`work/exp2.py`)**: src の `git_status` に同じ混入を与えた。利用者の設定は `GIT_CONFIG_GLOBAL` の切り替えで模した。
  - `.idea/workspace.xml` を残す: 一時リポジトリでは `'?? .idea/workspace.xml\n'`(検出)、`core.excludesFile` がある設定では `''`(見落とし)。
  - `notes.local` を残す: 一時リポジトリでは検出、`.git/info/exclude` に `*.local` がある worktree では `''`。
  - 「混入の検査が見落とす」という指摘は、一時リポジトリでは「起きなかった」になり、落ちる。
- **代案**:
  - (a) 影響が高は、不再現だけでは落とさず、「どのガードが防ぐか」をコードで示せたときだけ却下する。示せなければ未解決として利用者に報告する(継続の理由にはしない)。失うのは、報告が長くなること。
  - (b) 不再現は一律「保留」として報告に載せる。失うのは、採否の明快さ。

### 4. 3つの規則は親の文章の遵守だけに載り、記録が残らない

- **規則**: 範囲の判断、再現の有無、「回さずに終えた」ことが、利用者への約束(終了時の報告)になる。
- **成り立たない理由**: スクリプトは見出し2つしか見ず、状態にも持たない。親の文脈が切れると(圧縮、失敗による中断)、差分の外の一覧と採らなかった理由が消える。また、PR 上の状態コメントは最後の修正を示さなくなる。
- **反例(実行、`work/exp3.py`)**:
  - 次の3つの判定がすべて終了コード0で通る: 影響が高の defect で範囲・再現の欄がないもの、根拠なしで「差分の外」としたもの、範囲が「差分の内 / 差分の外」で再現が `rm -rf ~/repo` のもの。欄がないときの扱いは SKILL.md にない。
  - 3回目の修正を push して終えると、状態コメントは「反復 3、completed 4d64182」のまま、PR の head は 8daa47d。状態の鍵は SHA、結果、トークンなどだけで、未レビューか再現済みかを区別できない。
- **代案**:
  - (a) 作業ディレクトリに採否の台帳を置き、終了用のサブコマンドが報告を作る。そこで head が未判定であることも状態コメントに記す。失うのは、スクリプトの単純さ。
  - (b) 欄が欠けていたら「差分の内・再現が必要」と読む、と SKILL.md に1行足すだけにする。失うのは強制力。

### 妥当と判断した方針

- 指摘を仮説として扱い、確かめるのを親に置くこと。判定役は作業ツリーを変えられないという制約と合っている。
- 破壊的な再現を禁じること、範囲を確かめられなければ「差分の内」に倒すこと。
- 差分の外は尋ねてから issue にすること、公開リポジトリで悪用の手順を書かないこと。
