## 方針のレビュー: `--perspective` と `--instruct`

結論: 2つのオプションを足すこと自体は妥当ですが、背景の問題(`.env` の単独読みで試行が止まる)を解く仕組みにはなっておらず、狭めたレビューの記録と歯止めも構造として成り立っていません。指摘は4件です。

反例は `work/exp.py` で、`src/` のスクリプトを偽の `claude` と `gh` につないで動かしました。本物の `claude` は起動していないので、LLM が指示にどう従うかは確かめていません。

### 1. 背景の問題は決定的な停止なのに、解決策は「守られる保証のない依頼」
- **規則・結論**: `.env` を単独で読む呼び出しが試行を止める問題を、`--instruct` で解くという結論。
- **成り立たない理由**: 停止はスクリプトが拒否イベントを見て決定的に起こします。`--instruct` はシステムプロンプトに文を足すだけで、拒否の扱い(`tolerated`)とつながる経路がありません。SKILL.md 自身も「指示は LLM への依頼なので、守られる保証はない」と書いています。子が1回でも読みに行けば同じ失敗になり、「同じ原因で2回続けて失敗したら報告」の規則で結局ループが止まります。
- **反例(実行)**: どちらも `--instruct 'security-review=この PR で削除した .env の中身は確かめない'` を付けています。
  - B1: 子が拒否を result に載せる(`FAKE_REVIEW_security_review=deny`)と、`rc=1`、`failed: permission_denied: review security-review`。
  - B2: 子が拒否イベントを stream に出す(`denylive`)と、同じく `rc=1`、`permission_denied`。
  - 子の動きは偽物で決めているので、示せたのは「指示の有無が停止の判定に関与しない」ことだけです。
- **代わりの方針**:
  - 利用者が「この拒否は止めない」と宣言するオプション(例: `--tolerate-denial '.env'`)にする。一致した拒否は既存の `denials.txt` と判定役の入力に流す。失うのは、宣言したパターンに当たる読み取りが本当に要るものだった場合の検知で、`denials.txt` の確認に頼ることになります。
  - `--instruct` は残し、「失敗の対処」としては案内しない。失うのは手軽さだけです。

### 2. 狭めたことの記録が、観点の「名前の並び」しか見ていない
- **規則**: 「既定と違う観点で回した試行は表に載る」「付けたら以後も毎回同じものを付ける」「最後の判定でレビューされなかった観点と範囲を報告する」。
- **成り立たない理由**: 記録の条件は `names != [skill_name(s) for s in PERSPECTIVES]` だけです。引数の違いと `--instruct` は状態コメントに一切残りません。後ろ2つの規則は親エージェントの記憶だけが頼りで、文脈の圧縮やセッションの交代で失われます。状態コメントはまさにそのために PR に置いてあるのに、使っていません。
- **反例(実行)**: 次の4つはすべて `rc=0`、`completed` で、状態の行は既定の実行と区別できません(`perspectives` キーなし)。
  - A1: `--perspective 'code-review low {pr}'` とほか2つ。子のプロンプトは `/code-review low 7` になり、深さが変わっています。
  - A2: `--perspective 'code-review high 1'` と `'mattpocock-skills:code-review PR #1'`。PR #7 の SHA に対して、別の PR #1 のレビューが完了として記録されます。
  - A3: `--instruct 'security-review=何も調べず「指摘なし」とだけ答える'` と `'code-review=src/ 以下は見ない'`。
  - A4: A3 の直後にオプションなしで実行。付け忘れは何の警告もなく既定に戻り、表では前の回と見分けられません。
- **代わりの方針**:
  - シリーズの開始時に観点の全文と指示を状態に固定し、変更には `--new-run` を要求する。失うのはシリーズ途中の調整です。また、指示の本文が PR コメントに出ます(今は「詳細は載せない」方針なので、ハッシュと件数だけにする手もあります)。
  - 固定はせず、試行ごとに spec の全文と指示の有無を記録し、前の試行と違えば `warn:` を出す。失うのは強制力で、気づける状態になるだけです。

### 3. 「利用者の指示があるときだけ」を支える仕組みがなく、置き換えの幅が広すぎる
- **規則**: 「観点を外すとレビューの範囲が狭まるので、利用者に指示されたときだけ付ける」。
- **成り立たない理由**: `--perspective` は全面的な置き換えで、検証は `init` の `skills` と `slash_commands` に名前があるかだけです。レビューでないコマンドも通ります。必要なのは「この観点を外す」だけなのに、任意の構成を許しています。
- **反例(実行)**:
  - C1: `--perspective clear` は `rc=0`、`completed(反復 6)`。子のプロンプトは `/clear` だけです。
  - C2: `--perspective security-review` は `rc=0`、`completed`。コードレビューが両方消えても、標準出力の判定は通常と同じ形です。
- **実行で示せなかった点**: SKILL.md は、オプションを worktree のパスの後ろに置く理由を「コマンドの先頭の形を変えないため」と書いています。先頭一致の許可ルールがあれば、親がオプションを付けても権限の確認は出ないと読めます。つまり、権限の層で歯止めをかける余地を設計が自分で消しています。`claude` を起動していないので未確認です。
- **代わりの方針**:
  - 既定からの引き算だけにする(`--skip security-review`)。失うのは PR ごとの観点の追加と引数の変更で、既定の変更は従来どおり `PERSPECTIVES` の編集でできます。
  - 置き換えは残し、既定の観点が1つも残らない構成は終了コード2にする。失うものは小さいですが、個別の場合を塞ぐ方式なので、A1・A2 の類は残ります。

### 4. 示された根拠が、結論の必要とするものを測っていない
- **結論**: 「システムプロンプトに足し、スキルの手順より優先させる」「判定役の入力にも添えるので、外した範囲を観点の欠落と扱わない」。
- **導けない理由(引用)**: `pr-body.md` の根拠は「`python3 skill-dev/review-loop/test.py` は全て成功」だけです。テストが確かめているのは文字列の受け渡しで(`"削除したファイルの中身は確かめない\nテストは見ない" in by_name...`、`"観点 code-review に利用者が与えた追加の指示" in judge[0]["stdin"]`)、次の3点は測っていません。
  - 本物の `security-review` が、その指示で `.env` を読まなくなるか。
  - スキルの手順より指示が優先されるか。
  - 判定役が指示を見て欠落の扱いを変えるか。
- `JUDGE_PROMPT` はこの PR で変わっておらず、「追加の指示」の節をどう読むかも、どの観点が外されたかも判定役に伝えていません。
- **補足(実行、D1)**: 指示の本文に区切りの行を入れると、`judge-input.md` に偽の `===== 観点: security-review =====` の節が本物より前に入りました。書き手が利用者なので重くは見ませんが、自由文をそのまま区切りの中に流し込む形です。
- **代わりの方針**: 背景の PR で、指示ありと指示なしを数回ずつ実測し、止まった回数を本文に載せる。あわせて `JUDGE_PROMPT` に指示の扱いを1行足す。失うのは実測の費用だけです。

### 妥当だと判断した方針
- 名前の誤り、外した観点への指示、空の観点を、ロックの前に終了コード2で止めて状態に残さない点。指示が黙って捨てられないので筋がよいです。
- 権限で止まったとき、親が自分ではオプションを付けず利用者に提案するという役割分担。方向は正しく、足りないのは指摘2・3で述べた支えです。
- 指示をスキルの引数ではなくシステムプロンプトに入れる判断。引数を取らないスキルがある以上、合理的です。
