## 指摘の俯瞰

- `references/overview.md` の材料の用意は、書いてあるコマンドがそのまま全て通った。入力を判定(`verdict.md`)にした形は、これが初めて。`history/` を渡した形は、まだ使っていない
- 規則ごとのまとめは、そのまま修正の単位に使えた

  | 規則 | 当たる指摘 | 直し方 |
  |---|---|---|
  | 「再現して直した」は、修正の有無だけが違う2つのコードで、指摘の症状を見分けたときにだけ成り立つ | F2、F3、F4、F6 | 方式を変える |
  | 修正役への依頼文は、それだけで閉じる | F1、F7、F8 | 箇所ごと |
  | 親は、規則ごとに採否を決められ、禁じた操作を実行で検出できる | F5、F10 | 箇所ごと |
  | レビュー役の名前は、観点の役と `--focus` の役を合わせて一意 | F9 | 方式を変える(小さい) |

- 俯瞰の役は、頼まれていない実行もした(名前の重なりを関数の呼び出しで確かめた、`repeat.py` を流し直した、既存のテストを写しで流した)。一時リポジトリでの git の実行は、親のセッションの worktree の隔離に拒否され、3件は読んだだけになった
- 止まる条件は、今回は妥当に働いた。15件のうち9件が修正役の依頼文に集まり、どれも実行で示せないことを理由に、裏づけのある変更(既定の観点)と分けるよう判断した
- 手順の穴が1つ見つかった。SKILL.md の決まりでは、継続の理由になる指摘(影響が高、または中で普通の使い方)が無いと、俯瞰は省く。今回は0件で、決まりどおりなら省いていた。影響が中の指摘が同じ仕組みに集まった場合も行うよう、条件を足した

## 修正役

入力は、この記録の時点の `references/fix.md` の依頼文(コミット `bd08038` の版)。規則1は F9、規則2は F12。

- 再現のコマンドは `repro-1/`、`repro-2/`(`sh run.sh <対象のルート>`。作業場所は、コマンドのあるディレクトリの下に作る)
- 親が流し直した結果は、4本とも報告と一致した

  | | 修正前(`bd08038` の写し) | 修正後(`5589866` の作業ツリー) |
  |---|---|---|
  | 規則1 | 終了コード1。指摘の箇所と横展開の候補で「起動したレビュー役=4、残った出力=3」「2 と 1」 | 終了コード0。どちらも起動前に終了コード2で断る。対照の2件は、修正前も修正後も通る |
  | 規則2 | 終了コード1。`ZeroDivisionError` | 終了コード0。説明を出して終わる |

- 再現は、指摘の症状を見る作りだった。規則1は、起動したレビュー役の数と残った出力の数を比べる。修正の形(関数名や文言)には頼らず、「起動前に断る」と「名前を付け替える」のどちらの直し方でも通る判定で、断ってはいけない場合の対照が2つ入っている
- 横展開の候補(スキル `focus-1` と `--focus`)も、同じコマンドの中で失敗させ、同じ修正で塞いだ
- `mattpocock-skills:diagnosing-bugs` は実際に呼び出された。判定の全文(`findings.md`)は、同じディレクトリにあったが読まれなかった
- 依頼文に症状を書かなくても、規則の1文から入力を選べた。ただし、今回の規則は条件が単純だった

## 限界

- PR は1本。修正役が再現した規則は2つで、どちらも条件が単純
- 修正役は、依頼文を直す前の版で使った。直した後の版(症状と起きる条件の欄、終了コードの3通り、修正後の写しに流す確認)は、使っていない
- 片方だけの場合の数えは、判定役が書いた「観点」の欄による。判定役がまとめ方を変えれば、数は変わる
- 採点は LLM の判断で、採点役はどの出力かを知っている。mattpocock の出力は各題材1回分
- 俯瞰の役の出力と、修正役の報告の原文は、残していない(要点はこの文書と、PR #21 の本文にある)
