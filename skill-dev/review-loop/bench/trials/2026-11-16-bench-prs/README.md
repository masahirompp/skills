## 3. 修正役

2回使った(sk-12 反復1、wn-313 反復1)。どちらも Opus 5.5。

| 見ること | sk-12 | wn-313 |
|---|---|---|
| 依頼文の欄を判定から埋められるか | 埋められた。症状は「影響」、起きる条件は「起きやすさ」から | 同じ |
| 再現が症状を見ているか | 見ている。返った判定の中身、`denials.txt` の行数、判定役への入力の中身、失敗の種類 | 見ている。本物の tmux を専用ソケットで立て、セッションとクライアントが残るか、ペインが閉じるか |
| 対照と横展開 | 規則1は症状5・対照4、規則2は症状4・横展開2・対照3。横展開の2件は「起きなかった」と返し、直さなかった | 規則1は症状2・横展開2・対照2ほか、規則2は症状2・対照1 |
| 終了コード 0 / 1 / 2 | 使い分けた(前提のファイルが無い、症状と関係のない例外は 2) | 使い分けた(ビルドできない、クライアントをつなげない、は 2) |
| コミットを規則ごとに分け、SHA を返すか | 規則ごとに2つと、再現なしの1つ。対応を返した | 規則ごとに3つと、再現なしの1つ。対応を表で返した |
| `diagnosing-bugs` を呼び出すか | 呼び出した | 呼び出した |

依頼文で引っかかった点:

- 欄が規則ごとに「症状」1つ、「起きる条件」1つだが、俯瞰の役がまとめた規則には、症状の違う箇所が複数入る(sk-12 の規則2は3つ)。箇所ごとに (a)(b)(c) と書き分けた
- 俯瞰の役が選んだ直し方を、親が一部だけ採ることがある(2回とも、共有の処理を大きく変える部分を外した)。「直し方」の欄に、外す部分を書き足した
- SKILL.md の決まりでは、再現を求めるのは「影響が高、または中で普通の使い方」の指摘を含む規則。今回の4回の判定に、それに当たる指摘は1件も無い(中の指摘は全て「特定の操作の組み合わせ」か「まれな条件」)。決まりは、それ以外を「再現なしで採否を決めてよい」と許しているだけなので、親の判断で、影響が中の規則を再現の対象にした

そのほかに見えたこと:

- 判定役が「実行では示せない」としたタイミングの指摘(sk-12 反復1の F5)を、修正役は、偽の claude に待ち合わせの手順を持たせて再現した
- 再現のコマンドを途中で直した回がある(sk-12。規則2の修正で `run_reviews` の戻り値の形が変わり、規則1の再現が例外で落ちたため)。判定は変えていない、と返した
- wn-313 の時間の再現は、`date +%s` を PATH の偽物で差し替えて時計を進める。修正が `date` を使う形に寄った判定になっている(修正前は回数だけで落ちるので、修正前の結果には響かない)
- 修正が、次の反復の指摘を呼んだ。wn-313 反復2の中の指摘3件のうち2件(F1、F3)は、修正役が足した仕組み(案内のペインの見分け方、それ以外のペインを閉じる扱い)から出ている

## 4. 親の確認

| | sk-12 | wn-313 |
|---|---|---|
| 再現を流す前に読む | 書き込みは作業場所の下。ネットワークなし | 書き込みは一時ディレクトリと、tmux のソケットの置き場(下の「sandbox」) |
| 修正前の写し | 2本とも終了コード 1(各1秒) | 2本とも 1(5秒、1秒) |
| 修正後の写し | 2本とも 0(1〜2秒) | 2本とも 0(10秒、1秒) |
| 既存のテスト | 全て成功(約2分) | 単体115件、e2e 67件が成功(e2e は約7分) |
| 禁じた操作 | 残り物なし、ブランチ変わらず、履歴の書き換えなし | 同じ |
| 2 になった規則 | 0 | 0 |

見込みと違った点: wn-313 は、写しに `node_modules` が無いので 2 になる見込みだった。実際は、修正役が自分で回避した。再現の共通部分に作業ツリーの絶対パスを書き込み、対象のルートに `node_modules` が無ければ、作業ツリーの `tsc` と型を借りて一時ディレクトリへビルドする。そのため、写しでも実行でき、修正前 1 → 修正後 0 を確かめられた。2 のために増えた反復は無い。

この回避の評価:

- `fix.md` の狙い(修正の有無のほかの条件を、修正前と修正後で揃える)には合う。どちらの写しも、同じ依存物で動く
- 一方で、再現のコマンドが、特定の作業ツリーの場所に頼る。修正が依存物を変える PR では、修正前の写しを、修正後の依存物で動かすことになる(今回の修正は依存物を変えていない)
- 修正役がいつもこう回避するとは限らない。1回の観察

## 限界

- PR は2本で、どちらも bench の題材。題材は、過去のレビューで不具合が見つかった PR なので、指摘が出やすい
- 子の `gh` は認証済みで、リポジトリ名から元のリポジトリが分かる。レビュー役が、元の PR の修正を読んだかは調べていない
- 親(このセッション)は、sk-13、sk-14、sk-16 の経緯の要約をメモリから読んでいる。sk-12 と wn-313 の正解は、ループを終えるまで読んでいない
- 4回の判定の全てで、継続の理由になる指摘が0件だった。「終了の判断」の基準だけなら、2本とも反復1で終えていた。修正と2反復目は、手順を確かめるために、親の判断で行った
