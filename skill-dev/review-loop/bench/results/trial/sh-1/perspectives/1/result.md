「挙動は変えない」というコミットメッセージに反して、挙動が変わる箇所が 2 つあります。どちらも一時リポジトリで main 版と HEAD 版の `scan.sh` を並べて実行し、再現を確認しました。

## 正確性

- **`skills/housekeeping/scripts/scan.sh:93` — `is_ancestor` の引数が逆で、未取り込みコミットのあるブランチが削除候補になる(重大)**
  - 旧コードは `--is-ancestor "$sha" "$oid"`(手元の先端が PR の head に含まれるか)でしたが、新コードは `is_ancestor "$oid" "$sha"` です。
  - PR マージ後に手元で 1 コミット足したブランチは、main 版では `keep`(追加コミットが 1 件)、HEAD 版では `delete`(PR #1 マージ済み)になりました。
  - 逆に、手元が PR の head より古いだけのブランチは `delete` から `keep`(追加コミットが 0 件)に変わり、理由の文言も矛盾します。
  - 同じ関数を 230 行目がリモートブランチの判定にも使っています。マージ後に追加 push されたリモートブランチも削除候補になるはずですが、こちらは再現していません。
  - 修正は `is_ancestor "$sha" "$oid"` に戻すことです。

- **`scan.sh:82` — 既定ブランチの ref が片方無いと、first-parent 判定が黙って壊れる(重大)**
  - `git rev-list` は ref を 1 つでも解決できないと、何も出力せずに失敗します。旧コードは存在する ref だけを渡し、空ならエラー終了していましたが、その両方が消えています。
  - ローカルの `main` を消したリポジトリでは `$tmp/first-parent` が空になり、`grep` が常に 1 を返します。
  - その結果、PR が無く既定ブランチに含まれるブランチがすべて「merge コミットで取り込み済み」の `delete` になります。未着手のブランチは main 版では `ask` でしたが、HEAD 版では `delete` でした。
  - 81 行目のコメント「和集合を返す」は、両方の ref が存在するときしか成り立ちません。
  - 修正は、存在する ref の絞り込みと、空のときのエラー終了を戻すことです。

- **`scan.sh:84-85, 122-123` — 「履歴を読めない」の分岐にほぼ到達しなくなった**
  - 82 行目のリダイレクトがファイルを必ず作るので、`grep` が 2 以上を返すのは一時ディレクトリが消えた場合くらいです。
  - 読めなかった場合は、上記のとおり「first-parent 上に無い」に化けます。

- **`scan.sh:74, 93` — `is_ancestor` が失敗と「祖先でない」を区別しない(軽微)**
  - `git merge-base --is-ancestor` は祖先でなければ 1、エラーならそれ以外を返しますが、どちらも偽として扱われます。
  - 93 行目は旧コードでは stderr を出していましたが、`2>/dev/null` が付いたのでエラーが見えなくなりました。
  - 現状は偽が `keep` に倒れるので安全側ですが、引数の向きを直した後もこの前提に依存します。

## 設計

- **`scan.sh:73-74` — 向きを取り違えやすい関数なのに、守るテストが無い**
  - コミットメッセージは `skill-dev/housekeeping/test.sh` が全件成功と書いていますが、今回は `test.sh` を実行していません。
  - 全件成功が事実なら、上の 2 ケース(マージ後の追加コミット、ローカルの既定ブランチ無し)はテストで検出できていません。修正と一緒にこの 2 ケースを足すのが妥当です。

- **`scan.sh:118-119` — `on_first_parent` への切り出し自体は妥当**
  - 判定の中身は旧コードの `grep` と同じで、問題は入力ファイルを作る 82 行目の側にあります。
  - `merged_into_default`(76-78 行目)の書き換えも旧コードと等価です。

## セキュリティ / 並行性 / プライバシー

- 指摘はありません。差分は外部入力の扱い、一時ファイルの作り方、出力内容を変えていません。
- `$sha` や `$oid` は引用符付きで git に渡されており、新しい注入経路もありません。

## 結論

このままのマージは勧めません。削除候補を出すスクリプトで、2 件とも「残すべきものを `delete` と判定する」方向の退行だからです。93 行目の引数を戻し、82 行目の存在確認とエラー終了を戻せば、残りの整理(`is_ancestor` と `on_first_parent` の切り出し)は問題ありません。
