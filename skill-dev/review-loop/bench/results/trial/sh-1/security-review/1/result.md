# セキュリティレビュー: `skills/housekeeping/scripts/scan.sh`

攻撃者が外部から突ける脆弱性(コマンド注入、パス操作、秘密情報の露出など)は、この差分にはありません。ただし、削除してよいかを確かめる安全判定が逆向きになっており、未マージのコミットを消す方向に倒れるため、1件報告します。

判定はコードを読んだ結果で、実行による再現はしていません(検証用リポジトリを作る操作が権限で拒否されました)。差分が24行のため、サブタスクには分けず自分で確認しました。

# Vuln 1: 安全判定の反転(データ損失): `skills/housekeeping/scripts/scan.sh:93`

* Severity: Medium
* Category: `authorization_logic_bypass`(破壊的操作の前の保護判定が逆になっている)
* Confidence: 9/10(不具合であること)。攻撃者を必要としない誤動作で、古典的な意味の exploit ではありません。
* Description: `verify_pr_merged` の判定が、引数の順序ごと入れ替わっています。
  * 変更前は `git merge-base --is-ancestor "$sha" "$oid"` で、手元の先端が PR の head に含まれるときだけ `delete` でした。
  * 変更後は `is_ancestor "$oid" "$sha"` で、PR の head が手元の先端に含まれるときに `delete` になります。
  * その結果、PR のマージ後に追加コミットを積んだブランチが「PR #N マージ済み」という理由で `delete` になります。
  * 逆に、手元が PR の head より古いだけのブランチは「追加コミットが 0 件ある」という理由で `keep` になります。
  * 両者が同じコミットを指す場合だけ結果が変わらないので、既存のテストは通ります。`test.sh` に「追加コミット」の分岐を確かめるテストはありません。
  * コミットメッセージの「挙動は変えない」は、この箇所については成り立ちません。
* Exploit Scenario:
  * ローカル: PR #1 がマージされた後、同じブランチ `feat` に続きの作業をコミットして、まだ push していない状態で housekeeping を実行します。`feat` は「PR #1 マージ済み」として削除候補に出て、承認すると `apply.sh` が `git branch -D` で消します。表示される理由が誤っているので、承認時に気づく手がかりがありません。
  * リモート: 同じ関数が 230 行目からも呼ばれます。マージ後に誰かが追加で push したリモートブランチが削除候補になり、`git push --force-with-lease` で消えます。そのコミットを手元に持つ人がいなければ復元できません。223 行目のコメント「リモートの先端が PR の head に含まれるものだけを候補にする」とも食い違っています。
* Recommendation:
  * 93 行目を `elif is_ancestor "$sha" "$oid"; then` に戻します。
  * `test.sh` に、マージ後の追加コミットがあるときは `keep`、手元が PR の head より古いときは `delete` になるテストを足します。ローカルとリモートの両方で確かめます。

## 報告の基準に届かなかったもの

82 行目の first-parent 履歴の作り方も挙動が変わっていますが、コミットは失われないので脆弱性としては挙げません。

* **何が変わったか**: 変更前は存在する ref だけを `rev-list` に渡し、読めなければエラーで終了していました。変更後は2つの ref を無条件に渡し、終了コードも見ません。
* **どうなるか**: ローカルに既定ブランチが無いなど片方の ref が欠けると、`rev-list` は失敗して空のファイルが残ります。`grep` は空のファイルに対して 1 を返すので、既定ブランチに含まれる PR なしのブランチがすべて「merge コミットで取り込み済み」として `delete` になります。
* **影響**: 未着手のブランチに対する `ask` が `delete` に変わります。85 行目のコメントにある「それ以外は履歴を読めない」の経路には入りません。
* **扱い**: 通常のコードレビューでは直す価値があります。存在する ref だけを渡す処理と、失敗時にエラー終了する処理を戻すのが素直です。
