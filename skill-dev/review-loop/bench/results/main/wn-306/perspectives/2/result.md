## 正確性

- **[要修正] `src/screen/screen.ts:215` と `:233`:メモの入力中に、入力欄と選んだ行が画面から消える。**
  - 原因:`trailing` で `cursorBlock[1]` を、すぐ下に続く `(sub)` の行の終わりまで伸ばしています。その一方で、`:233` の「入力欄は最後の行まで窓に入れる」は今も `b1` を入力欄の終わりとして扱っています。そのため塊が窓より大きいと、`start = b1 - avail` で窓が `(sub)` の行の末尾に寄ります。
  - 再現:高さ 10 で、`p` の下に `(sub)` が 10 行あり、`p` でメモを入力中のとき、画面に出るのは `w3 (sub)`〜`w9 (sub)` と `2/3` だけでした。`> p` も入力欄も見えないまま、文字を打つことになります。
  - 直し方の案:入力欄の終わりは、`trailing` で伸ばす前の値として別に持つ。または、入力欄があるときは `trailing` で伸ばさない。

- **[要修正] `src/screen/screen.ts:213`:最初の選べる行の上に `(sub)` の行が多いと、選んだ行が窓の外に出る。**
  - 原因:`rowIndex.length === 1 ? 0 : start` で塊の始まりを 0 にしています。上にある `(sub)` の行と見出しの合計が窓の高さ以上になると、`:230` で `blockLen >= avail` となり `start = b0 = 0` になって、選んだ行が下にはみ出します。
  - 再現:高さ 10 で、先頭に起動元が一覧に出ていない `(sub)` の行が 12 行あり、`s0` を選んだとき、画面には `w0`〜`w5` と `1/2` だけが出て、`> s0` が見えませんでした。
  - 起きやすさ:利用者は会話の外の MCP サーバから `claude -p` を日常的に起動しているので(PRODUCT.md 末尾の観察)、トップレベルの `(sub)` が溜まる状況は起こりえます。
  - 追加したテスト(`test/unit/screen.test.ts` の 24)は `(sub)` 4 行・高さ 10 なので、この境界に届きません。
  - 直し方の案:上を広げるのは、選んだ行が窓に収まる範囲に限る。たとえば `b0 = max(0, b1 - avail)` のように始まりを抑える。

- **[軽微] `src/screen/screen.ts:215`:`trailing` が区切りの境界をまたぐ。**
  - 選んだ行が区切りの最後の行で、次の区切りの先頭がトップレベルの `(sub)` の行(起動元が一覧に出ていない行)だと、空行、見出し、その `(sub)` の行まで塊に入ります。これらは選んだ行の子ではありません。
  - PRODUCT.md の「選んだ行のすぐ下に続く起動された行」は子の行を想定していると読めるので、`s.groups.forEach` の頭で `trailing = false` にするのが素直です。
  - 単独では見える範囲が少し変わるだけですが、上の1件目と重なると、隠れる範囲が広がります。

- **[軽微] `src/ops/app.ts:263-265` と `:1215`:行が残っているのに「left the list」と出る。**

## 設計

- **`src/screen/screen.ts:201` と `src/model/cursor.ts:11`:「選べる行」の判定が2か所にある。**
  - 描画は `r.marker !== 'sub'` で数え、カーソルは `selectableOrder`(layout の `spawned`)で動かしています。両者が一致するのは、`app.ts:447` が `marker: n.spawned ? 'sub' : ...` と作っているからにすぎません。
  - `<通し番号>/<総数>` と `↑` `↓` の並びが同じ規則であることは、仕様(シナリオ 24)の要です。印の付け方が変わると、黙ってずれます。`ScreenRow` に `selectable` を持たせて app 側で `selectableOrder` から埋めるなど、出どころを1つにすることを勧めます。

- **`src/ops/app.ts:835-858`:`openNote` と `openWait` から起動された行の断りを外した。**
  - 今は「カーソルが起動された行に乗らない」という不変条件だけで守られています。経路も確かめました。キーの経路(`listKey`)はカーソル経由です。作業台の経路(`attachKey`、`sidOfSession`)は `id` で引くので、`id` を持たない起動された行には届きません。`GUIDE` の経路はカーソル経由です。どれも起動された行に届かないので、現状に問題はありません。
  - 気になるのは、入力欄やメニューを開いたまま、その行が更新で起動された行に変わる場合です。メモや待ち先を確定する時点で、起動された行への関係が保存されえます。これは変更前からある穴で、この差分で悪化したわけではありません。ただ、断りの判定が開く時点にしか無かった以上、確定する時点で `spawner` を確かめるほうが、DESIGN.md の「起動された行には待ち先もメモも結ばない」を確実に守れます。

- **`src/model/cursor.ts:41-57`:起動された行に変わった行の移り先は、その時点の起動元ではない。**
  - カーソルは、前の並びの隣の行に移ります。DESIGN.md の「消えたときと同じに隣の行へ移る」のとおりなので、不具合ではありません。
  - ただし、トップレベルの `(tty)` だった行が別の区切りの起動元の下に入ると、カーソルは元の区切りに残り、その行を追いません。消した規則の理由は「見ていた組から離れてしまう」でした(PRODUCT.md の削除した段落)。それと同じ理由が、ここにも当てはまるかもしれません。これは層2(観測できる挙動)なので、「隣の行に移る」と「起動元に移る」のどちらが欲しいかを、利用者に二択で確かめる価値はあると考えます。
