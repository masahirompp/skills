# セキュリティレビュー結果: `sub-rows-unselectable`（`main...HEAD`）

## この変更で新たに入った脆弱性：なし

確信度 8 以上の脆弱性は見つかりませんでした。審査役のサブタスクが候補を1件も挙げなかったので、誤検知を除く段階は実行していません。

## 該当なしと判断した根拠

- **`src/model/cursor.ts`**
  - 足したのは `selectableOrder` だけで、`initialCursor` と `followCursor` は簡単にしただけです。
  - どれも、メモリ上の Layout の配列を絞り込んで探す処理です。
  - 外部コマンドの実行、ファイルパスの組み立て、端末への出力のどれにもつながりません。
- **`src/screen/screen.ts`**
  - 変わったのは、カーソルの窓に入れる行の範囲（`cursorBlock`）と、`rowIndex` に入れる行の選び方だけです。
  - 書き出す文字列は増えても変わってもいません。これまでどおり、既存の `rowLine` と `annotationLine` を通ります。
  - 範囲を誤っても、表示が崩れるだけです。
- **`src/ops/app.ts`**
  - ↑↓ の移動先と、カーソルを追い直す判定は、`selectableOrder` を使うように替わりました。
  - `openNote` と `openWait` から、起動された行を弾く確かめを外しています。ただ、これは認可の迂回にはあたりません。
    - あの確かめは、ローカルの TUI の操作の制約で、権限の境界ではありません。
    - 今は、起動されたときの行も、更新のあとの行も、選べる行の中から選ばれます。そのため、カーソルが起動された行に乗ることはありません。
    - 仮に乗ったとしても、利用者自身のローカルの状態にメモや待ち先が付くだけです。
  - `enter` の通知から ` (sub)` の付記を外したのは、出力を減らしただけです。

外部プロセスの起動、パスの組み立て、秘密情報の扱い、端末のエスケープ列を出す経路のどれにも、新しい入力の流れは入っていません。
