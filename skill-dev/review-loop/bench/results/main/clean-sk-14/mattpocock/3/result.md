## Standards

文書化された規約へのはっきりした違反は見つかりませんでした。以下はどれも判断事項です。

- **lib.sh(Primitive Obsession の可能性)**: `hk_path_in_use` は1つの文字列で「使用中(`pid …`)」と「lsof で確かめられない」の両方を表しています。
  - そのため apply.sh の理由が「使用中か、確かめられない(lsof でプロセスを確かめられない)」と重複した文になります。
  - SKILL.md の手順5も、この文言の部分一致に頼っています。
  - 終了コードか別の値で分けると、名前と中身が一致します。
- **SKILL.md(Duplicated Code、文書)**: 「`!` の結果では終了コードが見えないので…確かめてから進む」が手順1と手順4に同じ形で2回あります。片方を参照にすれば一本化できます。
- **scan.sh(Speculative Generality、軽微)**: `on_fp -gt 1` の「first-parent 履歴を読めない」分岐は、直前の `[ -s "$tmp/first-parent" ] || exit 1` があるのでほぼ通りません。防御として残すなら問題はありません。
- **lib.sh のコメント**: `skill-dev/…/test.sh` を参照していますが、skill-dev/ はプラグインに含まれません。「(リポジトリ側)」と注記してあるので許容範囲です。
- **test.sh**: `in_lib` があるのに `bash -c '. lib.sh …'` を独自に書いている箇所があります。グローバル変数を出力するためと `set +f` を挟むためなので、必要な重複と判断しました。ヒアドキュメントが無いことを grep で確かめるテストは壊れやすいものの、理由をコメントで説明しているので妥当です。
- **コミットの粒度(Divergent Change)**: コミット名は mktemp/TMPDIR ですが、次の変更も同じコミットに入っています。
  - lsof で見えないときの扱い
  - jq の確認
  - PR 一覧 JSON の検証
  - first-parent の ref の選び方
  - `hk_parse_action` の導入
  - `git config` の読み取り失敗の扱い

  どれも「確かめられなければ残す」という同じ方針ではあります。ただ revert やレビューのしやすさを考えると、タイトルを実態に合わせるか、分割するのが望ましいです。
- **妥当な点**: `hk_` 接頭辞の使い分け、グローバル変数 `action`/`reason` への書き込み、apply.sh で一時ファイルをやめたことは、既存の書き方や今回の方針と一致しています。

## Spec

スコープの膨張はありません。要件もほぼ満たしています。

**(a) 欠けている・部分的な要件**
1. 仕様の「lsof が無い…ときは…残す。scan.sh と apply.sh の両方に効く」に対して、テストは scan.sh だけです(test.sh:162-169)。
   - apply.sh で skipped になることは検証していません。
   - `command -v lsof` が失敗する「lsof が無い」経路もテストがありません。
   - 実装(`hk_process_cwds`)はどちらの経路も正しく扱っています。
2. 「jq が無い…ときは止まる」は scan.sh:20 に実装がありますが、テストはありません。テスト一覧に挙がっていない項目なので、仕様違反ではありません。

**(c) 誤っていそうな点・削除側に倒れる経路の残り**
1. **awk が失敗すると削除側に倒れる**(コードで確かめました):
   - `hk_path_in_use`(lib.sh:108-109)の awk が失敗すると、出力が空になります。
   - apply.sh:43 は `[ -z "$proc" ]` なので、そのまま削除に進みます。
   - scan.sh:164 も `&& [ -n "$proc" ]` が偽になって次の分岐に進むため、keep になりません。
   - 起きる可能性は低いです。ただ、仕様の「判定の結果が空になったときは残す側に倒す」が徹底されていない最後の経路です。
2. **lsof の完全性の確かめ方が弱い**: 自分自身(`$$`)が一覧に出れば、プロセス一覧は完全とみなされます。
   - サンドボックスが自分と子プロセスだけ見せて外のプロセスを隠す場合、他のプロセスが使っている worktree が「使用中でない」と判定されます。
   - 仕様の「自分自身すら一覧に出ない」の文言どおりではあります。しかし、この判定で防げるのは「プロセスが何も見えない」場合だけで、「一部しか見えない」場合は防げません。
   - 実際の Seatbelt での見え方は確かめていません。

**妥当と判断した点**
- `hk_is_protected`: 一覧が取れない・空なら保護対象とみなし、1行ずつ case で照合しています。`git config` は rc が 2 以上を失敗として扱います。
- `hk_parse_action` / `parse_pr_info`: 空・複数行・未知の値は keep になります。
- first-parent: 存在する ref だけを渡し、読めなければ止まります。
- mktemp: テンプレートを付けて呼び、作れなければ fetch より前に止まります。
- SKILL.md の `!` の案内は、仕様の項目(コマンドの形、絶対パス、実行後に確かめること)をすべて含んでいます。

---

**まとめ**: Standards は判断事項6件(はっきりした違反は無し)で、最も重いのは `hk_path_in_use` の返り値が「使用中」と「確かめられない」の2つの意味を兼ねている点です。Spec は4件(欠けている要件2、誤っていそうな点2)で、最も重いのは awk が失敗すると apply.sh が worktree を削除してしまう経路です。
