## Standards

**規約違反: なし。** README.md が定めているのは次の3点で、差分はどれにも反していません。
- SKILL.md の frontmatter の規則(この差分では変更なし)
- `skills/` と `skill-dev/` の役割分担
- housekeeping はスクリプトのテストで検証すること

**暗黙の規約との食い違い(判断の余地あり)**
- **`lib.sh` の `hk_mktemp_dir`**: lib.sh の既存の関数は、失敗すると空を返すだけで、エラー文は呼び出し側が出しています(例: `hk_default_branch`)。この関数だけが lib の中で `error:` を出しており、書き方が揃っていません。
- **`lib.sh` 冒頭のコメント**: プラグインとして配布されるコードが、配布されない `skill-dev/housekeeping/test.sh` を参照しています。インストールした環境ではたどれません。
- **`hk_protect_patterns` 内の `set -f`**: lib.sh 先頭の `set -f` と重複しています。方針を2か所で持つことになります。
- **`scan.sh:85` の `git rev-list --first-parent $fp_refs`**: 引用符で囲まず、単語分割に頼っています。同じ差分の `hk_is_protected` では「単語分割を使わない」と書いているので、方針が揃っていません。ここに入るのは既定ブランチ名などの ref だけなので、実害は小さいです(この行は私も確認しました)。

**コードの臭い(すべて判断の余地あり)**
- **名前が中身を表していない可能性**(`hk_path_in_use`、`hk_process_cwds`): 「使用中のプロセスがある」と「確かめられない」という別々の状態を、同じ文字列の戻り値で返しています。空文字は「不明」を表す特別な値になっています。状態を分けて返すか、関数名を中身に合うものに変えるとよいです。
- **一緒に受け渡される値の組**(`parse_pr_info`、`hk_parse_action`): `st num oid` と `action reason` が、いつも組でグローバル変数を経由しています。bash の制約上、やむを得ない面があります。
- **重複**(SKILL.md の手順1と手順4): 「`!` で実行すると終了コードが見えないので、結果を確かめてから進む」という案内が、ほぼ同じ形で2回書かれています。
- **1コミットに複数の変更理由**: 件名は mktemp と TMPDIR の修正ですが、jq の確認、PR 一覧の JSON の検証、first-parent の修正、保護パターンの強化、lsof の扱いも同じコミットに入っています。コミットの粒度の規約は無いので、判断の余地ありとしました。
- **読み取りにくい条件式**(test.sh の `temp_usage` を使う if): `||` で5つの条件がつながっていて、それぞれ何を確かめているのか読み取りにくいです。

## Spec

test.sh を実行すると全件成功し、実行後の `git status` は clean でした。コミットメッセージに書かれた要求は、ほぼすべて実装と一致しています。たとえば次の点を確かめています。
- `hk_mktemp_dir` は TMPDIR の下にテンプレート付きで作る。
- scan.sh は jq の確認と一時ディレクトリの作成を fetch より前に行う。
- 判定の経路に `<<` と `<<<` は1件も残っていない。
- 形の違う判定結果は keep になる。
- git config の終了コードは、2以上なら保護対象とみなす。

**(c) 実装が誤っている可能性(要確認)**
1. **自分自身が見えても、他のプロセスが見えるとは限りません。**
   - 該当する記述: 「自分自身すら一覧に出ない(サンドボックスなどでプロセスを見られない)ときは…残す」
   - `lib.sh:96` は、lsof の出力に `$$` があれば十分に見えているとみなします(これは私もコードで確認しました)。
   - サンドボックスが自分のプロセス(と子プロセス)だけを見せる場合、この確認は通ってしまいます。すると、ユーザーのターミナルがカレントにしている worktree を「使用中でない」と判定し、`git worktree remove` まで進みます。安全側に倒すはずの経路で、逆に削除側に倒れることになります。
   - サンドボックスの外では再現していません。Seatbelt の中で lsof がどこまで見えるかを一度確かめてください。足りなければ、自分の親子以外のプロセスが見えることも条件に加えれば塞げます。

**(a) 部分的なもの**

2. **lsof の扱いを apply.sh でテストしていません。**
   - 該当する記述: 「scan.sh と apply.sh の両方に効く」
   - 偽の lsof を使うテストは scan.sh だけです。
   - 偽の lsof は何も出力しないため、「出力はあるが自分自身が載っていない」場合の処理も通っていません。この処理が壊れていても、テストは全件成功のままです。
3. **「PR の状態が分からなければ keep」を確かめるテストがありません。**
   - 削除しすぎを防ぐ主要な経路ですが、ケースが無いです。
   - テスト項目の一覧には挙げられていないので、コミットメッセージと矛盾はしていません。

**(c) 軽微**

4. **相対パスの TMPDIR**: `TMPDIR=tmp` のように渡すと、カレントの worktree の中に一時ディレクトリができます。終了時に消えるので実害は小さいですが、エラー文に「絶対パス」と一言添えるのが妥当です。

**(b) 書かれていない変更**

5. **出力の文言が変わっています。**
   - scan.sh: 判定が keep のときに「worktree と一緒に消す」という前置きを付けなくなりました。
   - lib.sh: `hk_path_in_use` の出力が `pid N cmd` の形になりました。
   - どちらも妥当な修正ですが、コミットメッセージに書かれていません。

**まとめ**: 規約の観点は、規約違反0件、暗黙の規約との食い違い4件、コードの臭い5件です。最も重いのは、「使用中」と「確かめられない」を同じ文字列で返している点です。仕様の観点は5件で、最も重いのは指摘1です。サンドボックスで自分自身しか見えない場合、使用中の worktree を削除してしまう可能性があり、確かめる価値が高いと考えます。
