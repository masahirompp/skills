差分の5ファイル(`lib.sh` / `scan.sh` / `apply.sh` / `SKILL.md` / `test.sh`)を読みました。全体として、方針は筋が通っています。一時ファイルを作れないと判定の入力が空になり、削除側に倒れてしまう(fail-open)経路を塞ぎ、判定できないときは残す側に倒す、という方針です。中核の主張も手元で確かめました。macOS の `mktemp` はテンプレートなしだと `TMPDIR` を無視します(`TMPDIR=/nonexist mktemp` が `/var/folders/...` を返して成功)。スクリプトが動くのが bash 3.2(この環境の `/bin/bash`)で、ヒアドキュメントに一時ファイルを使うという前提にも合っています。それでも残っている穴と設計上の懸念は次のとおりです。

## 正確性 / 並行性

- **`skills/housekeeping/scripts/lib.sh:96` lsof で自分自身が見えても、ほかのプロセスが見えている保証にはならない(要確認)**
  - この自己チェックで分かるのは「lsof がまったく機能しない」場合だけです。
  - サンドボックスが同じサンドボックス内のプロセス情報だけを許す設定(Seatbelt の `process-info*` を `same-sandbox` に絞るなど)だと、`$$` は見えます。一方で、サンドボックスの外のエディタ、ターミナル、dev server の cwd は見えません。この場合は今までどおり「使用中でない」と判定されます。
  - 影響は、未変更の worktree を外部のプロセスが cwd にしていても `delete` になり、`apply.sh:42` で消されることです。未コミットの変更や未追跡ファイルがあれば `git worktree remove` が拒否するので、被害はきれいな worktree に限られます。
  - 想定する環境(サンドボックス)そのもので起きうる fail-open です。テスト(`test.sh` の fake lsof)は「何も出ない」場合しか見ていません。
  - 対策案: 自分の祖先や子孫ではないプロセスが少なくとも1つ見えることを条件にする。または、サンドボックスの外に必ずいる同じユーザーのプロセス(macOS なら `loginwindow` など)が見えることを確かめる。
- **`skills/housekeeping/scripts/lib.sh:45-47` `set -f` が外に漏れないことを、コメントの約束だけに頼っている**
  - 「`$(...)` の中で呼ぶので外には漏れない」が成り立つのは、今の呼び出し元(`hk_is_protected`)の書き方のおかげです。将来だれかが直接呼べば、呼び出し元のシェルに `set -f` が残ります。
  - 関数本体を `hk_protect_patterns() ( ... )` とサブシェルで書けば、構造として保証できます。影響は小さいです。
- **`skills/housekeeping/scripts/lib.sh:81` `hk_parse_action` が `prune` も正しい値として通す**
  - 呼ばれる経路(`classify_branch` / `verify_pr_merged`)が出すのは delete / ask / keep だけです。
  - 「既知の action 以外は keep に倒す」という意図からすると、受け入れる値は必要な分だけに絞る方が一貫します。現状で実害はありません(prune は `git worktree prune` になるだけ)。
- **`skills/housekeeping/scripts/scan.sh:49-54` `parse_pr_info` が想定外の形の入力を黙って受け入れる**
  - 空白を含まない文字列が来ると、`num` と `oid` に同じ値が入ります。
  - それでも `st` は `OPEN` / `CLOSED` / `MERGED` / `NONE` 以外なら keep に落ちる(`scan.sh:134`)ので、安全側に倒れます。実害はなく、記録として挙げておきます。
- **`skills/housekeeping/scripts/scan.sh:83-86` first-parent 履歴を作る部分は妥当**
  - 存在する ref だけを渡し、空なら止まる修正で、ローカルの既定ブランチが無いと全件が delete になるバグを塞げています。
  - `$fp_refs` をクォートしていませんが、`set -f` と ref 名の制約(空白不可)があるので問題ありません。
- **`skills/housekeeping/scripts/scan.sh:120-133` 履歴を読めないときの扱いも妥当**
  - `on_fp > 1` で keep に倒す分岐は正しく効いています。
  - reflog のパイプで `-q` を避けた理由のコメントは、少し不正確です。`-q` で途中終了して pipefail が失敗を返すと、結果は `ask` になります。つまり安全側の誤判定で、危険ではありません。動作は今のままでよいです。

## セキュリティ / プライバシー

- **`skills/housekeeping/SKILL.md:20` と `:61` 予測できる固定のパスを `/tmp` に置く**
  - `${TMPDIR:-/tmp}/housekeeping-scan.tsv` は、`TMPDIR` が未設定の環境(主に Linux)では、だれでも書ける `/tmp` 直下の固定名になります。
  - 起きうること:
    - 他のユーザーが同じ名前で先にファイルやシンボリックリンクを置ける。
    - ファイルは umask 022 だと読める権限で作られ、ブランチ名や worktree の絶対パスが他のユーザーに見える。
    - 何より、他のユーザーが置き換えた TSV を `apply.sh` に流すと、削除対象を差し替えられる。保護パターンと sha の確認はあるものの、入力の出どころを信頼している前提が崩れます。
  - 対策案: 手順の中で `mktemp` で作ったファイルを使う。
  - 一方で、`scan.sh` 自身の一時ディレクトリ(`lib.sh:23`、`mktemp -d` で権限 0700)は問題ありません。
- **`skills/housekeeping/SKILL.md:73` 破壊的な操作をサンドボックスの外で実行してもらう案内になっている**
  - `! awk '<承認した行の条件>' <ファイル> | apply.sh` は、エージェントが組み立てた条件を、ユーザーがサンドボックスの外で実行する形です。中にはリモートブランチの削除(push)も含みます。
  - awk の条件を読み違えると、承認していない行まで流れます。
  - 対策案: 実行前に、条件に当たる行の一覧を `!` なしで表示して、ユーザーに見せる手順を入れる。
