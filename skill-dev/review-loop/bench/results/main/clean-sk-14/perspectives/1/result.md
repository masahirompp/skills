bash 3.2.57(macOS 標準)で `skill-dev/housekeeping/test.sh` を流し、全件成功しました。作業ツリーは変更していません。

差分の方向性は妥当です。ヒアドキュメント、空の判定結果、読めない PR 一覧、ローカルの既定ブランチが無いとき、という各経路で、これまで削除側に倒れていたところを残す側に倒しています。どれも根拠がはっきりした修正です。そのうえで、残っている弱点を挙げます。

## セキュリティ / プライバシー

- **`skills/housekeeping/SKILL.md:20`, `:61`: 新しく足した `/tmp` へのフォールバックが、複数ユーザーの環境で改ざんの入口になる**
  - Linux では `TMPDIR` が未設定なのが普通なので、`/tmp/housekeeping-scan.tsv` という全ユーザー共通の固定名になります。
  - 別のユーザーが先に誰でも書き込めるファイルを置いておけば、`>` はそのファイルに書きます。すると走査から apply までの間に、`delete branch <name> <sha>` の行を差し込めます。sha は TSV から読めるので、apply.sh の「sha が変わっていない」確認も通ります。保護パターン以外のローカルブランチやリモートブランチを消させられます。
  - macOS の `/tmp` には `protected_symlinks` に当たる仕組みがありません。シンボリックリンクを置いて別のファイルを上書きさせる攻撃も成り立ちます。
  - 書かれる TSV は umask 次第で誰でも読めます。そこに絶対パス(ユーザー名を含む)やブランチ名が出ます。
  - 修正案: 置き場所を `mktemp -d` で作ったディレクトリ(0700)にするか、`umask 077` と `set -o noclobber` を案内する。複数ユーザーの環境はまれなので重大度は低〜中ですが、フォールバックを足したのはこの差分です。

## 正確性 / fail-open

- **`skills/housekeeping/scripts/lib.sh:96`: 「自分が一覧に出れば、ほかのプロセスも見えている」という推定は、fail-open の穴を残す(可能性あり)**
  - この確認で拾えるのは「何も見えない」場合だけです。サンドボックスの方針が「同じサンドボックスの中のプロセスは見える、外は見えない」なら、自分自身は一覧に出ます。それでも、守りたいプロセス(ユーザーのターミナルやエディタの cwd)は見えません。その worktree は「使用中でない」と判定されます。
  - Linux でも、root 以外は他ユーザーのプロセスの cwd を読めないのに、自分は見えるので「見えている」扱いになります(これはこの差分の前からの性質です)。
  - Seatbelt が実際にどう振る舞うかは確かめていません。せめて自分の子孫でないプロセス(例: `$PPID` のさらに親や、ログインシェル)が見えることを条件にすれば、確かめ方が一段強くなります。テストも「一覧が空」の場合しかありません(`test.sh` の偽の lsof は `exit 1` するだけ)。

- **`skills/housekeeping/scripts/lib.sh:81`: `hk_parse_action` が、呼び出し元に関係なく `prune` を受け付ける**
  - `classify_branch` と `verify_pr_merged` は `prune` を返さないので、いまは表に出ません。
  - ただ、もし branch の行に `prune` が出ると、`apply.sh:29` の `rows` は `$1 != "keep"` で絞るだけなので、`git branch -D` まで進みます。
  - 許す action を呼び出し側から渡すか、判定の経路では `delete|ask|keep` だけにしておくと、「判定できなければ残す」という意図と合います。

- **`skills/housekeeping/scripts/lib.sh:46`: `set -f` の効き目が呼び出し方に依存している**
  - コメントのとおり、`$(...)` の中で呼ぶ限り外には漏れません。
  - ただ `hk_protect_patterns` は lib.sh の公開関数のような位置にあり、直接呼べば呼び出し元のシェルに `set -f` が残ります。いまの呼び出し元は `hk_is_protected` だけなので実害はありません。関数本体を `( ... )` にすれば、呼び出し方への依存を消せます。

- **`skills/housekeeping/scripts/scan.sh:46`: 確かめているのは一番外側が配列であることだけ**
  - 要素がオブジェクトでなければ、`open_pr_based_on` が失敗して空を返し、スタックした PR の保護が外れます。
  - ただ `pr_info` も同時に失敗し、その結果 `UNKNOWN`、つまり keep か `continue` になるので、いまは残す側に倒れます。2つの関数の失敗がそろって起きることに頼った安全さで、偶然に近いです。`jq -e 'type=="array" and all(.[]; type=="object")'` にすると、意図が書き方に出ます。

## 設計

- **`skills/housekeeping/scripts/scan.sh:85-86`: 既定ブランチの履歴を読めないと、走査全体が止まる**
  - PR の無いブランチが1本も無い場合でも止まります。安全側ではありますが、作ったばかりのクローンなどでは使えない場面が増えます。
  - `first-parent` は `NONE` の経路でしか使いません。読めないときは止めずに「読めない」と印を付け、`classify_branch:123` の keep に任せる手もあります。どちらを選ぶかは方針の問題で、いまの「止まる」も筋は通っています。

- **`skills/housekeeping/SKILL.md` のサンドボックスの案内: 「外で走査して、中で apply する」とどうなるかが、手順の形で避けられていない**
  - この組み合わせでは、worktree の行がすべて skipped になります。
  - 起きたあとの案内(`!` で実行し直す)は書かれています。ただ、最初から「scan を `!` で外で実行したら、apply も外で実行する」と手順1の時点で決めておけば、二度手間を防げます。

- **`skill-dev/housekeeping/test.sh`: ヒアドキュメントが無いことを grep で確かめる方式は、コメントを除く判定が粗い**
  - 除いているのは、行頭が `#` の行だけです。行末のコメントや文字列の中にある `<<` は、誤検知の元になります。
  - いまは問題になっていません。

## 検討してほしい問い

- 守りたいのは「エージェントのサンドボックスの中で走らせたときの安全さ」でしょうか、それとも「どの環境でも fail-closed であること」でしょうか。前者なら lsof の確認を強めるのが本筋です。後者なら、そもそも lsof を判定の根拠にしてよいか(外から見えないプロセスがいつでもありうるか)を問い直す価値があります。
- scan.tsv は、「scan と apply の間を TSV ファイルで渡し、ユーザーが承認する」という信頼の境界になっています。ここを、誰が書けるファイルとして扱うかを決めておくと、上の `/tmp` の指摘を直す方向が定まります。
