# `main...HEAD` のレビュー(d212b82「作業台の画面が開いた直後に閉じる不具合を直す」)

コミットに issue 番号がないので、仕様は `docs/PRODUCT.md`、`docs/DESIGN.md`、`docs/lib/tmux.md` を基準にしました。Spec 側の主な2点(回数が戻らないこと、`not running` でもキーを待つこと)は、私が差分を読んで裏を取りました。

## Standards

`npm run check` と、関係する単体テスト(11件)は通りました。依存の向きは `src/` → `lib/` の一方向で、守られています。lib を変えた分も、契約とテストを先に書いています。

**(a) 規約から外れている箇所**

1. **`docs/lib/tmux.md` の「名前の約束」に載っていないものがある(確度: 中)**
   - 載っていないのは、ペインのオプション `@wn_respawned` と、新しい頼みごとの形 `guide` の2つです。
   - `docs/lib/README.md` には「契約に書いていない振る舞いに頼らない」とあります。
2. **`docs/PRODUCT.md` を直していない(確度: 低)**
   - 案内のセッションを作り直すことと、キーを待つことは、利用者から見えます。
   - 不具合の修正と読めば、直さなくてよいことになります。
3. **lib のテストは字面を見るだけ(確度: 低)**
   - 「5回までは起動し直し、超えたら畳む」のテストは、sh の本文に `respawn-pane` などの文字列があるかを見ているだけです。
   - 契約の範囲内なので、違反ではありません。ただ、動かして確かめる e2e は使い捨ての層にあり、サイクルが終わると消えます。

**(b) smell(判断)**

- **Duplicated Code**
  - `workbench.ts` の `askListToRefreshGuide` が、`guide.ts` の74〜80行目と同じ形です(`@wn_req_…` を書いて、`@wn_pid` に SIGUSR2 を送る)。
  - `list.ts` は `ensureGuide` のすぐあとで `workbenchOptions(GUIDE, '')` を呼びます。案内を作ったときは同じ処理が2回走ります。
- **Divergent Change(の可能性)**: `guide.ts` は案内のプログラムそのものですが、セッションを作る役(`ensureGuide`)も持つようになりました。
- **Mysterious Name(軽微)**: `GUIDE_REFRESH = 'guide'` は、`GUIDE`(セッション名の `wbguide`)と紛らわしいです。
- **Primitive Obsession(軽微)**: 頼みごとを文字列で組み立てています。ただし、今までの書き方に合わせたものです。

## Spec

**(b) docs にない、利用者から見える変更(CLAUDE.md の層2にあたり、利用者の判断が要る)**

1. **PRODUCT.md は差分がない(確度: 高)**。次の挙動は DESIGN.md と lib の契約にしか書かれていません。
   - **新しいエラーの文言**: 標準エラーに `could not create the workbench guide` と `could not open the workbench screen` の2つを出します。
   - **Ghostty の分割**: 失敗すると `Press any key to close.` と出して、キーを待ちます。PRODUCT 478「whatnext が作った分割は、作業台の画面が終わると閉じる」と食い違います。
   - **`not running` のとき**: この経路も `fail()` を通ります(`workbench.ts:14`)。そのため、PRODUCT 490 とシナリオ 59 の「示して終了する」が、分割の中ではキーを押すまで終わらなくなりました。終了コード 1 は変わりません。
   - どれも「失敗したら、分割はすぐ閉じるか、キーを待つか」という二択で書けるので、層1(内部設計の変更)としては扱えません。
2. **上限を超えたとき(確度: 中)**: 起動し直しが5回を超えると案内のセッションを畳み、作業台の画面が離れます。これも PRODUCT に書かれていません。

**(c) 意図とずれていそうな実装**

3. **`@wn_respawned` が0に戻らない(確度: 高、差分で確認済み)**
   - コメントの意図は「起動してすぐ終わるときに、回り続けないため」です。
   - 実際の上限は「ペインが生きている間に通算5回」です。長く動いては時々落ちる場合も、6回目で畳まれます。
   - 時刻の窓で数えるか、しばらく動いたら0に戻すのがよいと考えます。
4. **作り直した案内の版と環境(確度: 中)**
   - 作り直した案内は、`whatnext workbench` 側の `env.node`、`env.cli`、`process.env` で起動します。
   - DESIGN 203「スクリプトは、動いている一覧と同じ版のものにする」に反し、更新の直後は版が混ざりえます。PATH なども、一覧のものではなく利用者のシェルのものになります。
5. **`ensureGuide` の取り合い(確度: 低)**
   - 相手が先に作ると `'exists'` が返り、`askListToRefreshGuide` が呼ばれません。
   - 2つの `whatnext workbench` が同時に作り直すと、`@wn_name`(名前)が入らないままの窓が残ります。
6. **attach の失敗の見分け方(確度: 低)**
   - 「0 以外で終わり、かつ一覧が残っている」で失敗と見なしています。tmux の終了コードを実測した記録は docs にありません。
   - 上限で案内を畳んで画面が離れたときも、同じ条件に当たって失敗と取り違える可能性があります。

**(a) 欠けているもの**

7. **シナリオとの対応**: 新しい e2e 2つ(作り直し、起動し直し)にシナリオ番号がなく、DESIGN「確かめ方」の対応表にも行がありません。サイクル9の完了条件 7 の形に乗っていません。
8. **テストがない挙動**: 次の3つは、どれも動かして確かめるテストがありません。
   - 5回を超えたら畳むこと(本文の字面を見るだけ)
   - attach に失敗したときに行を消さず、理由を出すこと
   - キーを待つこと
9. **良い点**: `exec` の重複の修正は妥当です。bash、zsh、sh の3つで流して確かめていて、DESIGN の記述とも合っています。

**まとめ**: Standards は8件で、最も重いのは lib の契約(`docs/lib/tmux.md` の「名前の約束」)に `@wn_respawned` と頼みごと `guide` が載っていないことです。Spec は8件(良い点を除く)で、最も重いのは利用者から見える挙動の変更(分割でキーを待つこと、とくに `not running` のとき)が PRODUCT.md になく、利用者の判断を経ていないことです。直す順は、先に利用者に二択を確かめ、そのあと `@wn_respawned` の数え方を直すのがよいと考えます。
