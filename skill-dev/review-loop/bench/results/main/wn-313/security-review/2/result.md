# セキュリティレビュー結果: `main...HEAD`(wbguide-recover)

確信度 8 以上の脆弱性は見つかりませんでした。差分は、ローカルのユーザー専用 tmux サーバの中だけで動く後始末と再接続の処理です。信頼境界を越えて入ってくる入力はありません。

## 確認した箇所と、問題なしとした根拠

**1. `lib/tmux/tmux.ts` の `pane-died` スクリプト(`set -g @wn_guide_died "$(... capture-pane ...)"`)**
- コマンド置換の結果は二重引用符の中で 1 つの引数になります。sh が中身を解釈し直すことはありません。
- tmux はこの値を `set-option` の値としてそのまま受け取ります。`-F` を付けていないので、`#{...}` の書式も展開されません。
- 末尾が `;` になっても、後に続く引数がないため、別のコマンドが差し込まれることはありません。改行は `tr` で空白に置き換えています。
- 取り込む画面の中身は、案内のプログラム(whatnext 自身)の出力です。攻撃者が自由に書き込める経路はありません。

**2. `src/cli/workbench.ts` の `askListToRefreshGuide`(`@wn_pid` を読んで `SIGUSR2` を送る)**
- `@wn_pid` は、利用者本人の専用 tmux サーバのオプションです。書き換えられるのは、すでに同じ UID でサーバを操作できる者だけなので、権限の境界を越えません。
- 頼みごとの名前に入る `Date.now()` と `process.pid` は、プロセスが自分で作る値です。

**3. `src/cli/guide.ts` の `ensureGuide`(`new-session ... paneCommand(env, 'guide')`)**
- `paneCommand` は、既存の `shq` で値をクォートしています。
- 入力は `env.node`、`env.cli`、環境変数で、いずれも信頼できる値です。

**4. `src/cli/env.ts` の `workbenchCommand` と Ghostty の分割への打ち込み**
- `shq` でクォートしたまま `exec` を 1 つに減らす変更で、注入の経路は増えていません。
- 単体テストでは `'` を含むパスで bash、zsh、sh のどれでも動くことを確かめています。

**5. `WHATNEXT_WORKBENCH_SPLIT` と `fail()`**
- 環境変数で、キーを待つかどうかを切り替えるだけです。
- 環境変数は信頼できる値として扱う、という前提の範囲内です。

なし
