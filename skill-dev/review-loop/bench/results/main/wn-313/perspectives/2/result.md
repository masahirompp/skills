## レビュー結果(`git diff main...HEAD`、コミット d212b82)

全体としては妥当な修正です。根本原因(案内のペインを `kill-pane` していたこと、`exec` が二重に付いていたこと)をそれぞれ直接直しており、つなぐ側で確かめる(`ensureGuide`)方針の理由も DESIGN.md に書かれています。挙動が変わる指摘は 1 と 2 です。

### 正確性
- **`lib/tmux/tmux.ts:52-58` 起動し直しの回数が、起動してすぐ終わった回数ではなく、ペインが生まれてからの通算になっている**
  - `@wn_respawned` はペインのオプションで、`respawn-pane` してもペインの ID は変わりません。回数は減らず、元に戻すところもありません。
  - そのため、何日も動かしている間に案内がたまに落ちるだけでも、6 回目に `kill-pane` が走ります。案内のセッションに作業台の画面がつながっていれば、`detach-on-destroy on` で離れます。
  - tmux のクライアントは、セッションが消えて離れたときは 0 で終わると考えられます(未確認)。そうなら `workbench.ts:34` の失敗の判定にかからず、分割が黙って閉じます。直したはずの症状が、回数を置いて再び出ることになります。
  - DESIGN.md と `docs/lib/tmux.md` には「起動してすぐ終わるときに回り続けないため」と書かれており、意図と実装が合っていません。前に起動した時刻を残し、それから(例えば)10 秒以上たっていれば回数を戻す、といった形が意図に合います。
- **`src/cli/workbench.ts:34` 「つなげなかった」の判定が、シグナルで終わった場合も失敗に数える**
  - `res.status` はシグナルで終わると `null` になり、`!== 0` が真になります。一覧が残っていれば、エラーを出してキーを待ちます。
  - 分割を閉じたときの SIGHUP なら node 自身も終わるので実害は出ません。ほかの経路(tmux のクライアントだけが kill される場合など)で、誤ってエラーを出してキーを待つ余地があります。
  - `res.status !== null && res.status !== 0` のように、シグナルで終わった場合を分けるほうが意図に合います。
- **`src/cli/workbench.ts:58-60` `fail()` が端末の状態を前提にしている**
  - 端末が切れたあとに `setRawMode(true)` を呼ぶと、EIO で投げることがあります。そうなると例外が捕まらずに落ちます。影響は小さいものの、`try` で囲んでおけば安全です。

### 設計
- **`src/cli/guide.ts:19` `whatnext workbench` が作り直す案内が、一覧と違う版・違う環境になりうる**
  - `paneCommand(env, 'guide')` は、`whatnext workbench` を動かしているプロセスの `env.node`・`env.cli`・`process.env` を使います。Ghostty の分割から起動したときは一覧と同じ `node` と `cli` ですが、利用者が手で `whatnext workbench` を打つと、別に入れた whatnext の版の案内が作られえます。`PATH`、`CLAUDE_CONFIG_DIR`、`WHATNEXT_DEBUG_LOG` も、一覧ではなく作業台の画面のシェルのものになります。
  - `scripts()` のコメントには「動いている一覧と同じ版のものを使わせる」とあり、この方針と食い違います。対策は二つ考えられます。一つは、一覧の起動時に案内のペインのコマンドをサーバのオプション(例: `@wn_guide_cmd`)に置き、`ensureGuide` はそれを使うこと。もう一つは、作り直し自体を頼みごとで一覧に任せることです。
  - ただし DESIGN.md は、つなぐ側で確かめるほうが確実だという理由で後者を採らなかったと書いています。前者なら、その理由を崩さずに版の食い違いを避けられます。
- **`src/cli/workbench.ts:43-51` 頼みごとを書いてから一覧に知らせる処理が 3 か所目になる**
  - 同じ処理が `guide.ts:74-80` と、sh の `@wn_req_sh` にもあります。どちらも `@wn_req_<秒>_<pid>` の形で書いてから SIGUSR2 を送るので、`Tmux` に `request(line)` のような関数として 1 つにまとめられます。`lib/` の契約に足すことになるので、cycle 9 の方針に照らして判断してください。
- **`src/ops/names.ts:12` 頼みごとの名前 `'guide'` が一般的すぎる**
  - いまの頼みごと(`key`、`agentview`、`focus`)とはぶつかりません。ただ `app.ts:1156` は先頭の語だけで分けているので、`guide-refresh` のように目的の分かる名前のほうが、将来ぶつかりにくくなります。

### プライバシー・セキュリティ
- **`lib/tmux/tmux.ts:51` `@wn_guide_died` に案内の画面の末尾 5 行を残している**
  - 案内には、セッションの名前と作業場所のパス(`~/...`)が出ます。それがサーバ全体のオプションに残ります。
  - 残るのは専用の tmux サーバのメモリの中だけで、ソケットに触れるのは同じ利用者だけです。ディスクにも外にも出ないので、問題はないと判断します。
  - 将来、診断のためにこの値をログや issue に貼る流れを作るときは、パスが含まれることに注意してください。
  - シェルへの注入の余地もありません。`capture-pane` の出力は `"$(...)"` の結果として 1 つの引数で渡され、評価し直されないからです。スクリプトの本文も `set -g name body` の引数として置かれ、設定ファイルとして読まれません。
