## まとめ

修正の方向は妥当です。案内のペインを `kill-pane` せずに起動し直すこと、attach の前に `ensureGuide` で作り直すこと、`exec` を1か所だけで付けることの3点は、コミットメッセージにある原因に正しく対応しています。`pane-died` のフックは `run-shell -b` で動くので、`sleep 1` で tmux サーバが止まる心配もありません(`lib/tmux/tmux.ts:179`)。セキュリティ上の問題は見つかりませんでした。tmux のソケットに届くプロセスはもともと何でもできるので、新しい頼みごと `guide` が攻撃面を広げることもありません。

気になる点は、案内のセッションを一覧以外の側でも作るようになったことから生じる、作り手の食い違いです(1)。もう1つは、起動し直しの上限を使い切ったときに、直そうとした「分割が黙って閉じる」症状が形を変えて残ることです(2)。

## 指摘

### 正確性・設計

1. **`whatnext workbench` が作った案内は、版と環境が一覧と違うことがある**(`src/cli/guide.ts:19`)
   - `paneCommand(env, 'guide')` が使う `env.node`、`env.cli`、`PATH`、`CLAUDE_CONFIG_DIR` などは、`whatnext workbench` 自身のプロセスのものです。
   - Ghostty の分割から起動したときは、一覧が渡したコマンドなので node と cli は一覧と一致します。ただし `PATH` などはいつものシェルのものになります。
   - 利用者が別の端末で `whatnext workbench` を手で打った場合、npm で更新した直後(`@wn_newer` が立つ状況)なら、新しい版の案内が古い版の一覧の `@wn_guide` を読みます。
   - `lib/tmux/tmux.ts:21` は「動いている一覧と同じ版のものを使わせる」という方針で、案内を作る側だけがそこから外れます。
   - 改善案は2つあります。一覧が自分の `paneCommand` をサーバのオプション(例:`@wn_guide_cmd`)に置き、workbench 側はそれで作る方法と、DESIGN.md にこの制約を書いておく方法です。
   - DESIGN.md の「作り直した案内のプログラムもそのまま読める」は、同じ版であることを暗に前提にしています。

2. **起動し直しの回数は元に戻らず、使い切ると分割が何も言わずに閉じる**(`lib/tmux/tmux.ts:52-60`)
   - `@wn_respawned` はペインのオプションで、`respawn-pane` してもペインの ID は変わりません。そのため回数は一度も減りません。
   - コメントの意図は「起動してすぐ終わるときに回り続けないため」ですが、実際はペインごとに生涯5回の上限です。長く動かしていると、まばらに5回落ちただけで6回目に `kill-pane` され、セッションが消えます。
   - そのとき作業台の画面のクライアントは wbguide から外れます。tmux はおそらく 0 で終わるので、`whatnext workbench` はエラーを出さずに終わります(未検証)。`exec` で起動しているので分割ごと閉じ、今回直したはずの「開いていた作業台の画面が閉じる」が説明なしで起きます。次に開けば `ensureGuide` で直ります。
   - 改善案は、一定時間(例:30秒)以上動いたら回数を0に戻すか、終わった時刻を残して短い間隔で続いたときだけ数えることです。

3. **attach が失敗したかどうかの判定が、シグナルでの終了を「つなげなかった」と誤って扱う**(`src/cli/workbench.ts:33`)
   - `spawnSync` は、子プロセスがシグナルで終わると `status: null` を返します。`null !== 0` は真なので、tmux のクライアントだけがシグナルで終わり一覧が残っている場合に、一度つながっていても「could not open the workbench screen」と出ます。分割ではキーを待つことにもなります。
   - 改善案は `res.status !== null && res.status !== 0` とするか、`res.signal` を別に扱うことです。
   - コメントの「サーバごと閉じたときに 0 以外」も、実測したことなのかを DESIGN.md か working-with-tmux スキルで確かめておくとよいです。

4. **`@wn_guide_died` は上書きなので、手がかりとして弱い**(`lib/tmux/tmux.ts:51`)
   - DESIGN.md は「なぜ終わったかはまだ分かっていない。その手がかりを残す」と書いていますが、残るのは最後の1回だけです。
   - 5回続けて落ちて畳まれた場合、最初の原因(多くはこれが本命)が消えます。
   - サーバのオプションなので、whatnext を終えると消え、ファイルにも残りません。
   - 原因を調べることが目的なら、`WHATNEXT_DEBUG_LOG` のようなログに追記するか、少なくとも最初の1回を別のオプションに残すほうが目的に合います。

5. **一覧の起動時に `workbenchOptions` を二重に呼ぶ**(`src/cli/list.ts:67`、`src/cli/guide.ts:22`)
   - `ensureGuide` が作ったときは中で `workbenchOptions` を呼び、`startList` も直後にもう一度呼びます。
   - 害はありませんが、セッションがあるとき(前の版から引き継いだとき)に入れ直すためなら、一覧の側だけで呼ぶ形のほうが意図が読み取りやすいです。

6. **頼みごとを送る処理が3か所目の複製になった**(`src/cli/workbench.ts:43-51`)
   - `guide.ts:74-80` と同じ処理(`@wn_req_<秒>_<pid>` に書いて `@wn_pid` に SIGUSR2 を送る)が、`@wn_req_sh` とは別に、TS の中で2つめの複製になりました。
   - キー名の書式を変えると、受け手(`lib/tmux/tmux.ts:250`)と合わせて3か所直すことになります。
   - `Tmux` に `request(line)` のメソッドを持たせるのが自然です。ただし `lib/` の契約(`docs/lib/tmux.md`)を変えることになるので、層1の判断として decision-log に残す扱いになります。

### 並行性

7. **同時に作られたときの扱いは妥当**(`src/cli/guide.ts:21`)
