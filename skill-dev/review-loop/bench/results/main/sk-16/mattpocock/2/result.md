## Standards

**(a) 文書化された規約への違反: なし**
- frontmatter は変わっていないので、README「構成」の決まりに触れるところはありません。
- スクリプトで変わったのはプロンプトの文字列だけです。スクリプトが判定から確かめるのは `VERDICT_SECTIONS` の見出し2つだけなので、テストを足さなくても README「開発」の決まりには反しません。
- 新しい欄「範囲」「再現」は、SKILL.md の欄の一覧と `JUDGE_PROMPT` の出力形式で同じ順に並んでいます。欄の値に使う語(差分の内・差分の外、実行では示せない、対象外)も、プロンプト、SKILL.md、fake で同じです。

**(b) コードの臭いの典型(すべて判断事項)**
1. **欄名がわかりにくい(Mysterious Name)の可能性。** 欄名「範囲」が、`--instruct` で絞る「範囲」や「再現が確かめた範囲」と同じ語です。終了報告の1文の中で、「範囲が『差分の外』」と「レビューされなかった観点と範囲」が別の意味で並んでいます。「差分との関係」や「発生源」に変えれば紛れません。
2. **同じ文の重複(Duplicated Code)の可能性。** 「実行では示せない種類(文書やプロンプトの書き方、外部のサービスの挙動…)」の例が、`JUDGE_PROMPT` と SKILL.md 手順5にほぼ同じ文で入っています。SKILL.md は定義の正を `JUDGE_PROMPT` としているので、片方だけ直すとずれます。
3. **1つの変更が数か所に散る(Shotgun Surgery)の可能性、軽微。** 欄を1つ足すと、プロンプト、SKILL.md、fake の3か所を変えることになります。この結合自体はコメントで明示されています。ただ fake には、分類・起きやすさ・横展開といった既存の欄がもともとありません。そこに範囲と再現だけを足したので、揃え方が中途半端です。

## Spec

**(a) 欠けている要件**
1. **再レビューを回さずに終える経路で、最後の修正を push する手順がありません。**(仕様の行:「再現で確かめた修正だけなら、そのための再レビューは回さない」)
   - これまでは「修正したら手順1に戻る」と、手順1の「毎回 push する」の組み合わせで push されていました。
   - 新しい経路では、修正のあとスクリプトを起動せずに終わるので、修正がローカルに残ったまま終わりえます。終了報告にある「終了時の HEAD」の差とも噛み合いません。
   - 私も差分を見て、該当の記述がないことを確かめました。妥当な指摘です。

**(c) 実装が誤っていそう・曖昧なもの**

2. **「再現しなければ採らない」より実装が広くなっています。**
   - SKILL.md は「実行では示せない」指摘を、コードを追って採ることを認めています。
   - 補完としては妥当です。仕様の文言から読み取れないので、PR の本文に書いておくとよいです。
   - 終了判定とは整合しています。この種の修正は「実行で確かめていない修正」に当たるので、もう1回回します。
3. **「どの修正も、再現が修正前に失敗して修正後に通り」の対象がはっきりしません。**
   - 文字どおりに読むと、同じ回に直した影響が低の指摘やテスト不足(test_gap)も対象に入ります。そうすると毎回もう1回回すことになり、反復を減らすという仕様の意図に反します。
   - 文の前半に「上の基準に当たる指摘を採って直したとき」とあるので、文脈からはそれに限ると読めます。それでも、「その修正のどれも」のように明示したほうが確実です。

**そのほか**
- fake の判定には分類の行がないのに、「再現: 対象外」と書かれています。厳密には矛盾しますが、テストはこの欄を見ないので実害はありません。
- issue にするかを「尋ねる」部分は、答えが返らなければ issue を作らない側に倒れるので、安全です。ただ、別のスキルが親になって呼んだとき、誰に尋ねるのかは書かれていません。
- 求められていない振る舞い(スコープクリープ)は見つかりませんでした。
