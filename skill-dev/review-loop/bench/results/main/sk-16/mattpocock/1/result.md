## Spec

仕様の4項目と a1bccb6 の内容は、どちらも SKILL.md と `JUDGE_PROMPT` に入っています。「範囲」「再現」の欄は2か所で中身も順も一致しています。差分の外の指摘の扱い(直さない、継続の理由にしない、終了時に報告して issue にするか尋ねる)も漏れなく入っています。

1. **(b) 頼まれていない条件の追加**(`SKILL.md:128`)
   - 仕様の行は「再現で確かめた修正だけなら、そのための再レビューは回さない」です。
   - 実装はこれに2つの条件を足しています。「既存のテストも通っている」と「修正が大きく…挙動を変えているなら回す」です。
   - どちらも再レビューを増やす方向なので、抜け道にはなりません。
   - ただ「修正が大きく」には基準がなく、判断が揺れます。また、仕様の「回さない」が「回さずに終えてよい」と、してもよいことに弱まっています。
2. **(c) 「どの修正も」がどこまでを指すか読めない**(`SKILL.md:128`)
   - 前半は「上の基準に当たる指摘を採って直したとき」と対象を絞っています。後半の「実行で確かめていない修正が1つでもあれば…回す」は、基準に当たらない修正まで含むのかが読めません。
   - 含むと読むと、defect でない低影響の修正を1つ混ぜるだけで毎回もう1回回すことになります。仕様の「そのための再レビュー」より広がります。
3. **(a)/(c) 「実行では示せない」が抜け道になる余地**
   - 仕様の「再現しなければ採らない」に対し、実装にはコードを追うだけで採否を決める第3の扱いがあります。
   - 歯止めはあります。手順5の「手段がないときだけ」と、終了の判断の「実行で確かめていない修正が1つでもあれば…回す」です。
   - ただ、判定役が「実行では示せない」と書いたときに、親がそれをそのまま信じないよう求める文がありません。「判定の手順が合っていなければ組み直す」は再現の手順についての文で、この分類には触れていません。
4. **(a) 軽微**: 冒頭の親の責任一覧(`SKILL.md:19`「利用者とのやり取り」)に、issue にするかを尋ねることが入っていません。「終了時の報告」に含まれると読めば足ります。

**まとめ**: Standards は明文化された規約への違反が0件、smell が2件です。一番重いのは「実行では示せない」の例示が2か所に重なっている点です。Spec は4件で、一番重いのは `SKILL.md:128` の再レビューの条件です。「どの修正も」の範囲が読めないことと、仕様にない条件が足されたことの2つが重なっています。

直すなら、128行の「どの修正も」を「上の基準に当たる指摘の修正がどれも」と書いて範囲をはっきりさせるのが先だと考えます。もう1つ、検討の材料として問いを置きます。「修正が大きく」の但し書きは本当に要るでしょうか。仕様の狙いは反復を減らすことです。基準のない但し書きは、結局ほぼ毎回「回す」に倒れて、その狙いを打ち消すおそれがあります。
