`git diff main...HEAD` の3コミット分(SKILL.md、`review_loop.py` の `JUDGE_PROMPT`、偽の claude)をレビューしました。方向性は妥当です。読んだだけの指摘を仮説として扱い、再現を採否と終了判断の根拠にする。差分の外の指摘を PR に混ぜない。どちらも、コミットメッセージにある「反復が伸び、PR が目的の外へ膨らむ」への対策として筋が通っています。

その一方で、再現の手順そのものの安全性と、再現が誤って失敗したときに何が起きるかの扱いが抜けています。重い順に挙げます。

## セキュリティ / プライバシー

- **`skills/review-loop/SKILL.md:134` 差分の外の指摘を `gh issue create` で公開するとき、公開範囲と脆弱性の扱いに触れていない**
  - issue の本文には「場所、影響と起きやすさ、起きる操作の順」を書く決まりです。差分の外の指摘には security-review の指摘も含まれます。公開リポジトリだと、まだ直っていない脆弱性の再現手順をそのまま公開することになります。
  - 利用者は issue にすると承認するだけで、本文の中身とリポジトリの公開範囲を意識しているとは限りません。
  - 提案: 影響が高のものや security 観点のものは、尋ねるときにリポジトリが public かを添える。そのような指摘は private vulnerability reporting(Security Advisory)を勧めるか、本文から再現手順を省く、と明記する。

- **`SKILL.md:99` と `:101` 影響が高の defect を「実際に実行して」再現させると、取り返しのつかない操作を本物の環境で起こしうる**
  - 影響が高の定義(`review_loop.py:854` 付近)は「データの消失、消すべきでないものを消す」です。これは必ず再現の対象になります。
  - 例: housekeeping のようなブランチや worktree を消すスキルで「消すべきでないブランチを消す」を指摘どおりに実行すると、利用者の実際のブランチが消えます。
  - 再現の手順は判定役(LLM)が書いたものなので、親がそのまま実行するおそれもあります。
  - 提案: 影響が高の再現は、使い捨てのリポジトリ、一時ディレクトリ、偽のコマンド(このリポジトリの `skill-dev/review-loop/fakes` のようなもの)で隔離して行い、本物の状態を変える手順はそのまま実行しない、と書く。

## 正確性 / 設計

- **`SKILL.md:102` と `:126` 再現が一度うまくいかなかっただけで、影響が高の指摘が継続の理由から外れる**
  - 変更前は、影響が高の指摘は起きやすさに関係なく継続の理由でした。今は「再現を試みたが起きなかった」だけで採らなくなり、影響の段階に関係なく終了を妨げません。
  - 再現を組み立てるのは、早く終えたい側の親です。手順の誤り(前提の状態を作っていない、別の経路を叩いている)で再現が失敗しても、見分ける仕組みがありません。確証バイアスが、読むだけの過大評価から、再現が失敗したことによる過小評価へ移るだけになります。
  - 提案: 影響が高のものだけは、再現しなかったときに試した手順を利用者への報告に必ず含める。または、「起きなかった」と判断する前に、判定の手順と自分で組み直した手順の少なくとも2通りを試すことを求める。

- **`SKILL.md:107` ベースのコードで確かめる方法を書いていない。親が PR の worktree を checkout しうる**
  - 手順5は修正の途中なので、作業ツリーに未コミットの変更がある可能性が高い段階です。そこで「PR のベースのコードで同じことが起きるか確かめる」と言われると、`git checkout main` や `git stash` を使いがちです。変更が失われる、戻し忘れて次の起動の前提(手順1のクリーンな状態)を壊す、といったことが起きます。
  - 提案: `git worktree add <一時ディレクトリ> <base>` で別の worktree を作って確かめる、または `git show <base>:<path>` で読む、と書く。

- **`review_loop.py:863` 判定役に PR のベースを渡さずに範囲を判定させている**
  - `run_judge`(`review_loop.py:905-927`)の入力はレビューの出力と拒否だけで、ベースのブランチ名も SHA も渡していません。
  - 範囲を判定するには、判定役が自分で `gh pr view --json baseRefName` や `git show`、`git diff` を叩く必要があります。これらが許可ルールにないと、`watch_denials` が `permission_denied` で試行全体を止めます。止まるのは今回の変更で新しく生じうる経路です。
  - 確かめられなければ「差分の内」にする、という倒し方は安全側で妥当です。ただ、失敗は止まる形で起きます。
  - 提案: スクリプトがすでに取っている PR の情報に `baseRefOid` を足し、プロンプトに埋める。そうすれば判定役が探す手間も、権限の拒否も避けられます。

- **`SKILL.md:128` 再現で確かめた修正だけなら回さずに終えてよい、という基準は、修正が持ち込んだ新しい defect を誰にも見せずに終えうる**
  - 括弧書きの「修正が大きく…なら回す」で手当てはしてあります。それでも「大きい」の判断は親に任されたままです。
  - 回さない終わり方では、最後に判定を受けた SHA と HEAD の間に差が残ります。この差は `:132` の報告項目にすでにあります。そこで「回さずに終えた修正の一覧と、それぞれを確かめたテスト」を明示的に報告させると、利用者が判断できます。重大度は中〜低です。

## 軽微

- **`review_loop.py:879` 出力の形の「範囲」の欄に、確かめられなかったときの書き場所がない**
  - `:863` は、確かめられなければ「差分の内」とし、確かめられなかったと書く、と求めています。一方で出力の形は `差分の内 / 差分の外。<差分の外なら、そう判断した根拠>` です。差分の内に注記を書く場所がないので、注記が落ちやすくなります。
  - 提案: `差分の内。<確かめられなかったならその旨>` のように形にも書く。親は `:107` で範囲を自分で決め直すので、この注記が手がかりになります。

- **`skill-dev/review-loop/fakes/claude:100` 偽の判定に範囲と再現の欄を足したが、テストは何も確かめていない**
  - スクリプトが見るのは `VERDICT_SECTIONS` の見出しだけなので、挙動は変わりません。偽の判定を実際の形に揃えておく意味はあります。
  - ただ、もともとの偽の判定には「分類」の欄がありません。揃えるなら「分類: other」なども足して、`JUDGE_PROMPT` の形と一致させるとよいです。

## 確かめていない点

- 3件目の再現の誤り(手順の取り違えで重大な指摘が落ちる)と5件目の権限の拒否は、コードと文書から推論したもので、実際には動かしていません。権限の拒否が起きるかどうかは、判定役の子に効く許可ルール次第です。
- 判断を委ねたい問い: 差分の外を一律に直さない方針は、PR がまさにその行を書き換えている場合(PR の前からある不具合が、PR が触った関数の中にある)にも適用しますか。その場合だけは直すほうが自然です。差分の外にする基準に「PR が変えた行そのものではない」を含めるかどうか、検討の余地があります。
