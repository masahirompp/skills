## 正確性

- **`skills/review-loop/SKILL.md:118` 手順5の「修正したら手順1に戻る。」が、新しい終了の基準と食い違う**
  - `:128` では「再現が修正前に失敗して修正後に通り、既存テストも通るなら、回さずに終えてよい」としています。一方、手順5の末尾は無条件に手順1へ戻す書き方のままです。
  - 手順5を順に読んだ親は、再現で確かめた修正でももう1回回します。この PR が減らしたかった反復が減りません。
  - 案: 「修正したら『終了の判断』に照らし、続けるなら手順1に戻る」のように条件を付ける。

- **`skills/review-loop/SKILL.md:102-103` 「再現を試みたが起きなかった」と「実行では示せない」の境目が、競合やタイミングの指摘ではっきりしない**
  - 例として、親が競合状態のテストを数回回したが当たらなかった場合を考えます。`:102` に従えば採りません。`:126` により継続の理由にもならず、影響が高でも落ちます。
  - `:103` は「狙って起こせないタイミング」を示せない側に置いています。しかし「試したが起きなかった」をどちらに数えるかは書かれていません。
  - 確率的に起きる問題では、1回起きなかったことは反証になりません。並行性の指摘ほど、この経路で落ちやすくなっています。
  - 案: 「起きなかった」として採らないのは、決定的に再現できる種類に限る。タイミングに依存するものは、試して起きなくても `:103` の扱い(コードで追って決める)にする。

## 設計

- **`skills/review-loop/SKILL.md:107` と `:126` 採るときと捨てるときで、確かめる強さが釣り合っていない**
  - 採る側は「再現しなければ採らない」と実行での確認を求めます。一方、「差分の外」で捨てる側は、判定役が読んだだけの判断を受け入れます。親が確かめ直すのも「疑わしければ」だけです。
  - 判定役が誤って「差分の外」とした影響が高の defect(データ消失、セキュリティなど)は、確かめられないまま修正の対象からも継続の理由からも外れます。報告と issue の候補には残りますが、PR はそのまま進みます。
  - `review_loop.py:863` の「確かめられなければ差分の内」という倒し方は妥当です。ただ、判定役が自信を持って誤ったときは効きません。
  - 案: 影響が高で「差分の外」とされた指摘は、ベース(`main`)のコードで同じことが起きるのを親が必ず確かめる。

- **`skills/review-loop/SKILL.md:102, 126` 再現を試すのが、早く終えたい親自身である**
  - 再現しなければ指摘は採られず、継続の理由も消えます。直す人が、反復を減らす方向に働く判断をすべて受け持つ形です。
  - `:102` が試した手順と結果を残すよう求めているので、あとから点検はできます。ただし、どこに残すかは書かれていません。次の反復に伝える経路は `:113-116` のコードコメントと PR 本文だけです。
  - 「試したが起きなかった」をそこに書く対象として明記しないと、同じ指摘が毎回出ては、毎回同じ再現を試すことになります。
  - 案: 終了時の報告(`:132`)に「再現を試みて起きなかった指摘と、その手順」を項目として足す。今は「残った指摘(採らなかったものはその理由も)」に含まれると読める程度です。

- **`skills/review-loop/SKILL.md:128` 再レビューを省いた修正は、観点別のレビューを一度も受けない**
  - 再現テストと既存テストが通っても、確かめられるのは指摘された挙動だけです。修正が持ち込んだ別の問題(セキュリティ、命名、横展開の漏れ)は見られません。
  - 括弧書きの「修正が大きく…なら回す」が歯止めですが、「大きい」の基準は親の判断に任されています。
  - 最後に判定を受けた SHA と HEAD の差は報告されます(`:132`)。利用者は気づけるので、致命的ではありません。それでも、「回さずに終えた修正」を報告で明示的に分けると判断しやすくなります。

## セキュリティ / プライバシー

- **`skills/review-loop/SKILL.md:134` 差分の外の脆弱性を、公開リポジトリの通常の issue として作りうる**
  - 本文に「場所、影響と起きやすさ、起きる操作の順」を書く決まりです。そのため、影響が高のセキュリティ指摘では、悪用の手順を公開の issue に書くことになります。
  - 利用者の承認が前提なのは良い設計です。ただ、尋ねる時点で「公開される」ことと「別の経路がある」ことが利用者に示されません。
  - 案: セキュリティに当たる指摘は、尋ねるときに公開リポジトリかどうかを添える。そのうえで、GitHub の private vulnerability reporting(security advisory)を選べるようにするか、本文から再現の手順を省く。

- **`skills/review-loop/scripts/review_loop.py:865` 「あなたは実行して確かめないので」が事実として書かれているが、制約にはなっていない**
  - `JUDGE_CONSTRAINT`(`:81`)が禁じるのは作業ツリーを変えることだけで、判定役は実行もできます。
  - 今の文は「実行しない」という前提の説明で、実害は小さいです。ただ、判定役が実行して確かめた場合でも、SKILL.md `:93` は「実行して確かめてはいない」と言い切っています。
  - 案: 「実行して確かめた場合は、その結果を根拠に書く」とするか、判定役に実行しないよう明示する。どちらに倒すかを決めておくと、文書と挙動が揃います。
