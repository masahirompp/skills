## Standards

**(a) 文書化された規約に照らした判断**
1. **同じ定義を2か所に書いている**: SKILL.md 自身が「範囲、再現の定義は `JUDGE_PROMPT` が正」と書いています。それなのに、手順4の箇条(SKILL.md:86)と手順5の文が、`JUDGE_PROMPT` の文をほぼそのまま写しています。写しているのは次の2つです。
   - 「PR の目的に含まれること(PR の本文やコミットが、直す・実現すると述べていること)の直し残しは…差分の内」
   - 「文書やプロンプトの書き方、外部のサービスの挙動、狙って起こせないタイミングなど」の列挙

   影響・起きやすさの箇条も元から要約しているので、要約までは慣習として許されていると見られます。問題は文の丸写しです。
2. **簡潔さ**(skill-authoring best practices): 長くなった箇所が3つあります。
   - 手順5の再現の進め方
   - 終了時の issue 作成の段落
   - 継続の判断の箇条(1つの箇条に条件が多すぎる)

   SKILL.md は156行で、目安の500行は下回っています。references/ に移すのは任意です。

**(b) baseline smell(どれも判断を要するもの)**
- **Duplicated Code の疑い**: (a)1 と同じものです。隔離して再現する規則も、SKILL.md:101 と `JUDGE_PROMPT` の両方にあります。
- **Mysterious Name の疑い(用語の衝突)**: 新しい「範囲」は差分の内か外かの意味です。一方、既存の「範囲」は `--instruct` で範囲を絞る意味で使われています(`JUDGE_PROMPT`:850, 894、SKILL.md の終了時の報告)。終了時の報告の段落では、両方の意味が同じ段落に並びます。「差分との関係」など別の語にする案があります。
- **Divergent Change の疑い**: コミットの題は「再現で確かめてから直す」です。そこに、差分の外の扱い、`gh issue create` の手順、公開リポジトリでの悪用手順の扱いまで入っています。差分の外の指摘は再現せずに外すので両者に関係はありますが、分ける余地はあります。
- **Speculative Generality の疑い(弱い)**: `fakes/claude` に範囲と再現の欄を足しましたが、test.py も review_loop.py もこの欄を読みません。しかも偽の判定には元から分類の欄がないのに「再現: 対象外」だけを足しているので、形が揃いきっていません。

用語の一貫性(継続の理由、横展開、観点の欠落、影響の段階)は保たれています。

## Spec

仕様はコミットメッセージ dc3a218 の本文です。issue はありません。

**(a) 欠けている、または部分的な要件**
- 大きな欠けはありません。仕様の1〜3、判定役の2欄、「確かめられなければ差分の内に倒す」はすべて入っています。
- 確かでない点が1つあります。仕様の「実行で確かめていない修正が1つでもあれば、これまでどおり回す」は、SKILL.md:131 では「継続の理由になる指摘を採って直したとき」の中に置かれています。継続の理由にならない指摘を任意で直し、それを実行で確かめていないときに回すのかが読み取れません。仕様の側も曖昧です。

**(b) 求められていない振る舞い(スコープの広がり)**
- SKILL.md:116: 公開リポジトリなら、PR 本文に悪用の手順を書かない。
- SKILL.md:136: issue を作る前の重複検索、セキュリティの指摘を公開にするかの確認、反復をまたぐ指摘を1件にまとめる、影響が高のものを先頭に置く。
- SKILL.md:99 と `JUDGE_PROMPT`:863: PR の目的の直し残しは、PR の前から起きていても差分の内とする例外。
- SKILL.md:99: 影響が高の指摘を差分の外とするときは、PR のベースで確かめるのを必須にしている。仕様は「確かめて決め直せる」までです。
- SKILL.md:101: PR が意図して変えた挙動への指摘は、再現の前に却下する。
- SKILL.md:103: 再現は隔離した場所でだけ行う。別の OS など、条件を作れないときは実行では示せないとして扱う。
- 横展開の候補のうち差分の外になるものも、終了時の報告に載せる。

どれも妥当そうですが、コミットの「変更」節に書かれていません。残すなら本文に書き足すべきです。

**(c) 実装が誤っていそうな点**
1. 仕様は「修正が大きく、再現が確かめた範囲を超えて挙動を変えているなら回す」です。SKILL.md:131 は「修正の大きさに関係なく回す」で、「大きく」の条件を落としています。仕様より回す範囲が広がります。意図した変更なら、仕様の文言のほうを直すべきです。
2. 終了の基準は分類を問いませんが、再現が必須なのは defect だけです。test_gap や other で影響が高の指摘は、読んだだけの仮説のまま継続の理由になります。仕様の範囲内ですが、反復を減らすという背景の目的には効きません。
3. SKILL.md と `JUDGE_PROMPT` の食い違いは見つかりませんでした。

---

**まとめ**: Standards は4件で、どれも判断を要するものです。最も重いのは、「`JUDGE_PROMPT` が正」としながら範囲・再現の定義を SKILL.md に丸写ししている点です。Spec は8件です。最も重いのは、再レビューの条件で仕様の「修正が大きく」が落ち、仕様より回す範囲が広がっている点です。

**検討のための問い**:
- 範囲と再現の定義の丸写しは、`JUDGE_PROMPT` を正とする方針と両立しますか。SKILL.md を要約にとどめるか、`JUDGE_PROMPT` への参照に寄せるかで、Standards の1件目と Duplicated Code はまとめて片付きます。
- Spec の (b) のうち、悪用手順の扱いと issue 作成の細則は、この PR の目的(反復を減らす)に必要ですか。コミット本文は PR #14 が +234/-55 行に膨らんだことを問題にしています。この PR が同じ形で膨らんでいないかは確かめる価値があります。
- 「修正の大きさに関係なく」は意図した厳しさですか。そうなら仕様の文言を直し、そうでないなら SKILL.md を直します。
