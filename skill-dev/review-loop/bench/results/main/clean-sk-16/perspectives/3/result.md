## 設計

- **`skills/review-loop/SKILL.md:106`, `:128`: 再現を1回試して起きなければ、影響が高い指摘でも捨てられる**
  - 再現の手順を組むのは、ループを早く終えたい親自身です。手順が間違っていても、影響が高い指摘が1回で外れて継続の理由から消えます。
  - 「読んだだけの仮説で採る」という偏りを、「再現が下手なら捨てる」という逆向きの偏りに置き換えただけになりかねません。
  - `:103` で「環境が違う条件で起きなかったものは数えない」と防いでいますが、それ以外の手順の誤りには手当てがありません。
  - 提案: 影響が高い指摘だけは、再現しなくても即座に捨てず、試した手順を添えて利用者に判断を委ねる。または判定役の「再現」の手順と自分の手順がどこで違うかを書かせる。

- **`skills/review-loop/SKILL.md:130`: 「修正した箇所を通る既存のテスト」があるかを、親が読むだけで判断している**
  - ここは再レビューを省いてよいかを決める条件です。
  - この PR は「読んだだけの判断は仮説」という前提に立っていますが、この条件だけはカバレッジなどで確かめず、親が読んで決めます。親には終えたい動機があるので、判断が甘くなりやすい箇所です。
  - 提案: テストが通ることを実行で確かめた範囲だけを根拠にする。判断できなければ回す側に倒す、と明記する。

- **`skills/review-loop/SKILL.md:107`, `:130`: このリポジトリでは反復の短縮がほとんど効かない見込み**
  - 主な成果物は SKILL.md とプロンプトなので、指摘の多くは「実行では示せない」に入ります。
  - `:130` は「実行で確かめていない修正が1つでもあれば回す」ので、文書の修正が混ざるたびに今までどおり再レビューになります。
  - 実行で効くのは #14 のような、スクリプトそのものを直す PR に限られそうです。コミットメッセージの「確かめていないこと」に、この見通しを足すと測るときの比較軸になります。

- **`skills/review-loop/SKILL.md:130`: 「実行で確かめていない修正が1つでもあれば回す」がどの修正を指すのか曖昧**
  - 文の主語は「継続の理由になる指摘を採って直したとき」です。一方で `:129` の影響が低い修正(命名やコメント)も同じ反復に入ります。
  - それらも「1つでも」に入ると読めば、ほぼ毎回回すことになります。
  - 提案: 対象は「継続の理由になる指摘への修正」に限ると明記する。また、この箇目は1文に条件が5つ以上入っているので、小さな箇目に分けた方が LLM も読み違えにくいです。

## セキュリティ / プライバシー

- **`skills/review-loop/SKILL.md:136`: issue を作る先のリポジトリを決めていない**
  - fork から上流へ出した PR だと、`gh issue create` が上流のリポジトリに作られることがあります(`gh repo set-default` 次第)。上流は利用者の持ち物ではありません。
  - 利用者に確認はとりますが、どこへ作るかは確認に表れません。
  - 提案: `--repo <PR のベースのリポジトリ>` を明示し、作る先を尋ねるときに添える。

- **`skills/review-loop/SKILL.md:99`, `:136`: 範囲の外のセキュリティの指摘が、直されずに残りやすくなる**
  - この PR の方針から生じる結果で、公開リポジトリで悪用の手順を書かない配慮は `:116` と `:136` にあります。
  - ただ、ループの中では直さないので、同じ指摘が反復ごとに出るはずです。判定役が「再指摘」と見分ける手がかりは PR 本文とコードコメントだけで、公開リポジトリでは手順を書けないので見分けられません。
  - トークンを無駄にするだけで実害は小さいですが、その範囲の外の指摘を PR 本文に「範囲の外として報告済み」とだけ書く、と決めておくと蒸し返しを抑えられます。

## 並行性

- 指摘はありません。再現するのは手順5、つまりスクリプトの実行が終わったあとです。再現に使ったファイルを作業ツリーに残さないこと(`:103`)と、スクリプトが起動時に作業ツリーがクリーンか確かめることがかみ合っていて、実行中のレビュー役と競合する経路はありません。

## 全体

範囲の外を直さないことと、再現できない指摘を採らないことは、#14 で修正が膨らんだ原因に正面から効く、筋のよい変更です。一方で、ループを終える判断の材料がほとんど親の自己申告になっています。上の最初の2点(再現できなかった指摘を即座に捨てる点と、テストがあるかを読んで判断する点)は、親の判断が誤ったときに影響が高い不具合を見逃す側に偏ります。実際の PR で回して確かめるときは、反復回数だけでなく、捨てた指摘があとで本当の不具合だと分かった件数も記録すると、この偏りを測れます。
