## 設計 / 正確性

- **`skills/review-loop/SKILL.md:106` と `:128` 再現できなかったことを、却下の根拠として強く扱いすぎている**
  - 再現を試みて起きなければ、影響が高でも採らず、継続の理由にもしない、という規則です。
  - ところが再現を組むのは、その PR を書いた親です。テストの組み方が甘くても、指摘を消す方向に働きます。「起きなかった」が示すのは、その手順では起きなかったことだけです。
  - 別の OS などの条件は `:103` で除外してありますが、手順そのものの質を確かめる仕組みはありません。
  - 失敗の例: 「無い ref があると全ブランチが delete になる」のような高影響の指摘で、入力の作り方を誤ったテストが通ってしまうと、却下されて終わります。以前の規則なら、少なくとも次の反復でもう一度見られていました。
  - 案: 影響が高のものだけは、起きなかったときに試した手順を次の反復の判定役に渡します(コードコメントか PR 本文で)。または終了時の報告で「再現できずに却下した高影響の指摘」を別の項目にして、利用者の目に触れるようにします。

- **`SKILL.md:130` 「回さずに終えてよい」かどうかを、修正した本人が判定している**
  - 条件のうち「修正した箇所を通る既存のテスト」があるかどうかは、カバレッジを測らないので親の自己申告です。
  - 「再現が確かめた経路の外の挙動も変えているか」も同じく本人が判断します。
  - 最後の修正がレビューされない経路を開く判断が、確証バイアスに最も弱い当事者に任されています。
  - `:133` の「最後に判定を受けた SHA と HEAD の差」を報告に含めてあるので、利用者には見えます。それでも、少なくとも「回さずに終えた」こと自体を報告項目として明記するべきです。

- **`SKILL.md:99` 「再現もしない」と「ベースで確かめてから外す」が両立しない**
  - 同じ段落で、差分の外の指摘は「再現もしない」としつつ、影響が高なら「PR のベースのコードで同じことが起きるかを確かめてから外す」としています。
  - 「確かめる」が、実行するのか読むだけなのかが書かれていません。実行するなら、それはベースでの再現です。
  - 解釈が割れると、高影響の指摘を読んだだけで差分の外として外せてしまいます。
  - 案: 「影響が高なら、`:103` の隔離の規則に従ってベースで再現を試み、起きたら差分の外とする」と書き切ります。

- **`SKILL.md:103` ベースのコードを取り出す方法が限定されていない**
  - 「一時ディレクトリへの取り出し」と書くだけで、方法は決めていません。
  - `git worktree add` を使うと、`.git` の worktree 一覧という共有された状態を変えます。housekeeping スキルの掃除の対象にもなり得ます。
  - 作業ツリーを変えない、という趣旨に合わせて、`git archive <base> | tar -x -C <tmp>` や `git show` に限ると書くほうが安全です。

- **`SKILL.md:105` 回帰テストを残すと、PR を膨らませない狙いとぶつかる**
  - 再現に書いたテストは、置き場があれば残すことになっています。テストを足せば差分が増え、次の反復でそのテストへの指摘(test_gap、style)が出ます。
  - コミットが掲げた「PR が目的の外へ膨らむ」問題を、一部もう一度作ることになります。
  - 規則として誤りではありませんが、「残したテストへの影響が低の指摘は継続の理由にしない」と明記しておくと、振動を防げます。

- **効果の見込み(コミットの「確かめていないこと」に関連)**
  - このリポジトリの修正の多くは SKILL.md やプロンプトで、`:107` の「実行では示せない」に当たります。
  - そうなると `:130` の「実行で確かめていない修正が1つでもあれば回す」に該当するので、反復は減りません。
  - 減るのは、#14 のようにシェルや Python に再現テストを書ける PR に限られる見込みです。実測するときは、PR の種類で分けて比べないと、効果を取り違えます。

## セキュリティ

- **`SKILL.md:99` と `:128` 差分の外の高影響のセキュリティ指摘が、直されずに残る**

  - `verdict.md` はローカルの一時ディレクトリにしか残らず、状態コメントにも載らないので、手順が外に漏れる経路もありません。問題なしです。
