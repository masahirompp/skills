## 正確性

- **`skills/review-loop/SKILL.md:106` と `:128`**: 再現が1回起きなかっただけで、影響が「高」の指摘でも採らず、継続の理由からも外れます。
  - この変更の前提は「判定役の指摘は仮説」です。そうであれば、判定役が書いた「再現」の手順も同じく仮説です。手順が合わなかったことと、不具合がないことは区別できません。
  - 起きなかったときに、親がそれ以上の手を打つ決まりはありません。「手順を組み直す」(:101)は努力目標にとどまり、何回試すか、手順の誤りを疑ったかを確かめる仕組みもありません。
  - 例: データの消失のように、特定の操作を組み合わせたときだけ起きる指摘を考えます。親が手順を1つ試して起きなければ、それで採らないことが確定し、次の反復でも継続の理由になりません。
  - 提案: 影響が「高」のものに限り、「起きなかった」で外すには、試した手順が指摘の起きる操作の順を全て辿ったことを条件にします。外したら終了時の報告に「再現できず却下(高)」として必ず載せます。今の :134 の「採らなかったものはその理由も」では、ほかの却下に埋もれます。

- **`skills/review-loop/SKILL.md:99`**: 「差分の外の指摘は再現もしない」の直後に「影響が高の指摘を差分の外として外すときは、ベースのコードで同じことが起きるかを確かめてから外す」とあります。
  - この「確かめる」が、実行のことか、コードを読むことかが書かれていません。前の文の「再現もしない」と並ぶと、読むだけで十分と取れます。
  - 範囲の判定は、どの指摘を直さないかを決める一番効く分かれ道です。ここが読むだけで済むと、「仮説を確かめて採る」という方針が、外す側には効きません。
  - 提案: 高の指摘については、ベースのコードで同じ再現を実行して確かめる、と明記します。示せない種類なら、:107 の扱いに合わせます。

- **`skills/review-loop/scripts/review_loop.py:863`(`SKILL.md:86` も同じ)**: 範囲の基準が「PR の前から**同じように**起きるか」です。
  - PR の前からある不具合を、PR の変更が「普通の使い方」で起きるようにした場合が扱えません。たとえば、使われていなかった経路を PR が既定の経路にしたときです。
  - 判定役が「ベースでも同じ操作の順で起きる」と根拠を書けば差分の外になり、直されません。
  - 提案: 起きやすさや影響の段階を PR が上げた場合は差分の内とする、と一文を足します。

- **`skills/review-loop/SKILL.md:130`**: 「実行で確かめていない修正が1つでもあれば、もう1回回す」の「修正」が何を指すかが曖昧です。
  - 文頭の「継続の理由になる指摘を採って直したとき」に限るなら、影響が低い指摘の修正や命名の修正は対象外になります。
  - 一方で文だけを読むと、全ての修正が対象とも取れます。そう読まれると、命名の修正1つで反復が1回増え、この PR の目的(反復を減らす)と逆になります。
  - 提案: 「継続の理由になる指摘の修正のうち」と、文の中で範囲を限ります。

## 設計

- **`skills/review-loop/SKILL.md:130`**: 再レビューを省くと、修正の差分を誰も独立に読まないまま終わります。
  - 再レビューを省く条件は、親が自分で書いたテストが修正の前に失敗し、修正の後に通ることです。修正もテストも同じ親が書いており、修正が新しく持ち込んだ不具合(テストが見ていない側の影響)は、この条件では捕まりません。
  - 「経路の外の挙動も変えているなら回す」という判断も、親が自分で下します。
  - 終了時の報告に「最後に判定を受けた SHA と HEAD の差」はあるので、利用者には見えます。コミットメッセージの「確かめていないこと」にもこの点は挙がっていません。
  - 実際に回すときは、省いた回数と、省いた修正の行数を状態コメントか報告に残すと、後で効果を測れます。

- **`skills/review-loop/SKILL.md:99` と `:136`**: 差分の外の指摘は、PR 本文にもコードコメントにも残す決まりがありません。
  - 判定役は過去の判断を PR 本文とコードコメントからしか知りません(:847、:120)。差分の外の指摘は毎回の判定に「再指摘: なし」で出続けることになります。
  - 継続の理由にはならないので、ループは止まります。ただ、親が毎回範囲を確かめ直す手間と入力トークンがかかり、「反復を減らす」狙いを一部打ち消します。
  - 提案: 差分の外として外した指摘を、PR 本文に1行ずつ書く決まりにします。これで判定役が再指摘として見分けられます。

- **`skill-dev/review-loop/fakes/claude:100`**: 偽の判定に `範囲` と `再現: 対象外` を足しましたが、`分類` の行がありません(これは前からです)。
  - `JUDGE_PROMPT` の決まりでは、`対象外` は defect 以外の分類で書くものです。分類がないまま `対象外` が並び、例として意味が通りません。
  - テストは見出ししか見ないので無害ですが、合わせるなら `- 分類: style` などを足します。

## 妥当だと考える点

- 範囲の判定に迷ったら「差分の内」に倒す既定(:863)
- issue を作るのは利用者が選んだものだけにし、作る前に重複を探すこと(:136)
- 判定役が作業ツリーを変えられないことに合わせて、実行で確かめるのを親の受け持ちにしたこと

検討いただきたいのは1点です。この変更の効き目は、親が「再現を試みたが起きなかった」と「差分の外」をどれだけ正しく使えるかにほぼかかっています。どちらも、外す方向に倒れたときの損失(高の不具合を見逃す)が大きく、外さない方向に倒れたときの損失(反復が1回増える)は小さい判断です。反復とトークンを減らす効果を測るときは、外した指摘のうち後で本当の不具合と分かったものの数も一緒に数えないと、片側しか見えません。
