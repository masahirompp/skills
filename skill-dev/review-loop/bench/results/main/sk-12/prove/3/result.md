## 題: 判定役が複数ターン回ると、後ろの雑談や更新前の判定まで verdict に入る

`run_judge` は、つないだテキストのうち最初の見出しより前だけを捨て、それより後ろは全部残します。そのため次の2つが起きます。

- 判定のあとに出た短い文(コミットメッセージが例に挙げる「変わりません」型)が、`## 競合` の節の中身として残る。
- 判定役が判定を出し直すと、`## 指摘` が2つ並ぶ。更新前の F1 と更新後の F1・F2 が同じ番号で両方残るので、親はどちらに従えばよいか決められない。

判定役も、コードを読んで確かめるためにツールやサブエージェントを使えます(`JUDGE_PROMPT` の「コードを読んで確かめ」)。レビュー役と同じく、ターンを複数回すことはありえます。

### 実行したコマンド

`scratch/bin/claude` は判定役の偽物で、`SCRATCH_JUDGE` の値に応じて result の行を複数出します。`scratch/judge_repro.py` は、本物の `review_loop.run_judge` を呼んで、戻り値(`verdict.md` に書かれるもの)を表示します。

```
for m in trailing revised; do echo "=== $m"; SCRATCH_JUDGE=$m python3 -I scratch/judge_repro.py skills/review-loop/scripts; done
```

偽物が出す行は次のとおりです。
- `trailing`: 「検証をバックグラウンドで実行しています」→ 判定 V →「前のメッセージの内容から変わりません」
- `revised`: 判定 V →「検証が終わったので判定を更新します。」+ 更新した判定 V2

### 出力

```
=== trailing
## 指摘

### F1: s
- 観点: code-review

## 競合

なし

前のメッセージの内容から変わりません
----- ## 指摘 の数: 1
=== revised
## 指摘

### F1: s
- 観点: code-review

## 競合

なし

検証が終わったので判定を更新します。

## 指摘

### F1: s(確認後に修正)
- 観点: code-review

### F2: t

## 競合

なし
----- ## 指摘 の数: 2
```

### 出るべきだった出力

既存テストの「判定役の result の行が複数でも、つないだテキストで見出しを確かめ、前置きは落とす」が示す意図は、`JUDGE_PROMPT` の形の判定が1つだけ返ることです。

- `trailing`: `## 競合\n\nなし` で終わり、「前のメッセージの内容から変わりません」は含まない。
- `revised`: 最後の判定だけが返る(`## 指摘` は1つ。`F1: s(確認後に修正)` と `F2: t`)。

main と比べると次のとおりです。main は `--output-format json` で最後の result だけを使っていました。
- `trailing`: main では「判定の見出しがない」という `no_output` で、はっきり失敗していた。今は失敗せず、余計な文が混ざったまま成功する。
- `revised`: main ではきれいな V2 が返っていた(最後の result の行が判定役の最終出力だという前提での推定)。今は判定が2つ並ぶ。

レビュー役の出力に途中経過が混ざることは、コミットメッセージが「読む側が読み飛ばせる」として受け入れています。しかし判定は、親が直す範囲を決める最終成果物です。その点で、レビュー役と同じ扱いを当てはめるのは妥当でないと考えます。直し方の候補は2つあります。見出しを含む result の行のうち最後のものだけを判定として使う方法と、判定役だけは最後の行を使い続ける方法です。どちらを採るかは利用者の判断です。
