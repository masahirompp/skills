## 正確性・設計(重い順)

- **`skills/review-loop/scripts/review_loop.py:308`: `source == "config"` の拒否には、deny ルールに当たったもの以外も含まれるかもしれない(要確認)**
  - SKILL.md:24 と :103 は「設定のルール(利用者の deny ルールなど)に当たった拒否」と説明しています。一方、偽の claude が出しているのは `reason_type: "subcommandResults"` です(`fakes/claude:49`)。
  - これはおそらく複合コマンドの各部分の判定をまとめた結果で、deny ルールに当たったとは限りません。どれかの部分が許可リストにないだけで、`-p` によって ask が deny に変わったものも含まれる可能性があります。
  - もし含まれるなら、`gh pr diff 7; <未許可のコマンド>` のように `;` でつないだだけで、未許可のコマンドが試行を止めずに通ります。これまでの前提(未許可なら試行は失敗、SKILL.md:24)が崩れ、権限の足りない環境でも試行は「成功」として記録されます。
  - 実際の stream で、ask から変わった拒否の `source` と `reason_type` を確かめてください。そのうえで、止めない条件を「deny ルールに当たったもの」に限るのが安全です(例: `reason_type` が rule 系のときだけにする、`message` で区別する)。

## セキュリティ・プライバシー

- **`review_loop.py:337-339`: `denials.txt` と stderr に、拒否されたコマンドの入力を最大200文字まで残す**

## 妥当だと考える点

- result の行のうち、最上位(`parent_tool_use_id` がない)だけを拾う区別は正しいです。サブエージェントの結果が混ざらないことも、テストで確かめています。
- 成否を最後の行で判定し、テキストはすべての行から作る、という分け方はレビュー役については筋が通っています。
- 判定役も stream-json にして、拒否の扱いをレビュー役と揃えた変更は一貫しています。

最大の論点は1件目です。`source: config` が何を意味するかで、この変更が「.env の誤爆を許すだけ」なのか、「未許可のコマンドを許す抜け道」なのかが変わります。実際の `claude -p` で、未許可の部分を含む複合コマンドを1回流して、イベントを確かめることを勧めます。
