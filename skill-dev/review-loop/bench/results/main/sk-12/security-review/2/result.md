候補が1件も出なかったため、誤検知を除く段階(手順2)は実施していません。調べたのは `skills/review-loop/scripts/review_loop.py` と `skills/review-loop/SKILL.md` の差分です。`fakes/claude` と `test.py` はテスト専用のファイルなので、除外条件に従い対象から外しました。

## 検討したが脆弱性ではないと判断した点

1. **設定のルールで拒否されたとき(source=config)に試行を止めなくなった点**
   - 拒否されたツールを実行させないのは CLI の権限判定です。スクリプトが止めるのは、時間と費用を省くために早く打ち切るためだけです。
   - そのため、止めなくても拒否された操作が実行されることはなく、権限の迂回にはなりません。
   - 作業ツリーへの混入の検知と、HEAD が変わったことの検知は今回の変更で変わっていません。

2. **`source` フィールドが偽装される可能性**
   - stream-json の最上位の行は claude CLI が書き出します。PR の内容やツールの出力は、JSON の文字列の値の中に入るだけです。
   - 行ごとに `json.loads` で読んで最上位の `type` と `subtype` を見ているので、文字列の中身から `permission_denied` のイベントを作ることはできません。
   - 仮に偽装できても、起きるのは「拒否されたのに試行が続く」ことだけで、拒否された操作が実行されるわけではありません。

3. **source のない拒否と、result の行にだけ載る拒否**
   - どちらも今までどおり止める扱いで、変更前より緩くなっていません。
   - 細かい点が1つあります。config の拒否で `tool_use_id` が None だと、result の `permission_denials` のうち `tool_use_id` のないものが読み飛ばされます。これは判定の正確さの問題で、拒否そのものは CLI が強制しているのでセキュリティ上の影響はありません。

4. **result の行をすべてつなぐようにした点**
   - 判定役に渡す文が増えますが、変更前からレビュー役が生成した文を判定役に渡しており、信頼の境界は変わっていません。
   - `parent_tool_use_id` のある result 行(サブエージェントのもの)は除外しています。
   - プロンプトに外部の内容が入ること自体は、除外条件(AI のプロンプトに利用者の内容が入る件)にも当たります。

5. **判定役を stream-json で起動するようにした点**
   - 引数はリストで渡しており、シェルを通していません。コマンドインジェクションの余地はありません。
   - 判定役も拒否を見張るようになったので、監視は変更前より強くなっています。

6. **`denials.txt` と stderr にツールの入力を記録する点と、出力ファイルのパス**
   - 記録はローカルのディスクに残るだけで、除外条件(ディスク上の秘密情報)に当たります。
   - 出力先のパスは、スクリプトが作った作業ディレクトリと固定のファイル名からできています。外から来る値が混ざらないので、パストラバーサルはありません。
