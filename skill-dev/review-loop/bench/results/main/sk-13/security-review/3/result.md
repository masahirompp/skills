この PR で新たに入った脆弱性のうち、確信度 8 以上で報告すべきものは**ありませんでした**。洗い出しの段階で候補が1件も出なかったため、偽陽性を除く段階は実行していません。

## 確認した範囲と、問題なしとした根拠

* **子プロセスの起動(コマンドインジェクション・引数インジェクション)**
  * `--perspective` と `--instruct` の値は CLI フラグなので、信頼できる値として扱いました。
  * `claude -p` は引数のリストで起動され、シェルを通らないため、コマンドインジェクションは起きません。
  * プロンプトは必ず `"/" + expand(spec, pr)` の形で、先頭が `/` です。そのためオプションとして読まれることはありません。
  * `--append-system-prompt` の値は独立した1つの引数で、先頭は固定の `REVIEW_CONSTRAINT` です。
* **プロンプトへの指示の追加**
  * `review_constraint()` が指示をシステムプロンプトにつなぎ、`run_judge()` が判定役の入力 `judge-input.md` に書き込みます。
  * 利用者が書いた内容を AI のプロンプトに入れているだけなので、除外基準により脆弱性には当たりません。
* **パストラバーサル**
  * 出力ファイルの名前は、これまでどおり `safe_name(skill_name(spec))` を通ります。この関数は `[^A-Za-z0-9_.-]` を `_` に置き換えます。
  * 新しい `review_config()` も、重複の検査に同じ `safe_name` を使っています。
* **状態コメント(PR に投稿する部分)**
  * 書き込むとき:
    * `perspectives` は CLI から来た値です。
    * `render()` がエスケープし、表のセルにする処理も既存の経路を通ります。
    * 投稿は `gh api --input -` で、JSON を標準入力から渡しています。
  * 読み込むとき:
    * 自分のアカウントのコメントで、かつマーカーで始まるものだけを読みます。
    * 新しく足した `valid_state` の検査で、`perspectives` の要素が文字列であることを確かめています。
    * 読み戻した値は表示にしか使われず、コマンド・パス・プロンプトには渡りません。
* **認可と権限の境界**
  * 再帰起動を防ぐ `GUARD_ENV`、事前確認 `preflight`(新しい観点の一覧で確認するよう変わった)、作業ツリーへの混入の検出は、変更の前後で同じように効いています。
  * 新しいオプションを使っても、これらを迂回する経路はありません。

## 備考(脆弱性ではない)

`--instruct` は観点の検査を緩め、`--perspective` はレビューの範囲を狭めます。この2つを付けるのは利用者に指示されたときだけ、という運用上のルールは `SKILL.md` に書かれています。これは設計の判断で、コードの脆弱性ではありません。
