**スメル(どれも判断の問題):**
1. **Duplicated Code**: `[skill_name(s) for s in ...]` が4か所にあります。`review_config` の中だけで2回あり、しかもループの中で毎回作り直しています。`review_config` で一度だけ作り、名前の一覧も返せば重複が消えます。
2. **Data Clumps**: `perspectives` と `instructions` は、`review_config` から `iterate`、`run_reviews`、`run_judge` へ常に組で渡っています。`run_reviews` の引数は8個になりました。小さな型にまとめる候補です。ただ、既存コードは `start` や `ctx` を辞書で回しているので、辞書に揃えるのも筋は通ります。
3. **Mysterious Name(軽微)**:
   - 関数 `review_constraint(instruction)` は、定数 `REVIEW_CONSTRAINT` と同じ名前なのに、指示を足したシステムプロンプトを返します。`review_system_prompt` などが候補です。
   - `instructs` は動詞に見えます。生の引数の値だと分かるよう、`instruct_args` などが候補です。
4. **Speculative Generality(軽微)**: `iterate(..., specs=None, instructs=None)` の既定値は使われていません。呼ぶのは `main` だけで、常に両方を渡しています。

## Spec

**(a) 欠けている要件:** 実質的にはありません。
- 終了コード2になる場合はテストされています。`=` なし、名前が空、指示が空、外した観点への指示、空白だけの観点です。
- `--perspective` の重複も既存の検査で終了コード2になりますが、これを確かめるテストはありません。
- SKILL.md には「指示があるときだけ付け、以後の反復でも同じものを付ける」「権限の拒否で止まったときの提案として使う」の両方が書かれています。

**(b) スコープクリープ(軽微で、妥当な範囲):**
- レビュー役のシステムプロンプトに「スキルの手順と食い違うときは、この指示を優先」と書き足しています。仕様は「指示を足す」だけです。この一文があると、指示は観点の検査を緩める方向に効きます。
- SKILL.md の終了報告に、レビューされなかった観点と範囲を載せるようにしています。範囲を狭めたことが見えなくなるのを防ぐ補完です。

**(c) 実装が誤っていそうな要件:**
1. **判定役に指示ブロックの読み方を伝えていない(中)**
   - 仕様の行: 「判定役の入力にも添え、指示で外した範囲を観点の欠落と取り違えないようにする」

   - 「観点の欠落」の規則(`review_loop.py:805`)はこのブロックに触れておらず、入力は「観点別レビューの出力」と説明されたままです。判定役がブロックを観点の一つと誤読するか、無視するおそれがあります。
   - テストが確かめているのは、ブロックが stdin に入ることだけです。
   - 対策: 規則に「指示ブロックで外した範囲は欠落とみなさない」という1文を足せば済みます。
2. **「既定と違う観点」の判定がずれる(低)**

   - 逆に、`code-review max {pr}` のように引数だけを変えた場合は、中身が違っても載りません。規約の担当も同じ点に気づいています。
   - 順序を問わない比較にすれば前者は直ります。後者は「名前を載せる」という仕様の文言には反していませんが、意図どおりかは確認が必要です。
3. **状態の型検査が緩い(低)**: `valid_state` は、`perspectives` がリストかどうかを確かめていません。値が文字列 `"abc"` でも検査を通り、表に「a, b, c」と出ます。
