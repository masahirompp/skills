## 確かめて、問題がなかったこと

- **`^Q%` などが本当に効くか**: サーバ全体の設定に `bind -n C-q switch-client -T wnq`(`lib/tmux/tmux.ts:128`)があるので、`C-q` を押すと whatnext の表に入ってしまい、`%` が効かないのではと疑いました。
  - 作業台のセッションは `prefix C-q` を設定しています(`lib/tmux/tmux.ts:324`)。tmux はキーを表で引く前に prefix を判定するので、作業台では prefix の表に入り、既定の `%`、`"`、`c` が効きます。
  - 受け入れシナリオ26(`ctrl+q %` で分割)も、この前提で成り立っています。
- **whatnext のキーとぶつからないか**: whatnext が prefix の表に割り当てる文字は `l w v e x n f` です(`src/ops/keys.ts:16-22`)。`c`、`%`、`"` とは重なりません。
- **`%%` の書き方**: 書き換えたのは固定の文字列だけで、利用者の入力は混ざりません。`@wn_name` の扱いもこの差分では変わっていません。
- **ステータス行と docs の例が一致するか**: ウィンドウの一覧は各要素の後ろに空白が付くので、`*` と `·` の間はちょうど2つの空白になります。docs の例とテストの正規表現(`\* {2}·`)の両方と合っています。
- **docs の図の幅**: `docs/PRODUCT.md:442` の図は、ほかの行と同じ字数です。「採らなかった形」の例は60桁で、右寄せにして左から欠けた場合の計算(左の36桁+右の残り24桁)とも合います。
- **セキュリティ・並行性・プライバシー**: 変わったのは固定の表示文字列だけで、該当する点はありません。

## 指摘

- **[設計/低] `lib/tmux/tmux.ts:340`: キーの説明の文字列を、キーの設定と別に手で書いている**
  - claude の画面のキーの説明 `ATTACH_KEYS_HELP` は、キーの表から作られています(`src/ops/keys.ts:25`)。一方、今回の `^Q% split │ · ^Q" split ─ · ^Qc window` は直書きで、prefix の `C-q`(`:324`)とも別々に保たれています。
  - 起こりうること: 将来、prefix の表に `c` を割り当てる whatnext のキーを足すと(`bare: true` のもの、`tmux.ts:133`)、tmux の既定の `^Qc` が上書きされます。それでもステータス行には `^Qc window` と出続けます。
  - 直し方: `ATTACH_KEYS` の文字が `c`、`%`、`"` とぶつからないことを確かめる単体テストを1つ足すのが安く済みます。

- **[正確性/低] `lib/tmux/tmux.ts:321-341`: 版を上げる前から残っている作業台には、キーが出ない**
  - `workbenchOptions` が呼ばれるのは、作業台を作るとき(`createWorkbench`)と、案内を出すセッションを作るとき(`src/cli/list.ts:68`)だけです。
  - 起こりうること: whatnext が異常終了すると、何かが動いている作業台は消されずに残ります(`src/ops/app.ts:1539-1542`)。その状態で新しい版を起動すると、残った作業台のステータス行は古い形のまま、キーが出ません。
  - 起きる場面は狭く、作業台を作り直せば直ります。直すなら、起動時に残っている `sh-*` のセッションへ `workbenchOptions` をかけ直すことになります。直さない場合は、`decision-log` に「起き直しても設定は入れ直さない」と書いておけば足ります。

- **[テスト/低] `test/e2e/workbench.test.ts:117`: 「狭くても `^Q%` が残る」ことを確かめていない**
  - 右寄せをやめた理由は、PRODUCT.md の「右から欠けるので `^Q%` が最後まで残る」です。しかしテストは、広い画面で文字列全体が出ることしか見ていません。
  - 起こりうること: 将来ステータス行を右寄せや二つに分ける形に戻しても、このテストは落ちません。
  - 直し方: 作業台の画面を60桁ほどに狭め、`workbench: … ^Q% split` が出ていて末尾が欠けていることを1つ確かめれば、決めたことをテストで守れます。cycle 9 は本番の品質が条件なので、足す価値があります。

- **[docs/低] `docs/PRODUCT.md:557-562`: 「採らなかった形」が実際の描画から取ったものか、差分からは分からない**

  - 桁数は計算と合うので、内容が誤っているとまでは言えません。ただ、tmux が左右の重なりをどう切るか(右側の頭から欠けるか)は実際の挙動に頼る部分です。手で作った例なら、実際に描いて確かめる価値があります。

- **[表記/観察] `^Q^L` と `^Qc` の書き方の違いが、利用者に伝わるか**

  - ただ、claude の画面と作業台の画面を並べて見ると、`^Q^C` と読み違える余地はあります。`Ctrl+Q`、離して `c` の意味で `^Q c` と空白を入れる案もありますが、幅が増えるので、今の形で足りるかの判断材料として挙げておきます。

## 総評

変更の狙い(右から欠けるので、いちばん使う `^Q%` が最後まで残る)は、ステータス行が狭いという制約に合っていて妥当です。挙動も、prefix の優先順位とキーの割り当てを確かめた範囲では正しく動きます。

残る弱点は、キーの説明をキーの設定と別に手で保っていることです。将来キーを足したときに表示と挙動がずれても、テストでは見つかりません。
