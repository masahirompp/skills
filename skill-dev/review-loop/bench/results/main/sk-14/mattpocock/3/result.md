# コードレビュー: `main...HEAD`(be0ad06、5ファイル、+41/−7)

- **仕様**: issue も PR も無いので、コミットメッセージを仕様として使いました。
- **規約**: CODING_STANDARDS.md や CONTRIBUTING.md などは無く、文書化された規約は README.md だけです。既存スクリプトの書き方を、事実上の規約として照らし合わせました。
- **テスト**: `skill-dev/housekeeping/test.sh` は HEAD で全件成功しました(両方のエージェントで確認)。

## Standards

README.md の規約(「housekeeping はスクリプトのテストで検証する」)には違反していません。以下はすべて判断事項です。

- **既定値の連鎖が2か所にある(Duplicated Code)**
  - `${HOUSEKEEPING_TMPDIR:-${TMPDIR:-/tmp}}` が `lib.sh` の `hk_mktemp_dir` と `scan.sh` のエラーメッセージの両方に書かれています。
  - 既定値を変えると2か所を直す必要があります。エラーの出力を `hk_mktemp_dir` 側に寄せるか、基準の場所を返す関数を1つ置く案があります。
- **エラーが2行に分かれる**
  - mktemp が失敗すると、mktemp 自身のメッセージが先に出て、続けて `error: 一時ディレクトリを作れない(...)` が出ます。
  - 既存の `error: PR 一覧を取得できない($slug): $(cat gh.err)` は、下位コマンドの出力を1行に埋め込む形です。こちらに揃える余地があります。実害は小さいです。
- **確かめ方が弱いテスト**
  - 「HOUSEKEEPING_TMPDIR の下に作り、終了時に消す」のテストは、終了後に `hk-tmp` が空であることしか見ていません。
  - そのため、scan.sh が別の場所を使っても通ります。
- **軽い Speculative Generality**
  - `lib.sh` の `[ -n "$d" ] && [ -d "$d" ] || return 1` は、直前の `mktemp -d ... || return 1` とほぼ同じことを確かめています。
  - `test.sh` は apply.sh に `HOUSEKEEPING_TMPDIR` を渡していますが、apply.sh はこの変数を読みません。
- **SKILL.md の箇条書きが長い**: サンドボックスの項目は1つの箇条書きに5文を詰めています。文体の規約は無いので、読みやすさの指摘にとどめます。
- **問題が無いと確かめた点**: `hk_` の接頭辞、`local` の宣言、lib.sh 冒頭の環境変数一覧への追記、`error: ...` の形式は、既存の書き方に揃っています。

## Spec

**(c) 実装が誤っていそうな要件**

1. **【高】ヒアドキュメントが一時ファイルを使い、判定が黙って誤る**
   - 該当 spec: 「apply.sh: 承認済みの行を変数で持ち、一時ファイルを使わない」
   - apply.sh が読み込む `lib.sh` の `hk_is_protected`(48行目)と `hk_path_in_use`(67行目)はヒアドキュメント `<<EOF` を使っています。
   - この環境の `/usr/bin/env bash` は bash 3.2.57 です。bash 3.2 はヒアドキュメントを一時ファイルで実装します。この2点は私も確かめました。
   - サブエージェントは、一時領域への書き込みを禁じた sandbox-exec の中で次の結果を確認しています(この再現は私は再実行していません)。
     - `cannot create temp file for here document` が出る。
     - `hk_is_protected main main` が rc=1(保護対象ではない)を返す。
     - `hk_path_in_use` が空(使用中ではない)を返す。
   - つまり保護判定と使用中判定が、安全でない側へ黙って倒れます。SKILL.md の「apply.sh は一時ファイルを使わない」も事実と合いません。
   - scan.sh にも、同じ形のヒアドキュメントが7か所(98, 110, 156, 197, 203, 218, 222行目)あります。
   - **影響範囲についての私の補足**: bash は、テンプレートなしの macOS の mktemp と違って `$TMPDIR` を見ます。そのため、このコミットが直したケース(TMPDIR は書けるのに `/var/folders` に書けない)では、ヒアドキュメントはおそらく成功します。問題になるのは、TMPDIR 自体に書けないサンドボックスです。範囲は限られますが、起きたときは削除の安全判定が黙って崩れます。ヒアドキュメントをパイプや `printf … |` に置き換える価値はあると考えます。
2. **【中】apply.sh の新テストは旧実装でも通る**
   - 該当 spec: 「test.sh: … apply.sh が TMPDIR に依存しないことを検証」
   - macOS のテンプレートなし `mktemp` は TMPDIR を見ないので、`TMPDIR=no-such-dir` を渡しても失敗しません。
   - サブエージェントが main の apply.sh を一時コピーに戻して test.sh を走らせたところ、全件成功しました。このテストでは退行を検出できません。
   - 失敗する偽の `mktemp` を PATH の先頭に置く形にすれば検出できます。

**(a) 欠けている・部分的な要件**

3. **【軽微】フォールバックの順序がテストされていない**
   - 該当 spec: 「HOUSEKEEPING_TMPDIR → TMPDIR → /tmp の下に」
   - テストしているのは HOUSEKEEPING_TMPDIR の経路だけです。
   - 実装そのものは正しく、空文字列のときも次の候補に進みます。

**(b) スコープクリープ**: 実害のあるものはありません。

**問題が無いと確かめた点**

- scan.sh に、テンプレートなしの mktemp はもう残っていません。
- apply.sh を変数化しても、入力が空のときやヘッダーだけのときの挙動は変わりません(空行は awk の条件で落ちます)。
- SKILL.md の案内文は、scan.sh のエラーメッセージと一致しています。

---

**まとめ**: Standards は判断事項が6件で、硬い違反はありません。重いのは、既定値の連鎖が2か所にあることと、HOUSEKEEPING_TMPDIR の下に作ることを確かめるテストが弱いことです。Spec は3件で、最も重いのはヒアドキュメントの件です。TMPDIR に書けないサンドボックスでは、保護判定と使用中判定が黙って安全でない側に倒れます。
