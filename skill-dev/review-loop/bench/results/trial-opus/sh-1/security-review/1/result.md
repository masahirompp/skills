## 参考: セキュリティの対象外だが、マージ前に直すべきロジックバグ

コミットメッセージには「挙動は変えない」とありますが、実際には次の 2 か所で挙動が変わっています。どちらも攻撃者がいなくても起き、削除する側に倒れます。

### 1. `verify_pr_merged` で祖先判定の向きが逆になった(`scan.sh:93`)

- **変更前**: `git merge-base --is-ancestor "$sha" "$oid"`。手元の先端が PR の head に含まれていれば delete でした。
- **変更後**: `is_ancestor "$oid" "$sha"`。PR の head が手元の祖先であれば delete になります。
- **影響**: PR がマージされた後に手元で追加コミットしたブランチが、本来は keep のところ「PR #N マージ済み」として delete と判定されます。
  - 対象のブランチと worktree が削除され、未プッシュのコミットが失われます。
  - リモートブランチの走査も同じ関数を使うため、マージ後に追加 push されたリモートブランチも delete と判定されます。その場合は `apply.sh` が GitHub 上のブランチを消します。
- **テストで見つからない理由**: `skill-dev/housekeeping/test.sh` の MERGED の例は、すべて `headRefOid` が手元の sha と同じです。同じコミットはどちら向きでも祖先と判定されるので、向きの逆転を検出できません。
- **悪用の可能性**: 低いと判断しました。フォーク由来の PR は対象外です。悪用するには、同じリポジトリへの書き込み権限とマージ権限が必要で、さらにユーザーの承認も通らなければなりません。
- **修正**: `elif is_ancestor "$sha" "$oid"; then` に戻します。あわせて test.sh に、「マージ後に追加コミットしたブランチ(`oid ≠ sha`)は keep」という例を、ローカル版とリモート版の両方で加えます。

### 2. first-parent 履歴を作るときのエラー確認が消えた(`scan.sh:82`)

- **何が起きるか**: `refs/heads/$default` と `refs/remotes/$hk_remote/$default` のどちらかが無いと、`git rev-list` 全体が失敗して出力が空になります。
  - 空のファイルに対して `grep -qxF` を実行すると 1 が返ります。そのため「読めない(>1)」ではなく「first-parent 上に無い」と扱われます。
  - 結果として、PR が無いブランチはすべて「merge コミットで取り込み済み」として delete と判定されます。
- **影響の範囲**: この判定の手前に `merged_into_default` の条件があります。そのため、コミット自体は失われません。失われるのは、作ったばかりで未着手のブランチ名程度です。
- **修正**: 旧方式に戻します。存在する ref だけを集めて rev-list に渡し、失敗したときや出力が空のときは止めます。
