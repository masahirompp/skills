1. `skills/review-loop/SKILL.md:99`: defect は直す前に「実際に実行して」再現するよう求め、手段がない場合以外は実行を省かせない(103行)が、隔離した環境(一時リポジトリ、fake、使い捨ての worktree)で再現するという指示がないため、影響が高(データの消失、消すべきでないものを消す)の指摘を再現すると、その被害が利用者の実環境で起きる。

   Failure scenario: housekeeping のようなスキルの PR で「マージされていないブランチや worktree を誤って消す」という影響が高の defect が出る。親は判定の再現手順に従い、利用者のリポジトリでそのままスクリプトを実行する。手順が正しければ、まさに指摘どおり利用者のブランチや worktree が消え、元に戻せない。

2. `skills/review-loop/SKILL.md:128`: 以前の不変条件「直前に直した修正はまだレビューされていないので、もう1回回す」が外された。再現テストと既存テストが通れば回さずに終えてよいため、終了時の HEAD がどの観点にもレビューされないまま終わりうる。

   Failure scenario: 反復3で影響が中の defect を直す。再現テストは修正前に失敗、修正後に通り、既存テストも通るので終える。しかしその修正は、再現テストが触れない別の経路に、新しい不具合や security-review が拾うはずの問題(入力検証の抜けなど)を持ち込んでいた。どのレビュー役も見ていない差分が「収束した」として利用者に渡る。「修正が大きく、再現が確かめた範囲を超えて」は親の主観なので歯止めにならない。

3. `skills/review-loop/SKILL.md:134`: 差分の外の指摘を `gh issue create` で issue にする手順に、セキュリティの指摘を扱う例外がない。本文に場所、起きる操作の順、影響まで書かせるので、公開リポジトリでは脆弱性の再現手順を公開してしまう。

   Failure scenario: 公開リポジトリで、PR の前からある認証の回避(影響は高、セキュリティ)が差分の外と判定される。親は影響が高のものを先頭に置いて尋ね、利用者が「全部 issue に」と答える。場所と悪用の手順を書いた公開 issue ができ、修正前に誰でも読める。非公開の security advisory に回すよう案内すべき。

4. `skills/review-loop/SKILL.md:102`: 「再現を試みたが起きなかった」指摘は影響に関係なく採らず、継続の理由にもならない(126行)。親の再現手順そのものが誤っていた(前提の組み違い、環境の差)場合に、本物の影響が高の defect が黙って落ちる。差分の外の指摘と違って、issue にするかも尋ねない。

   Failure scenario: データの消失を起こす defect に対し、親は前提の状態を作り損ねた再現テストを書き、失敗しなかったので採らない。126行により終了の妨げにもならず、ループは終わる。報告の「残った指摘」に一行載るだけで、利用者には「再現しなかった=問題なし」と読まれる。

5. `skills/review-loop/SKILL.md:126`: 継続の理由から除くのは「差分の外」と「再現を試みて起きなかった」指摘だけ。「実行では示せない」defect をコードで追って却下した場合が抜けており、影響が高のものは125行の基準で毎回継続の理由になる。

6. `skills/review-loop/SKILL.md:109`: 横展開の候補のうち差分の内のものだけを修正に含めるとしたが、差分の外の候補の扱いが決まっていない。指摘の範囲は差分の外ではないので107行と134行の報告・issue の流れにも乗らず、どこにも残らない。

7. `skills/review-loop/SKILL.md:134`: issue を作る前に、既存の issue に同じものがないかを確かめる手順がない。差分の外の指摘は PR の前からある問題なので、同じリポジトリの別の PR でも繰り返し見つかり、そのたびに重複した issue ができる。
