PR #1(review-loop: 指摘を仮説として扱い、再現で確かめてから直す)の差分を読んだ指摘です。変更は文書とプロンプトだけで、テストは実行していません。

方向性には賛成です。PR 本文の実績(#14 は6反復で991万トークン)から見て、「再現できない指摘で反復を伸ばさない」「差分の外は直さない」は肥大化の原因に直接効きます。一方で、反復を止める条件を緩めた分、取りこぼしの経路が増えています。

### 重要度: 中

- **`skills/review-loop/SKILL.md:102` と `:126`:再現の失敗が、影響「高」の指摘を無条件に落とす**
  - 「再現を試みたが起きなかった → 採らない」が、影響の段階を問わず継続の理由から外れます。
  - 再現の手順は親が組み直すことも認めているので(`:99`)、手順が間違っていたせいで起きなかった場合と、本当に起きない場合を見分けられません。
  - 影響「高」はデータの消失などで、取り返しがつきません。そのため、ここだけは確証バイアスの逆向き(自分の手順の失敗を「起きない」と読む)が一番効きます。
  - 案:影響「高」で再現しなかったものは、試した手順を状態として残し、次の反復の判定役に再指摘として判断させる。または終了時の報告に必ず載せる。

- **`skills/review-loop/SKILL.md:128`:再レビューを省くと、確かめていない別の修正もレビューされずに残る**
  - 「どの修正も」が指すのは「上の基準に当たる指摘」の修正だけです。`:105` で再現なしに直してよいとした修正(基準に当たらない defect、test_gap など)が同じコミットにあっても、再レビューを省けます。
  - これまでは基準に当たる修正が1つあれば必ずもう1回回していたので、ほかの修正もついでにレビューされていました。この変更で、その安全網が外れます。
  - `:132` に「最後に判定を受けた SHA と HEAD の差」を報告する項目はあります。ただし、それは報告だけで止める仕組みではありません。
  - 案:省いてよい条件に「直前の判定のあとに入れた変更が、すべて再現で確かめた修正だけであること」を足す。

- **`skills/review-loop/SKILL.md:128`:「既存のテストも通っている」が、テストの無いプロジェクトでは無条件に満たされる**
  - テストの置き場が無いリポジトリでは、この条件が常に成り立ちます。その結果、再現1本だけで終えられます。
  - 括弧内の「修正が大きく、再現が確かめた範囲を超えて」も、どこからが大きいのかの目安がありません。親がもう回したくないときに、都合よく解釈される余地があります。
  - 案:既存のテストが無い場合は除外する。「大きい」には変更行数や触ったファイル数など、目安になる例を添える。

### 重要度: 低

- **`skills/review-loop/SKILL.md:99` と `:107`:差分の外の defect を再現するかの順序が書かれていない**
  - `:99` だけを読むと、差分の外の指摘も、基準に当たる defect なら再現が必要に見えます。その次の `:107` で、差分の外は直さないと書いています。
  - 親が、直さない指摘の再現に時間を使う可能性があります。
  - 一方で、issue にする(`:134`)なら再現の結果は価値があります。
  - 案:どちらにするかを明記する。たとえば「範囲を先に見る。差分の外の再現は任意で、したなら issue に結果を書く」。

- **`skills/review-loop/SKILL.md:134`:issue の本文に「確かめたかどうか」を書く項目が無い**
  - 差分の外の指摘は判定役の仮説のままのことが多いのに、本文の項目は場所・影響・起きる操作の順だけです。
  - このままでは、確かめていない仮説が、確かめた不具合と同じ書き方で issue になります。
  - 案:「再現で確かめた / 実行では確かめていない」の欄を足す。

- **`skills/review-loop/SKILL.md:107`:「PR のベースで同じことが起きるか確かめる」方法が書かれていない**
  - 今の worktree をベースに切り替えると、HEAD を元に戻し忘れたときに次のスクリプト起動の前提(`:32`)を壊します。
  - 案:`git worktree add` で別の場所に取り出す、または `git show <base>:<path>` で読むなど、作業ツリーを変えない方法を一言添える。

- **`skill-dev/review-loop/fakes/claude:100`:偽の判定に「分類」の行が無い**
  - 新しく足した「再現: 対象外」は分類が defect 以外のときの値ですが、分類の行が無いので、中身として筋が通っていません。分類の行の欠けはこの PR より前からです。
  - スクリプトが確かめるのは見出しだけ(`review_loop.py:837-839`)なので、テストには影響しません。
  - ただ、同じ所で「JUDGE_PROMPT と揃える」とコメントしているので、`- 分類: other` などを入れておくと食い違いが残りません。

### 問題ないと判断した点

- **`review_loop.py:863`(範囲の決め方)**:「場所が PR の変えていない行でも、PR の変更が原因で起きるなら差分の内」と書いてあり、確かめられなければ差分の内に倒しています。差分の外に偏って取りこぼす方向には倒れていません。
- **`review_loop.py:865`(再現の欄)**:判定役は作業ツリーを変えられないので、実行は親の受け持ちに残しています。「修正前に失敗するはずの手順」を書かせるだけに留めた分け方は、既存の制約と矛盾しません。

### 検討してほしい問い

この PR の目的は反復を減らすことです。ただ、止まりやすくする緩和が3つ同時に入ります(再現しなければ落とす、差分の外は継続の理由にしない、確かめた修正は再レビューしない)。PR 本文にあるとおり効果はまだ測っていないので、どれが効いたのか、またどれが取りこぼしを生んだのかを後から切り分けられません。最初の数回は、終了時の報告に「緩和のどれで止まったか」も残しておくと評価しやすくなります。
