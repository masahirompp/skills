PR #1 の差分は3ファイルです。SKILL.md と JUDGE_PROMPT は文書とプロンプトの変更なので、指摘はどれもコードと文面を読んだ結果で、実行して確かめたものはありません。

方向性は妥当だと考えます。PR 本文の表にあるとおり反復とトークンが膨らんでいたので、「再現を採用の条件にする」と「差分の外を切り離す」は効く手です。確かめられないときに「差分の内」に倒す既定(`review_loop.py:863`)も正しい向きです。ただ、新しい規則の中に「重大な不具合を黙って落とす」経路と「再現のときの危険」があります。

## 正確性・設計

- **`skills/review-loop/SKILL.md:102` と `:126`: 再現できなかった指摘は、影響が高でも黙って落ちる。**
  - 再現の手順を組むのも、起きなかったと判断するのも、早く終えたい親自身です。`:99` で「判定の手順が合っていなければ、自分で組み直す」ことも許しているので、起きない手順に組み直して落とす方向に偏りやすくなっています。
  - 再現できなかったことは、不具合がないことの証明になりません。環境の違いや、手順の組み違いでも起きなくなります。
  - 提案: 影響が高で再現できなかったものは、「採らない」ではなく終了時の報告に必ず載せて、利用者に判断を委ねる。
- **`skills/review-loop/SKILL.md:107` と `:126`: 差分の外の指摘も、影響に関係なく継続の理由にならない。**
  - PR 本文が認めているとおり、#14 の「全ブランチが delete になる」と同じ種類のものは直らなくなります。
  - 特に気になるのは、PR がまさに書き換えている関数の中に前からあった不具合です。これも「差分の外」に分かれて直せません。
  - 提案: 「PR が変更した行や関数の中にあるもの」は例外にするか、少なくとも高のものは終了の前に利用者へ確認する。
- **`skills/review-loop/SKILL.md:109`: 横展開の候補で差分の外にあるものが、どこにも報告されない。**
  - `:109` では差分の内にあるものだけを修正に含めます。
  - 一方、終了時の報告(`:132`)と issue の対象(`:134`)は「範囲が差分の外の指摘」だけで、横展開の候補は入っていません。
  - その結果、同じ規則の破れが差分の外にあっても、利用者に伝わりません。
- **`skills/review-loop/SKILL.md:128`: 回さずに終えてよい条件が、修正による新しい不具合を見ていない。**
  - 再現のテストが確かめるのは、元の不具合が直ったことだけです。修正が持ち込んだ不具合は誰も見ないまま終わります。
  - 例外の「修正が大きく、再現が確かめた範囲を超えて」は量の基準がなく、親の裁量でいくらでも狭められます。
  - 「プロジェクトの既存のテストも通っている」は、テストのないプロジェクトでは常に満たされ、条件として働きません。
  - 提案: 「既存のテストがなければ回す」「修正の差分が N 行を超えたら回す」のように、判断できる基準にする。
- **`skills/review-loop/SKILL.md:103` と `:128`: このリポジトリでは、狙った削減がほとんど効かない可能性がある。**
  - このリポジトリの PR は大半が SKILL.md やプロンプトで、`:103` では「実行では示せない」側に入ります。そうなると `:128` によって毎回もう1回回ることになり、今までと変わりません。
  - 効くのは、#14 のようなスクリプトの PR に限られます。効果を測るときは、PR の種類を分けて見る必要があります。
- **`skill-dev/review-loop/fakes/claude:100`: 偽の判定の形が、プロンプトの形と合っていない。**
  - 偽の判定には前から「分類」の行がありません。そこに「再現: 対象外」だけを足したので、分類のない指摘が非 defect の扱いになっています。
  - `test.py` が見るのは見出しだけなので実害はありません。ただ、この変更は何も検証していない、と考えた方が正確です。
- **`skills/review-loop/scripts/review_loop.py:865`: 判定役に「あなたは実行して確かめないので」と書いているが、実際に禁じているのは作業ツリーの変更だけ。**
  - `JUDGE_CONSTRAINT`(`:81`)が禁じているのは作業ツリーを変えることです。作業ツリーを変えない実行、たとえば一時ディレクトリで完結するテストは禁じていません。
  - 「実行は親の受け持ち」とするのは設計上の選択であって、制約から出てくる結論ではありません。判定役に作業ツリーを変えない再現をさせる余地は残っています(コストとの兼ね合いです)。

## セキュリティ・プライバシー

- **`skills/review-loop/SKILL.md:99`-`:101`: 再現をどこで実行するかの指定がない。**
  - 再現が必須になるのは影響が高の指摘で、これは「取り返しがつかない(データの消失、消すべきでないものを消す)」と定義されています。
  - 指摘どおりのことを実際に起こすと、本物のリポジトリでブランチや worktree が消えます。housekeeping 系のスキルが典型です。
  - 提案: 「破壊的な操作の再現は、使い捨ての一時リポジトリかテストの fake の中で行う」と明記する。
- **`skills/review-loop/SKILL.md:134`: 差分の外にあるセキュリティの不具合を、公開リポジトリの issue に書くことになる。**
  - 本文には「場所、起きる操作の順」を書くので、公開リポジトリでは修正の前に脆弱性の手順を公開することになります。
  - 利用者に尋ねる手順はありますが、利用者が判断に使える材料が渡されません。
  - 提案: 分類がセキュリティのものは、issue ではなく GitHub の Security Advisory(非公開の報告)を勧める一文を足す。尋ねるときに、リポジトリが公開かどうかも示す。
- **`skills/review-loop/SKILL.md:134`: 既存の issue との重複を確かめていない。**
  - 反復をまたいだ重複はまとめますが、前の PR で同じ不具合を issue にしていれば二重に作られます。
  - 提案: `gh issue list --search` で既存の issue を確かめる手順を足す。
  - あわせて、fork から上流へ出した PR では `gh issue create` の宛先が曖昧になるので、`--repo` で宛先を明示する指定もあるとよいです。

## 並行性

- 新しく持ち込んだ並行性の問題は見当たりません。再現の実行は親が反復の合間に行い、試行の実行中ではありません。そのため、混入の検査(`contamination`)や `head_changed` とは重なりません。

## 検討の材料

- 「再現を試みたが起きなかった」を採らない理由として残しても、`:116` にあるとおり次の反復に伝わる経路はコードコメントと PR 本文だけです。同じ指摘がまた出て、また再現を試みる、を繰り返さないでしょうか。PR 本文に、試した手順まで残す決まりにするかどうかを決める必要があります。
- 効果は「反復が減ったか」だけでなく、「採らなかった指摘や差分の外とした指摘に、本物の不具合がどれだけ混ざっていたか」でも測らないと、早く終わることと見落としが増えることを見分けられません。
