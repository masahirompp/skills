# PR #1 レビュー: 「review-loop: 指摘を仮説として扱い、再現で確かめてから直す」

対象は3ファイル(+27/−4)です。差分と周辺のコード(`JUDGE_PROMPT`、`JUDGE_CONSTRAINT`、テスト、SKILL.md 全体)を読んで判断しました。テストは実行していません。

全体の方向は妥当です。指摘を仮説として扱い、再現してから直すようにすれば、推論だけの指摘で修正が行ったり来たりするのを抑えられます。差分の外の指摘を PR に含めないことで、指摘が新しい指摘を呼ぶ連鎖も断てます。どちらも理にかなっています。ただし、ガードを緩めた箇所が3つあり、緩め方の境界がゆるいと考えます。

## セキュリティ / 安全性

- **`skills/review-loop/SKILL.md:99` 「実際に実行して」に、使い捨ての環境で再現するという条件がない(影響: 高)**
  - 再現が必須になるのは「影響が高」の defect です。影響が高とは、データの消失や消すべきでないものを消すといった、取り返しのつかないものを指します。
  - たとえば housekeeping の「作業中の worktree を消す」という指摘を、本物のリポジトリで実行して再現すると、利用者のデータが実際に消えます。
  - 状態コメントや PR コメントを書くコードの不具合を再現すると、本物の PR に書き込むことも起こります。
  - 案: 次のように限定する文を足します。
    - 再現は一時ディレクトリの使い捨てリポジトリか、`skill-dev/.../fakes` のような偽物で行う。
    - 実際のリポジトリ・ブランチ・外部サービスに対して、破壊的な操作や書き込みの操作で再現しない。
- **`skills/review-loop/SKILL.md:134` `gh issue create` で、セキュリティの指摘が公開 issue に載りうる(プライバシー / セキュリティ)**
  - 状態コメントは、指摘の内容や判断の理由を載せない作りです(SKILL.md:154)。issue の作成はその方針から外れる初めての経路です。
  - 公開リポジトリで「差分の外」の脆弱性を、場所と起きる操作の順まで書いた issue にすると、修正前に手順を公開することになります。
  - 利用者に確認してから作る点は良いのですが、利用者がこの危険に気づける材料が渡りません。
  - 案: 尋ねるときに、リポジトリが公開かどうかと、セキュリティに関わる指摘かどうかを示します。セキュリティの指摘は、公開 issue ではなく GitHub の private security advisory を勧めます。
  - 本文に引用するコードに秘密(トークンなど)が含まれていないかを確かめる、という一文もあると安全です。

## 正確性 / 設計

- **`skills/review-loop/SKILL.md:102` と `:126` 再現を1回試みて起きなければ、影響が高でも捨てて終われる**
  - 再現の手順を組み直すのも(`:99`「自分で組み直す」)、起きなかったと判断するのも、修正する本人です。
  - 手順の誤り、環境の違い、条件の取り違えで偽陰性が出ると、影響が高の指摘が「継続の理由にしない」に入ります。修正する本人が判断するので、確証バイアスが入り込みやすい構造です。
  - 以前は「影響が高は起きやすさに関係なく継続の理由」でした。今回の変更で、ここが一番大きく緩んでいます。
  - 案: 影響が高で再現できなかったものは、捨てずに終了時の報告に「再現を試みたが起きなかった」として載せ、利用者に判断を委ねます。少なくとも、試した手順を報告に含めます。
- **`skills/review-loop/SKILL.md:128` 再現が通れば、修正をレビューせずに終えられる**
  - 再現のテストが確かめるのは、指摘された症状が消えたことだけです。修正がほかの経路に回帰を持ち込んでいないかは確かめません。
  - 「プロジェクトの既存のテストも通っている」という条件は、テストがない、または薄いプロジェクトでは何も保証しません。このリポジトリも `skill-dev/review-loop/test.py` が1つあるだけです。
  - 「修正が大きく」の基準も、修正した本人の主観になります。
  - 以前の「修正はまだレビューされていないので、もう1回回す」は、修正を独立した目で見るという機能を持っていました。それを、自分で書いたテストで置き換えています。
  - 案: 回さずに終える条件を次のように絞ります。
    - 既存のテストが変更した経路を実際に通ることを確かめている。
    - 修正の差分が小さい(行数の目安を置くなど)。
    - 回さずに終えたことを報告に明記する。
- **`skills/review-loop/SKILL.md:107` 差分の外の指摘を持ち帰れるのは、正常に終了したときだけ**
  - issue にするかを尋ねるのは「終了したら」の報告の中だけです(`:134`)。
  - 「失敗したとき」で利用者に報告して止まる経路(同じ失敗が2回続いた、上限に達したなど)では、それまでに集めた差分の外の指摘を報告する手順がありません。
  - この指摘は反復をまたいで親の記憶にしか残らないので、ここで落ちると失われます。
  - 案: 失敗して止まるときの報告にも、差分の外の指摘を含めると書きます。
- **`skills/review-loop/SKILL.md:107` 差分の外でも、PR の変更で悪化したものの扱いが決まっていない**
  - `JUDGE_PROMPT` (`review_loop.py:863`) は「PR の前から同じように起きる」を差分の外としています。
  - PR の前からあった問題でも、PR の変更で起きやすさや影響が上がるものがあります。たとえば、まれな経路を普通の使い方の経路にしたものです。これがどちらに入るかが曖昧です。
  - 案: 「PR の変更で、影響か起きやすさが上がったものは差分の内」と明記します。
- **`skills/review-loop/SKILL.md:99` 再現が必須かどうかを分類で決めているが、その分類は判定役が付ける**
  - 判定役が実質的な不具合を `test_gap` や `other` に分類すると、`:105` により再現なしで採否を決めてよくなります。
  - 再現の手順も書かれません(`review_loop.py:865`「ほかの分類では対象外」)。
  - 判定役の分類に任せる点は以前と同じなので、影響は中程度です。
  - ただ、新しく足した規則の効き目が分類の揺れに左右されることは意識しておくべきです。

## 文書の正確さ

- **`skills/review-loop/SKILL.md:93` 「判定役もレビュー役も…実行して確かめてはいない」は、事実として保証されていない**
  - `JUDGE_CONSTRAINT` と `REVIEW_CONSTRAINT` (`review_loop.py:77-81`) が禁じているのは、作業ツリーやブランチを変える操作だけです。実行することは禁じていません。
  - 観点スキル(組み込みの `code-review` など)が、読み取りのコマンドやテストを実行することはありえます。
  - `review_loop.py:865` の「あなたは実行して確かめないので」も同じく、断定になっています。
  - 結論の「仮説として読む」は妥当です。理由だけ「実行して確かめたとは限らない」に弱めるのが正確です。

## テスト / 偽物

- **`skill-dev/review-loop/fakes/claude:100` 偽物の判定に `分類` の行がないのに、`再現: 対象外` だけがある**
  - `JUDGE_PROMPT` の形では、「対象外」は defect でない分類に付けるものです。分類がないと、この組み合わせが形として意味をなしません。
  - スクリプトが確かめるのは `VERDICT_SECTIONS` の2つの見出しだけです。テストは `### F1: s` だけを確かめています(`test.py:146`)。なので、実害はありません(影響: なし)。
  - 形を揃えるなら `- 分類: other` も足すのが一貫しています。

## 並行性

- 並行性の問題は見つかりませんでした。
  - 再現のテストを書いたり実行したりするのは手順5で、スクリプトが動いていない間です。手順1でコミットして push してから起動する、という順序とも食い違いません。
  - 再現で書いたテストを「回帰テストとして残す」(`:101`)と、次の反復でレビューの対象に入ります。これは意図どおりと考えます。

---

**検討の材料として**: この PR は「推論だけの指摘で修正が振れる」という問題への対策です。一方で、判断する役が、独立した判定役から修正する本人へ移っています。上の指摘のうち3つ(再現できなければ捨てる、再現が通ればレビューせずに終える、手順を自分で組み直す)は、どれもこの移動から来ています。

これまでの反復で困っていたのが、偽陽性(採らなくてよい指摘を採った)と偽陰性(見逃した)のどちらだったかで、緩めてよい度合いは変わります。過去の判定の記録から、再現なしで採った指摘のうち実際に誤りだったものの割合を見ると、判断の根拠になります。
