### セキュリティ / プライバシー
- **`skills/review-loop/SKILL.md:134`: issue の作成で、修正していない脆弱性の詳細が公開される**
  - 状態コメントは「指摘の内容や判断の理由…は載せない」(`SKILL.md:154`)と、公開の場に指摘を出さない作りになっています。
  - 一方、新しい手順は issue 本文に「場所、影響と起きやすさ、起きる操作の順」を書かせます。公開リポジトリでは、差分の外にある影響が高のセキュリティの指摘が、再現手順付きで公開されることになります。差分の外のものは「直さない」と決めているので、未修正のまま公開されます。
  - 利用者に確認はしますが、公開されることもセキュリティの種類であることも示されません。そのため、利用者が知らずに承認しうる作りになっています。
  - 案: 尋ねるときに、リポジトリが公開か(`gh repo view --json visibility`)と、セキュリティ由来の指摘かを示す。セキュリティの指摘は issue にせず、private vulnerability reporting などに誘導する。

### 正確性(手順の書き方)
- **`SKILL.md:102` と `SKILL.md:126`: 1回の再現失敗で、影響が高の不具合を確定的に捨てられる**
  - 「再現を試みたが、起きなかった: 採らない」と「影響の段階に関係なく継続の理由にしない」の組み合わせです。親が間違った手順で再現を組むと(`SKILL.md:99` で「自分で組み直す」ことを認めています)、本物の欠陥が理由付きで却下されます。間違いの例は、BSD と GNU の違い、前提の状態を作り損ねる、入力が違う、などです。
  - 親は PR の作成者で、早く終えたい誘因があります。反証の手続きなのに、確証バイアスとは逆向きの偏り(都合のよい棄却)がかかりやすい構造です。
  - 案: 「起きなかった」で捨てられるのは、影響が中以下か、手順が判定の示す経路を決定的に通ったと示せるときに限る。影響が高のものは「実行では示せない」扱いに戻し、もう1回回す。

- **`SKILL.md:102-103`: 並行性の指摘を「起きなかった」に分類する抜け道がある**
  - 「狙って起こせないタイミング」は「実行では示せない」に入れる、と書かれています。ただ、競合状態は1回試して起きなくても、それは何の証拠にもなりません。
  - 親が試しに1回走らせて起きなければ、文言上は「試みたが起きなかった」に当てはまり、捨てられます。
  - 案: 「タイミングに依存する指摘は、1回の実行で起きなくても、起きなかったとしない」と明記する。

- **`SKILL.md:128`: 「どの修正も」がどの修正を指すかが曖昧**
  - 前の文脈は「上の基準に当たる指摘を採って直したとき」なので、基準に当たらない修正(文書、命名、test_gap)を含むのかが読み取れません。
  - 含むと読む場合: そうした修正は再現できないので、それが1つあるだけで毎回再レビューになり、この PR の狙い(反復を減らす)が効きません。
  - 含まないと読む場合: レビューを通らない変更が HEAD に入ります。
  - どちらの意図かを書く必要があります。

- **`SKILL.md:128`: 「既存のテストも通っている」の扱いが決まっていない**
  - テストがないプロジェクトでは、この条件が自動で満たされるのか、満たされないのかが決まっていません。
  - このリポジトリは文書やプロンプトが中心なので、指摘の多くは「実行では示せない」になります。再レビューを省ける場面はそもそも少ない見込みです。効果を測るときは、#14 のようなシェルスクリプト中心の PR と分けて見るべきです。

### 設計
- **`SKILL.md:107` と `scripts/review_loop.py:863`: 差分の外の指摘が、毎回の反復で出し直される**
  - 判定役が過去の判断を知る経路は、PR 本文とコードコメントだけです(`SKILL.md:116`)。差分の外として見送った指摘はどちらにも記録されないので、毎回の反復でまた出てきます。
  - その結果、判定役が「再指摘」として扱えず、トークンと親の仕分けの手間を毎回使います。
  - 案: 見送った差分の外の指摘を PR 本文に記録するよう、手順5に足す。

- **`SKILL.md:134`: 既に起票された issue との重複を確かめる手順がない**
  - 「反復をまたいで1件にまとめる」のは同じ PR の中だけです。差分の外の不具合は直されないので、同じ箇所を触る次の PR でもまた見つかり、また起票を勧められます。
  - 案: 作る前に `gh issue list --search` で既存の issue を確かめる手順を足す。

- **`SKILL.md:107`: 「この PR では直さない」に例外がない**
  - PR の目的そのものが、差分の外とされた箇所に関わる場合でも直さない、と読めます。#14 の「無い ref があると全ブランチが delete になる」のような、影響が高のデータ消失も報告だけになります。
  - PR 本文の「確かめていないこと」で自覚はされていますが、手順には逃げ道がありません。
  - 案: 「PR の意図に照らして親が覆してよい」(`SKILL.md:97` と同じ考え方)を範囲の判断にも明示する。

- **`SKILL.md:101`: 再現のために書いたテストが、レビューを通らずに入りうる**
  - 「回帰テストとして残す」は、再レビューを省く条件(`:128`)と組み合わさると、レビューされない新しいテストのコードが PR に入る経路になります。
  - PR の膨らみを抑えたいという動機とも少しぶつかります。テストを足したら、それも「修正」に数えるかを決めておくべきです。
