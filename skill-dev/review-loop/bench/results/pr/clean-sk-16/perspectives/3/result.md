PR #1 をレビューしました。差分は3ファイル（`SKILL.md`、`review_loop.py` の `JUDGE_PROMPT`、テスト用の偽 `claude`）で、中身はほぼ LLM 向けの手順書です。何かを実行して確かめた指摘はなく、どれも文面とコードを読んだ結果です。

**総評:** 方向は妥当です。「指摘は仮説」として扱い、差分の外を切り分けて反復が膨らむのを止める仕組みは、PR 本文の実績（#14 は6反復で991万トークン）に対する手当てとして筋が通っています。主な弱点は、「確かめる人」が「書いた本人」（親）だけになることです。

## 正確性・設計

- **`skills/review-loop/SKILL.md:106`, `:128` — 一度再現しなかっただけで、影響が高の指摘も落ちる（設計、重要度: 中〜高）**
  - 再現を組むのは PR の作者でもある親です。親には、再現しない方向に寄る動機があります。手順が浅くても「起きなかった → 採らない → 継続の理由にしない」で、影響が高の指摘まで消えます。
  - `:134` で利用者への報告には残るので、完全には消えません。それでも、ループを止める判断は親の試行1回に任されています。
  - 案: 影響が高の指摘で再現しなかったものは「却下」とせず「未再現」という扱いを作る。その回は終えてよいが、報告では先頭に置き、試した手順を必ず添える。もう一つの手は、判定役が書いた再現の手順と親が実際に行った手順の差を記録させることです。

- **`SKILL.md:99` — 「再現もしない」と「ベースで確かめてから外す」がぶつかる**
  - 差分の外は「再現もしない」としながら、影響が高なら「PR のベースのコードで同じことが起きるかを確かめてから外す」とも書いています。
  - この「確かめる」が実行なのかコードを読むことなのか、書かれていません。読むだけなら、それも仮説のままです。
  - ベースでも確かめられないときの扱いもありません。差分の内に戻すのか、外のままにするのかが決まっていません。
  - 案: 「ベースで実行して確かめる。実行では示せないなら、差分の内として扱う」と明記する。判定役の既定（確かめられなければ差分の内、`review_loop.py:863`）と揃えるのが自然です。

- **`SKILL.md:130` — 「修正した箇所を通る既存のテスト」を親が見分ける手段がない**
  - カバレッジなしでは、どのテストがその箇所を通るかはコードを読んで推し量るしかありません。もう1回回すかどうかの判断は、ここが根拠になっています。
  - 「通っている気がする」で打ち切る余地が残ります。
  - 案: 修正した行を一時的に壊すとそのテストが落ちることを確かめる、のような手軽で検証できる基準を置く。それが重ければ、判断の根拠にしたテスト名を報告に載せる。
  - 細かい点ですが、PR 本文は「修正が大きく…なら回す」と大きさを基準に書き、`SKILL.md` は「修正の大きさに関係なく」と経路を基準に書いています。本文を `SKILL.md` に合わせてください。

- **`SKILL.md:101`, `:109` — 分類 1 つで再現の要否が変わる**
  - 再現が必要かどうかは、判定役が付けた分類（defect かどうか）だけで決まります。
  - 実害のある不具合が test_gap や other に分類されると、再現なしで採否を決めてよい側に入ります。その結果、再現がないまま判断されるか、再現を通さずに見過ごされます。
  - 案: 「分類が defect でなくても、影響が高・中と書かれていれば defect と同じに扱う」と1行足す。

- **`review_loop.py:863` — 判定役がベースの見方を知らされていない**
  - 判定役は「範囲」を決めるのに PR の前のコードを見る必要があります。それなのに、`git diff <base>...HEAD` や `gh pr diff`、`git show <base>:<path>` を使えることがプロンプトにありません。
  - 作業ツリーを変えない制約（`JUDGE_CONSTRAINT`）があるので、読むだけの手段を明示しないと「確かめられなかった → 差分の内」に倒れ続けます。そうなると、差分を切り分けるという目的が働きません。

## セキュリティ・プライバシー

- **`SKILL.md:115` と `:116` — 悪用の手順の禁止が PR 本文にしかかかっていない**
  - `:116` は、公開リポジトリの PR 本文に、直していないセキュリティの指摘の悪用手順を書くことを禁じています。
  - 一方、`:115` は「次の反復で確実に伝えたい理由はコードコメントに書く」としています。却下したセキュリティ指摘の理由をコードコメントに書くと、コメントもマージ後は公開されるので、同じ情報が漏れます。
  - `:106` が求める「試した手順と結果」の記録も、書く場所次第で同じことになります。
  - 案: 禁止の対象を「PR 本文・コードコメント・コミットメッセージ」に広げる。

- **`SKILL.md:103` — 一時ディレクトリでは隔離にならない再現がある**
  - セキュリティ指摘（パストラバーサル、コマンドインジェクション、`~` やネットワークに触れるものなど）の再現は、一時ディレクトリで実行しても、その外に作用する場合があります。
  - 「隔離した場所」の定義が「場所」にしか触れていません。
  - 案: 「再現の入力の作用が隔離した場所の外（ホームディレクトリ、ネットワーク、資格情報）に及ぶなら、実行では示せないとして扱う」と1文足す。

- **`SKILL.md:136` — issue の扱いは妥当**
  - 公開リポジトリのセキュリティ指摘では手順を書かず、利用者に尋ねる。尋ねずに作らない。重複も探す。必要な手当ては揃っていて、指摘はありません。

## 並行性

- 差分そのものに並行性の問題はありません。親が再現と修正をするのはスクリプトが終わったあとで、判定役は実行しません。
- **`SKILL.md:107`, `:130` — 並行性の指摘は打ち切られにくい（設計上の帰結。今は様子見でよい）**
  - 「狙って起こせないタイミング」は「実行では示せない」に入ります。直すと `:130` の「実行で確かめていない修正が1つでもあれば回す」に当たるので、並行性の指摘を直すたびに必ずもう1回回ります。
  - 安全側の設計としては正しいです。ただ、反復を減らすという狙いはこの種類には効きません。PR 本文の「確かめていないこと」に書いておく価値があります。

## テスト

- **`skill-dev/review-loop/fakes/claude:100` — 偽の判定の形が本物と揃っていない（軽微）**
  - 偽の判定に「範囲」「再現」を足していますが、`分類` や `起きやすさ` の欄はもともとありません。それなのに「再現: 対象外」と書いてあり、本物の形とも、分類との関係とも合いません。
  - `test.py` はどちらの欄も見ていないので、挙動には影響しません。「欄の追加で挙動は変わらない」という PR 本文の主張はそのとおりです。
  - 揃えるなら `分類: other` を足せば整合します。

## 判断の材料として

この変更で、親（PR の作者でもある）の判断が採否と終了の両方を決めるようになります。その判断が甘いとどこで分かるのか、が要になります。いまの安全網は終了時の報告（`:134`）だけです。実際の PR で回すときは、反復とトークンが減ったかに加えて、「再現しなかった」として採らなかった指摘を利用者があとで見直し、本当に誤検出だったかを数えておくことを勧めます。それが減った反復の質を測る反証になります。
