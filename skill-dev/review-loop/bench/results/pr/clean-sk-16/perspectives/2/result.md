## セキュリティ

- **`SKILL.md:103` の隔離の条件が「消す・書き換える」操作に限られています(影響: 高寄り)**
  - 「一時ディレクトリに作ったリポジトリ」を `git clone` で作ると、`origin` は本物のリモートのままです。
  - その中で `git push --delete` や `gh` を使う再現をすると、隔離したつもりでも本物のリモートと PR に届きます。#14 の housekeeping のように、ブランチを消す処理の指摘を再現する場面がまさにこれに当たります。
  - また、外へ送る操作(`gh pr comment`、`gh issue create`、`curl` による送信)は「消す・書き換える」に当たらないので、この文では止められません。
  - 直し方の例: 「リモートは一時ディレクトリの bare リポジトリに差し替える」「再現では外部への送信をしない」を加える。

- **判定役の「再現」欄の手順を、親が読まずに実行する道ができています(`scripts/review_loop.py:865`、`SKILL.md:101`)**
  - レビュー役の出力は、リポジトリの内容(コメントや文書)に影響されます。それがそのまま判定役の手順になり、親が実行します。
  - `:101` は「手順が合っていなければ組み直す」と言うだけで、「実行する前にコマンドを読み、隔離の条件に合うかを確かめる」とは書いていません。
  - 自分の PR が前提なので起きやすさは低めですが、1文足すだけで済みます。

## 並行性

- **ベースを取り出すときの後片付けが書かれていません(`SKILL.md:103`、影響: 低)**
  - `git worktree add` で取り出すと、共有の `.git` に worktree が登録されます。消し忘れると、この worktree で並行して動く別のセッションや housekeeping から見えてしまいます。
  - 「`git worktree add` を使ったら必ず `git worktree remove` する」か、「`git archive` で取り出す」と指定したほうが安全です。
  - スクリプトの実行中に親は再現をしない流れになっているので、試行への混入(`contamination`)は起きません。

## 設計

- **「再現しなかったら採らない」の判断を、書いた本人だけが下します(`SKILL.md:106`、`:128`)**
  - 以前は影響が高の指摘は無条件で継続の理由になり、次の反復で別のレビュー役の目がもう一度入りました。
  - 今回の変更で、影響が高の指摘も、親の再現で起きなければそこで消えます。その判断を誰も見直しません。
  - 親は PR の作者なので、「起きない」と結論したい側に偏りやすい立場です。テストの組み方が悪くて再現しなかった、という誤りも見つけられません。
  - 終了時の報告(`:134`)に理由が載るのが唯一の歯止めです。影響が高に限っては、次のどちらかを検討してください。
    - 再現しなかった手順をコードコメントか PR 本文に残し、次の反復で反証できるようにする
    - 終了時の報告で先頭に置く

  - 変更の大半が SKILL.md やプロンプトの PR では、ほとんどの指摘が「実行では示せない」に入ります。そのため `:130` により、これまでどおり毎回回ります。
  - PR 本文の目的(反復を減らす)が効くのは、#14 のようにスクリプトとテストがある PR に限られます。不具合ではありませんが、PR 本文の「確かめていないこと」に書いておくと、効果を測るときに迷いません。
