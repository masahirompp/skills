## Standards(規約)

**README.md の規則に反するところはありません。**
- 差分は frontmatter に触れていません。
- `fakes/` の変更は `skill-dev/` の中に収まっています。
- 偽の判定(`fakes/claude`)も新しい形に合わせて更新されています。

以下はすべて判断の分かれる指摘です。

1. **SKILL.md と `JUDGE_PROMPT` で同じ定義を二度書いている**
   - SKILL.md は「範囲、再現の定義は `JUDGE_PROMPT` が正」と書いています。それなのに、手順4・5で次の3つをほぼ同じ文で書き直しています。
     - 「PR の目的の直し残しは差分の内」
     - 「実行では示せない種類」の例の並び
     - 「隔離した場所で再現する」という縛り
   - すでに1つ食い違っています。`JUDGE_PROMPT` にある「確かめられなければ差分の内」が SKILL.md にはありません。
   - 片方だけ直すと、どちらが正かわからなくなります。
2. **欄の名前「範囲」が、別の意味の「範囲」とぶつかる**
   - 同じファイルの中に、別の意味の「範囲」が以前からあります。
     - `JUDGE_PROMPT` の「親が直す範囲」「指示で外した範囲」
     - SKILL.md の「`--instruct` で範囲を絞った」
   - `JUDGE_PROMPT` は判定役のモデルが読むので、取り違えるおそれがあります。「差分との関係」のような重ならない名前にする手があります。
3. **終了の判断の項目が詰め込みすぎ**
   - 「もう1回回すか」の1項目に、4つ以上の条件分岐が入っています(再現の成否、既存テストの有無、共有関数の変更、実行で確かめていない修正)。
   - issue を作る段落も、5つの関心事を1段落に抱えています。
   - 既存の短い箇条の書き方と比べて読みにくいです。
4. **セキュリティの規則が2か所にある**: 「公開リポジトリなら悪用の手順を書かない」が、PR 本文を書く箇条と issue を作る段落にそれぞれ書かれています。

## Spec(仕様)

**(a) 欠けている要件**: ありません。
- 本文の「スクリプトが確かめるのは判定の見出しだけ」は正しいです。`VERDICT_SECTIONS = ("## 指摘", "## 競合")` しか見ていません(`review_loop.py:837`, `953-958`)。
- 再現の対象(差分の内、defect、影響が高か、影響が中で普通の使い方で起きる)は、終了の基準と一致しています。

**(b) 本文にない追加**
1. **PR の目的の直し残しを「差分の内」に入れる例外**
   - 本文は「PR の前から同じように起きる指摘は、この PR では直さず」と書いています。この例外は本文にありません。
   - 本文の「#14 の…これからは同じ PR では直らない」とも食い違うおそれがあります。
2. **セキュリティ指摘の扱い**: 公開リポジトリで悪用の手順を書かないこと、issue を公開にするか尋ねること。
3. **issue を作るときの追加の手順**: 既存 issue との重複確認、反復をまたいだ同じ指摘の統合、影響が高のものを先頭に置くこと、本文に書く項目の指定。本文は「issue にするかを尋ね、言われたものだけを作る」までです。
4. **再現の安全の規則**: 隔離して実行すること、作れない環境条件は「実行では示せない」に回すこと、意図した挙動の変更を指す指摘は手順4で却下すること。
5. **ベースのコードでの確認を必須にした**
   - 本文は「親が PR のベースで確かめて決め直せるように」という任意の書き方です。
   - SKILL.md は、影響が高の指摘を差分の外として外すなら、ベースで確かめることを必須にしています。

**(c) 本文と実装のずれ**
1. **再レビューの条件**
   - 本文は「修正が大きく、再現が確かめた範囲を超えて挙動を変えているなら回す」です。
   - SKILL.md は「修正の大きさに関係なく回す」で、本文より厳しくしています。この変更は本文で説明されていません。
2. **「実行で確かめていない修正が1つでもあれば回す」がどこまでかかるか**
   - この規則は「継続の理由になる指摘を採って直したとき」の中に書かれています。
   - そのため、再現しなかった影響の低い修正が混ざっただけで回すのかが読み取れません。
3. **`JUDGE_PROMPT` の再現欄が自己矛盾している**
   - 「defect の指摘にだけ書く」と書いたすぐ後に、「ほかの分類では『対象外』と書く」とあります。
   - 判定役は defect すべてに手順を書きますが、親が再現するのは終了の基準に当たるものだけです。この食い違いが意図したものかどうかも書かれていません。

**まとめ**: 規約の指摘は4件(どれも判断の分かれるもので、いちばん重いのは SKILL.md と `JUDGE_PROMPT` の二重定義と、すでに出ている食い違い)。仕様の指摘は8件(本文にない追加5件とずれ3件、いちばん重いのは再レビューの条件から「修正が大きく」を外したこと)。
