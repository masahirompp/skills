再現を採用の条件にし、差分の外を分けるという方向は妥当だと考えます。過去の実績（#14 で反復6、991万トークン）が示す膨らみの原因に直接効く変更です。ただ、運用で穴になりそうな点がいくつかあります。

## 指摘

### 影響が中（運用で判断を誤るおそれ）

- **`skills/review-loop/SKILL.md:113` と `:99`: 差分の外とした判断を PR 本文に残す指示がない**
  - 理由を残すよう指示しているのは「指摘の却下、裁定の変更」だけです。差分の外として外した指摘は、これに当たるかがはっきりしません。
  - 判定役は過去の判定を受け取りません（`:118`）。そのため次の反復でも同じ指摘が出て、親は毎回分類し直すことになります。
  - 判定役の範囲の判断は揺れうるもので、PR 本文も「未確認」と書いています。ある回に「差分の内」と出れば継続の理由に戻り、`:131` の振動を自分で作り出します。
  - 提案: 差分の外として外した指摘も、その根拠（ベースで確かめた結果）とともに PR 本文に残すと明記してください。そうすれば判定役が「再指摘」として扱えます。

- **`skills/review-loop/SKILL.md:106` と `:128`: 影響が高の指摘でも、再現が1回起きなかっただけで外せる**
  - 差分の外の場合は、影響が高ならベースで確かめてから外す、という歯止めがあります（`:99`）。再現が起きなかった場合には、それに当たる歯止めがありません。
  - 親が組み直した再現の手順が間違っていても（前提の状態を作れていない、別の経路を叩いている、など）、データの消失のような指摘がそのまま継続の理由から外れます。
  - 「起きなかったことに数えない」としているのは、環境の条件が違う場合だけです（`:103`）。手順そのものが誤っている場合は、この扱いに入りません。
  - 提案: 影響が高の指摘で再現が起きなかったときは、再現の手順が指摘の「起きる操作の順」をすべて満たしているかを照らし合わせて残すようにしてください。それでも疑わしければ「実行では示せない」側に倒す、と書くと非対称が解けます。

### 影響が低（文言の曖昧さ・ずれ）

- **`skills/review-loop/SKILL.md:99`: 「再現もしない」と、ベースで確かめてから外す指示がぶつかって読める**
  - 影響が高の差分の外の指摘をベースで確かめるのは、実質的にはベースでの再現です。
  - 読むだけで確かめればよいのか、実行するのかが読み取れません。
  - 提案: 「再現もしない」を「修正のための再現はしない」に変え、ベースでの確認の手段（読む / 隔離して実行する）を明記してください。

- **`skills/review-loop/scripts/review_loop.py:863`: 範囲の定義に、逆向きの場合が書かれていない**
  - PR が変えていない行でも PR が原因なら差分の内、という向きは書かれています。
  - 逆向き、つまり PR が書き換えた行に、前からの不具合がそのまま残っている場合が書かれていません。リファクタで関数を書き直したが同じ不具合を引き継いだ、という場合です。
  - 今の定義ではこれは差分の外になります。それが意図どおりなのかを明記したほうが、判定役の揺れが減ります。
  - 判定役に PR のベースの取り方（`gh pr view --json baseRefOid` や `git merge-base`）を示していない点もあります。そのため「PR の前のコード」をどう見るかは判定役任せです。

- **`skills/review-loop/SKILL.md:130`: 1つの箇条に条件が5つ以上入っている**
  - 回さずに終えてよい条件、括弧書きの例外、テストがないとき、確かめていない修正があるとき、5回の目安を超えるとき、がすべて1つの箇条に入っています。
  - 終える・回すの判断はループで一番効く分岐なので、読み違えると費用に直結します。
  - 提案: 「回さずに終えてよい条件」と「回す条件」に箇条を分けてください。

- **`skill-dev/review-loop/fakes/claude:100`: 偽の判定が JUDGE_PROMPT の形とまだ揃っていない**
  - 「範囲」「再現」は足しましたが、`分類`、`起きやすさ`、`根拠`、`横展開`、`競合` の欄はもともとありません。
  - `分類` がないまま「再現: 対象外」だけがあるので、`review_loop.py:838` の「揃える」というコメントに対して半端な状態です。
  - スクリプトが確かめるのは見出しだけなので、テストへの影響はありません。揃えるなら全部の欄を、揃えないなら今回の1行の変更は不要です。

## 考えておくとよい点（不具合ではありません）

- **このリポジトリ自身では、反復はほとんど減らない見込みです。**
  - 変更の大半は `SKILL.md` やプロンプトです。これは `:107` の「実行では示せない」に当たります。
  - `:130` は「実行で確かめていない修正が1つでもあれば回す」としているので、文書が中心の PR では再レビューを省ける場面がほぼありません。
  - PR 本文の「測っていない」は正直な書き方です。ただ、効果を測るなら、コードの PR（#14 の mktemp のようなもの）で比べる必要があります。
- **再レビューを省いて終えると、最後の修正は親の再現と既存のテストでしか確かめられていません。**
  - 終了の報告で「最後に判定を受けた SHA と HEAD の差」を出す設計なので、ここは許容範囲だと考えます。
  - ただ、「修正した箇所を通る既存のテスト」をカバレッジなしで判断するのは親の推測です。この推測が甘いと、省くべきでない回まで省くことになります。
