## 重要な指摘

- **`skills/review-loop/scripts/review_loop.py:863` 判定役に PR のベースと本文が渡されていない**
  - 判定役は「PR の前のコードでも同じ操作の順で起きる」か、「PR の本文やコミットが直すと述べていること」かを見分けるよう求められています。ところがプロンプトには、比べる元になるベースの ref も PR 本文も入っていません。判定役は自分で `gh pr view` や `git merge-base` を探して打つしかありません。
  - その結果、次のどちらかに偏ると考えます。
    - 規則どおり「確かめられなければ差分の内」に倒れ、変更3の効果がほとんど出ない。
    - 確かめずに「前からありそう」と推測して、差分の外にしてしまう。
  - スクリプトは `:454` で既に `gh pr view --json number,headRefOid,...` を呼んでいます。ここに `baseRefName` と `body` を足して `JUDGE_PROMPT` に埋めるだけで済み、手間は小さいです。

- **`skills/review-loop/SKILL.md:106` 「再現を試みたが起きなかった」だけで、影響が高の指摘も採らなくなる**
  - `:107` の「実行では示せない」場合はコードを追って採否を決めます。一方 `:106` は、再現が1回起きなかっただけで却下します。さらに `:128` で継続の理由からも外れます。
  - 再現手順の組み方の誤り(前提の状態や入力が違う)はよくあります。それでも、データ消失級の指摘が、親の1回の試行の失敗で消えます。
  - `:103` の「条件を作らずに試して起きなかったことは数えない」は、OS やツールの実装が違う場合しか防いでいません。
  - 提案: 影響が高のものは、起きなかった理由をコードで説明できたとき(たとえば判定役が言う経路が実際には通らない)だけ採らない、とする。説明できなければ「実行では示せない」と同じく、コードを追って採否を決める。

- **`skills/review-loop/SKILL.md:130` 再レビューを省く条件が、親の自己判定だけで成り立つ**
  - 「修正した箇所を通る既存のテスト」か、「再現が確かめた経路の外の挙動も変えているか」を判断するのは、修正した本人である親です。カバレッジなど客観的に確かめる方法も示されていません。
  - スクリプトが過去の判定を子に渡さないのは独立性を保つためでした(`:140` 付近)。最後の修正だけは、その独立した目を通らずに終わることになります。
  - トークンを減らすためのトレードオフとしては妥当な判断です。ただ、少なくとも終了報告(`:134`)で「再レビューを省いた修正」と、省いた根拠(どのテストが通ったか)を分けて報告させるべきです。今の「最後に判定を受けた SHA と HEAD の差」だけでは、なぜ省いたかが利用者に伝わりません。

- **`skills/review-loop/SKILL.md:109` と `:130` の関係が曖昧**

  - 例として、既にあった不具合のある関数に、PR が普通の使い方の経路から新しい呼び出しを足したとします。不具合そのものは前からあり、起きやすさだけが「まれ」から「普通」に上がります。
