PR #1(review-loop-verify-findings)の差分をレビューし、指摘を9件にまとめました。ほとんどは SKILL.md の手順の論理の穴です。`review_loop.py` は判定の見出し `## 指摘` と `## 競合` しか確かめません。そのため、プロンプトに欄を足してもスクリプトの挙動は変わらず、コードが壊れる不具合は見つかっていません。リポジトリに CLAUDE.md はなく、適用されるのはユーザー全体の `~/.claude/CLAUDE.md` だけです。そこに差分が破っている規則はありませんでした。

10 findings, most severe first:

1. `skills/review-loop/SKILL.md:107`: 「再現を試みたが起きなかった → 採らない」の再現は、PR の作者である親が自分で組み直してよい。その再現が指摘の経路を実際に通ったかを確かめる手順がないので、影響が高の指摘でも、外れた再現1回で落とせてしまう。

   Failure scenario: 判定役がデータ消失(影響が高)を指摘し、親が「判定の手順が合っていない」として再現を組み直す。組み直した再現は条件の分岐に入らないので失敗しない。終了の判断(131行)ではこの指摘を継続の理由にしないので、データ消失の不具合が残ったままループが終わる。再現の前に指摘の経路を通ったと示すこと(ログ・カバレッジ・アサーション)を条件にしていないのが原因。

2. `skills/review-loop/SKILL.md:133`: 修正を再レビューせずに終えてよい条件「修正した箇所を通る既存のテストも通っている」は、どのテストがその行を通るかを測る手段を決めておらず、親の推測で満たせてしまう。修正で足したコード自体も、誰にもレビューされない。

   Failure scenario: 親が影響が高の指摘を直すときに新しい分岐を足し、同じファイルの既存テストが通るのを見て「通る」とみなして終える。足した分岐はどのテストも通っておらず、別の入力で例外になるが、もう1回の判定がないので見つからない。最後に判定を受けた SHA と終了時の HEAD の差としては報告されるが、利用者はその差がレビューされていないと気づきにくい。

3. `skills/review-loop/SKILL.md:133`: SKILL.md は「修正の大きさに関係なく回す」と書くが、PR 本文の変更2は「修正が大きく、再現が確かめた範囲を超えて挙動を変えているなら回す」と書き、大きさを条件にしていて食い違う。

   Failure scenario: 次の反復でレビュー役か判定役が PR 本文を仕様として読むと(mattpocock-skills:code-review は PR 本文を仕様として使う)、小さな共有関数の修正を回さずに終えたことを正しいと判断するか、逆に仕様違反として指摘し、反復が無駄になる。

4. `skills/review-loop/SKILL.md:101`: 影響が高の指摘を差分の外として外すには「ベースのコードで同じことが起きるかを確かめる」ことが要るが、実行では示せない種類の指摘(文書・プロンプト・タイミング)や、隔離して再現できない指摘で、どう確かめるかが決まっていない。
