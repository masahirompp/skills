PR #2(`wbguide-recover`)をレビューしました。原因の切り分け(`kill-pane` で案内のセッションが消えること、`exec exec` になっていたこと)と直し方の方向は妥当です。テストも、打ち込む文字列を bash・zsh・sh で実際に動かしており、良い作りです。指摘は次の通りです。

### 直したほうがよいもの

- **`lib/tmux/tmux.ts:52-58` 起動し直しの回数が戻らず、6回目の終了で元の不具合が再発する**
  - `@wn_respawned` はペインのオプションで、`respawn-pane` のあとも値が残ります。手元の tmux 3.8 で、`set -p @c 1` → `respawn-pane` → `show -pqv @c` が `1` を返すのを確かめました。このため上限は「続けて落ちたら5回まで」ではなく、「サーバが動いている間の通算で5回まで」になっています。
  - 長く使っていて6回目に落ちると `kill-pane` でセッションが畳まれます。作業台の画面は `detach-on-destroy on` で離れ、Ghostty の分割ごと閉じます。直そうとした「開いた直後ではなくても、急に閉じる」がそのまま残ります。
  - 原因がまだ分かっていない以上、通算で数える根拠は弱いです。たとえば次のどちらかを勧めます。
    - 前に起動し直した時刻を残し、一定時間(例: 60秒)以上もってから落ちたときは回数を 0 に戻す。
    - 畳む代わりに、作業台の画面のクライアントを `list` 以外のどこかへ逃がす。

- **`docs/DESIGN.md:227`、`docs/lib/tmux.md` の「ペインごとに 5 回まで」が通算か連続か読み取れない**
  - 上の挙動のまま残すなら「起動し直した回数はサーバが終わるまで戻らない」と書く必要があります。直すなら、回数を戻す条件を書きます。`docs/lib/tmux.md` は昇格済みモジュールの契約なので、言葉の曖昧さが後まで残ります。

### 確かめておきたいもの

- **`src/cli/workbench.ts:33` 0 以外の終了をすべて「つなげなかった」とみなしている**
  - tmux のクライアントは、端末を失ったとき(SIGHUP、`lost tty`)も 1 で終わります。そのとき一覧は残っているので、エラーの文を書いたうえで `fail()` に入り、閉じかけた tty に `setRawMode(true)` を呼びます(`workbench.ts:59`)。node もたいてい SIGHUP で先に終わるので実害は出にくいですが、`res.signal` や「attach の前に届いたか」で見分けたほうが、意図(つなげなかったときだけ)に合います。

- **`src/cli/guide.ts:19` 作り直した案内のプロセスが、`whatnext workbench` 側の環境と版を引き継ぐ**
  - `paneCommand(env, 'guide')` は呼んだプロセスの `PATH`、`CLAUDE_CONFIG_DIR`、`WHATNEXT_DEBUG_LOG` と `env.cli` を埋め込みます。一覧の起動時に作ったものとは環境が変わりうるということです。
  - 一覧を動かしたまま npm で更新したあとに `whatnext workbench` を打つと、一覧より新しい版の案内が `@wn_guide` を読みます。今の案内は tmux のオプションしか読まないので実害は小さいはずですが、DESIGN.md に一言あると後で迷いません。

- **`test/e2e/workbench.test.ts:255` `/signal=kill/` が macOS の書き方に頼っている**
  - tmux は `sys_signame` があれば名前(macOS では小文字の `kill`、手元で確かめました)を出し、なければ番号を出します。glibc の Linux では `9` になるはずです。ただし実機で確かめたのは macOS だけで、Linux 側は推測です。macOS でしか流さない前提なら問題ありません。`/signal=(kill|9)/` にしておくと安全です。

### 小さな整理

- **`src/cli/list.ts:66-67`** `ensureGuide` が `'created'` のときは中で `workbenchOptions(GUIDE, '')` を済ませているので、直後の呼び出しと二重になります。引き継いだサーバ(`'exists'`)のために残すなら、`'exists'` のときだけ呼ぶと意図が読めます。`ensureGuide` の `'failed'` も、一覧の側では握りつぶしていてログに出ません。
- **`src/cli/workbench.ts:43-51`** 頼みごとを書いて `SIGUSR2` を送る処理が、`src/cli/guide.ts:74-79` とほぼ同じ形で2か所目になりました。`Tmux` に `request(action)` のような口を1つ置けば重複が消えます。
- **`lib/tmux/tmux.test.ts:75-81`** 文字列が含まれるかだけを見るテストなので、`-lt 5` と `kill-pane` の順序や分岐が逆になっても通ります。挙動は E2E で押さえているので、これは残すかどうかの好みの範囲です。

### 書かれていないこと

- PR の本文にあるとおり、Ghostty と bash の実機(`test/real`)は流していません。`exec exec` の不具合は bash の実機でしか出ないので、マージの前に一度流すことを勧めます。単体テストで bash に文字列を渡して確かめてはいますが、Ghostty の `initial input` を通したときの挙動までは押さえていません。
