## 指摘(重い順)

- **`lib/tmux/tmux.ts:52-56` 起動し直しの回数が戻らず、セッションが続く間の合計で数えている**
  - `@wn_respawned` はペインのオプションです。`respawn-pane` してもペインの ID は変わらないので、値はずっと残ります。そのため「起動してすぐ終わるとき」(コメントの 49 行、`docs/lib/tmux.md` の追記)だけでなく、数日に1回落ちる場合でも、6回目で `kill-pane` に入ります。
  - 起きること: 作業台の画面が案内を映している最中にセッションが消えます。`detach-on-destroy on` のため、クライアントが離れて分割が閉じ、#1 と同じ症状が出ます。開き直せば `ensureGuide` で戻りますが、落ちる原因はまだ分かっていません。なので、まれに落ちる場合こそ起きやすい形です。
  - 直し方の案: 起動から N 秒以上動いていたら数え直す(時刻を一緒に残して比べる)。または上限を「直近 M 分の回数」にする。

- **`src/cli/workbench.ts:33-35` 「つなげなかった」と「つないだあとに異常で終わった」を区別していない**
  - 判定は「tmux が 0 以外で終わり、かつ一覧がある」だけです。一度つないだあと、一覧が生きたまま tmux のクライアントが 0 以外で終わる場合(端末を失った、外から SIGHUP や kill を受けたなど)にも、`could not open the workbench screen` と出ます。分割から起動していればキーを待ちます。
  - 加えて、この経路は 38 行のタイトルを消す処理を通りません。つないでいた場合は古いタイトルが残り、DESIGN.md が防ぎたい「古いタイトルの分割へ移る」が起きえます。
  - 本当に0以外で終わるかは実機で確かめていません。ただ判定がこの前提に乗っているので、最低限、失敗の経路でもタイトルは消すべきです。

- **`src/cli/guide.ts:19` 案内を作り直すときの環境を `whatnext workbench` を動かしたプロセスから取っている**
  - `paneCommand(env, 'guide')` は既定で `process.env` を使います。そのため作り直した案内には、一覧ではなく Ghostty の分割のシェル(または手で `whatnext workbench` を打った端末)の `PATH`、`CLAUDE_CONFIG_DIR`、`WHATNEXT_DEBUG_LOG`、`XDG_STATE_HOME`、`LANG` が入ります。
  - 起きること: 一覧を `WHATNEXT_DEBUG_LOG` 付きで起動していても、作り直した案内のログが出ません。原因が分からない落ち方を追いたいときに、手がかりが欠けます。
  - 手で別のインストールの `whatnext workbench` を打った場合は、`env.node`/`env.cli` も一覧と別の版になります。
  - DESIGN.md の追記は `@wn_guide` を読める点しか書いていないので、この違いも書くか、一覧の環境(`set-environment -g` 済みの値など)から組み立てるのが妥当です。

- **`src/cli/list.ts:66-67` `workbenchOptions(GUIDE, '')` を二重に呼んでいる**
  - `ensureGuide` が作った場合は、中で同じ呼び出しを済ませています(`src/cli/guide.ts:22`)。害はありませんが、`ensureGuide` が `'failed'` を返しても一覧は何も記録しません。以前と同じ挙動とはいえ、せっかく戻り値を持たせたので `log` に出すほうがよいです。

- **`lib/tmux/tmux.test.ts:75-81` 回数の上限を、文字列が含まれるかでしか確かめていない**
  - `'-lt 5'` や `kill-pane` が含まれるかを見ているだけで、「5回で止まる」挙動は誰も実行していません。E2E(`test/e2e/workbench.test.ts:242-256`)は1回の起動し直ししか見ていません。
  - 上の1件目(回数が戻らない)も、このテストでは見つかりません。上限を詰めるなら、`T` を偽の tmux に差し替えて本文を実行するか、E2E で6回 kill するテストが要ります。

- **`lib/tmux/tmux.ts:51` 画面の末尾に tmux の注記が混ざる可能性**
  - `remain-on-exit` の死んだペインは、tmux が `Pane is dead (...)` の行を描きます。`capture-pane` の末尾5行にそれが入ると、手がかりの枠が1行減ります。tmux 3.7c で実際にどうなるかは確かめていません。`@wn_guide_died` を見るときの注意として書いておく程度で十分です。

## 問題ないと判断した点(根拠つき)

- `sleep 1` は `run-shell -b`(`lib/tmux/tmux.ts:181`)の中で動くので、サーバを止めません。
- 本文の `#{pane_dead_status}` は、`show -gv` で取り出したあとに `display -p` に渡ります。フックの時点で書式として展開されることはありません。
- 一覧が `wbTty` をまだ知らない間に頼みごと `guide` が届くと、`doFollow` は何もせずに戻ります。ただ `lastGuide` は `undefined` のまま残るので、次の `follow` で名前が入ります(`src/ops/app.ts:1468,1487`)。競合で名前が抜けたままになることはありません。
- 一覧の側で作り直さない理由(`session-closed` の知らせが間に合う保証がない)は、DESIGN.md に「採らなかった案」として書かれています。判断として妥当です。
