PR #2 の差分(13ファイル、+177/−15)を読みました。直し方の筋(案内のセッションを消さずに起動し直す、つなぐ側で作り直す、`exec` を1つにする)は妥当です。ただし、元の不具合(作業台の画面が閉じる)が別の形で戻る経路が1つ残っています。テストは流しておらず、作業ツリーには触れていません。

## 正確性

- **`lib/tmux/tmux.ts:52-58` 起動し直しの回数が元に戻らず、元の不具合が戻る(重要)**
  - `@wn_respawned` はペインに付く値で、増えるだけで減りません。このため「すぐ終わり続けるときに回り続けない」ための上限が、実際には「セッションが続く間の通算5回」になっています。
  - 案内のプログラムが落ちる原因はまだ分かっていない、と DESIGN.md に書かれています。数時間おきにたまに落ちるような場合、6回目で `kill-pane` が走り、案内のセッションが消えます。そのとき作業台の画面がそこにつながっていると、`detach-on-destroy on` で画面ごと閉じます。これは #1 の症状そのものです。
  - 直し方の案:前に起動し直した時刻もペインの値に残し、たとえば30秒以上たっていれば数え直す。
- **`src/cli/workbench.ts:33` tmux がシグナルで終わったときに失敗と取り違える**
  - tmux がシグナルで終わると `res.status` は `null` になり、`null !== 0` は真です。一覧がまだ動いていれば「could not open the workbench screen」と出し、Ghostty の分割ではキーを待ちます。
  - 一覧を手早く起動し直したとき、新しい `list` を見て失敗と判断する余地も同じ条件にあります。
  - 直し方の案:`res.status !== null && res.status !== 0` にする。
- **`src/cli/workbench.ts:17-27` 失敗したときに `@wn_wb_tty` が残る**
  - `WB_TTY` の設定と `MAIN_TTY` の取り消しを、`ensureGuide` の前に済ませています。このため案内を作れずに終わっても、一覧はこの tty を作業台の画面と見なしたままになります。
  - 直し方の案:`ensureGuide` を先に呼ぶ。
- **`src/cli/guide.ts:19` 作り直す案内が、一覧ではなく `whatnext workbench` の node・cli・環境で動く**
  - `paneCommand(env, 'guide')` は、呼んだプロセスの `env.node`/`env.cli` と、`PATH`・`CLAUDE_CONFIG_DIR`・`XDG_STATE_HOME` などを使います。
  - Ghostty の分割から起動したときは一覧と同じ値になります。しかし利用者が別の端末で、更新後の `whatnext workbench` を手で打つと、動いている一覧とは版の違う案内が `@wn_guide` を読みます。
  - `@wn_version` を突き合わせるか、一覧が `paneCommand` の結果をオプションに置き、それを使う形にすると食い違いません。

## 並行性

- **`src/cli/guide.ts:20-21` 同時に作られる場合の処理は妥当**:`new-session` に失敗したら `hasSession` で見直すので、一覧の起動と `whatnext workbench` が重なっても大丈夫です。
- **`lib/tmux/tmux.ts:56` 1秒の待ちは問題なし**:`pane-died` は `run-shell -b` から呼ばれるので、`sleep 1` は tmux サーバを止めません。この1秒の間につないでも、死んだペインが1秒見えるだけで、つなぐこと自体は成り立ちます。

## セキュリティ・プライバシー

- **`lib/tmux/tmux.ts:51` 取り込んだ画面の文字列で命令は動かない**:画面の文字列は、二重引用符の中のコマンド置換として1つの引数で `set -g` に渡ります。sh の注入にはならず、tmux も `set` の値を書式として展開しません。
- **同じ行に、セッション名と cwd のパスが残る(軽微)**:案内の画面の末尾には、claude のセッション名と cwd のパスが写っています。それがサーバ全体のオプションに、サーバが終わるまで残ります。手元のサーバの中だけなので実害は小さいですが、何が残るかを DESIGN.md に一言書いておくと監査しやすくなります。
- **同じ行、原因の手がかりが上書きで消える(設計)**:`@wn_guide_died` は終わるたびに上書きされ、最後の1回の様子しか残りません。原因を突き止めるための値なら、最初の1回が一番役に立つはずです。`WHATNEXT_DEBUG_LOG` に追記するか、最初の分を別に残す案があります。

## 設計

- **`src/cli/list.ts:66-67` オプションを2回入れている**:`ensureGuide` は作ったときに `workbenchOptions` を呼びますが、そのすぐ後でもう一度呼んでいます。既にあるセッションに今の版のオプションを入れ直すために必要なので、害はありません。`ensureGuide` の中の呼び出しを外すか、「呼び出す側が入れる」と契約を揃えると読みやすくなります。
- **`src/ops/names.ts:12` 頼みごとの名前が汎用的**:`GUIDE_REFRESH = 'guide'` は、ほかの頼みごと(`key …`、`focus`、`agentview`)と比べて何をするのか読み取りにくい名前です。`guide-refresh` のような名前のほうが、後で `grep` しても誤って当たりません。
- **`src/cli/workbench.ts:43-51` 同じ処理が3か所目**:「頼みごとを書いて `@wn_pid` に SIGUSR2 を送る」処理は `guide.ts:74-80` にもあり、sh 版の `@wn_req_sh` と合わせて3か所目です。`Tmux` に `request(text)` を1つ置けば、キーの名前の形(`@wn_req_<秒>_<pid>`)の約束を1か所にまとめられます。
- **原因が分からないまま症状を抑える直し方**:今回の直し方は症状を抑えるもので、案内が落ちる原因は分かっていません。CLAUDE.md の学びの捕捉の約束に沿って、`learning` か `bug` の issue に起票されているかを確かめてください。
- **`test/unit/cli.test.ts:26` zsh がないと落ちる**:`it.each(['bash','zsh','sh'])` は zsh が入っていない環境では失敗します。今は CI がなく macOS で流すだけなので、実害はありません。
