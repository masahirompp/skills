PR #2(`wbguide-recover`)を読みました。直し方は原因に見合っていて、方向は妥当です。`exec` の二重付けは、付ける場所を `splitWorkbench` の1か所に絞っていて、bash・zsh・sh で実際に動かすテストもあります。`ensureGuide` は同時に作られた場合を `hasSession` で引き直しています。一覧があるかどうかで、つなげなかったのかサーバが閉じたのかを見分けるのも筋が通っています。ただし、作り直しの上限と原因の手がかりの残し方に穴があり、報告された症状がまた起きえます。重い順に挙げます。

### 正確性

- **`lib/tmux/tmux.ts:52-60` 上限の5回は時間で戻らず、通算で数えている**
  - `@wn_respawned` はペインのオプションです。`respawn-pane` してもペインは同じなので、値は減りません。数日のあいだにまばらに5回落ちると、6回目で `kill-pane` が走ります。
  - そのとき作業台の画面が `wbguide` を映していると、`detach-on-destroy on` で画面ごと離れます。
  - 離れた tmux はたぶん 0 で終わります(これは確かめていません)。0 で終わると `workbench.ts:33` の失敗の判定に入らず、`workbench.ts:38` が行を消して 0 を返します。分割はエラーを出さずに閉じます。
  - つまり今回直したい「開いた直後に閉じる/何も出ずに閉じる」が、回数を使い切ったあとにまた起きます。次に `whatnext workbench` を開けば `ensureGuide` で直りますが、閉じた理由は画面に何も出ません。
  - 目的は「起動してすぐ終わるときに回り続けない」なので、たとえば「前に起動してから N 秒以上動いていたら数を 0 に戻す」ほうが目的に合います。起動した時刻をペインのオプションに残せば判定できます。
- **`lib/tmux/tmux.ts:51` の `@wn_guide_died` は毎回上書きされ、最初の手がかりが消える**
  - 原因はまだ分かっておらず、この値はそれを探るための手がかりです(DESIGN.md の追加部分)。なのに5回落ちると、最後の1回の様子しか残りません。
  - しかも残すのは「空行を除いた画面の末尾5行」です。案内の node が例外で落ちた場合、末尾5行は `Node.js v24.x` とスタックの下のほうになりがちで、肝心のエラーの1行目が消えます。
  - `src/cli/guide.ts` には `uncaughtException` と `unhandledRejection` の受け手がありません。一覧には `list.ts:117-118` にあります。案内でも同じく `WHATNEXT_DEBUG_LOG` に書かせるほうが、手がかりとして確かです。
- **`test/e2e/workbench.test.ts:255` の `signal=kill` は macOS の tmux でしか通らない見込みが高い**
  - tmux の `#{pane_dead_signal}` は、`sys_signame` があれば小文字の名前、なければ番号を返す作りだと理解しています。Linux では `signal=9` になりそうです。実機では確かめていません。
  - 作るもの自体が Ghostty と osascript 前提なので、影響は小さいです。それでも `/signal=(kill|9)/` にしておくのが無難です。
- **`src/cli/workbench.ts:33` で、tmux がシグナルで終わったときも「つなげなかった」と出す**
  - シグナルで終わると `res.status` は `null` になり、`null !== 0` が真になります。一覧が残っていれば、誤ったメッセージを出して `fail()` に入ります。
  - 端末を閉じた場合は、node も SIGHUP で終わるので実害は出にくいです。とはいえ、判定は `res.status !== null && res.status !== 0` のように意図を明示したほうが読み違えません。

### 並行性

- **`src/cli/workbench.ts:42-51` で、頼みごとを一覧に渡す手順の実装が3つ目になる**
  - すでに sh の `@wn_req_sh`(`lib/tmux/tmux.ts:26-31`)と `src/cli/guide.ts:74-80` があり、どちらも「`@wn_req_<秒>_<pid>` に書き、`@wn_pid` に SIGUSR2 を送る」手順です。
  - 名前の決め方は `takeRequests`(`tmux.ts:243-262`)の並べ方と食い違ってはならないのに、3か所にばらけています。
  - 名前は秒と pid だけでできているので、同じプロセスが1秒に2回頼むと前のものを上書きします。今は1回しか呼ばないので問題は出ません。
  - `Tmux.request(line)` として lib にまとめるのが本筋です。lib は昇格済みなので、`docs/lib/tmux.md` の契約にも足す必要があります。
- **`src/ops/app.ts:1156-1160` の `guide` の頼みごとが、`wbTty` がまだないと効かずに終わることがある**
  - `doFollow` は `this.wbTty` がないと何もせずに戻ります(`app.ts:1468`)。`myTty()` が取れなかった場合(`workbench.ts:16-20`)、名前は空のままになり、自分からは直りません。
  - `lastGuide` が `undefined` のまま残るので、次に何かが follow を呼べば直ります。重さは中程度です。E2E は tty が取れる場合しか確かめていません。
- 順序の問題は見つかりませんでした。`ensureGuide` の作成と、一覧の `setSessionName` が前後しても、知らせ(`askListToRefreshGuide`)は `workbenchOptions(GUIDE, '')` のあとに送られるので、最後には一覧の名前が勝ちます。

### 設計

- **`src/cli/workbench.ts:22` で、`whatnext workbench` 側が作る案内は、一覧ではなく workbench のプロセスの環境と版で動く**
  - `paneCommand(env, 'guide')` が使うのは、workbench のプロセスの `process.env`(PATH、LANG、XDG_STATE_HOME など)と、そのプロセスの `env.node`/`env.cli` です。
  - 利用者が別に入れた whatnext(`npx` など)で `whatnext workbench` を打つと、一覧と版の違う案内が動きえます。
  - `scripts` には「動いている一覧と同じ版のものを使わせる」という方針があります(`tmux.ts:21` のコメント)。それと合わせるなら、一覧が起動時に案内のコマンドを `@wn_guide_cmd` のようなオプションに置き、workbench はそれで作るほうが一貫します。
  - Ghostty の分割から開く場合は一覧のパスを使うので、実害が出るのは手で打った場合に限られます。
- **`src/cli/list.ts:66-67` で、作ったときに `workbenchOptions(GUIDE, '')` が2回走る**
  - `ensureGuide` が作ったときに呼び、`list.ts:67` でもう一度呼んでいます。
  - 引き継いだ案内のためには list 側の呼び出しが要るので、どちらかを消すのではなく、`ensureGuide` が `'exists'` を返したときだけ呼ぶなど、意図が読める形にしたほうがよいです。
- **`lib/tmux/tmux.test.ts:75-81` のテストは文字列が含まれるかしか見ていない**
  - 5回を超えたら畳むという肝心の動きを、実際には動かしていません。`-lt 5` を `-le 5` に変えても通ります。
  - E2E は1回の作り直ししか試していません。`@wn_respawned` を 5 に置いてから落とす E2E を1本足せば、上限の動きを確かめられます。
- **PR の本文「確かめたこと」によると、Ghostty と bash の実機は流していない**
  - bash の失敗は、打ち込む文字列を `sh -c` で動かす単体テストで押さえています。Ghostty の `initial input` の渡し方そのものは確かめていません。
  - 報告された症状の半分はこの経路なので、`test/real` を一度流してから閉じる価値はあります。

### セキュリティ・プライバシー

- `lib/tmux/tmux.ts:51` で画面の中身を残しますが、問題は見つかりませんでした。取った値は `$(...)` の中で展開されるだけで、シェルが読み直すことはありません。`tr` で末尾が空白になるので、tmux が引数の末尾の `;` を区切りと読む心配もありません。
- `@wn_guide_died` には、案内の画面の末尾(セッションの名前と作業場所のパス)が入ります。ただし tmux サーバのメモリにあるだけで、ファイルにも外部にも出ません。案内のログをファイルに書くように変えるときは、出力先が `WHATNEXT_DEBUG_LOG` と同じ扱い(手元だけ)になることを確かめてください。

### 差分の外で気づいたこと

- `lib/tmux/tmux.ts:399-406` の `signalGuide` が読む `@wn_guide_pid` を、書いているコードがリポジトリのどこにもありません(grep で確かめました)。そのため一覧からの知らせはいつも何もせず、案内は 300ms ごとの読み直しだけで画面を更新しています。
- 今回の不具合とは関係ありませんが、案内が落ちた原因を探すときに、知らせが届いている前提で考えないよう、知っておいたほうがよい事実です。

自分で判断する材料として一つ問いを置きます。作り直しは症状を隠す手当てです。案内が落ちる原因が分かる前に回数を5回にして、上限に達したときに理由を何も出さずに閉じる今の作りで、次に再発したとき原因に迫れるでしょうか。迫れないなら、上限より先に、落ちたときの記録(案内での例外の記録と、最初の1回の保存)を固めるほうが優先です。
