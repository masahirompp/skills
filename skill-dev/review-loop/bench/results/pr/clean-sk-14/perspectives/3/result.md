PR #1 には、そのまま削除の誤りにつながる重大な不具合は見つかりませんでした。テスト `skill-dev/housekeeping/test.sh` は一時ディレクトリの中で動き、手元でも全件成功しました(作業ツリーは clean のまま)。PR が狙う「一時ファイルを作れないと削除する側に倒れる」経路は、判定に使う箇所ではおおむね塞がっています。以下は残っている穴と設計上の懸念で、重要な順に並べています。

## 正確性

- **`skills/housekeeping/scripts/lib.sh:96`:「lsof にプロセスが見えているか」の判定が、自分自身が見えるかどうかしか確かめていません。**
  - 起きること: 自分は見えるのに他のプロセスが見えない環境では、使用中の worktree が「使用中でない」と判定され、`delete` に倒れます。
  - 具体例: devcontainer など PID 名前空間で区切られたコンテナで、ホスト側のエディタやシェルが bind mount 越しに worktree を開いている場合です。コンテナの中の lsof には自分のプロセスしか出ないので、この判定は通ってしまいます。この PR は「見えないなら残す」を目的にしていますが、一部だけ見える場合は防げていません。
  - なお、手元の macOS(サンドボックスの外)では lsof に 598 プロセスが出ており、一部だけ見える状況は再現できていません。
  - 案: PID 1 や親プロセス(`$PPID`)が一覧にあるか、または `ps` で数えたプロセス数と lsof に出た数がおおむね合うかも条件に加えます。それでも完全には判定できないので、SKILL.md に限界として書いておく方が誠実です。

- **`skills/housekeeping/scripts/scan.sh:143`、`:151`、`:156`、`:184`:一時ファイルを作ったあとの書き込みの失敗を確かめていません。**
  - `git worktree list --porcelain >"$tmp/wt"` が失敗したり、`>>"$tmp/wt-branches"` が書けなかったり(容量不足など)すると、worktree の情報が無いままブランチを判定します。その結果、使用中や未コミットの変更がある worktree のブランチも `delete` になり得ます。
  - 実際には、`git branch -D` がチェックアウト中のブランチを拒否するので、消されはしません。ただ、`$tmp/first-parent`(`scan.sh:85-86`)だけ `-s` で確かめているのと扱いが揃っていません。
  - 案: `git worktree list` の終了コードを確かめ、`$tmp/wt` が空なら止めます(少なくともメインの worktree が1行あるはずです)。

- **`skills/housekeeping/scripts/scan.sh:104-105`:`hk_is_protected` は、保護パターンの一覧を取れなかったときも 0 を返します(`lib.sh:62`)。**
  - 安全側には倒れていますが、出力の理由が「保護対象(既定ブランチ・監査用・設定による保護)」になります。設定を読めなかったことが利用者に伝わりません。
  - 案: 失敗を別の終了コード(例: 2)で返し、理由を分けます。

## 設計

- **`skills/housekeeping/scripts/lib.sh:101-109` と `SKILL.md:70`、`SKILL.md:79`:「使用中」と「確かめられない」という別々の状態を、1つの文字列で返しています。**
  - 呼び出し側の `scan.sh:164-165` と `apply.sh:42-43` は2つを区別できず、理由の文言も「使用中か、確かめられない」と曖昧になっています。
  - SKILL.md は、エージェントに「lsof でプロセスを確かめられない」という文言を見分けさせています。メッセージを書き換えると案内が働かなくなる、壊れやすい取り決めです。
  - 案: 終了コードで分けます(0: 使用中でない / 1: 使用中 / 2: 確かめられない)。そのうえで、理由の文言を状態ごとに固定します。

- **`lib.sh:89-97`:lsof が無い環境では、すべての worktree が永久に `keep` になり、回避の手段もありません。**
  - Linux の最小構成のコンテナなどでは lsof が無いことがよくあります。この PR から、スキルが実質的に worktree を消せなくなります。
  - 案: Linux では `/proc/*/cwd` を読んで代わりに使います。安全側に倒すという判断自体は妥当なので、代わりの手段で補うのがよいと考えます。

- **`skill-dev/housekeeping/test.sh`(ヒアドキュメントを禁じるテスト):書き方で確かめるのは割り切りとして妥当です。ただし範囲が足りません。**
  - `<<` で検出するので、`$((1<<2))` のようなビットシフトでも失敗します(誤検出)。
  - 偽の lsof(`exit 1`)は「何も出ない」場合しか試していません。上の正確性の1件目にある「自分だけ見える」場合はテストされていません。

## 並行性

- **`SKILL.md:20`、`SKILL.md:61`:走査結果を固定のファイル名 `${TMPDIR:-/tmp}/housekeeping-scan.tsv` に書いています。**
  - 同じユーザーが複数のセッションで別々のリポジトリを並行して片付けると(このリポジトリでもレビューを並列に回しています)、互いの scan.tsv を上書きします。その結果、別のリポジトリ向けの行が apply.sh に渡り得ます。
  - apply.sh が sha を照合し、`git worktree remove` が他のリポジトリの worktree を拒否するので、実際に消されることはまずありません。ただ、判断の土台が取り違えられる点は問題です。
  - 案: `mktemp "${TMPDIR:-/tmp}/housekeeping-scan.XXXXXX"` でファイルを作り、そのパスを使うよう案内します。

- **`apply.sh:37`:プロセスの一覧を、ループの前に1回だけ取っています。**
  - 取ったあとに worktree でプロセスが動き出しても検出されません(この PR より前からある、時刻のずれによる問題です)。
  - worktree が多いときは、各行の直前に取り直せば隙間を狭められます。lsof を何度も呼ぶ負担とのトレードオフです。

## セキュリティ

- **`SKILL.md:20`:`TMPDIR` が未設定の Linux では、全ユーザーが書き込める `/tmp` の、名前が予測できるファイルに `>` で書きます。**
  - 他のユーザーがシンボリックリンクを先に置いて、書き込み先を差し替える攻撃が考えられます。`fs.protected_symlinks=1` であれば防がれます。
  - 他のユーザーが行を仕込んだファイルを先に置き、走査の書き込みが失敗したのに気づかず apply.sh に流す、という経路も考えられます。この場合は sha の照合で大部分が弾かれます。
  - 深刻度は低めです。修正前は `$TMPDIR` が未設定だと `/housekeeping-scan.tsv` になっていたので、改善はしています。上の `mktemp` の案で一緒に解消できます。

## プライバシー

- 新たな懸念はありません。エラー文に出るのは `$base`(一時ディレクトリのパス)と、もとからあった gh の stderr だけで、外部に送るものは増えていません。SKILL.md は `!` で実行するコマンドに絶対パスを書くよう求めていますが、出るのは手元の会話の中だけです。

## 妥当と判断した点

次の変更は根拠を持って妥当と判断しました。
- `scan.sh:81-86`:存在する ref だけを `rev-list` に渡し、空なら止めます。修正前は、取り込み済みのブランチがすべて「merge コミットで取り込み済み」の `delete` に倒れていたので、実害のあった不具合の修正です。
- `scan.sh:46`:PR 一覧が JSON の配列か確かめ、`scan.sh:134`:状態の分からない PR を `keep` にします。
- `lib.sh:47-51`:`git config` の終了コード 1 を、それ以外の失敗と区別しています。
- `hk_parse_action`:判定の結果の形が想定と違えば `keep` に倒します。

このうち `hk_parse_action` で残す側に倒す仕組みは、ヒアドキュメントを外すことよりも本質的な対策です。今後、判定を出力する関数を増やしたときも、この関数を通すことを決まりにしておくとよいと考えます。

確認していただきたいのは1点です。上の正確性の1件目は、利用する環境でどこまで起こり得るかで重要度が変わります。このスキルをコンテナや devcontainer の中で使う予定はありますか。
