## 指摘(重い順)

- **[セキュリティ / プライバシー / 並行性] `skills/housekeeping/SKILL.md:20`, `:61`**: 走査結果を `${TMPDIR:-/tmp}/housekeeping-scan.tsv` という決まった名前で書いています。`TMPDIR` が未設定の Linux では、全ユーザーが書ける `/tmp` に置かれます。`/tmp` への逃げ道はこの PR で加わりました(元は `$TMPDIR` だけ)。
  - セキュリティ: 別のローカルユーザーが同じ名前のファイルを誰でも書ける権限で先に作れば、scan.sh はそこに書き込みます。そのユーザーは走査と apply の間に `keep` の行を `delete` に書き換えられます。apply.sh が確かめ直すのは sha と保護パターンだけで、オープン PR があるかや未取り込みのコミットがあるかは見ません。そのため、残すべきブランチに `git branch -D` やリモートの削除が走ります。
  - プライバシー: umask が 022 なら、ブランチ名・worktree のパス・プロセス名が他のユーザーから読めます。
  - 並行性: 同じマシンで別のリポジトリや別のセッションが同時に走ると、互いのファイルを上書きします。
  - 対策: `scan_tsv=$(mktemp "${TMPDIR:-/tmp}/housekeeping-scan.XXXXXX")` のように、毎回一意で 0600 のファイルにし、そのパスを apply の手順に引き継ぐよう書き換えるのがよいです。

- **[正確性 / 安全側への倒れ方] `skills/housekeeping/scripts/lib.sh:96`**: 「自分自身(`$$`)が一覧に出れば、プロセスを見られる」とみなす判定は、全く見えない場合しか見分けられません。Seatbelt のような制限が「同じサンドボックスの中のプロセスだけ見せる」形なら、自分は見えて、外のエディタやシェルだけが消えます。その結果、使用中の worktree が「使用中でない」と判定され、`delete` の候補になります(fail-open)。
  - この環境では lsof に 597 件、`ps` に 911 件のプロセスが見えました。差は root 所有のプロセスだと思われ、部分的に見えなくなる現象は再現できていません。可能性の指摘にとどまります。
  - 対策: 外にあると分かっているプロセス(例えばログインシェルの祖先)が見えるかを調べる方法があります。それが無理なら、SKILL.md に「自分が見えても、他のプロセスが見えている保証はない」と限界を書いておくのが妥当です。

- **[正確性 / 文書] `skills/housekeeping/SKILL.md:72` と `skills/housekeeping/scripts/apply.sh:21`**: 「何も渡さないと、何も消さずに終わる」と書いていますが、これが成り立つのは標準入力が EOF のときだけです。`!` でパイプを付けずに apply.sh を実行し、標準入力が端末につながっていれば、`grep` が入力を待ったまま止まります。
  - 対策: apply.sh の先頭で `[ -t 0 ] && { echo "error: 承認した行を標準入力で渡す" >&2; exit 1; }` とするか、文書の書き方を改めます。

- **[設計] `skills/housekeeping/scripts/lib.sh:46`**: `hk_protect_patterns` の中の `set -f` が外に漏れないのは、`$(...)` の中で呼んだときだけです(コメントもそれを前提にしています)。将来、直接呼ばれると呼び出し元の設定を書き換えます。macOS 標準の bash 3.2 には `local -` が無いので、今の書き方は仕方がありません。ただ、この前提は関数名かコメントの冒頭ではっきり示すか、関数の中で `( ... )` に包んで閉じ込める方が安全です。

- **[設計 / テスト] `skill-dev/housekeeping/test.sh` の `temp_usage`**: ヒアドキュメントが無いことを `'<<'` の grep で確かめています。これでは、行の途中のコメントや文字列に含まれる `<<` も失敗になり、逆に `eval` などで間接的に使われると見逃します。今の規模なら実用上は十分ですが、確かめているのは書き方の規約であり、動きそのものではありません。PR 本文では「ヒアドキュメントへの依存を外した」ことの保証として読めるので、テストの名前を規約の確認だと分かるものにしておくのが正確です。

## 確かめて問題なかった点

- `scan.sh:81-86`: 存在する ref だけを `rev-list` に渡す修正は正しいです。元のコードでは、ローカルの `main` が無いだけで first-parent の履歴が空になり、取り込み済みのブランチがすべて `delete` になっていました。この PR で一番価値のある修正です。
- `scan.sh:46` と `parse_pr_info`: トップレベルの検証が配列かどうかだけでも、`open_pr_based_on` と `pr_info` は同じ JSON を走査します。要素が壊れていれば、両方の jq が失敗して `st=UNKNOWN` から `keep` に倒れます。抜け道は見つかりませんでした。
- `scan.sh:127-128`(reflog の照合): `git reflog` が失敗すると、pipefail によって `ask` に倒れます。安全側です。
- `apply.sh:42`: `cd` に失敗するとパスが空になり、どのプロセスにも一致して使用中と判定されます。偶然ですが安全側に倒れています。
- `hk_mktemp_dir`: `mktemp -d` は 0700 で作るので、`/tmp` に置いても問題ありません。

## 判断の材料

一番目の指摘が実際に効くかは、他のユーザーと共有するマシンで使うかどうかによります。個人の Mac だけで使うなら、`$TMPDIR` はユーザーごとの場所なので、実害はほぼ同時実行の衝突だけです。ただ、このスキルは Linux や開発用サーバーでも動く書き方なので、一意なファイル名にしておく手間は小さく、得るものの方が大きいと考えます。

二番目は、「`$$` が見えるなら全部見える」という前提を反証できる環境があるかどうかが分かれ目です。Claude Code のサンドボックスのプロセス可視性の設定を確かめる価値があります。
