# PR #1 レビュー(housekeeping: mktemp の失敗で止まり、TMPDIR に従わせる)

全体としては妥当な修正です。一番大きいのは、これまで削除側に倒れていた経路を残す側に倒したことです。具体的には、first-parent の履歴が空になると全件 delete になっていた件、読めない PR 一覧で保護が外れていた件、ヒアドキュメントが空になる件の3つです。`hk_mktemp_dir` は `mktemp -d` にテンプレートを付けて呼ぶので、作られるディレクトリは 0700 で、名前も予測できません。trap は作成に成功してから張っています。どちらにも問題はありません。

以下の指摘は、重いものから順に並べています。

## セキュリティ / プライバシー

- **`skills/housekeeping/SKILL.md:20`, `:61`: `TMPDIR` が無いときの退避先が、共有の `/tmp` の決め打ちのファイル名(`/tmp/housekeeping-scan.tsv`)になる。**
  - Linux の多人数ホストでは、別のユーザーがこのファイルを先に 0666 で作っておけます。すると scan と apply の間に、`delete` 行を差し込めます。sha も同じファイルから読めるので、apply.sh の sha の照合も通ってしまいます。結果として、承認した覚えのないローカルブランチの `-D` や、リモートブランチの `--force-with-lease` による削除が起きえます。
  - umask 022 だと TSV は 0644 で作られます。中身はリポジトリのパス、ブランチ名、ignored のファイル名で、この PR からはプロセスのコマンド名も加わります。これらがほかのユーザーから読めます。
  - 変更前の `"$TMPDIR/..."` は、未設定なら `/housekeeping-scan.tsv` に書こうとして失敗していました。退避先の `/tmp` はこの PR で入ったものです。
  - 案: 走査の結果も `mktemp`(テンプレート付き)で作ったファイルに書き、そのパスを持ち回る手順にする。
- **同じ箇所(並行性): 名前が固定なので、同時に走る2つの housekeeping が互いの結果を上書きする。** 同じリポジトリの clone が2つあると、ブランチ名も sha も一致します。そのため、もう一方の結果の行が apply.sh の照合を通ります。これは変更前の `$TMPDIR` 版からある問題ですが、上と同じ直し方で解消できます。

## 正確性

- **`skills/housekeeping/scripts/lib.sh:96`: 「自分自身が一覧に出るか」だけでは、一部のプロセスしか見えない状態を見分けられない。**
  - この環境で試したところ、`lsof -d cwd` が出したのは 597 プロセスで、`ps -A` の 912 より少なく、自分自身は見えていました。
  - サンドボックスが同じユーザーのほかのプロセス(外のターミナルやエディタ)を隠し、自分の子孫だけを見せる場合、このチェックは通ります。そうなると、使用中の worktree が delete になります(fail-open)。
  - 未検証で、Seatbelt が同じユーザーのプロセスをどこまで隠すかによります。
  - 案: 親プロセス(`$PPID`)、またはサンドボックスの外にあると分かっているプロセスが見えることも条件にする。完全な判定ができないなら、そのことを SKILL.md に明記する。
- **`skills/housekeeping/scripts/scan.sh:208`: worktree が「確かめられない」で keep になっても、そのブランチの理由は `worktree … で使用中` と出る。** この PR から、サンドボックスの中ではすべての worktree が keep になります。そのため、使用中でないのに「使用中」と報告する場面が普通に起きます。SKILL.md では、確かめられないときは外で実行し直すよう案内していますが、ブランチの行の理由からはその判断ができません。worktree 側の reason を引き継ぐのが妥当です。
- **`skills/housekeeping/scripts/lib.sh:24`: `TMPDIR` が相対パスでも、そのまま使われる。** カレントの worktree の中にディレクトリができます。scan.sh の中で cd しないので、今の作りでは片付けも含めて壊れません。ただ、前提が暗黙なので、`case $base in /*)` で弾くか絶対パスに直しておくと安全です。軽微です。
- **`skills/housekeeping/scripts/lib.sh:51`: `git config --get-all` の終了コード 1 には、「キーが無い」のほかに「キー名が不正」も含まれる。** キー名は固定なので、実害はありません。コメントの「1 はキーが無いだけ」は、厳密には言い切りすぎです。指摘というより注記です。

## 設計 / テスト

- **`skill-dev/housekeeping/test.sh:164`: lsof のテストは、何も見えないケース(exit 1、出力なし)しか試していない。**
  - 上の「一部だけ見える」ケースが試されていません。自分自身の行だけを返す偽の lsof を置けば、今の実装が delete に倒れることを再現できるはずです。
  - 直す方針を決める前に、まずこの再現テストを書くことを勧めます。
- **`skills/housekeeping/scripts/lib.sh` 冒頭のコメントと、test.sh の静的なチェック: 「ヒアドキュメントが一時ファイルを使う」ことを、grep で書き方を禁じて守っている。**
  - 根拠そのものは正しいです。この環境の `/bin/bash` は 3.2.57 で、ヒアドキュメントに一時ファイルを使います。
  - ただし、grep で見ているのは scan.sh、apply.sh、lib.sh の3つだけです。lib.sh を source する別のスクリプトや、今後足す関数は守られません。
  - 根本の対策は、fail-open にならない作り(hk_parse_action のように、判定の結果が空なら keep)をすべての入口でそろえることです。今回、判定の経路ではそうなっています。静的なチェックは、補助として位置づけるのが妥当だと考えます。

## 検討の材料

- 「サンドボックスの中では worktree をすべて残し、外で実行してもらう」という方針は、安全側の判断としては正しいです。ただ、その分の手間は運用で毎回かかります。この方式で、ユーザーが毎回 `!` で実行することに耐えられるかは確かめておく価値があります。
- 別の選択肢として、サンドボックスの中では worktree の削除を候補にすら出さず、ブランチの判定だけを行うモードも考えられます。
