PR #1(`housekeeping-mktemp`)をレビューしました。手元で `skill-dev/housekeeping/test.sh` を macOS 標準の bash 3.2.57 で実行し、全件成功しています。作業ツリーは変更していません。

全体として、PR の目的(mktemp が失敗したら止まる、ヒアドキュメントが空になったときに削除側へ倒れる経路を塞ぐ)はよく達成されています。`hk_parse_action` で判定の結果の形を確かめる設計や、存在する ref だけを `rev-list` に渡す修正は、実際に削除側へ倒れていた不具合を直しており妥当です。ほかに残る指摘は次のとおりです。

### 安全性(削除側に倒れうるもの)

- **`skills/housekeeping/scripts/lib.sh:96`**: 「自分自身が lsof の一覧に出れば、ほかのプロセスも見えている」と仮定しています。この仮定は保証されません。
  - サンドボックスの権限は、自プロセスやその子プロセスだけを見せる設定にもできます。その場合、自分は見えてもユーザーのエディタやシェルは一覧に出ません。
  - その状態ではどの worktree も「使用中でない」と判定され、削除候補になります。この PR が塞ごうとしている fail-open と同じ形です。
  - Claude Code のサンドボックスが実際にそう振る舞うかは確かめていません。問題の可能性として挙げています。
  - 対策案は二つです。
    - 自分のプロセスツリーの外にあるプロセス(親をたどった先のログインシェルや端末)が一覧に出るかで判定する。
    - 自分と祖先以外のプロセスが1つも無ければ「確かめられない」とみなす。
- **`skill-dev/housekeeping/test.sh:164`**: 偽の lsof は `exit 1` で何も出さない場合しか試していません。次の2つの場合はテストがありません。
  - lsof がそもそも無い場合(`lib.sh:91` の `command -v` の経路)。
  - 自分の行だけを出す場合。上の仮定が崩れる経路で、どう判定すべきかもテストで固めていません。

### 表示が実態と食い違うもの

- **`skills/housekeeping/scripts/scan.sh:208`**: lsof で確かめられずに worktree を keep にしたとき、そのブランチの理由が「worktree X で使用中」になります。実際には使用中かどうか分かっていません。SKILL.md は「確かめられない」なら `!` で外で走査し直すよう案内していますが、ブランチの行からはこの原因が分かりません。`test.sh:30` も action が keep かしか見ていません。wt-branches に理由も残して引き継ぐと直ります。
- **`skills/housekeeping/scripts/apply.sh:43` / `scan.sh:165`**: `hk_path_in_use` が返す文字列「lsof でプロセスを確かめられない」をそのまま括弧に入れるため、「プロセスが使用中か、確かめられない(lsof でプロセスを確かめられない)」と同じ言葉が重なります。また「使用中」と「確かめられない」が1つの文にまとまっていて、ユーザーはどちらなのか読み分けなければなりません。SKILL.md:179 で二つを分けて伝えさせているので、理由の文言を出し分けるほうが一貫します。

### 保守性

- **`skills/housekeeping/scripts/lib.sh:46`**: 関数の中の `set -f` は、`$(...)` の中で呼ばれる前提でしか外に漏れません。今の呼び出し元は `hk_is_protected` だけで問題はありません。ただ、将来この関数を直接呼ぶと、呼び出し元の設定を変えてしまいます。`set -f` を使わずに、`HOUSEKEEPING_PROTECT` も `hk_is_protected` と同じく文字列を1語ずつ切り出して照合すれば、この前提自体が要らなくなります。
- **`skill-dev/housekeeping/test.sh:64-66`**: ヒアドキュメントが無いことの確認はパターン照合なので、行の途中のコメントや文字列リテラルに `<<` があると誤検知します。ただ、誤検知しても失敗する側に倒れるだけで実害はありません。代わりの方法も作りにくいので、今の形で妥当だと考えます。

### 問題ないと確かめた点

- `scan.sh:85` の `$fp_refs` はクォートしていませんが、lib.sh が `set -f` しており、ref 名に空白は入らないので安全です。
- `parse_pr_info` は jq が失敗して空になると `UNKNOWN` になり、keep に倒れます。`open_pr_based_on` が失敗した場合も、続く `pr_info` が同じく失敗して keep(リモートブランチの場合は飛ばす)になります。保護は外れません。
- `apply.sh:20` の `input=$(grep -v ...)` は、入力が空だと grep が 1 を返します。apply.sh は `set -e` ではないので止まらず、「何も消さずに終わる」という SKILL.md の記述どおりに動きます。

一番大きいのは、最初に挙げた「自分が見えれば、ほかのプロセスも見えている」という仮定です。マージする前に、実際のサンドボックスの中で `lsof -w -a -d cwd -Fpcn` を実行し、自分以外のプロセス(ユーザーのエディタやシェル)の cwd が出るかを確かめてください。
