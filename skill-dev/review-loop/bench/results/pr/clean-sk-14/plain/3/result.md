PR #1(`housekeeping-mktemp` → `main`、head `8a3b4f6` で、ローカルの HEAD と一致)をレビューしました。`skill-dev/housekeeping/test.sh` を手元(macOS、bash 3.2.57)で実行し、全件成功しました。作業ツリーは変わっていません。

PR の中心の修正は、いずれも妥当だと判断しました。
- `hk_mktemp_dir` でテンプレートを付けて作り、fetch より前に止める
- ヒアドキュメントを外す
- 判定の結果が想定外の形なら `hk_parse_action` で keep に倒す
- first-parent の履歴に渡す ref を、存在するものだけに絞る

「テンプレートを付けない macOS の `mktemp` は TMPDIR を見ない」という前提も、`TMPDIR=/tmp/zz mktemp -u -d` が `/var/folders/...` を返すことで確かめました。指摘は以下です。

## 指摘

- **[重要・推測を含む] `skills/housekeeping/scripts/lib.sh:96`: 「自分自身が一覧に出るか」だけでは、一部のプロセスしか見えない場合を見逃す**
  - 今の判定で捕まえられるのは、何も見えない場合だけです。
  - サンドボックスが「同じサンドボックスの中のプロセスだけ見せる」作りだと、`$$` は一覧に出るので確認を通ってしまいます。sandbox-runtime の Seatbelt プロファイルは `process-info* (target same-sandbox)` だったと記憶していますが、この会話では確かめていません。
  - その場合、ユーザーのシェルやエディタなど外のプロセスは一覧に出ません。そのプロセスがカレントにしている worktree も「使用中でない」とされ、`delete` 候補になります。この PR が塞ごうとしている fail-open そのものです。
  - `SKILL.md:70` 自身も「サンドボックスの中では、ほかのプロセスを見られないことがある」と書いています。
  - 対策案: `ps -U "$(id -u)" -o pid=` の件数と lsof の件数を比べる、`$PPID` より上の祖先(サンドボックスの外のプロセス)が見えるかを確かめる、など。
  - この会話はサンドボックスの外で動いていて(lsof で 597 プロセスが見え、`$PPID` も見えた)、サンドボックスの中の挙動は再現できていません。実際のサンドボックスの中で `lsof -w -a -d cwd -Fp` に何が出るかを一度確かめてください。

- **`skills/housekeeping/scripts/lib.sh:108` と `skills/housekeeping/scripts/scan.sh:165`、`skills/housekeeping/scripts/apply.sh:43`: 理由の文が「使用中」と「確かめられない」を区別していない**
  - 確かめられないときは「…使用中か、確かめられない(lsof でプロセスを確かめられない)」と同じことが二重に出ます。
  - 本当に使用中のときは「…使用中か、確かめられない(pid 123 sleep)」となり、どちらの意味かが読み手に伝わりません。
  - `SKILL.md:70,79` は、理由に「lsof でプロセスを確かめられない」が含まれるかで案内を分けるようエージェントに指示しています。今は部分一致で動きますが、文言が変わると黙って壊れます。
  - 対策案: `hk_path_in_use` が状態を区別して返し(終了コードや接頭辞)、呼び出し側で「プロセスが使用中(pid …)」と「lsof でプロセスを確かめられない」を別の文にする。

- **`skills/housekeeping/scripts/scan.sh:208`: worktree を「確かめられない」で残したとき、そのブランチの行が「worktree … で使用中」になる**
  - サンドボックスの中で走査すると、すべての worktree が keep になります。そのブランチの行は、どれも「使用中」と出ます。
  - 確かめられなかっただけなのに使用中と報告され、`SKILL.md:79` が求める区別と食い違います。worktree の行の理由をブランチの行に引き継ぐか、「worktree … を残すため」のような中立的な文にするのがよいと考えます。

- **`skill-dev/housekeeping/test.sh:163-165`: lsof が見えないときのテストは、何も出さない偽の lsof しか使っていない**
  - 1点目の「自分は見えるが、ほかは見えない」場合を確かめるテストがありません。
  - 自分の pid の行だけを出す偽の lsof(引数を見て `p$PPID` などを出すスクリプト)で、`wt-busy` が keep になるかを確かめるケースを足すとよいです。今の実装では、このテストは失敗するはずです(推測で、実行はしていません)。

- **[軽微] `skills/housekeeping/scripts/lib.sh:46`: `set -f` を関数の中で実行する前提を、コメントにしか書いていない**
  - コメントは「`$(...)` の中で呼ぶので外には漏れない」としていますが、`hk_protect_patterns` を直接呼べば呼び出し元に漏れます。
  - 実害は小さいです(lib.sh:14 で全体に `set -f` 済みのため)。漏れないことを保証したいなら、関数の本体を `( … )` のサブシェルにする手があります。

- **[軽微] `skills/housekeeping/SKILL.md:20,61`: `TMPDIR` が未設定だと、ほかのユーザーと共有する `/tmp` の固定のファイル名に結果を書く**
  - Linux などで TMPDIR が未設定だと `/tmp/housekeeping-scan.tsv` になります。ほかのユーザーが同名のファイルやシンボリックリンクを先に置けば、上書きされたり、すり替えた行を apply.sh に渡されたりし得ます。
  - 承認の前に行をユーザーに見せる手順があるので、危険は低いです。それでも、手順1でも `mktemp` を使ってパスを作るよう案内したほうが一貫します。

## 確かめて問題が無かった点
- bash 3.2 で `$'\n'` をパターンに使う書き方(`${rest%%$'\n'*}`、`case … in *$'\n'*`)は、テストを通じて動いた
- `handle_wt` の中の `hk_parse_action` は、動的スコープによって `local action reason` に書き込む
- `HOUSEKEEPING_PR_JSON` の `cp` が失敗しても、続く `jq -e` で止まる

ここまでの指摘のうち、1点目(一部のプロセスしか見えない場合の見逃し)だけが、この PR の目的(サンドボックスで fail-open にしないこと)に直接関わります。マージの前に、実際のサンドボックスで lsof に何が出るかを確かめることを勧めます。
