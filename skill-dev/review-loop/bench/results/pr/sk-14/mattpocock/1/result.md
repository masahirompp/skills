規約の出典は `README.md` だけです。`CODING_STANDARDS.md`・`CONTRIBUTING.md`・`CLAUDE.md` はありません。起点の Issue もないため、PR #1 の本文を仕様として扱いました。2つのサブエージェントの報告のうち Spec 軸の (c)-1 と (c)-2 は、私が `test.sh` の差分を読んで中身を確かめました。(c)-1 の根拠である「macOS の mktemp はテンプレートなしだと TMPDIR を見ない」は、PR 本文にも書かれています。

## Standards

**ハード違反はありません。** README の規約はすべて守られています。具体的には、SKILL.md の frontmatter を変えていないこと、テストを `skill-dev/` に置いていること、housekeeping をスクリプトのテストで検証していることの3点です。既存コードの書き方にも合っています。`hk_` 接頭辞と `local` 宣言、`echo "error: ..." >&2; exit 1` の形、test.sh の `set +e … rc=$? … set -e` と `pass`/`fail` がその例です。

判断事項は2点です。

- **Duplicated Code の可能性(`lib.sh` / `scan.sh`)**
  - 既定値の連鎖 `${HOUSEKEEPING_TMPDIR:-${TMPDIR:-/tmp}}` が、`hk_mktemp_dir` の中と scan.sh のエラーメッセージの2か所にあります。
  - 片方だけ順序を変えると、エラーに出るパスが実際に使ったパスとずれます。
  - `hk_tmp_base` を一度だけ決めておけば、直す場所が1か所になります(`hk_remote` と同じやり方)。軽微です。
- **SKILL.md の箇条が長い**
  - 「サンドボックスの制限」の箇条は1文に3つの内容を詰めています。案内するコマンドの形、パスを展開済みで書く理由、apply.sh が失敗したときの対応です。
  - apply.sh の部分を別の文に分けると読みやすくなります。規約違反ではありません。

ベースラインのスメルは上の1件以外ありませんでした。`hk_mktemp_dir` の呼び出し元は1か所だけですが、置き場所が共通処理用の lib.sh なので Speculative Generality には当たりません。

## Spec

**仕様の要件はすべて実装されています。ただし、テスト2件は主張どおりのことを検証できていません。**

### (a) 欠けている要件
ありません。探索順、テンプレート付きでの作成、失敗と空パスの判定、scan.sh の停止、apply.sh の変数化、SKILL.md への追記は、どれも PR 本文どおりです。

### (b) 仕様の範囲外
- SKILL.md が、apply.sh が失敗したときも `!` で実行してもらうよう案内しています。仕様は scan.sh についての案内だけを挙げています。内容は妥当なので、PR 本文に一言足せば済みます。

### (c) 実装はあるが、正しくなさそうな点
1. **apply.sh のテストは macOS では回帰を検出できません**
   - 仕様: 「apply.sh が書き込めない TMPDIR でも動くことを検証」
   - macOS の `mktemp` はテンプレートなしだと TMPDIR を見ません。そのため、変更前の `input=$(mktemp)` のままでも、`TMPDIR=$root/no-such-dir` を渡したこのテストは通ります。
   - 意味のある検証になるのは、Linux の GNU mktemp で走らせたときだけです。
2. **片付けのテストは「作って消した」ことを確かめていません**
   - 仕様: 「片付けること」
   - テストが見ているのは、実行後に `ls -A "$root/hk-tmp"` が空かどうかだけです。
   - そのため、scan.sh が `HOUSEKEEPING_TMPDIR` を無視して別の場所に作った場合でも通ります。消し忘れがそこで起きていても検出できません。
   - 実行中にこのディレクトリが作られたことを記録する仕掛けがないと、検証になりません。たとえば、偽の PR 一覧を読み込むときに場所を記録しておく方法があります。
3. **SKILL.md の書き方が実際の動きとずれています**
   - 仕様: 「作れなければ error で止まる(git fetch 以外は何もしない)」
   - 実装は仕様どおりで、mktemp の前に `git fetch --prune` が走ります。
   - 一方、SKILL.md は「作れなければ何もせずに止まる」と書いていて、fetch が済んでいることと合いません。「fetch のあと止まる」と書くほうが正確です。

### 問題のなかった点
- 空パスの判定と、trap を設定する順序は正しく、空のパスに `rm -rf` が走ることはありません。
- apply.sh の変数化でも、行の区切りと空入力の扱いは変更前と同じです。

**まとめ**: Standards 軸は判断事項2件で、重いのは既定値の連鎖の重複(軽微)です。Spec 軸は指摘4件で、重いのは apply.sh のテストが macOS で回帰を検出できない点です。PR 本文の「test.sh 全件成功」は、この検証の弱さを裏付けにはなりません。

自分で判断するための問いを1つ置いておきます。このテストは Linux の CI で走っていますか。走っていないなら、(c)-1 は「検証済み」とは言えません。直し方は2通り考えられます。1つは、テスト側で `mktemp` を失敗する偽コマンドに差し替えて、どの OS でも失敗させる方法です。もう1つは、apply.sh が `mktemp` を呼んでいないことを grep で直接確かめる方法です。
