# PR #1 レビュー

一番大きいのは、「apply.sh は一時ファイルを使わない」という前提が誤っている点です。一時ファイルを置ける場所がまったく無い環境では、保護判定が「保護しない」側に倒れます。これは `sandbox-exec` で再現を確認しました。

## 正確性・セキュリティ

- **`skills/housekeeping/scripts/lib.sh:43-51`(`hk_is_protected`)と `apply.sh:53,65`:書き込める一時ディレクトリが無いと、保護対象の判定が素通りになる**
  - macOS 標準の `/bin/bash` 3.2 は、ヒアドキュメント(`<<EOF`)を一時ファイルで作ります。置き場所は `$TMPDIR` → `/tmp` → `/var/tmp` の順に探します。
  - 全部に書けないと `cannot create temp file for here document` になり、`while read` が1回も回らずに `return 1`(保護しない)を返します。
  - 再現:`/private/tmp` と `/private/var` への書き込みを禁止して `hk_is_protected entire/checkpoints/v1 main` と `hk_is_protected main main` を実行すると、どちらも `NOT-protected` でした。制限なしなら `protected` です。
  - この状況で偽装した行や誤った行が渡されると、apply.sh が `entire/checkpoints/v1` を `git branch -D` し、リモートからも `git push :refs/heads/...` で消しに行きます。
  - 問題自体は PR 以前からあります。ただ、この PR は「一時ファイルを作れない環境」を対象にしており、そこで apply.sh を動かす方向に寄せているので、この PR で扱うべきです。
  - 修正案:ヒアドキュメントをやめ、`printf ... | while` や `case` のループで判定する。あるいは判定が失敗したら保護する側(`return 0`)に倒す。
  - `hk_path_in_use`(`lib.sh:66-69`)も同じ仕組みで「使用中のプロセスなし」に倒れます。こちらは `git worktree remove` 自身の検査が残るので、影響は小さめです。

- **`skills/housekeeping/SKILL.md:98`、PR 本文:「apply.sh は一時ファイルを使わない」は誤り**
  - 上のとおり、ヒアドキュメントが暗黙に一時ファイルを使います。この文を読んだエージェントやユーザーが「書けない環境でも apply.sh は安全」と判断するおそれがあります。

- **`skills/housekeeping/scripts/scan.sh:31` のエラー案内と、`scan.sh:98,156,197,203,218` の関係**
  - エラー文は「`HOUSEKEEPING_TMPDIR` で書き込める場所を指定する」と案内します。しかし `$TMPDIR` と `/tmp` が書けない環境で、案内どおり `HOUSEKEEPING_TMPDIR` だけを書ける場所にすると、mktemp は成功し、その後のヒアドキュメントが失敗します。
  - 実測では `line 203: cannot create temp file for here document` → `line 209: action: unbound variable` で落ち、stdout にはヘッダと1行だけが残って rc=1 でした。
  - 今は `set -u` のおかげで途中で止まっていますが、壊れ方は偶然に頼っています。また stdout に途中までの TSV が出るので、`> ファイル` に保存させる運用では、不完全なファイルが残ります。
  - 修正案:mktemp の前に `TMPDIR` も同じ場所に揃える(`export TMPDIR=$tmp` など)。あるいはヒアドキュメントそのものをなくす。

- **`skills/housekeeping/SKILL.md:98`、PR 本文:「作れなければ何もせずに止まる」は事実と違う**
  - `scan.sh:22` の `git fetch --prune` は一時ディレクトリを作るより前に走るので、リモート追跡ブランチの削除という副作用は起きた後です。PR 本文の「git fetch 以外は何もしない」のほうが正確です。
  - 修正案:`hk_mktemp_dir` を fetch より前に移す。そうすれば文書どおりになり、無駄な通信も省けます。

## テスト

- **`skill-dev/housekeeping/test.sh:186`:回帰テストとして効いていない**
  - `TMPDIR=no-such-dir` は存在しないディレクトリなので、bash は `/tmp` に退避して普通に動きます。これでは「書き込めない TMPDIR」の検証になりません。
  - しかも PR 本文にあるとおり、macOS の旧実装の `mktemp`(テンプレートなし)は TMPDIR を見ません。そのため旧コードでもこのテストは通るはずで、変更前後の差を検出できるのは GNU mktemp の環境だけです。
  - 最初の指摘(保護が素通りになる問題)も、このテストでは見つかりません。
  - 修正案:macOS では `sandbox-exec` で一時ディレクトリへの書き込みを禁止したうえで、偽装行が `skipped ... 保護対象` になることを確かめる。

- **`test.sh:173-175`:正常終了の後片付けしか見ていない**
  - error で終わる経路(PR 一覧の取得失敗など)でも消えることを確かめる1件があると、`trap` の位置が変わったときの退行を拾えます。重要度は低めです。

## 設計

- **`scan.sh:31` と `lib.sh:18`:既定値の連鎖 `${HOUSEKEEPING_TMPDIR:-${TMPDIR:-/tmp}}` が2か所に重複している**
  - `hk_mktemp_dir` が失敗時に自分でパス入りのメッセージを出すか、`hk_tmp_base` のような関数に切り出すと、ずれを防げます。

- **`SKILL.md:35`:apply.sh を `!` で実行してもらう案内が不足している**
  - apply.sh は標準入力から読むので、`! <skill-dir>/scripts/apply.sh < <承認済みファイル>` の形まで書かないと、ユーザーが正しく実行できません。
  - 「同じ理由で失敗したとき」も曖昧です。apply.sh は mktemp を使わなくなったので、実際に起きる失敗は `.git` や worktree への書き込み、`git push` の制限が中心です。
  - 削除を実行する操作を利用者に任せるなら、渡すファイルの中身が承認した行だけであることを、エージェントが先に示す手順も入れたほうが安全です。

## プライバシー・並行性

- 問題は見つかりませんでした。`mktemp -d` はランダムな接尾辞と 0700 の権限で作られるので、`/tmp` に置いても他のユーザーから覗かれたり差し替えられたりする心配は小さいです。scan の出力もブランチ名とパスだけです。
- 確認できなかった前提が1つあります。`!` で実行したコマンドが本当にサンドボックスの外で動くのか、また環境変数(`$TMPDIR`)がエージェントと違うのかは、この環境では確かめられませんでした。`SKILL.md:35` の案内はこの前提に依存しているので、実機で一度確認することをすすめます。

## 妥当な点

- `hk_mktemp_dir` でテンプレートを明示し、失敗や空のパスを失敗として返すこと、それを呼び出し側で止めることは正しい修正です。空のパスのまま `/prs.json` に書きに行くことを確実に防げます。
- apply.sh で入力を変数に持つ変更も、空入力のときに1行の空行になるだけで、動作は変わりません。
