PR #1(`housekeeping-mktemp`)を5観点で見ました。大きな問題は1点です。apply.sh は一時ファイルを使わないと書かれていますが、実際はヒアドキュメント経由で使っており、作れないと保護判定が素通りになります。macOS の `sandbox-exec` で再現を確認しました。

## 正確性・セキュリティ

- **`skills/housekeeping/scripts/lib.sh:48`(保護判定)と `lib.sh:67`(使用中プロセスの判定): ヒアドキュメント用の一時ファイルを作れないと、どちらも「安全」側に倒れる**
  - macOS 標準の `/bin/bash` 3.2 では、ヒアドキュメントの中身を一時ファイルに書き出します。書き出す先は `$TMPDIR` で、使えなければ `/tmp` などに移ります。
  - `/private/tmp` と `/private/var` への書き込みを禁じて実行すると、`cannot create temp file for here document` のあと `hk_is_protected main` が **NOT protected** を返しました。
  - そうなると apply.sh は保護対象のチェック(`apply.sh:53`, `:65`)を通過し、`git branch -D` や `git push` の削除まで進みます。同様に `hk_path_in_use` は空を返すので、プロセスが使用中の worktree も消しにいきます(`apply.sh:42-43`)。
  - 原因のコード自体は既存ですが、この PR は「apply.sh は一時ファイルを使わない」と明記しています(`SKILL.md:98`、PR 本文)。まさにその環境を対象にした変更なので、この PR で直すのが妥当です。
  - 直し方: ヒアドキュメントを `printf '%s\n' "$x" | while …` や awk への変数渡しに置き換えます。あるいは `hk_protect_patterns` の出力が空なら失敗として止める、つまり安全側に倒すやり方もあります。
- **`skill-dev/housekeeping/test.sh:185-186`: 書き込めない TMPDIR でも動くことを確かめるテストが、上の穴を見逃す**
  - bash は使えない `$TMPDIR` を見ると `/tmp` に移るので、このテストは常に通ります。
  - 一時ファイルを本当に作れない状況は再現できていません。そのため、上の安全側に倒れる問題を見逃したまま「全件成功」になっています。

## 設計

- **`scan.sh:22` と `scan.sh:29-33`: 一時ディレクトリの確保が `git fetch --prune` と `hk_default_branch`(`gh` を呼ぶことがある)より後にある**
  - `SKILL.md:98` は「作れなければ何もせずに止まる」と書いていますが、実際にはリモート追跡ブランチを prune したあとで止まります。
  - `hk_mktemp_dir` を `git rev-parse` の直後に移せば、説明と挙動が合い、早く失敗できます。
- **`SKILL.md:34`: apply.sh を `!` で実行してもらうときの書き方がない**
  - apply.sh は承認済みの行を標準入力で受け取ります。`! <skill-dir>/scripts/apply.sh` とだけ伝えると、入力が空のまま何もしないか、入力待ちで止まるおそれがあります。
  - 手順4の `awk … <scan.tsv の絶対パス> | <apply.sh の絶対パス>` という形を、パスを展開した状態で示すべきです。
- **`SKILL.md:34`: `!` で実行したコマンドがサンドボックスの外で動くという前提を確かめていない**
  - Claude Code の `!` がサンドボックスの対象外かどうかは、私は確認していません。ここが違うと、この案内はそもそも成り立ちません。
  - 一次情報で確認するか、実際に動かして確認した結果を PR に書いておくことを勧めます。

## テスト

- **`test.sh:172-175`: 片付けのテストが、作る場所の指定を確かめていない**
  - scan.sh が `HOUSEKEEPING_TMPDIR` を無視して別の場所に作っても、`hk-tmp` は空のままなのでテストは通ります。
  - 例えば `trap` の前に場所を書き出すデバッグ出力を足すか、`ls` の結果で作られたことを確かめるとよいです。
  - 優先順位そのものは、`:162-170` の「作れなければ止まる」テストで間接的に確かめられています。

## 並行性・プライバシー

- 並行性: 変更による悪化はありません。`apply.sh:21` は削除の前に入力を最後まで読みます。これは一時ファイルを使っていた頃と同じです。
- プライバシー: 問題ありません。`scan.sh:31` のエラーには一時ディレクトリのパスが入り、ユーザー名を含むことがありますが、ローカルの stderr に出るだけです。
- `hk_mktemp_dir` 自体は妥当です(`lib.sh:17-22`)。macOS の `mktemp` が TMPDIR を見ない問題を、テンプレートで場所を明示して避けています。0700 で推測しにくい名前のディレクトリを作り、空のパスかどうかも二重に確かめています。`rm -rf "$tmp"` に空のパスが渡る危険はなくなりました。

最初の指摘は、削除ツールの安全性が環境によって崩れるという問題なので、マージ前に直すのが妥当です。ただし、Claude Code の実際のサンドボックスで `$TMPDIR` が書き込み可能なら、通常は発生しません。どれだけ起こり得るかは、実際の環境で `/tmp` と `$TMPDIR` に書き込めるかどうかで変わります。
