## PR #2 のレビュー結果

全体の方向(選べる行の並びを `selectableOrder` にまとめ、`↑` `↓`・起動時・自動で移るときの3経路で使う)は妥当です。旧シナリオ 70 の大本の起動元へ戻す分岐を消せたのも、仕様が単純になって良い変更です。問題は、新しく足した窓の計算(`src/screen/screen.ts`)にあります。2件は作業ツリーの外にビルドし、`render` の実際の出力で再現を確かめました。

### 不具合(確かめたもの)

- **`src/screen/screen.ts:211-213` — 先頭の選べる行が画面に出ないことがある。**
  - 原因:最初の選べる行を選ぶと、`cursorBlock` が `[0, body.length]` になる。その上に並ぶ `(sub)` の行と見出しだけで窓を超えると、`blockLen >= avail` から `start = b0 = 0` になる。
  - 再現:高さ10、トップレベルに `(sub)` が12行、そのあとに `p`、`q`、カーソルは `p`。出力は `w0`〜`w5 (sub)` と `1/2` だけで、`> p` の行がない。
  - 起こる場面:一覧に出ていない対話セッションが `claude -p` を多く起動したとき。この PR が想定している構成です。
  - PRODUCT.md の24は「選んだ行が見えるようにスクロール」と定めているので、こちらを優先すべきです。直し方は、ブロックが窓を超えるときは先頭行の扱いを諦めて `start` の位置から出すのが簡単です。

- **`src/screen/screen.ts:214` と `:233` — メモの入力中に、入力欄と選んだ行が窓の外に押し出される。**
  - 原因:`trailing` で `b1` を後ろの `(sub)` の行の末尾まで延ばした。一方で、入力欄用の補正 `if (s.inline && b1 > start + avail) start = b1 - avail` は、`b1` が入力欄の最終行だという前提のまま残っている。
  - 再現:高さ12、子の `(sub)` を10行持つ `p` で `e` を押して入力中にする。出力は `└ w1 (sub)`〜`└ w9 (sub)` と `3/4` だけで、`> p` も `Note for p:` も見えない。
  - 起こる場面:オーケストレーター役の行にメモを付けるのは普通の操作です。入力欄の末尾は `trailing` で延ばす前の値として別に持ち、`:233` ではそれを使うべきです。

### 仕様とのずれ(軽め)

- **`src/screen/screen.ts:201-204`、`:214` — 区切りをまたいでも `trailing` がリセットされない。**
  - 区切りの最後の行を選ぶと、次の区切りの先頭に並ぶトップレベルの `(sub)` の行(その行の子ではない)が、空行と見出しも含めて同じ塊に入る。
  - 再現:高さ9で `app` の最後の `b` を選ぶ。`> b` が窓の最上段に寄り、`lib` の見出しと `x0`〜`x2 (sub)` が続く。`b` の上にある `a0`〜`a3` は隠れる。
  - PRODUCT.md の「選んだ行のすぐ下に続く起動された行」は、選んだ行の子孫と読むのが自然です。区切りの境目(`forEach` の先頭)で `trailing = false` にするか、`depth` で子孫かどうかを判定すべきです。

- **`src/ops/app.ts:262-265` — 行が消えていないのに「left the list」と表示される。**
  - 原因:条件を `selectableOrder` に変えたので、選んでいた行が更新で起動された行に変わった場合(DESIGN.md に追記された場面)もこの分岐に入る。`prevLayout.order` に行があるので `goneName` が入り、守りの文言が `Ctrl+X ignored: <名前> left the list and the selection moved.` になる。
  - 実際には行は一覧に残っていて、文言が事実と合いません。シナリオ 51 の文言は「消えた」場面専用です。
  - 守りの時間そのものは残してよいと思います。`goneName` を `!this.lay.order.includes(this.cursor)` の場合に限るか、別の文言にするかは、層2(利用者に二択で聞く)の判断になります。

- **`docs/PRODUCT.md:296` — 文の読み方が割れる。**
  - 「効くのは `cwd` と `pid` を示す `Enter` と `v` だけだが」は、選べない行についての文です。いまでも `Enter` と `v` が効くと誤読できます。
  - 「選べたとしても効くのは〜だけで、場所は WHERE の列と起動元の行で分かる」のように、選べなくした根拠として書いていると分かる形にするべきです。

### テスト

- **`test/e2e/deps.test.ts:442-447`(シナリオ 70)— 飛ばすことを確かめない場合がある。**
  - `below ? 'Down' : 'Up'` で、`other` が `orchestrator` の上にも下にも来うる前提で書いている。`other` が上に来ると、並びは `other, orchestrator, worker, worker-2` になり、どの `↑` `↓` も `(sub)` の行をまたがない。5回の `Down` も `orchestrator` で止まるだけなので、シナリオ 70 の「`↓` で起動された行を飛ばす」がまったく確かめられない。
  - 並び順を固定すべきです(`seen` の `attached` を状態のファイルで与える、など)。そのうえで、`↓` が `worker-2` の次の行に着くことを直接確かめてください。

- **`test/unit/screen.test.ts:136-154` — 上の2件の不具合を拾えない。**
  - 起動された行の数が窓に収まる場合だけを試しているので、先頭行が隠れる件も、入力欄が押し出される件も検出できない。窓より多い `(sub)` の行と、`inline` がある場合を足すべきです。

- **`test/unit/model.test.ts:323-328` — 「隣の行」の向きを区別できない。**
  - `S` が区切りの末尾なので、「次の行」「前の行」「起動元」のどの規則でも結果が `P` になる。`S` の下に選べる行を1つ置けば、「次の行を先に選ぶ」ことまで確かめられる。

### 指摘しないもの

`openNote` と `openWait` から起動された行の断りを外した点(`src/ops/app.ts:835`、`:856`)は、問題なしと判断しました。作業台からのキーの経路(`attachKey` → `sidOfSession`)は tmux のセッションの `id` で行を引きますが、起動された行は `interactive` で `id` がないので、カーソルがそこに乗る経路はありません。

確かめ方について。`tsc` で一時ディレクトリにビルドし、Node から `render` を呼んで画面を出しました。作業ツリーとブランチには触れていません。`npm test` と e2e は流していません。
