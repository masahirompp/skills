PR #2（`sub-rows-unselectable`、1コミット 459a5fc）のレビュー結果です。窓の計算の不具合が2件あり、どちらも `/tmp` に置いた使い捨てのスクリプトで `render` を呼んで再現しました。スクリプトはもう消してあります。作業ツリーは変えていません。

## 不具合（直すべきもの）

- **`src/screen/screen.ts:213`：最初の選べる行が窓の外に出ることがある**
  - 何が起きるか：最初の選べる行を選ぶと、塊の始まりを `0`（一覧の先頭）にしています。先頭の見出しと `(sub)` の行が窓の高さ以上あると、`:230` の `blockLen >= avail ? b0` で窓が先頭に固定され、選んだ行が画面に出ません。
  - 再現：高さ10、先頭に `(sub)` 8行、その下に選べる行10行で `s0` を選ぶ。見えるのは `w0`〜`w5 (sub)` と `1/10` だけで、`> s0` が出ません。
  - どんなときに起きるか：一覧に出ていない対話セッションが `claude -p` を何本も起動したとき（シナリオ71の形）です。
  - 直し方の案：先頭から見せるのは、先頭から選んだ行の終わりまでが `avail` に収まるときだけにする。収まらなければ `start` から始める。

- **`src/screen/screen.ts:233`：メモの入力欄が画面の外に押し出される**
  - 何が起きるか：`b1` が、すぐ下に続く `(sub)` の行の終わりまで延びるようになりました。このため「入力欄は最後の行まで窓に入れる」の補正が、入力欄ではなく最後の `(sub)` の行に合わせてしまいます。
  - 再現：高さ10、`p` の下に入れ子の `(sub)` が8行。`p` で `e` を開くと、窓は `w1`〜`w7 (sub)` と `6/6` になり、`> p` も入力欄も見えません。この PR の前は、`b1` が入力欄の終わりだったので見えていました。
  - 直し方の案：入力欄の終わりの位置を `cursorBlock` とは別に持ち、`:233` はそちらを使う。

- **`src/ops/app.ts:263-265`：行が消えていないのに「消えた」と言う**
  - 何が起きるか：判定が `!selectableOrder(...).includes(...)` に変わったので、選んでいた行が残ったまま `(sub)` に変わった場合もここに入ります。`prevLayout.order` にはまだあるので `goneName` が入り、guard が立ちます。その直後に `Ctrl+X` を押すと、`Ctrl+X ignored: <name> left the list and the selection moved.`（`:1215`）と出ますが、その行は一覧に残っています。
  - 判断が要る点：断ること自体は妥当です（カーソルが勝手に動いたので）。直すのは文言です。消えた場合と「選べなくなった」場合で分けるか、どちらにも当てはまる文言にしてください。
  - テスト：`test/unit/model.test.ts` の「選んでいた行が起動された行になったら」は `followCursor` だけを確かめていて、この経路は通っていません。

- **`src/ops/app.ts:1068`、`:275`、`:1197`：カーソルを `(sub)` の行に直接置ける経路が残っている**
  - 該当するのは `onReturn`、`pendingCursorId`、`attachKey` の3か所で、どれも選べるかを確かめずに `this.cursor = sid` としています。
  - 起きる場面：background の行に attach している間に、その行が起動された行だと分かった場合（親子の関係があとから分かった場合や、`MCP_CALLER_PID` の場合）です。
  - その結果：戻ったときに、カーソルが `(sub)` の行に乗ります。そこで `e`、`f`、`v` を押すと、この PR で外した断りの処理がないので、メモの欄や待ち先のメニューが開きます。次の更新で `:262` に入るとカーソルは移りますが、guard も立ちます（上の項目と同じ誤った文言）。DESIGN.md の新しい項目「カーソルは起動された行に置かない」と食い違います。
  - 直し方の案：3か所とも選べる行かどうかを確かめる。選べなければ `followCursor` を通す。
