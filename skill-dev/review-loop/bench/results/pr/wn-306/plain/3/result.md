## PR #2 レビュー指摘

### 不具合(直すべき)

- **`src/screen/screen.ts:213` 選んだ行が窓から消えることがある**
  - 最初の選べる行を選んでいるとき、塊の始まりを `0`(一覧の先頭)にしています。その上に並ぶトップレベルの `(sub)` の行と見出しが窓の高さ以上あると、`blockLen >= avail` の分岐で `start = b0 = 0` になり、カーソルの行は窓の外に出ます。
  - 実測:高さ 10 で `(sub)` が12行、その下に `s0`〜`s9` が並び、カーソルは `s0` の場合です。画面には `w0 (sub)`〜`w5 (sub)` と `1/10` だけが出て、`> s0` は出ません。
  - 最初の選べる行が2つ目の区切りにあるときも、1つ目の区切りの全部が塊に入ります。
  - 起動元が一覧に出ていない `(sub)` の行はトップレベルに並ぶので、この状態は実際に起こりえます(シナリオ 71 の状況が何件もある場合)。
  - 直し方の案:先頭から見せるのは `body.length の先頭〜選んだ行の終わり` が `avail` に収まるときだけにします。収まらなければ `start` を起点にします。
  - 追加の単体テストは `(sub)` が4行で窓に収まる場合しか見ていないので、この境界を通っていません(`test/unit/screen.test.ts:136`)。

- **`src/ops/app.ts:835`(`openNote`)、`:856`(`openWait`)の `isSpawned` の拒否を消したが、cursor を経ない入口が残っている**
  - `attachKey` の `action === 'note'` / `'wait'` は、`sidOfSession(attach 中の tmux セッション)` の sid で直接 `openNote(sid)` / `openWait(sid)` を呼びます(`src/ops/app.ts:1196-1202`)。
  - 起動元が分かる前に attach したセッションが、あとで起動された行に変わると、attach 先からメモ入力が開きます。`(sub)` の行にメモが保存されますが、`note: n.spawned ? undefined : …`(`:461`)で表示されないので、見えないデータが残ります。
  - `openWait` 側は `canLink` が spawned を弾くので結ばれません。ただしメニューは開き、断る文言もありません。
  - 「cursor は `(sub)` に乗らない」という不変条件だけに頼るなら、`openNote`/`openWait` の入口で `spawner.has(sid)` を見るガードは残したほうが安全です。

- **`src/ops/app.ts:1068`(`onReturn`)、`:1197`、`:275`(`pendingCursorId`)は `this.cursor = row.sid` を選べるかどうかを見ずに代入している**
  - 上と同じ経路で、cursor が `(sub)` の行に乗ります。このとき次のことが起きます。
    - 次の観測まで `<通し番号>` が `0/N` になる(`rowIndex.indexOf` が -1)
    - `↑` が効かず、`↓` で一覧の先頭(`order[0]`)へ飛ぶ(`:787-792`)
    - 窓の追従も効かない
  - PR の説明の「カーソルは `(sub)` に置かない」が、この3か所では守られていません。

### 小さめの指摘

- **`src/ops/app.ts:262-265` 行が消えていないのに「消えた」と出る**
  - 選んでいた行が残ったまま `(sub)` に変わった場合も、`goneName` が入って guard が張られます。
  - その間に `Ctrl+X` を押すと `… left the list and the selection moved.` と出ますが、行は一覧に `(sub)` として残っているので文言が事実と合いません。
  - 消えた場合(`!this.lay.order.includes`)と選べなくなった場合を分けるべきです。

- **`src/model/cursor.ts:30-31` 変わった行の起動元へ戻らない**
  - 残ったまま `(sub)` に変わった行でも、前の並びの同じ区切りの「次の行」へ移ります。この場合、その行の起動元はすぐ上にいるので、起動元へ戻すほうが自然だと考えます。
  - DESIGN.md は「消えたときと同じに隣の行へ移る」と明記しているので、仕様どおりではあります。PRODUCT.md にこの場合のシナリオがないので、挙動 A(隣の行)と挙動 B(起動元)の二択で利用者に確かめる価値があります(層2)。

- **`src/screen/screen.ts:201-215` `trailing` が区切りをまたいで続く**
  - `trailing` は区切りをまたいでもリセットされません。選んだ行が区切りの最後にあり、次の区切りがトップレベルの `(sub)` で始まると、見出しを越えて次の区切りの `(sub)` まで塊に入ります。
  - 関係のない行を「選んだ行と一緒に」見せることになり、PRODUCT.md の「選んだ行のすぐ下に続く起動された行」の意図(自分の配下)より広がります。
  - 一方、`s.groups.forEach` の頭で `trailing = false` にすると、その区切りの `(sub)` は誰の塊にも入らず、スクロールで見られない行になりえます。この条件ではどちらを採るかを決める必要があります。

- **`docs/PRODUCT.md:296` 一文が読み違えやすい**
  - 「起動された行は…選べない」の直後に「効くのは `cwd` と `pid` を示す `Enter` と `v` だけだが」とあり、選べない行でキーが効くように読めます。
  - 選べたとしても効くのはそれだけ、という理由の説明なら、「選べたとしても効くのは…」と書くか、経緯の節(`:972`)に移すとよいです。

### 問題ないと判断した点

- `followCursor` の簡略化(大本の起動元へ戻る規則の削除)と、`initialCursor`/`↑↓` で `selectableOrder` を使う形は、仕様の変更と合っていて妥当です。
- `canLink` が spawned を弾いているので、`openWait` のガードを外しても待ち先は結ばれません。そのため上の2件目の害は主に `openNote` 側です。
