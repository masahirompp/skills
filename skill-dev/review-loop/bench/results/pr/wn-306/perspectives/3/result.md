# PR #2 レビュー(cycle 9: 起動された行をカーソルで選べなくする)

`↑` `↓` で `(sub)` の行を飛ばす部分(`src/model/cursor.ts` と `listKey`)は筋が通っています。問題は2か所あります。スクロールの窓の計算と、`↑` `↓` 以外の経路でカーソルを書き換える箇所です。画面の3件は、作業ツリーの外に置いた使い捨てのスクリプトで `render` を呼び、実際の画面で確かめました。スクリプトは消してあり、作業ツリーには何も変更を加えていません。

## 正確性

- **`src/screen/screen.ts:213`(と `:230`)**: 最初の選べる行を選んだとき、窓が `[0, 選んだ行の終わり]` になります。その上の `(sub)` の行が窓の高さより多いと、`blockLen >= avail` から `start = b0 = 0` になり、**選んだ行が画面から消えます**。
  - 実測: 高さ10の画面で、トップレベルの `(sub)` の行12個のあとに `s0` `s1` が並び、`s0` を選んだ状態。画面には `w0`〜`w5 (sub)` と `1/2` だけが出て、`> s0` は出ませんでした。
  - 起きる場面: 一覧に出ていない対話セッションが `claude -p` を多く起動したとき(シナリオ71の形)。このときトップレベルの `(sub)` の行が先頭に並びます。
  - 直し方の案: 先頭から見せるのは、ブロック全体が窓に収まるときだけにする。収まらなければ `start` を起点に戻す。

- **`src/screen/screen.ts:214-215` と `:233`**: 選んだ行のすぐ下に続く `(sub)` の行まで `cursorBlock[1]` を伸ばしたため、メモの入力欄が出ている間に問題が起きます。`:233` の「入力欄は最後の行まで窓に入れる」が `b1`(最後の `(sub)` の行)を基準に窓を下へずらし、**選んだ行と入力欄の両方が画面から消えます**。
  - 実測: `p` の下に `(sub)` の行が12個あり、`p` で `e` を押した状態。画面には `└ w5 (sub)`〜`└ w11 (sub)` と `2/3` だけが出て、`> p` も `note> hello` も出ませんでした。main では、ブロックが行と入力欄だけだったので起きません。この PR で入った退行です。
  - 直し方の案: 入力欄の終わりの位置を別に持ち、`:233` はその位置で判定する。

- **`src/screen/screen.ts:201-215`**: `trailing` を「印が `sub` の行が続いている間」だけで決めていて、親子の関係を見ていません。次の2つの場合に、選んだ行と関係のない行まで窓に入ります。
  - 選んだ行が区切りの最後の行で、次の区切りがトップレベルの `(sub)` の行(起動元が一覧に出ていないもの)で始まる場合。区切りの空行と見出しも含めて、同じ塊として窓に入ります。実測では、`> p` のすぐ下に `── g2 ──` と `t0`〜`t3 (sub)` が入りました。
  - 同じ区切りの中で、選んだ行の直後に無関係なトップレベルの `(sub)` の行が並ぶ場合も同じです。

  PRODUCT.md の「選んだ行のすぐ下に続く起動された行」の意図は、選んだ行の子孫だと読めます。区切りが変わったら `trailing = false` にし、`depth` が選んだ行より深い間だけ続けるのが妥当です。

- **`src/ops/app.ts:1197-1202`(`attachKey`)**: attach している画面のキーから、`this.cursor = sid` のあと `openNote` / `openWait` を呼びます。この経路は `selectableOrder` を通りません。そのうえ、この PR で `openNote` と `openWait`(`:835`、`:856`)から `isSpawned` の確認を外しました。結果として、**起動された `background` の行にメモの入力欄と `f` のメニューが開きます**。
  - 開いたあとの結果は黙って捨てられます。メモは `:461` の `n.spawned ? undefined` で表示されず、待ち先は `save(true)` の `validWaits` で落ちます。利用者からは、入力したのに何も残らないように見えます。
  - 起きる場面: tmux 側で直接 attach している場合や、attach したあとで起動元が分かった場合です。カーソルも起動された行に乗るので、`↓` を押すと `i = -1` から先頭へ飛びます。
  - 直し方の案: 「起動された行は選べない」を `↑` `↓` で守るだけでは足りません。入口(`openNote` / `openWait`、または `attachKey`)で断る確認を残すべきです。

- **`src/ops/app.ts:1068`(`onReturn`)と `:275`(`pendingCursorId`)**: どちらも、確かめずに `this.cursor = row.sid` を代入します。起動された行に attach していて戻ると、カーソルが `(sub)` の行に乗ります。そのとき画面は `0/N` と出し(`screen.ts` の `rowIndex.indexOf` が -1 になるため)、次の更新で `followCursor` が隣の行へ移します。そこで次の指摘の「誤った文言の guard」も立ちます。不変条件(カーソルは選べる行だけ)を代入する場所ごとに守るより、`cursor` を設定する関数を1つにまとめたほうが漏れを防げます。

- **`src/ops/app.ts:263-265` → `:1215`**: この PR で、行が残ったまま起動された行に変わった場合も、カーソルを隣へ移すようになりました。このとき `prevLayout.order.includes(cursor)` が真なので `guard` が立ちます。直後に `Ctrl+X` を押すと `Ctrl+X ignored: worker left the list and the selection moved.` と出ますが、実際には行は一覧から消えていません。文言が事実と合いません。guard は残し、文言を「消えた」と「起動された行に変わった」で分けるのが妥当です。

## 並行性

- 上の `onReturn` と `pendingCursorId` は、非同期の attach からの戻りと更新(`apply`)が別々にカーソルを書き換える箇所です。どちらの順で起きても、カーソルが一時的に選べない行に乗る窓があります。正確性の指摘と同じ根で、直し方も同じです。そのほかに、新しく入った競合は見当たりませんでした。

## テスト

- **`test/e2e/deps.test.ts:464` 前後(シナリオ71)**: `keys('f')` と `keys('e')` の直後に、待たずに `not.toMatch(/waits for:|can't/)` を調べています。通知が少し遅れて描画される実装だと、壊れていても通ります。否定の確認は、更新を1回挟むか一定時間待ってからにしないと、確かめたことになりません。
- 上の窓の計算の3件(上に `(sub)` の行が多い場合、メモの入力欄が出ている場合、区切りをまたぐ場合)は、`test/unit/screen.test.ts` の新しいテストでは確かめていません。追加した `it` は、全部が窓に収まる大きさの例だけです。
- `attachKey` から `e` / `f` を押す経路で、起動された行を断るテストがありません。main では `openNote` 側の確認で守られていたので、テストがなくても困りませんでした。

## 設計

- `cursor.ts` の `selectableOrder` は `l.order` を走査するたびに `isSpawned`(全区切りと全ノードの走査)を呼ぶので、計算量は O(n²) です。しかも `listKey` のキー入力のたびに呼ばれます。行数が数十なら実害はありませんが、`Layout` に spawned の `Set` を持たせれば済みます(層1の内部設計なので、急ぎません)。
- 「カーソルは選べる行にだけ乗る」という不変条件を、`↑` `↓`、`followCursor`、`initialCursor` では守っていますが、直接代入する3か所(`:275`、`:1068`、`:1197`)では守っていません。上の2つの正確性の指摘の根はこれです。PR の説明の「自動で移るときも選ばない」と、実装の範囲が食い違っています。
- PRODUCT.md の「効くのは `cwd` と `pid` を示す `Enter` と `v` だけだが、場所は WHERE の列と起動元の行で分かる」は、選べなくしたことで失う機能を明記していて妥当です。ただ、`attachKey` の経路が残っているので、「起動された行に `f` も `e` も効かない」は実装上はまだ成り立っていません。
