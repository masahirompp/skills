**確かめて問題がなかった点**
- 1つ目は whatnext のキーとの衝突です。`C-q` は `bind -n C-q switch-client -T wnq` で root の表に割り当てられていますが、作業台では prefix の表の既定のキー `%` `"` `c` が効きます。既存の e2e テストが `C-q %` で分割していることで確かめられています(`test/e2e/workbench.test.ts:59`)。また whatnext が prefix の表に置く1文字のキーは `v` と `e` だけ(`src/ops/keys.ts:18-19`)で、`c` `%` `"` とはぶつかりません。
- 2つ目は空白の数です。`#{W:…}` の各窓は後ろに空白が付くので、` · ` と合わせて `0:zsh* 1:zsh  · ^Q%` になります。PRODUCT.md の例とも、テストの `{2}` とも合っています。
- 3つ目は図の幅です。PRODUCT.md の図で変えた行は表示幅75で、前後の行と揃っています。

**指摘**

- **`lib/tmux/tmux.ts:340`:今回の変更を守るテストが、使い捨ての層にしかありません。** `lib/` は昇格済みのモジュールなので、テストも持ち越す決まりです。ところが、ステータス行の書式を確かめているのは `test/e2e/workbench.test.ts:117` だけで、`lib/tmux/tmux.test.ts` には `workbenchOptions` も `status-format` も出てきません。`%%` を `%` に戻すと `^Q split` と表示が崩れますが、これは見落としやすい誤りです。使い捨ての層のテストを cycle-end で消すと、この誤りを捕まえるものがなくなります。`workbenchOptions` が送る引数に `^Q%% split` が入っていること、案内のセッション(`GUIDE`)では入らないことを、`lib/tmux/tmux.test.ts` で確かめることを勧めます。

- **`test/e2e/workbench.test.ts:25` / `:117`:「案内のセッションでは出さない」を誰も確かめていません。** issue #1 と PRODUCT.md(「作業台がないときは、セッション名だけを出す」)で決めた振る舞いですが、25行目は `/workbench: alpha/` しか見ていません。キーが出てしまっても通ります。案内の画面で `^Q%` が出ないことを否定の形で確かめる1行があると、仕様の両側が守られます。

- **`docs/PRODUCT.md:442`:図の右の分割の最下行が、実際の描画と1文字ずれているようです。** 図では `│ workbench: fix-login  0:zsh*  · ^│` と、左端に空白を1つ置いてから34桁に収めています。しかし tmux のステータス行は0桁目から描くので、幅34の分割では `workbench: fix-login  0:zsh*  · ^Q` まで出るはずです。CLAUDE.md の「見た目の決定」では、画面の例は手で書かず実際の描画から作ると決めています。ほかの行もペインの中身を空白1つ下げて描いているので、図の流儀に合わせたとも読めます。ただ、`^` だけが残る絵は読み手に「キーが壊れている」と見えかねません。capture で取った画面に合わせるか、少なくとも `^Q` で切れる形にすることを勧めます。

- **`lib/tmux/tmux.ts:340`(軽微):`│` と `─` は、東アジアの文字幅で「曖昧」に分類される文字です。** 端末で曖昧な幅の文字を全角として扱う設定にしていると、tmux の幅の計算(1桁)と実際の表示(2桁)がずれます。その場合、ステータス行の右端の切れ方が1〜2桁狂います。ペインの境目にも同じ文字を使っているので、新しく増える危険は小さいです。避けたければ、`split │` を `split |`、`split ─` を `split -` にする手があります。ただし、そうすると境目の向きとの対応が絵として伝わりにくくなります。どちらを取るかは利用者の判断です。
