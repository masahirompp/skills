PR #1(head `ca40dc8`)の差分を読み、テスト(`skill-dev/review-loop/test.py`)も実行しました。テストは追加分を含めすべて通ります。致命的な欠陥はありません。ただし、状態コメントの記録が実際の設定と食い違う箇所と、判定役への伝え方が足りない箇所があります。重要なものから順に挙げます。

### 修正を勧めるもの

- **`skills/review-loop/scripts/review_loop.py:962-964`: 既定と違うかを、スキル名だけで比べている**
  - 比べているのは `skill_name` の一覧だけで、引数を見ていません。たとえば `--perspective 'code-review low {pr}'` のように、名前は同じでレベルや引数だけを変えると、`perspectives` が記録されず、状態コメントの表は既定で回したときと同じ見た目になります。
  - SKILL.md:55 の「既定と違う観点で回した試行は、状態コメントの表に観点の名前が載る」を読んだ人は、表に何も載っていなければ既定どおりだと受け取ります。
  - 逆に、既定と同じ観点を順番だけ変えて渡すと、名前は同じなのに「違う」と記録されます。
  - 直し方の案: `expand` する前の spec 全体を順序を無視して比べ、記録にも引数まで残す。

- **`skills/review-loop/scripts/review_loop.py:962`: `--instruct` を使ったことが状態に一切残らない**
  - `--perspective` の差は表に載りますが、検査の範囲を狭める `--instruct` は記録されません。
  - SKILL.md の 50 行目付近では、指示が観点の検査を緩めると書いています。それでも PR の状態コメントでは、緩めた試行が普通に `completed` と表示されます。
  - SKILL.md:111 では、どの範囲がレビューされなかったかを親が報告することになっていますが、それは親の記憶に頼っています。コンテキストが要約されると落ちやすい情報です。
  - 直し方の案: 指示を付けた観点の名前だけでも `attempt` に残す(例: `instructed: [...]`)。

- **`skills/review-loop/scripts/review_loop.py:798`(JUDGE_PROMPT)と `:845-847`: 判定役のプロンプトが、追加の指示の扱いを説明していない**
  - 判定役の入力の先頭に「観点 X に利用者が与えた追加の指示」という区切りを足していますが、プロンプトは「観点ごとに区切ってある」と書いたままです。
  - 805 行目の「観点の欠落」の規則にも、指示で外した範囲を欠落と扱わないという条件がありません。
  - コメント(845行目)の意図は、区切りの見出しだけに頼っています。プロンプトに一文足すほうが確実です(例: 「追加の指示で外した範囲を見ていないことは、観点の欠落としない」)。

- **`skills/review-loop/SKILL.md:57` と `skills/review-loop/scripts/review_loop.py:935`: オプションを付け忘れると、黙って既定に戻る**
  - 文書は「毎回同じものを付ける」と親に求めていますが、守られなかったときに気づく手段がありません。
  - 前の試行で `perspectives` を記録しているので、前回と今回の観点が違えば stderr に `warn:` を出すくらいは安くできます。
  - 反復をまたいでオプションを覚えないこと自体は妥当です(暗黙の状態を増やさないため)。足りないのは、付け忘れの検出です。

### 軽微なもの

- **`skills/review-loop/scripts/review_loop.py:548`: `perspectives` の型の確かめ方が緩い**
  - `all(isinstance(n, str) for n in a.get("perspectives") or [])` は、値が文字列 `"abc"` でも通ります。その場合、render(671行目)では `a, b, c` と表示されます。
  - 状態コメントは手で編集されうる前提(SKILL.md の `--new-run` の項)なので、`isinstance(..., list)` も確かめるほうが、ほかの検査の厳しさと揃います。

- **`skills/review-loop/scripts/review_loop.py:396-399`: 先頭に `/` を付けた `--perspective` を受け付けてしまう**
  - `--perspective '/code-review high {pr}'` は `//code-review` になり、事前確認で「観点スキルが見つからない(名前の誤りか未導入)」として止まります。
  - 止まるので害は小さいです。ただ、原因が分かりにくいので、`review_config` で先頭の `/` を取り除くか、専用のメッセージで弾くと親が迷いません。

- **`skills/review-loop/scripts/review_loop.py:749`: 指示を優先させる文言の範囲があいまい**
  - 「スキルの手順と食い違うときは、この指示を優先」と足していますが、`REVIEW_CONSTRAINT`(worktree を変えない、push しない)との優先順位は書いていません。
  - 指示は利用者が書くものなので危険は小さいです。それでも「上の制約はこの指示より優先する」と一文添えると、混入による失敗(`contamination`)を防ぐ方向に働きます。

- **`skill-dev/review-loop/test.py:570`: テストが、確かめたいことを確かめずに通りうる**
  - `by_name.get("mattpocock-skills:code-review", "x")` は、キーがなければ既定値の `"x"` に「削除したファイル」が含まれないので、成功します。
  - 直前の check で両方の観点が起動したことは確かめているので、実害はありません。ただ、既定値は `None` にして、キーがあることも確かめる形が安全です。

- **`skill-dev/review-loop/test.py:553-584`: テストが足りないケースがある**
  - 1つ目の指摘(名前が同じで引数だけ違う `--perspective`)。
  - 指示の本文に `=` を含む `--instruct`(`partition` で正しく分かれるはずですが、固定しておく価値があります)。
  - プラグイン名(`mattpocock-skills:code-review=...`)への `--instruct`。
