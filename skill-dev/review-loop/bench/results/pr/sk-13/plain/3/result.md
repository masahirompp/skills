PR #1(`review-loop: 観点の入れ替えと、観点ごとの追加の指示`)をレビューしました。大きな欠陥はありません。入力の検証、終了コード2で止まる経路、それらの経路で状態を汚さないことは、実装とテストの両方で押さえられています。弱いのは、どの設定でレビューしたかが状態に残らない点と、判定役への伝え方です。テストは手元で実行していません。

## 指摘(重要度の高い順)

- **`skills/review-loop/scripts/review_loop.py:963` — 名前しか比べないので、引数だけ変えた場合が記録に残らない**
  `names != [skill_name(s) for s in PERSPECTIVES]` はスキル名の並びだけを比べています。`--perspective 'code-review low {pr}'` と既定の残り2つを渡すと深さが変わりますが、名前の並びは既定と同じなので `perspectives` が記録されず、表上は既定で回した試行と区別できません。逆に、同じ観点を順番だけ変えて渡すと「既定と違う」と記録されます。比べるべきなのは名前の並びではなく、引数を含めた spec の集合です。

- **`skills/review-loop/scripts/review_loop.py:963` 付近と `skills/review-loop/SKILL.md:57,111` — `--instruct` が状態に記録されない**
  記録されるのは観点の名前だけで、追加の指示は状態コメントにも表にも残りません。一方 SKILL.md:111 は、最後に「レビューされなかった観点と範囲」を報告するよう求めています。この情報を持っているのは親(LLM)の記憶だけになり、コンテキストが要約されると落ちる恐れがあります。SKILL.md:57 の「スクリプトは反復をまたいでオプションを覚えない」も同じ弱さを抱えています。付け忘れても既定に戻るだけで、警告は出ません。
  - 案: 指示の有無(内容のハッシュか先頭の数十文字)を `attempt` に残す。さらに、同じシリーズで直前の completed と設定が違えば stderr に `warn:` を出す。こうすれば、反復ごとに設定が混ざったことに気づけます。

- **`skills/review-loop/scripts/review_loop.py:847` と `:805`(`JUDGE_PROMPT`) — 判定役は指示ブロックをどう扱うか教わっていない**
  SKILL.md:54 は「判定役の入力にも添えるので、指示で外した範囲を『観点の欠落』とは扱わない」と書いています。しかし `JUDGE_PROMPT` には、このブロックの意味も、欠落の判定から外せという規則もありません。判定役が察してくれることに頼っています。さらに、ブロックの見出しが `===== 観点 X に…` で、レビュー出力の区切り `===== 観点: X =====` と形が近く、取り違える余地があります。
  - 案: `JUDGE_PROMPT` に「利用者の追加の指示で外した範囲は観点の欠落とせず、指摘にもしない」という一文を足す。見出しを `===== 利用者の追加の指示: X =====` のように、観点の区切りと形の違うものにする。

- **`skills/review-loop/scripts/review_loop.py:749` — 指示と NO_MUTATION のどちらが優先かが曖昧**
  今の文は「スキルの手順と食い違うときは、この指示を優先」です。このため、指示が `REVIEW_CONSTRAINT`(作業ツリーを変えない)とぶつかったときに、どちらを採るかが書かれていません。たとえば「テストを走らせて確かめて」という指示は、生成物で作業ツリーを汚しえます。「ただし作業ツリーやブランチを変えない制約は、この指示より優先する」と明記すれば済みます。

- **`skills/review-loop/scripts/review_loop.py:548` — `perspectives` に文字列が入っても検証を通る**
  `all(isinstance(n, str) for n in a.get("perspectives") or [])` は、値が文字列 `"abc"` でも一文字ずつ見て通してしまいます。その結果、`render` は `a, b, c` のように表示します。状態コメントを手で編集したときにしか起きないので影響は小さいものの、`isinstance(a.get("perspectives") or [], list)` を足せば防げます。

- **`skill-dev/review-loop/test.py:576` 付近 — テストの抜け**
  次の3つを確かめるテストがありません。
  - 引数だけ違う `--perspective` が記録されるか(1つ目の指摘が直ったことの確認)
  - 既定の観点のまま `--instruct` だけを付けた試行で、レビュー役のシステムプロンプトに指示が入り、状態がどうなるか
  - `--perspective` に `/code-review …` のように `/` を付けて渡したとき、事前確認で終了コード2になるか。今は preflight が「見つからない: /code-review」で止まるはずです。そのとき「`/` は付けない」と案内すれば親が直しやすくなります。

## 妥当だと判断した点

- 指示をスキルの引数ではなく `--append-system-prompt` に足す設計は理にかなっています。`security-review` のように引数を取らないスキルがあり、引数の読み方もスキルごとに違うからです。
- 観点にないスキル名への `--instruct` を終了コード2にしているので、名前の誤りで指示が黙って捨てられることはありません。重複の検査を `check_tools` から `review_config` に移したのも、観点を入れ替えられるようになったことと合っています。
- SKILL.md で「権限の拒否に対しては自分で付けず、利用者に提案する」としたのは、検査を緩める操作を利用者の判断に残すもので、妥当です。

## 検討してほしい点

今回の動機は「`.env` を単独で読む呼び出しの拒否で試行が止まる」ことでした。`--instruct` はそれを LLM への依頼で避けるもので、守られる保証はありません(SKILL.md:54 にもそう書かれています)。同じ拒否がまた起きたときに、根本の対処(拒否を止めない条件を見直す)に戻るのか、`--perspective` で観点ごと外すのか。その線引きを先に決めておくと、運用がぶれにくくなります。
