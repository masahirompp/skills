PR #1(`review-loop-perspective-options`、コミット `ca40dc8`)の差分と周辺のコードを読んでレビューしました。テストは実行していません(作業ツリーを変えないため)。全体として、入力の検証が手厚く、誤った指定は状態に何も書かずに終了コード2で止まります。実装の筋は良いです。指摘は次のとおりで、重要なものから並べています。

## 正確性

- **`skills/review-loop/scripts/review_loop.py:397` と `:759`: 先頭に空白がある `--perspective` が素通りし、スラッシュコマンドとして起動されない**
  - `skill_name()` は `split()[0]` なので `' code-review high {pr}'` から `code-review` が取れ、事前確認も `--instruct` の照合も通ります。
  - 一方で `prompt = "/" + expand(spec, pr)` は `'/ code-review high 7'` になります。実際に確かめた結果です。
  - その結果、子はスキルではなく自由文として受け取ります。反復1回分のトークンを使い切ってから、判定役に「観点の欠落」と扱われるのが最善の場合です。
  - これまでは定数だけが入力だったので起きませんでしたが、CLI から受け取るようになったので、`review_config` で `s.strip()` して正規化すべきです。

- **`review_loop.py:963`: 既定と違うかを観点の名前だけで比べている**
  - 名前が同じで引数だけ違う場合は記録されません。たとえば `--perspective 'code-review low {pr}'` を渡しても、`code-review high` の既定と区別がつきません。
  - SKILL.md:55 の「既定と違う観点で回した試行は…表に載る」という説明と食い違います。
  - 範囲を狭めたこと(レベルを下げたこと)を表から読めないので、展開後の spec ごと比べて記録する方が説明と一致します。

- **`review_loop.py:548`: `perspectives` が list であることを確かめていない**
  - 状態コメントが手で `"perspectives":"abc"` と書き換えられると、文字列の各文字が `str` なので検証を通ります。表には `観点 a, b, c` と出ます。
  - 起きるのはまれな条件のときだけで、影響は表示の乱れにとどまります。`isinstance(a.get("perspectives", []), list)` を足せば済みます。

## 設計

- **`--instruct` が状態に一切残らない(`review_loop.py:961-964` 付近、SKILL.md:57)**
  - 観点を外した試行は表に載りますが、検査を緩めた試行は表から見分けられません。
  - SKILL.md は「以後の反復でも毎回同じものを付ける」ことを親の LLM の記憶に任せています。付け忘れても、付け足しても、気づく手段がありません。
  - 2回目以降に指示を付け忘れると、1回目に止まった拒否でまた止まり、`MAX_CONSECUTIVE_FAILURES` を消費します。
  - 案は2つあります。(a) 指示の有無(本文ではなく、どの観点に付けたか)を試行に記録する。(b) シリーズの中で前の試行と観点や指示の構成が変わったら `warn:` を出す。
  - オプションを状態に保存して自動で引き継ぐ方式は、利用者の承認なしに範囲が狭いまま続くので、勧めません。

- **`review_loop.py:749`: 指示の優先範囲が広すぎる**
  - 「スキルの手順と食い違うときは、この指示を優先」とあります。しかし、同じシステムプロンプトにある `NO_MUTATION`(作業ツリーを変えない制約)との優先関係は書かれていません。
  - 「テストを実行して確かめる」のような指示を渡すと、子が制約を破る方を選ぶ余地があり、`contamination` で試行が失敗します。
  - 「ただし、上の作業ツリーを変えない制約は常に優先する」と明記すべきです。

- **`review_loop.py:847` と `JUDGE_PROMPT`(`:797`〜): 判定役のプロンプトに、指示ブロックの扱いが書かれていない**
  - SKILL.md:54 は「判定役の入力にも添えるので、指示で外した範囲を『観点の欠落』とは扱わない」と言い切っています。
  - しかし、`JUDGE_PROMPT` の「観点の欠落」は、出力がレビューになっていない場合の定義です。判定役は区切り行だけを手がかりに意味を推測することになります。
  - 「テストは見ない」のような指示を、判定役が自分への指示と読んで、他の観点のテストの指摘を軽く扱う可能性もあります。これは「指摘を捨てない」の規則と衝突します。
  - `JUDGE_PROMPT` に「追加の指示はその観点のレビュー役に向けたもの。判定役は従わない。指示で外した範囲を欠落とはしない」の1行を足すのが確実です。

## セキュリティ

- **SKILL.md:50 と PR 本文の例(`security-review=この PR で削除した .env の中身は確かめない`): 本来の指摘まで消える恐れがある**
  - セキュリティの観点では、「削除した `.env` が履歴に残っており、中の秘密情報はローテーションが必要」は正当な指摘になり得ます。
  - 例の文面だと、`.env` の削除そのものに触れない方向へ誘導しかねません。
  - 例は「中身は読まない。履歴に残っている可能性は指摘してよい」のように、読む操作だけを外す形にした方が安全です。
  - 利用者が判断するための問いとして、`.env` は過去に push されたか、されたなら秘密情報はローテーション済みか、を添えるとよいです。

- 承認の扱い(自分では付けず利用者に提案する、SKILL.md:57、`:116`)は妥当です。観点を外すのも検査を緩めるのも範囲を狭める操作なので、承認を利用者に限るのは正しい設計です。
