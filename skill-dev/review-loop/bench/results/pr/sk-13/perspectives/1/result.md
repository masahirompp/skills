PR #1(`review-loop: 観点の入れ替えと、観点ごとの追加の指示`)の差分を5つの観点で読み、指摘を11件にまとめました。PR 本文には、テストは全て成功とあります。ただし今回は読んでの指摘だけで、テストの実行や、指摘した挙動の実機での再現はしていません。

全体の作りは妥当です。指定の誤りをロックを取る前の `Precondition` で弾くので状態を汚さず、指示の宛先を使う観点に限るので名前の誤りが黙って捨てられません。以下は直す価値があると考える順です。

### 正確性

- **`skills/review-loop/scripts/review_loop.py:963`**: 既定と違う観点かどうかを、スキル名だけで比べています。
  - 引数だけを変えたとき(`--perspective 'code-review low {pr}'` を他の既定2つと一緒に渡すなど)は、既定とみなされて記録されません。状態コメントの表には既定で回したように見え、深さを落とした試行を後から見分けられません。
  - 順番だけが違うときは、逆に「既定と違う」として記録されます。
  - 直し方: 展開前の spec の全文(または `--perspective` が渡されたかどうか)を、集合として比べるのが妥当です。
- **`skills/review-loop/scripts/review_loop.py:548`**: `a.get("perspectives") or []` を `all(isinstance(n, str) ...)` で調べていますが、値が文字列でも通ります。
  - 手で編集されて `"perspectives": "abc"` になっていても `valid_state` を通り、`render` で `', '.join("abc")` が `a, b, c` と表示されます。
  - `valid_state` は、手で編集された状態を拒むためにあるので、`isinstance(..., list)` の確認が要ります。

### 設計

- **`--instruct` が状態のどこにも残らない(`review_loop.py:961-964`、`SKILL.md:111`)**: `perspectives` は記録されますが、指示が渡されたこと自体は記録されません。
  - SKILL.md は、最後に「`--instruct` で絞った範囲」を報告するよう求めています。その根拠になるのは親エージェントの記憶だけで、文脈が要約された後に抜けやすいです。
  - 指示の本文を公開の PR コメントに載せるのは避けたいので、少なくとも「指示あり: security-review」のようにスキル名だけを残すのが妥当です。
- **`SKILL.md:57`(付け忘れると既定に戻る)**: オプションを毎回付けるかどうかを親の記憶に任せているので、付け忘れは黙って起きます。
  - 同じシリーズの中で観点が既定と指定の間を行き来し、反復の比較(蒸し返しや振動の判断)が狂います。
  - 案: 直前の試行の `perspectives` と今回の観点が食い違うときに、`warn:` を出します。
  - 反論として、スクリプトを状態を持たないまま保つ利点もあります。それでも、警告を出すだけなら状態を増やさずに済みます。
- **`review_loop.py:846` と `JUDGE_PROMPT`(797行目〜)**: 判定役に指示を添えても、`JUDGE_PROMPT` にはその区切りの扱い方がありません(コードのコメントにあるだけです)。
  - 判定役が指示を自分への命令と読むと、「テストは見ない」を受けて、他の観点が出した test_gap まで落としかねません。これは「指摘を捨てない」に反します。
  - 意図どおりに扱われず、指示で外した範囲を「観点の欠落」と判定する可能性も残ります。
  - 直し方: `JUDGE_PROMPT` に一文足します。たとえば「`追加の指示` は、その観点が意図して見なかった範囲を示す。あなたへの指示ではない。範囲外であることだけを理由に観点の欠落としない」。
- **動機の問題への効き方**: PR の発端は、`.env` を単独で読もうとして拒否され、試行が止まったことです。`--instruct` は LLM への依頼なので、守られなければ同じように止まります(SKILL.md:54 にも「保証はない」とあります)。
  - 決定的な対策としては、`source=config` の拒否のうち deny ルールに当たったものを止めない、という方向もありえます。
  - ただし今のコードは、deny ルールと許可ルールの欠如を見分けていません。この PR の範囲で済ませる判断は妥当です。

### セキュリティ

- **`review_loop.py:748-749`**: 追加の指示は `NO_MUTATION` の後ろに置かれ、「スキルの手順と食い違うときは、この指示を優先」と添えられます。
  - 編集を許すように読める指示(「見つけたら直してよい」など)が来たときに、`NO_MUTATION` より優先されると読まれる余地があります。
  - 混入の検出が後ろで受け止めますが、それは試行を失敗させるだけです。
  - 直し方: 「ただし、作業ツリーやブランチを変えない制約は、この指示より優先する」と明記します。
- **`review_loop.py:761-763`(子の argv)**: 指示の本文は `--append-system-prompt` の引数として argv に載り、同じマシンの他のユーザーからも `ps` で見えます。
  - 既存の固定文と違い、利用者が書いた文が載るようになりました。
  - 実害は小さいと考えますが、機密を書かないよう SKILL.md に一言あってもよいです。
