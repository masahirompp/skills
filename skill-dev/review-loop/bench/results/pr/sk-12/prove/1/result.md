## 指摘1: 判定役の `result` の行もすべてつなぐため、判定の後ろの文や古い案が判定として出る

この変更では、判定役(`run_judge`)にもレビュー役と同じ処理 `check_result` を使います。この処理は空でない `result` の行を全てつなぐので、判定役が複数のターンを回すと次の3つが起きます。

- 判定の後ろに付いた短い文が判定に残る
- 途中で出した案と最後の判定が両方とも判定に入る
- コードフェンスの閉じを落とせない

前置きを落とす処理は、最初の見出しより前しか削りません。

判定役が `result` の行を複数出す場合があることは、この変更自身が前提にしています。偽の claude に `FAKE_JUDGE=multi` を足しているからです。

**再現の準備**
- `scratch/fakes/claude`: 判定役のときだけ、環境変数 `FAKE_JUDGE2` に応じて `result` の行を2つ出します。それ以外の呼び出しは、元の `skill-dev/review-loop/fakes/claude` にそのまま任せます。
  - `short`: 判定のあとに「前のメッセージの内容から変わりません」
  - `revise`: 「古い案」の判定のあとに「確かめた案」の判定
  - `fenced`: 前置きとコードフェンスで包んだ判定のあとに「以上です」
- `scratch/judge_multi.py`: `test.py` の1〜130行目(準備用の関数)を写し、`FAKES` と `SCRIPTS` の場所だけを書き換えたものです。3つのモードで `iterate` を本物の `review_loop.py` に対して実行し、標準出力(判定)を表示します。

**実行したコマンド**

**出るべきだった出力**

`JUDGE_PROMPT` は「次の形の Markdown だけを出力する」と求めています。また `run_judge` は前置きとコードフェンスを落とします。これに照らすと、3つのモードとも次の判定1つだけが出るべきでした。

```
## 指摘

### F1: 確かめた案
- 観点: code-review

## 競合

なし
```

実際の出力では、次の問題が起きています。

- `revise` では見出しが2組あり、F1 が2件出ます。親が修正の範囲を決めるときに、古い案も指摘として数えてしまいます。
- `short` と `fenced` では、判定ではない文が判定に残ります。`fenced` では閉じフェンスも残ります。

**この検証で確かめていないこと**

本物の claude で判定役が `result` の行を複数出すのが、どれくらいの頻度で起きるかは確かめていません。再現は偽の claude によるものです。
