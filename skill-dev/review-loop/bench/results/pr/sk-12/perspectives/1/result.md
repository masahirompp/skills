## 正確性

- **`skills/review-loop/scripts/review_loop.py:309` と `:249`: `tool_use_id` のない拒否の扱いで、PR 本文の「危ない方向には外れない」が成り立たない**
  - `config_denied` は `msg.get("tool_use_id")` をキーにしています。`source: config` のイベントに `tool_use_id` がないと、キーが `None` になります。
  - その場合 `seen = set(tail.config_denied)` に `None` が入ります。すると `:256` で、result 行の `permission_denials` のうち `tool_use_id` を持たないものは、`source` が何であっても `seen` に当たったとみなされて除外されます。止める側に倒れるはずの拒否が素通りします。
  - さらに `None` キーの拒否が2件あると上書きされます。dict の長さが増えないので、`new_config_denials` は2件目を報告せず、`denials.txt` から欠けます。
  - 直し方の案: `tool_use_id` がない config の拒否は除外の集合に入れず、`list` に追記して記録してください。または `tool_use_id` がないイベントは止める側に倒してください。

- **`review_loop.py:800-803`: 判定役の result 行をつないだ結果、判定の後ろに来たテキストが `verdict` に残る**

  - 判定役が判定を全文で2回出したとき(途中で一度書き、通知を受けて書き直したときなど)は、F1… が二重に並びます。親は古い方と新しい方を見分けられません。
  - 判定役がバックグラウンドでサブエージェントを使うなら、この並びは起きうる範囲です(観点スキルでは実際に起きている)。
  - `VERDICT_SECTIONS` の確認も、つないだ後のテキストに対して行うので、途中の行に見出しがあれば最後の判定が崩れていても通ってしまいます。
  - 判定役については、見出しを含む result 行のうち最後のものだけを採る方が、意図(最新の判定)に合います。

## セキュリティ

- **`review_loop.py:308-309`: config の拒否で止めないと、子が拒否されたあと別の手段で同じものに近づくのを止めるものがなくなる**
  - これまでは、拒否が出た時点で試行が止まっていました。結果として、利用者の deny ルール(`.env` など)を子が回り込もうとしても、続けられなかった面があります。
  - 今回の変更で子は続けられます。たとえば `Read(.env)` が deny で、`grep` を含む Bash が allow なら、`grep -r KEY .` のような形で読めてしまいます。
  - 根本は許可ルールの組み方の問題で、このスクリプトだけで防ぐことではありません。ただ、事実上あった歯止めを外す変更なので、SKILL.md の「失敗したとき」にこのリスクを書いておくべきです。
  - PR 本文が認めている「許可ルールが無いための拒否も `source: config` になる」場合は、`前提` の節の「読み取りのコマンドが許可されている」が強制されなくなります。
  - `reason_type` を記録しているので、止めない対象を `source: config` かつ特定の `reason_type`(実物で確かめた値)に絞れば、未検証の前提に頼る範囲を狭められます。いまの判定は `source` の1値だけに頼っており、その値を実際のイベントで確かめていない点が弱いです。
