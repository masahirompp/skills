PR #1(`review-loop-multi-result`)の差分を、ファイルを変えずに読んでレビューしました。テストは実行していません。結論として、大きな方針(`result` の行をつなぐこと、`source: config` の拒否は止めずに残すこと)は妥当です。ただ、判定役の出力を同じ方法でつなぐ部分と、拒否を除外する部分の条件に穴があります。

## 正確性

- **`skills/review-loop/scripts/review_loop.py:803`: 判定役の出力をつなぐと、`verdict.md` に余分な文や同じ節の重複が入りえます。**
  - `verdict = text[start:]` は、最初の見出しから「つないだテキストの最後」までを取ります。
  - 判定役が判定のあとに「以上です」のような `result` 行を出すと、その文が `verdict.md` に入ります。下書きと最終版の2回判定を出すと、`## 指摘` と `## 競合` が2組そのまま入り、同じ `F1` が2つできます。
  - レビュー役では「欠けるよりよい」が成り立ちます。しかし判定役の出力は形が決まっていて、親がそのまま方針に使います。そのため、判定役には別の方針が要ると考えます。たとえば、見出しを含む最後の `result` 行を使う、見出しが2回出たら `no_output` にする、などです。
  - テストの `FAKE_JUDGE=multi` は「最後の行が空」の場合しか確かめていません。

- **`review_loop.py:805`: 前置きでコードフェンスを開いた場合、後ろに別の行が続くと閉じフェンスが残ります。**

  - 判定本文の行が閉じフェンスで終わり、そのあとに短い `result` 行が続くと、```` ``` ```` が `verdict.md` の途中に残ります。

- **`review_loop.py:263`: 子の異常終了を報告するとき、原因が見えなくなります。**
  - `child_error` の詳細が `text[:500]`、つまりつないだテキストの先頭になりました。
  - 最後の行に `is_error` やエラー文がある場合、表示されるのは最初の途中経過の文や本文の冒頭で、原因が切り落とされます。

- **`review_loop.py:309` と `:249` 付近: `tool_use_id` がない `source: config` のイベントで、拒否を見逃す側に外れます。**
  - `config_denied[msg.get("tool_use_id")]` は、id がないと `None` をキーにします。その結果、`seen` に `None` が入ります。
  - すると、`result` の `permission_denials` のうち `tool_use_id` のないものが、出どころに関係なく除外されます。
  - PR 本文の「危ない方向には外れない」という前提は、`source` の位置だけを見ています。id がない場合は扱っていません。
  - 同じ理由で、id のない config 拒否が2件目以降に来ると辞書のキーが上書きされます。件数が増えないので、`new_config_denials` には出ず、`denials.txt` にも残りません(`:323-324`)。
  - 直し方の案: id がないものは除外の対象にせず、記録用にはリストで持つ。

- **`review_loop.py:237`: 補足の説明が自己矛盾しています(挙動には影響しません)。**
  - 「modelUsage はセッションの累計で、どの行も同じ値になる」とあります。累計なら行ごとに値は増えるはずで、「同じ値」とは両立しません。
  - 最後の行だけを数えるという実装はどちらの解釈でも正しいので、説明だけ「累計なので最後の行が全体」に直せば足ります。

## セキュリティ / プライバシー

- **`review_loop.py:337-339`: 拒否されたコマンドの入力が、試行を続けた場合にもファイルと stderr に残るようになりました。**
  - 拒否されたコマンドは、`summarize_denials` で先頭200字まで残ります。
  - 以前は失敗したときだけ stderr に出ていました。今回から、成功する試行でも `denials.txt` と `warn:` の行に残ります。
  - deny ルールが守っているのは `.env` のようなファイルの中身で、コマンドの文字列ではありません。それでも、`curl -H "Authorization: …"` のようにトークンを含むコマンドが拒否されると、それが残ります。
  - 作業ディレクトリの最上位は `0o700` です(`:926-931`)。そのため外への漏れは限られ、影響は小さいと判断します。SKILL.md に「親が `denials.txt` を読む」手順があるので、親の文脈に入る点だけは意識しておくとよいです。

- **設計上のリスク(PR 本文で既に認識済み): 許可ルールが無いための拒否も `source: config` になる場合、セキュリティではなく網羅性が落ちます。**
  - その場合、`permission_denied` で止まっていた失敗が黙って通るようになります。
  - 拒否イベントの実物をまだ確かめていないことが一番の不確実性です。マージ前に、本物の stream で `source` と `reason_type` の値を1件確かめるべきだと考えます。

## 設計

- **`review_loop.py:243` 付近: レビュー役の出力にも、同じ本文が2回入る可能性があります。**
  - 「最後の行が短い文」の場合だけを想定していますが、子が最後に本文をまとめ直して出すと、同じ本文が判定役に2回渡ります。
  - 判定役は観点の中の重複を想定していないので、件数の見積もりが歪むかもしれません。
  - 直さずに受け入れるなら、SKILL.md の「途中経過の文も混ざる」に「同じ本文が繰り返されることもある」を足しておくと、親が読み違えません。

- **テストの抜け(`skill-dev/review-loop/test.py`、`fakes/claude`):**
  - 偽の claude の拒否は、どれも `tool_use_id: "x"` の1件だけです。次の場合を確かめるテストがありません。
    - config の拒否と、id の違う source のない拒否が混ざる場合: 止まるべき。
    - config の拒否のあとに source のない拒否が来る場合: 動いている間に止まるべき。
    - id のないイベント: 上の見逃しの指摘。
  - 除外の条件が新しい理屈なので、この3つを足しておくと、外れる向きを固定できます。

優先度は、判定役の出力をつなぐ件(`:803`)と `tool_use_id` がない件(`:309`)が高く、残りは中から低と見ています。前者は、判定役が `result` 行を複数出す頻度で決まります。判定役がサブエージェントをバックグラウンドで使わないのが確実なら、実害はほぼ出ません。その前提が成り立つかどうかを確かめるのが先です。
