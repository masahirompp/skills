PR #1 の差分を読み、該当箇所の前後のコードも確認しました。修正を急ぐべき問題は 1 と 2 の2点です。どちらもコードから一意に決まる挙動ですが、実行しての再現はしていません。全体として方向は妥当です。最後の行だけ読んで本文を落としていた不具合を直し、トークン数の二重計上を避け、`source` が入っていない拒否は止める側に倒しています。

## 正確性

1. **判定役の出力が複数の `result` 行に分かれると、後ろの行が `verdict.md` に紛れ込む**
   - 場所: `skills/review-loop/scripts/review_loop.py:242` と `:803`
   - `text` は空でない `result` 行をすべてつないだものです。`verdict = text[start:]` は最初の見出しから末尾までを取ります。
   - 判定の後ろに「以上です」「前のメッセージの内容から変わりません」のような短い行が来ると、それが最後の節(`## 競合` や最後の指摘)の本文として残ります。
   - 判定役が判定を2回出した場合(書き直しなど)は、2つ分が重なります。見出しの確認は `re.search` で最初の一致しか見ないため、古い方を正としたまま通ります。
   - テストの `FAKE_JUDGE=multi` は最後の行が空のケースしか試していないので、この問題を検出できません。
   - 案: 判定役については「見出しをすべて含む `result` 行のうち最後のもの」を使い、つなぐのはレビュー役だけにする。少なくとも `multishort` 相当の判定役ケースをテストに足す。

2. **`child_error` のメッセージに、肝心のエラー文が出なくなる**
   - 場所: `review_loop.py:263`
   - 以前は最後の `result` 行の文(API エラーなど)を出していましたが、今はつないだ `text[:500]` を出します。
   - 途中経過の行が先にあると、先頭500字が「バックグラウンドで実行しています…」で埋まり、最後の行にあるエラー文が切り捨てられます。
   - 案: ここは `str(data.get("result") or "")[:500]` に戻すか、`text[-500:]` にする。

3. **`tool_use_id` がない拒否は、黙って見逃される**
   - 場所: `review_loop.py:250-258`、`:309`
   - `config_denied` のキーには `msg.get("tool_use_id")` をそのまま使っています。`tool_use_id` のない `source: config` のイベントが1件でもあると、`seen` に `None` が入ります。
   - その結果、`result` の `permission_denials` に載った `tool_use_id` のない拒否は、出どころにかかわらずすべて除外されます。PR 本文の「危ない方向には外れない」という前提に反し、止めるべき拒否を見逃します。
   - 案: `tool_use_id` が偽のときは `seen` に入れず、照合しない(止める側に倒す)。

4. **`new_config_denials` が報告を取りこぼす**
   - 場所: `review_loop.py:309`、`:323`
   - dict のキーが重なると(`tool_use_id` が `None` 同士、または同じ id のイベントがもう一度出たとき)、件数が増えません。`reported` と切り出す位置がずれ、新しい拒否が `denials.txt` と warn に出なくなります。
   - 案: dict ではなく list に追記し、照合用の id は別の set で持つ。

5. **子がすぐ終わったとき、止める拒否が `child_error` に化ける**
   - 場所: `review_loop.py:238` と `:340`
   - 終わった子については、`watch_denials(running=False)` は拒否で止めず、`check_result` に任せます。
   - ところが `check_result` は先に `if not tail.results` で `child_error` を投げます。拒否のあと `result` 行を出さずに異常終了した子は、`permission_denied` ではなく `child_error` に分類されます。
   - SKILL.md の「同じ原因で2回続いたら報告」という判断が、別の原因に見えてしまいます。
   - 案: `tail.denial` があるかどうかを先に確かめる。

## セキュリティ

6. **`source: config` を「止めない」根拠が実物で確かめられていない**
   - 場所: `review_loop.py:308`、`skills/review-loop/SKILL.md:24`
   - PR 本文も認めているとおり、拒否イベントの実物を確かめていません。偽の claude(`fakes/claude` の `deny()`)は、仮定した形のイベントを出しているだけです。
   - 「許可ルールが無いための拒否」も `source: config` になる場合、SKILL.md の前提「許可されていない呼び出しは試行の失敗になる」が丸ごと成り立たなくなります。観点スキルが `gh pr diff` を一度も実行できないまま「指摘なし」を返しても成功扱いになり、判定役は欠落を見分けられません。
   - 案: マージ前に、実際の `claude -p --output-format stream-json` で次の2つを起こし、イベントの形を記録する。
     - 許可ルールが無い場合の拒否
     - deny ルールに当たる場合の拒否

     少なくとも `reason_type` も条件に加えて、ホワイトリストを狭めるのが安全です。
   - 反対側の見方も挙げておきます。止めない対象を広げたこと自体は、`.env` への deny が日常的に起きるなら必要な変更です。ここでの論点は、その範囲が意図より広くなっていないかです。

## 並行性

7. **問題は見つかりませんでした**
   - `denials.txt` への追記は、単一プロセス・単一スレッドのポーリングループからだけ行われます(`review_loop.py:338`)。判定役もレビュー役のあとに順番に動くので、競合は起きません。
   - 判定役の制限時間は、見張り役の `JUDGE_TIMEOUT + WATCHDOG_GRACE` と二重に効いています。`p.wait` からポーリングに変えても、子プロセスが取り残されることはありません。

## プライバシー

8. **拒否されたコマンドの入力が平文で残る**
   - 場所: `review_loop.py:336-339`
   - `denials.txt` と stderr の `warn:` に、拒否されたツールの入力が最大200字そのまま書かれます。
   - deny ルールに当たるコマンドは、`.env` や認証情報まわりのものが多く、`curl -H "Authorization: ..."` のようにトークンそのものを含むこともあります。作業ディレクトリは `0o700` なので、ファイルの公開範囲は限られます。ただ、stderr は親エージェントの文脈に入り、利用者への報告や PR への書き込みに転記される経路が増えます。
   - 以前も `permission_denied` で同じ情報が出ていましたが、今回は試行が成功する場合にも出るようになり、出る頻度が上がります。
   - 案: stderr にはツール名と件数だけを出し、入力は `denials.txt` だけに残す。

## 設計

9. **レビュー役の出力に途中経過の文が混ざる方針は、判定役のプロンプト側でも扱う必要がある**
   - 場所: `review_loop.py:232-236`、SKILL.md の結果の節
   - 「欠けるよりよい」という判断自体は妥当です。ただし判定役は、途中経過の文(「Standards のレビューは終わりました」など)も観点の出力として受け取ります。これを指摘や欠落の判断材料として扱うおそれがあります。
   - 案: `judge-input.md` で各 `result` 行の境目に区切りを入れるか、判定役のプロンプトで途中経過の文があり得ることに触れる。

10. **テストが仮定の形をそのまま正としている**
    - 場所: `skill-dev/review-loop/fakes/claude` の `deny()`
    - `source` を最上位に置き、`tool_use_id` を必ず入れています。そのため、3・4 の入力(id なし)も、6 の入力(source が入れ子)も通りません。
    - 案: `tool_use_id` のない config の拒否と `source` のない拒否が混在するケースを1つ足す。3 の見逃しを検出できるようになります。

マージ前に確かめてほしい問いを1つ挙げます。実際の運用で `source: config` 以外の止めない拒否は起きていますか。もし `.env` の deny しか観測していないなら、`source == "config"` で一括して止めない代わりに、`denials.txt` に残したうえで、拒否の内容が特定のパターンに当たるときだけ止めない、という狭め方もあります。
