### 指摘

- **`skills/review-loop/scripts/review_loop.py:242` と `:802-803`：判定役まで「result の行を全部つなぐ」ので、判定の後ろに出た文が `verdict.md` に入る**
  - 判定は、最初の見出しから末尾までを切り出して作っています。判定のあとに「前のメッセージから変わりません」のような短い行が出ると、それが最後の節 `## 競合` の中に入ります。
  - 判定役が下書きと最終版の2回判定を出した場合は、`### F1` などの見出しが重なったまま親に渡ります。
  - レビュー役なら「欠けるより混ざるほうがよい」という理由は通ります。一方、判定役の出力は形が決まっていて、親がそのまま読みます。こちらは「`VERDICT_SECTIONS` が全部そろう最後の result の行を使う」とするほうが安全です。
  - テストの偽の claude(`skill-dev/review-loop/fakes/claude:92`)は最後の行が空のケース(`multi(..., verdict, "")`)しか試していません。判定の後ろに短い文が来るケースは確かめていません。

- **`review_loop.py:308`：`source == "config"` という前提が本物の出力で確かめられておらず、テストも確かめていない**
  - PR 本文にも書かれているとおり、本物の拒否イベントでの確認がありません。偽の claude の `deny()` はこの前提に合わせて書かれているので、テストが通っても前提の裏付けにはなりません。
  - 外れ方が「止める側」なら今までの挙動に戻るだけで、危なくはありません。問題は逆の外れ方です。許可ルールがないための拒否まで `config` になると、`gh pr diff` が拒否されてもレビューが静かに続き、読めていないまま「指摘なし」を返しかねません。
  - マージ前に、本物の `claude -p --output-format stream-json --verbose` で次の2種類の拒否を起こし、`source` と `reason_type` の値を見ておくべきです。
    - deny ルールに当たる拒否
    - 許可ルールがないための拒否

- **`review_loop.py:336` と `run_judge`：PR 本文の「判定役が観点の欠落として拾う」という安全網が、実際にはつながっていない**
  - `denials.txt` は作業ディレクトリに書かれるだけで、`judge-input.md` には入りません。
  - そのため判定役が欠落に気づけるのは、レビュー役が自分の出力で「読めなかった」と書いたときだけです。
  - 設定のルールでの拒否があった観点については、`judge-input.md` のその観点の区切りの中に拒否の要約を足せば、拾う流れが仕組みとして成り立ちます。

- **`review_loop.py:309` と `:251-256`：`tool_use_id` が `None` のとき、重複を除く処理が広く効きすぎる**
  - `config_denied[None]` が入ると `None` が `seen` に入り、`tool_use_id` を持たない `permission_denials` は全て除かれます。この中には、本来止めるべき拒否も含まれます。
  - 同じ理由で、id のない設定の拒否が2件以上あると1件にまとまり、2件目以降は `denials.txt` に残りません。
  - id がないものは重複を除く対象から外し、止める側に倒すのが一貫した扱いです。

- **`review_loop.py:238`(軽微。以前からある挙動)：止めるべき拒否のあとで result の行がないまま子が終わると、拒否の情報が消える**
  - この順で起きると、`tail.denial` があっても `child_error` の「result の行がない」になります。
  - `watch_denials(..., running=False)` は `tail.denial` を見ないので、ここでも拾われません。
  - `not tail.results` の分岐で、先に `tail.denial` を見て `permission_denied` として返せば、どの拒否で失敗したかが残ります。
