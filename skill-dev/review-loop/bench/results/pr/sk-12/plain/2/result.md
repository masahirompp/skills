## 指摘

**中**

- **`skills/review-loop/scripts/review_loop.py:309`(と `:328-340`)— 中身が分からない `source: config` だけで、止めるかどうかを決めている**
  - 拒否のイベントの実物が手元になく、`source` がどこにどんな値で入るかを確かめていないことは、PR 本文にも書かれています。ローカルの `$TMPDIR/review-loop` も探しましたが、`permission_denied` の実物はありませんでした。
  - 外れたときの向きは2つあり、片方は安全ではありません。
    - `source` が入れ子の場所にある場合: 全ての拒否で止まります。今までと同じなので安全です。
    - `-p` で許可ルールに当たらないだけの拒否も `config` になる場合: 何でも素通りします。
  - 後者になると、たとえば `gh pr diff` 自体が拒否されても、そのレビューは成功として扱われ、差分を読まない内容のまま判定役へ流れます。
  - 判定役が拾えるのは「観点ごと欠けている」ことだけです。1つの観点の中で入力が減ったことは見分けられません。
  - 提案: マージ前に本物の拒否イベントを1件取り、fake の `deny()`(`skill-dev/review-loop/fakes/claude:40-49`)をその形に合わせる。または `reason_type` も条件に入れて、止めずに続ける場合を狭める(例: `subcommandResults` のように一部だけの拒否に限る)。

- **`review_loop.py:777` — 設定のルールでの拒否を、判定役も最終の出力も知らない**
  - `denials.txt` と stderr の `warn:` には残りますが、`judge-input.md` にも `verdict.md` にも入りません。
  - SKILL.md:103 は「観点の欠落が出たときは `denials.txt` を確かめる」としています。ただ、上に書いたとおり、観点が欠けずに中身だけ薄くなる場合は、この手順のきっかけ自体が起きません。
  - 提案: 拒否のあった観点のブロックの末尾に「このレビューでは次の呼び出しが拒否された」と添えて、判定役に渡す。

  - なお、テスト(`FAKE_JUDGE=multi`)は最後の行が空の場合しか見ていないので、この問題は検出できません。

  - 止めるかどうかには影響しませんが、stderr の要約が不完全になります。

## 妥当だと判断した点

- **トークン数を最後の行だけで数えること**: modelUsage がセッションの累計なので筋が通っています。テスト(`4 * 300`)でも、二重に数えていないことを確かめています。
- **判定役を stream-json にそろえたこと**: タイムアウトと拒否の扱いがレビュー役と同じ流れになり、`check_result` から `tail=None` の分岐が消えて単純になりました。
- **プロセスが終わったあとの `tail.poll()` → `watch_denials(running=False)` → `check_result` の順番**: 終わる直前に書かれた拒否を読み残さない作りになっています。

いちばん効くのは、本物の `source: config` の拒否イベントを1件取ることです。上の「中」の2件は、どちらもその形が分かれば重さが決まります。
