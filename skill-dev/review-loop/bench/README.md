# review-loop のレビュー役の構成を比べる

不具合を含む差分に対して、レビュー役の構成を1つずつ実行し、見逃し、余計な指摘、時間、トークンを比べる。
本番(`skills/review-loop/SKILL.md`)の既定の観点を決める材料にする。本番のスキルは変えない。

子は `claude -p` で起動する(`claude_p.py`)。本番は 2026-11-17 に、親が観点スキルを直接呼ぶ形に変えたので、起動の仕方は本番と違う。ここでは、モデルを固定して構成どうしを比べるために、`claude -p` のままにしている(「本番との違い」)。

## 使い方

```sh
# 1. 実行する(題材 × 構成 × 試行。途中で止めても、同じコマンドで続きから回る)
python3 skill-dev/review-loop/bench/bench.py run --out skill-dev/review-loop/bench/results/<名前> --trials 3 --jobs 4

# 2. 採点する
python3 skill-dev/review-loop/bench/score.py score    skill-dev/review-loop/bench/results/<名前>
python3 skill-dev/review-loop/bench/score.py cluster  skill-dev/review-loop/bench/results/<名前>
python3 skill-dev/review-loop/bench/score.py classify skill-dev/review-loop/bench/results/<名前>

# 3. 集計する(report.md と scoring-review.md)
python3 skill-dev/review-loop/bench/score.py report   skill-dev/review-loop/bench/results/<名前>
```

`--cases sh-1,wn-313` と `--configs code-review,prove` で絞れる。子の `claude -p` を実際に起動するので、費用がかかる。

## 置いてあるもの

| 場所 | 中身 |
|---|---|
| `bench.py` | 題材の組み立てと実行。構成ごとのプロンプトは `CONFIGS` |
| `claude_p.py` | 子を `claude -p` で起動し、stream を読む部品。`test_claude_p.py` はそのテスト |
| `score.py` | 採点、余計な指摘のまとめと分類、集計。採点の基準は `SCORE_PROMPT` と `CLASSIFY_PROMPT` |
| `combos.py` | 構成の組み合わせごとの集計(1反復で見つかる不具合、余計な指摘、時間、費用)と、構成どうしの差の揺れ |
| `repeat.py` | 同じ構成を繰り返して合わせた場合と、ほかの構成を足した場合の比較。既存の結果から集計し、子を起動しない |
| `publish.py` | 題材を、GitHub の検証用の非公開リポジトリ(`rlbench-<題材>`)と PR にする。`bench.py run --pr` で、本番と同じく PR 番号を渡してレビューさせるため。`publish.py delete` で消す |
| `verify.py` | レビューの指摘を実行で確かめる検証役の試し。本物の指摘を誤って落とす率を測る |
| `cases/<題材>/` | 題材の定義(`case.json`)。skills の題材は `base.patch`(ベースへの加工)、`change.patch`(レビュー対象の差分)、`message.txt`(差分の意図) |
| `answers/<題材>.json` | 正解の一覧。子からは見えない |
| `answers/repro/` | 埋め込んだ不具合を再現するスクリプト |
| `trials/<日付>-<名前>/` | bench の仕組みを使わずに行った1回きりの試しの記録(依頼文、基準、出力、採点)。それぞれの README に手順と結果 |
| `results/<名前>/` | 結果。試行ごとに `result.md`(レビューの出力)、`meta.json`、`score.json`。子の stream(`*.jsonl`)は大きいのでコミットしない |

## これまでの結果

Opus 5.5 で測った。数字の出どころは `results/` の各 `report.md` と `combos.md`。

- `results/main`: PR なしの形。10題材 × 5構成 × 3回
- `results/pr`: PR ありの形。code-review・観点明示型(perspectives)・観点を書かない形(plain)は3回、ほかは1回
- `results/verify`: 検証役の試し。正解と一致した指摘58件と、正解に無い指摘58件

分かったこと(PR ありの形、不具合41件):

- code-review high が単独で最も多く見つけた(54%)。観点明示型 44%、観点を書かない形 38%。後の2つの差は誤差の範囲
- security-review と mattpocock-skills:code-review は、それだけが見つけた不具合が0〜1件だった。ただし、題材にセキュリティの不具合がほとんど無い
- code-review high を2回流して合わせると、28〜32件(68〜78%)。前の既定(code-review、security-review、mattpocock-skills:code-review を1回ずつ)は 21〜27件(51〜66%)で、本物でない余計な指摘は題材あたり 7.0〜7.7件に対し 11.1〜11.5件、費用は $1.22 に対し $2.09 だった(`results/pr/repeat.md`)。`results/pr` では、code-review の3回を全て合わせても見つからず、この2つのスキル(各1回)が見つけた不具合は無い。これをもとに、既定を code-review high 2つと security-review にした
- 上の差は、PR なしの形(`results/main`)では小さい。2回分が 21〜26件、前の既定が 20〜24件で、幅が重なる。そこでは、code-review の3回が見つけず、mattpocock-skills:code-review だけが見つけた不具合が1件(W306-7)、security-review だけが1件(W306-6)ある
- mattpocock-skills:code-review を外したのは、費用(題材あたり $1.08)と余計な指摘(単独で 7.9件)のため。失うものが無いとは言えない。設計・方針の水準の問題は、この表では測っていない。別に、`trials/2026-11-16-policy-overview/policy-review/criteria/` の基準(sk-13、sk-14、sk-16 の18項目)で `results/pr` の出力(1回分)を採点すると、○ は2件で、どちらも code-review high が3回のうち2回以上で挙げていた(3題材、1回分、採点は LLM の判断で、どの出力かを知っている)
- security-review を残したのは、同じく外す影響を測れておらず、こちらは安い(題材あたり $0.40、余計な指摘0件)ため
- 検証役は、本物の指摘を誤って落とさなかった(「起きなかった」3件は、どれも指摘の書いた経路が誤っていた)。正解に無い指摘は、半分強を落とした

言えないこと: 正解は全て、過去のレビューが見つけた不具合である(行単位の不具合で、設計の誤りは測っていない)。余計な指摘の分類は、重複や構造の好みの指摘を「些末」に数えるので、設計の指摘の価値は「余計な指摘」の数に表れない。security-review と mattpocock-skills:code-review は、`results/pr` では1回しか流していない。2回分の比較は、3回の試行から2つを選ぶ3通りだけで、ほかの構成を足す比較には、その構成の試行1だけを使っている(perspectives と plain の試行2と3は使っていない)。採点と分類は LLM の判断で、抜き取りでしか確かめていない。モデルは Opus 5.5 だけ。

## 題材の作り方

題材は「ベース+不具合を含む差分」の一時リポジトリで、`main` にベース、作業ブランチに差分を置く。origin はローカルの
bare リポジトリで、GitHub には触れない。

- **skills の題材**(`source.type: skills`): このリポジトリの固定した版の写しに `base.patch` を当てたものをベースにし、
  `change.patch` を差分にする。履歴は持ち込まない。ベースからは、不具合を言い当てるコメントと、対応する回帰テストを外す
  (残すと、既存のテストを流すだけで見つかる)。差分を当てても既存のテストが通ることと、`answers/repro/` のスクリプトで
  不具合が再現することを確かめてから足す
- **実際の PR の題材**(`source.type: repo`): 手元の clone から、PR のベースと「レビューを受ける前のコミット」までを取り込む。
  それより後の修正コミットは取り込まない。正解は、後の修正コミットが直した問題のうち、レビュー前のコミットに既にあったもの

## 守っていること

- 正解の一覧は、構成4(観点明示型)の観点の一覧と別に作る。観点は Qiita の記事
  (https://qiita.com/kunitomo926/items/7dfc85770cf5132f3d1c)の5つをそのまま使う
- 子は、試行ごとに専用の複製の中で動かす。複製のパスに、題材や構成の名前を入れない
- 子のツール呼び出しから、題材の外(手元の clone、GitHub、ほかの試行)を見に行った疑いのあるものを拾い、`meta.json` の
  `outside_access` と `report.md` に出す。機械的な照合なので、誤検知がある。1件ずつ見て判断する
- 採点役には、どの構成の出力かを渡さない。判定にはレビューの出力からの引用を付けさせ、引用が実在するかを照合する
- 余計な指摘は、題材ごとに同じ指摘をまとめてから、まとまりごとに1回だけ分類する(構成ごとに分類が揺れないように)。
  分類役は題材の複製の中で実行でき、根拠を残す
- 子の `gh` は未認証にする(`GH_CONFIG_DIR` を空のディレクトリに向ける)。題材のコードからリポジトリ名が分かるので、
  認証があると、子が GitHub の issue や PR を読みに行き、レビューで見つかった不具合を知りうる

## 本番との違い

本番は、2026-11-17 に、スクリプトも、俯瞰の役も、サブエージェントに呼ばせる形も無くした(下の「通しの実行と、作り直し」)。
この節の「本番の `review_loop.py`」と「サブエージェントに呼ばせる」は、それより前の版を指す。

- 子を `claude -p` で起動し、モデルを指定する(既定は `claude-opus-5-5`。`--model` で変える)。レビュー役、採点役、分類役の
  全てに同じモデルを使う。本番は、親が観点スキルを Skill ツールで直接呼ぶ(フォークで動かないスキルは、サブエージェントに
  呼ばせる)ので、レビュー役は親と同じモデルで動く。親のモデルが Opus 5.5 でなければ、ここの数字はそのままは当てはまらない
- `claude_p.py` は、本番の `review_loop.py` がレビュー役を `claude -p` で起動していた版から、bench が使う部品だけを写したもの。
  子の起動、stream の読み取り、権限の拒否の扱いは、その版のまま。`python3 skill-dev/review-loop/bench/test_claude_p.py` で、
  作り物の子を使って確かめる(claude は起動しない)。本番の `review_loop.py` は、試行の前後の確認と状態コメントだけを受け持つ
- PR ありの形(`--pr`)では、制約をシステムプロンプトで渡す。本番は、スキルの引数か、サブエージェントへの依頼文に書く
- 呼び方の違いで検出が大きくは落ちないことは、3題材で1回だけ確かめた(下の「親から呼ぶ形の試し」)
- PR が無い。スキルには PR 番号ではなく、ブランチの差分を対象として渡す(`code-review high {pr}` → `code-review high`)。
  対象(`main...HEAD`)と意図の在りか(コミットメッセージ)は、全構成に同じ文(`bench.py` の `TARGET`)で伝える
- 本番の `review_loop.py` に、検証役は無い(判定役も 2026-11-17 に外した)。`verify.py` は、検証役を足す案の試しで、
  渡すのは、レビューの出力から抜き出した指摘の文面。本番に足すときにプロンプトや入力を変えるなら、`results/verify` の結果は
  そのまま当てはまらない
- `claude -p` で起動していた版の本番は、試行を止める権限の拒否(auto mode の分類器など)が出たら、その反復を失敗にしていた。ここでは止めずに
  最後まで動かし、`status: denied` として記録する。出力は採点に含め、拒否のあった試行の数を別に出す

## 親から呼ぶ形の試し(2026-11-17)

本番の呼び方を変える前に、次を確かめた。出力は残していない(数字だけ)。

- サブエージェントに `code-review high` を呼ばせた(Opus。PR なしの形、題材は sk-12、sk-13、sk-16)。`results/main` と同じ採点役で採点した

  | 題材 | `claude -p`(`results/main` の3回) | サブエージェント |
  |---|---|---|
  | sk-12(不具合6件) | 4、4、2 | 6、5 |
  | sk-13(8件) | 5、4、3 | 5、4 |
  | sk-16(10件) | 5、3、3 | 4 |

  言えるのは、大きくは落ちないことまで。5回分で、題材を作業ディレクトリの外に置いたので、対象のパスと制約を引数に書き足して
  呼び直している(引数 `high` だけの呼び出しは、6本とも作業ディレクトリのリポジトリをレビューした)。1本は、サブエージェントが
  スキルを呼び直さずに自分でレビューしたので、外した
- 親が Skill ツールで `code-review high <PR番号>` を同じターンで2つ呼んだ(親は Fable 5.2、題材は実際の PR)。2つとも
  フォークで同時に動き、親と同じモデルで動いた。親の会話は引き継がれなかった。片方はバックグラウンドで起動され、結果と
  トークン数が完了の通知で届いた。もう片方は、その場で結果が返った(トークン数は付かない)。2つの指摘は、半分ほどが重ならなかった
- `security-review` と `mattpocock-skills:code-review` は、Skill ツールで呼ぶとフォークにならず、手順の本文が呼んだ側の
  文脈に読み込まれた
- 本番の強制の実績(状態コメントのある PR 29本、試行119回): completed 109、failed 10(`permission_denied` 4、`child_error` 3、
  `no_output` 2、`workdir_error` 1)。`contamination`、`timeout`、`head_changed`、反復の上限、連続失敗の上限は、1回も働いていない

## 通しの実行と、作り直し(2026-11-17)

親から呼ぶ形(begin と end を持つ版)を、sk-12 の PR で初めて通しで回した(2反復、約65分。利用者の判断で終了)。記録は残していない(数字だけ)。

- begin と end は4回とも終了コード0。レビュー役は3つとも、2回とも、自分で出力先に書けた
- 反復1の修正役は、24分かけて規則を3つ直したが、どれも作り物の入力に立つ「実行では確かめていない」修正だった。
  そのうち2つは、本物の stream の形が PR の前提と違うと分かって revert した。それを見つけたのは、修正役が、
  ほかの PR の一時ディレクトリに残っていた記録を読んだため(手順が用意した経路ではない)
- 俯瞰の役は、2回とも「範囲を変える」と正しく判断した。親は、1回目の勧め(先に実物を確かめる)を採らなかった
- 親は、表と役の対応の照合を2回とも飛ばし、俯瞰の役の出力を、ハーネスの内部の記録から抜き出して保存した
- 親の文脈は、2反復で約17万トークン。俯瞰の役は1回に4〜7分、出力約4万トークン

これを受けて、本番を、手順と終了の基準だけの1ファイルに作り直した。軸は「ループが入れる変更は、修正前に失敗し、
修正後に通る再現を持つものだけ」。無くしたものと、その根拠:

| 無くしたもの | 根拠 |
|---|---|
| スクリプト(前提と混入の検査、状態コメント) | 混入も head の変更も、119回で1回も起きていない。回数と経緯は PR 本文に置く |
| 俯瞰の役 | 指摘の真偽は、修正役の再現で確かまる。通しの実行では、俯瞰と修正で同じ再現を2度作っていた |
| 差分のレビュー役 | 修正を push したら、必ずもう1回レビューする |
| 再現なしの修正、実行では確かめていない修正、revert | 再現を持たない変更を入れない |
| レビュー役をサブエージェントに呼ばせる形、役ごとの出力先 | 全て Skill で直接呼ぶ |

作り直した版を、別のセッション(`claude -p`、Opus 5.5。利用者と話せない形)で2回試した。記録は残していない(数字だけ)。

| 題材 | 結果 | 所要 | 費用 |
|---|---|---|---|
| sk-12(通しの実行と同じ SHA) | 反復1のレビューのあと、既にある記録で、本物の拒否イベントに `source` が無いことを確かめ、直さずに判断を仰いで返った | 約12分(レビュー 8分41秒) | $2.57 |
| sk-13 | 反復1で対象2件。設計の代案が出たので判断を仰いで返り、「個別に直す」と答えて再開。修正役が2件とも再現して直し(7分38秒)、親が修正前 1、修正後 0 を見て push。反復2で対象が無くなり終了 | 約23分 | $6.51 |

- sk-12 は、通しの実行では「`source` が無い」と分かるまで約38分かかり、4コミットを revert した。作り直した版は、約10分で、直す前に分かった
- sk-13 の正解のうち、影響が中の挙動の不具合(S13-3)は直った。S13-4(SKILL.md の例が流せない)は doc に分類されて外れた。そのあと、流せば合否が出る指摘は defect にする、と書き足した
- 3つのレビュー役を Skill で直接呼ぶ形は動いた。`-p` では、`code-review` は2つともその場で返った(同時に動く)。`security-review` は親の文脈で進む
- sk-13 では、設計の代案が1つ出ただけで止まった。そのあと、止まる条件を「対象を直しても PR が成り立たないとき」に狭めた(狭めた形は、まだ試していない)

サブエージェントに任せる形(窓口のセッションが、ループを回す役を起動する)も、sk-12 で1回試した。動いたが、手順には入れなかった(利用者のセッションの文脈の節約は、別に考える)。試したときの記録:(約12分、$3.63)。サブエージェントの中から、`code-review` は2つともフォークで動き、`security-review` のサブタスクと修正役(入れ子の2段目)も起動できた。狭めた止まる条件でも、前提の誤りで止まり、質問は窓口まで戻った。関わりのない対象1件は修正役に渡り、「起きなかった」で返った。報告が英語で返り、窓口が訳した(依頼文に、利用者の言語で書くよう足した)。質問のあとに、同じサブエージェントへ続きを渡す流れは、試していない。

まだ確かめていないこと:

- `security-review` を直接呼んだとき、2反復目の親が、以前に採らなかった指摘を誤検知として落とさないか(3回とも候補が0件で、場面が起きなかった)。親が、サブタスクへの依頼を縮める逸脱は、3回とも出た
- 対話のセッションで回したときの、レビュー役の返り方と所要
- 3反復を終えた時点の、親の文脈の大きさ
