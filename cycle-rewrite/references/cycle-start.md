# cycle-start の詳細手順

サイクル N の開始。仕様を詰め、実装セッションに引き継ぐ。

1. N を導出し(SKILL.md「現在地の把握」)、マイルストーン `cycle-N` が無ければ作成する
2. **読むのは `docs/`(PRODUCT.md・adr/・昇格モジュールのインターフェース契約)・`CONTEXT.md`・`CLAUDE.md` のみ。** 旧サイクルの issue やコードは読まない。issue は時系列の生ログで矛盾・失効が混在するため、インプットは蒸留済み docs に限る。旧コードの参照がどうしても必要なら `git show cycle-N:src/...` を使う
3. ガード: `src/` が存在しマイルストーン `cycle-N` に open issue が残っているなら、サイクル進行中。cycle-start ではなく実装の続行か cycle-end かをユーザーに確認する
4. /grill-with-docs で仕様を詰める。第二システム症候群(Brooks)に注意 — 作り直しは過剰設計に走りがちなので、grilling では最新要件のみに絞る。grilling は、このサイクルの**業務的な完了条件** — 「何がどう動けばこのサイクルは完成か」をドメイン語の受け入れシナリオ数件で表したもの(実装の中身には踏み込まない) — を人間と合意してから終える。この問いは終了間際の点検項目ではなく、**grilling の最初の質問群に含めて**人間に直接ぶつける(例: 「このサイクルの完成を『招待リンクから登録すると自分のチームの一覧が表示される』のような動作の形で数件挙げてください」)— 完了条件が先に立つと以降の質問の要否と深さがそこから定まり、後回しにすると設計パラメータの質問に埋もれて、合意されないまま grilling が終わる
5. grilling 完了後:
   - **サイクル1**: 会話から `docs/PRODUCT.md` を合成する(to-prd は issue トラッカーに発行する設計でファイルを作らないため、この合成だけは本スキルの担当)。手順は [product-md-synthesis.md](product-md-synthesis.md)
   - **サイクル2以降**: grilling で判明した変更を `docs/PRODUCT.md` に反映する(同ファイルの更新手順参照)。前サイクルで PRODUCT.md が未合成のままなら、ここで初回合成する
   - どちらの場合も、grilling(手順4)で合意した業務的な完了条件を受け入れシナリオとして Testing Decisions に反映する。ここが完了条件の**正本**になり、実装セッション起動用の指示文(手順7)はここから転記する
6. **全ファイル棚卸し(grilling の波及反映)**: grilling で方向・仕様が変わったら、**リポジトリに残っている全ファイル**を「保持 / 書き直し / 削除」の三分類で棚卸しする(cycle-end で使い捨て層と付随成果物は削除済みの前提 — その残り全部が対象)。対象は永続層 docs(運用ポリシー、技術メモ、UI メモ、モデル図)、CLAUDE.md、CONTEXT.md、プロジェクトスキル、README、設定類(パッケージ定義、フック、CI)、データ層の資産まで。判断基準は「新方向でも真か・使われるか」。迷うものは人間に確認し、削除は git タグから復元できる旨を添える。旧方向の記述を残すと、docs だけをインプットに始まる次の実装セッションがそのまま汚染される。この段では手順2の読み取り制限を解除してよい(棚卸しは全ファイルの点検が前提。読まないのは旧 issue と旧コードのまま)
7. **実装は grilling と別セッションで始める**。仕様詰め(1〜6)を終えたら、**実装セッション起動用の指示文**(使い捨て。リポジトリにはコミットしない)をユーザーに渡してセッションを区切る。指示文は「現在地 / 正の docs のありか / capture 規律の適用 / **完了条件**」だけに絞り、仕様の中身や作業の細部を書き込まない — 細部は実装セッションが docs を読んで判断し、迷いは capture で捕捉すればよい(指示文に内容を重複させると docs との同期ずれの種になる)。実装セッションのインプットは蒸留済み docs のみとし、grilling の会話の記憶に依存させない — docs に書き漏れがあれば実装が詰まって表面化し、それ自体が capture 対象の学びになる(会話の記憶で補完できてしまうと docs の欠落に気づけない)
   - **実装ルート(チェーン / prototype / 直接実装)は cycle-start では決めない。** ルートは観測可能な挙動を変えないプロセス判断であり、タスク分割と同様に実装セッションに委ねる(SKILL.md「実装ルートの選択」参照)。人間がルートに制約を付けたい場合だけ、grilling で合意して制約として指示文に載せる。cycle-start が決めるのは方法ではなく**サイクルの目的**(受け入れシナリオを満たすものを作るのか、設計上の問いに答えるのか)であり、それは完了条件の形として指示文に現れる
   - **完了条件は、実装セッションが達成まで自律で進むための停止条件。** 中核は grilling(手順4)で合意した**業務的な完了条件**で、このサイクル分の受け入れシナリオを Testing Decisions から指示文に**そのまま転記**する(ドメイン語の観測可能な挙動のみ。実装の中身には踏み込まない)。この転記は「内容を書き込まない」原則の意図的な例外 — capture の規律で実装中は docs を直さない(挙動の決定は issue に留まる)ため、指示文と正本が別々に更新されて食い違う経路はなく、指示文はサイクルと共に捨てられる。設計上の問いに答えるのが目的のサイクルでは、受け入れシナリオの代わりに「問い X に答えが出て capture 済み」を完了条件とする。「マイルストーン `cycle-N` の open issue が 0」等の機械的条件は補助ゲートとして併記してよいが、完了の定義にはしない — タスク分割も実装ルートもレビューなしの AI 一任であり、issue 全消化は欲しい状態の達成を保証しない。完了条件が無いと、実装セッションは区切りごとに人間の指示待ちで止まるか、逆に根拠なく完成を宣言する。達成前に人間へ停止してよいのは3層判断の層2・層3のエスカレーションだけで、それも解消したら完了条件まで自律継続する
8. タスク分割は AI に一任(分割レビューなし)。実装・確認中は capture と実装セッションの規律(いずれも SKILL.md)を常時適用する
