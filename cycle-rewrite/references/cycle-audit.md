# cycle-audit の詳細手順(蒸留監査)

実装完了後に人間が手動で呼び出す任意の点検。前サイクルの実装と現況を突き合わせ、cycle-end → cycle-start の蒸留パイプライン(capture → 棚卸し → grilling → 実装)で失われた仕様・機能を検出し、issue 起票で回収する。このワークフローの中心の賭け「学びと仕様はすべて docs に蒸留され、コードは捨てても失われない」を、サイクルを一周した実物どうしの比較で検証する唯一の機会がここにある。

出口は issue 受信箱に一本化する。docs はこのモードでは編集しない — 直接編集すると issue → 棚卸し → docs の単一蒸留経路の外に第二の経路ができ、反映漏れと矛盾の温床になる。起票済み issue は cycle-end の棚卸し台帳に自然に乗り、そこで docs へ蒸留される。

## 0. ガードと前提

- タグ `cycle-(N-1)` が存在すること。サイクル1には比較対象が無く、このモードは対象外
- 現サイクルの実装がほぼ完了していること(完了条件を満たした後、cycle-end の前が定位置)。実装途中に走らせると「まだ作っていない」と「実装漏れ」を区別できず、差分が偽陽性だらけになる
- 任意実行であり、cycle-end の前提条件ではない。必須化は「儀式コストはサイクル境界に集中させ、サイクル内は最小化する」に反する

## 1. 比較の単位 — 観測可能な挙動

コード同士の diff は使わない。ゼロから書き直す方式ではほぼ全行が差分になり、「一定規模以上」の閾値をコード上で運用できない。比較の単位は3層判断の層2と同じ**外から見える挙動**とし、ドメイン語で目録化する:

- 提供している操作(コマンド、画面、API エンドポイント)
- 各操作の観測可能な挙動(入力に対する出力・状態変化)
- 扱っているエッジケース(重複時の挙動、空入力、境界値の扱い)

内部設計の違い(モジュール構成、ライブラリ選定、アルゴリズム)は監査対象外。層1 は毎サイクル変わるのが正常であり、差分に数えると目録がノイズで埋まる。

## 2. 挙動目録の抽出(サブエージェント隔離)

前サイクルの実装コードを本体セッションで読まない。規律「旧サイクルのコードを作業ツリーに置かない(AI が読んで勝手に流用する)」は監査でも生きている — 監査後に同じセッションで修正作業が続くことがあるため、抽出はサブエージェントに隔離する:

1. サブエージェントに `git show cycle-(N-1):<使い捨て層パス>/...`(または作業ツリー外への `git worktree add`)で前サイクル実装を読ませ、手順1の単位の挙動目録**だけ**をドメイン語で返させる。コード片・実装方式・内部構成は返させない
2. 現サイクルの実装からも同じ形式の挙動目録を作る(作業ツリーの現行コードなので本体で読んでよい)

worktree を作った場合は抽出後に必ず削除する。

## 3. 突合と証跡照合(4分類)

2つの目録を突き合わせ、前サイクルにあって現サイクルに無い挙動・変わった挙動を列挙する。各差分は**証跡ベース**で4分類する — AI の推測で「意図的だろう」と判定しない。証跡は安価な順に取得する:

- `git diff cycle-(N-1) HEAD -- docs/ CONTEXT.md` — PRODUCT.md の削除・Out of Scope 追記、ADR のステータス遷移が読める
- 前サイクルの cycle-end で遷移した superseded / rejected ADR の本文
- 前サイクルマイルストーンの `spec-change` issue(closed)。これは判決の証跡照合であって仕様のインプットではない — cycle-start の「旧 issue を読まない」原則は grilling への生ログ混入を防ぐ規則であり、差分に対応する issue を特定する検索には適用しない。読む範囲はその特定に限る

| 分類 | 判定条件 | 処理 |
| --- | --- | --- |
| A. 意図した変更・削除 | 証跡あり(superseded / rejected ADR、spec-change issue、PRODUCT.md の Out of Scope 等) | 監査通過。報告のみ。復活を提案しない — 意図的なスコープ削減は健全な蒸留 |
| B. 意図した先送り | 現 docs に仕様はあるが、今サイクルの完了条件(Testing Decisions の該当シナリオ)の範囲外 | 報告のみ。次サイクル以降の cycle-start が docs から拾う |
| C. 実装漏れ | 現 docs に仕様があり、完了条件の範囲内なのに未実装・挙動が違う | 完了条件の未達 — 蒸留は成功しており、失敗したのは実装。手順4で人間に提示 |
| D. 蒸留漏れ | 前サイクルには挙動があり、現 docs にもどの証跡にも痕跡が無い | 監査の本命 — capture・棚卸し・grilling のどこかで漏れた。手順4で起票 |

C と D の区別が対処を分ける: C は今サイクル内で完結する問題、D は docs の欠落であり次の grilling に送る問題。二値(意図した/しない)に潰すと、この違いが消える。

## 4. 出口 — 起票と人間への確認

全差分の分類台帳(差分 → A/B/C/D、各行に証跡の出典)を1つの応答で提示する。台帳は承認不要の分析。そのうえで:

- **D(蒸留漏れ)は capture と同じ規律で処理する**: まず `spec-change` issue に起票する(マイルストーン `cycle-N`。「正しい扱いは未決」として、次サイクルで復活させる / 廃止を確定する、のドメイン語二択を併記)。**起票してから**人間に確認し、回答が得られたら issue に反映する。回答待ちで起票を保留しない — 起票は受信箱への記録であって要承認の操作ではない
- **C(実装漏れ)は完了条件に照らして人間に提示する**: 「今サイクルで直す / 先送りを確定する」の二択(層2)。先送りなら spec-change issue として捕捉する
- A・B は台帳での報告のみで閉じる。「全部戻しましょうか」と聞かない

差分ゼロもそのまま報告する — 蒸留パイプラインが機能している証拠であり、監査の空振りではない。
