# cycle-end 儀式の詳細手順

順序が重要である理由: 棚卸しの前に issue を close すると学びのルーティング漏れが起きる。タグを打つ前に `src/` を消すと復元手段が消える。必ずこの順で進める。

## 0. 事前確認

- 現在のサイクル番号 N を確認する(`git tag -l 'cycle-*'` の最大番号 + 1)
- 作業ツリーが clean か(`git status`)。未コミットの変更があれば先に main へ取り込む
- main が起動するか(不変条件の最終確認)

## 1. issue 棚卸し(4宛先ルーティング)

**棚卸しの前に、ふりかえりを捕捉する。** サイクルを畳む動機とふりかえり(何がうまくいかず、どの決定が覆ったか)を人間から聞き取り、`spec-change` issue として起票してから全件取得に進む(会話や起動時の引数で既に提示されていれば改めて聞かず、そのまま起票する)。方向転換の判断は畳むと決めた瞬間に言語化されることが多く、issue 受信箱にまだ無いことがある — この捕捉が無いと、§2 の ADR 遷移(覆す issue との対応づけ)と §3 の CONTEXT 剪定(失効判定)が駆動できない。聞き取るのは判決(何が死んだか・何を排除するか)まででよく、次サイクルの新仕様の中身は cycle-start の grilling に送る。

`gh issue list --milestone "cycle-N" --state open --limit 200` で open issue を全件取得し、**1件ずつ・対話的に**レビューして学びを蒸留する。専用の学びファイル(LEARNINGS.md 等)は作らない — 蒸留先は既存の永続ドキュメントのみ。

進め方は2段階に分ける。**宛先の分析は全件一括で先に、反映の承認は1件ずつ。** 1件ずつに縛るべきなのは人間の認知負荷がかかる承認であって、AI 内部の宛先割当ではない。台帳は人間の承認を要しない AI の分析作業なので、**儀式を開始する最初の応答に必ず台帳まで含める** — 台帳より先に他の承認質問(モジュール昇格の可否等)を単独で挟むと、そこで停止して棚卸し本体が始まらない。承認事項はすべて台帳提示後の承認ループと後続手順(§5 の昇格承認、§8 の削除承認)に乗せる:

1. **台帳作成(一括)**: open issue 全件を下表の4宛先または「close(蒸留不要)」に割り当てた棚卸し台帳を先に作る。open issue の件数と割当済み件数が一致することを必ず照合する — 1件でも未割当が残っていれば棚卸しは未完。1つの issue が複数宛先を持つことがある(例: 機能廃止の spec-change → PRODUCT.md の Out of Scope + CONTEXT.md の用語剪定)— 台帳の宛先欄は複数可。「既存 docs と矛盾しないから対象外」という除外は誤り(close の基準は「コードを捨てても偽」であって「矛盾がない」ではない)。**台帳の段階ではファイルを一切編集しない** — 一括でよいのは宛先の分析だけで、反映(ファイル編集・コミット・タグ)まで一括で進めてはならない。反映は次の承認ループで各 issue の承認を得た後にのみ行う
2. **儀式全体の段取り提示**: 台帳と併せて、残りの手順(ADR 遷移 → CONTEXT 剪定 → 昇格 → close → `git tag cycle-N` → 承認を経た src/ 削除。昇格したモジュールとそのテストは削除対象から除外)をロードマップとして先に提示する。承認ループは複数ターンに渡るため、タグが削除に先行する安全順序と最終到達点を、人間がループに入る前に見えている必要がある — 途中でセッションが切れても、人間が儀式のどこにいるか分かる
3. **承認ループ(1件ずつ)**: 台帳に沿って issue を1件提示し(タイトル・要点・ラベル)、推奨宛先と**具体的な反映案**(どのファイルのどのセクションに何を書くか)を添えて、この1件だけの確認を取る。合意したらその場で反映(ファイル編集)してから次へ。保留した issue は最後にまとめて再訪する。全件一括の包括承認は求めない — 認知負荷を超え、確認ゲートが形骸化する。台帳を提示するメッセージは必ず**1件目の issue の反映案とその1件だけの確認**で締めること — 「この方針でよければ進めます」と台帳全体への同意を求めた時点で包括承認になっている
4. **締め**: 全件終了後、最終のルーティング結果一覧表(issue → 宛先)を提示する

| # | 学びの種別 | 宛先 | 処理 |
| --- | --- | --- | --- |
| 1 | 仕様レベル: 判明した要件、やらないと決めた機能 | `docs/PRODUCT.md` | 該当セクションを更新。「やらないことリスト」の正は Out of Scope セクション |
| 2 | 設計判断レベル: 採用しなかった案とその理由 | `docs/adr/` | 新規 ADR 起票、または既存 ADR のステータス遷移(→ §2) |
| 3 | 実装・環境レベルの個別ハマり: コードを捨てても再発しうるもの(ライブラリの罠等) | `.claude/skills/` | 対象単位で集約(→ 下記) |
| 4 | プロセスレベル: 進め方のルール(例:「並列度3以上でレビュー破綻」) | `CLAUDE.md` / `AGENTS.md` | 該当セクションに追記 |

どの宛先にも当てはまらない issue(単なる作業ログ、次サイクルには関係しない事象)はそのまま close してよい。判断基準: **「コードを全部捨てた後も、この知見は真か?」** — 偽なら蒸留不要。

**宛先2(ADR)と宛先3(プロジェクトスキル)の混同に注意。** どちらもライブラリの学びとして現れるが、性質が違う:

- **採用可否に関わる学び**(例: 「Fuse.js は5000件超で破綻 → 不採用にすべき」)は設計判断 — 宛先は ADR。既存 ADR がその技術を採用していれば、スキル化ではなく**その ADR のステータス遷移**(→ §2)+必要なら代替案の新 ADR が正しい処理。issue に出てくる技術名・ライブラリ名は `docs/adr/` を必ず突き合わせ、対応する ADR の有無を確認してから宛先を決める
- **使い方の罠**(例: 「dexie はトランザクション内 await で即コミットされる」)は、採用は覆さず次サイクルも使う前提の注意書き — 宛先はプロジェクトスキル

採用可否の学びをスキル化すると、覆った ADR が Accepted のまま残り、次サイクルの to-prd がそれを尊重し続けてしまう。

**受信箱は issue だけとは限らない。** パイプラインの実行ログなど issue 外の受信箱ファイルがあれば、その未蒸留の気づきも台帳に乗せる(そのファイル自体は使い捨て層の付随成果物として §8 で削除される — 削除前が最後の回収機会)。また「方針だけ決めて close した issue」はコメントに決定が眠ったまま棚卸し(open のみ)をすり抜ける — close 時に docs 反映まで済んでいない issue を見つけたら、その場で台帳に加える。

**既存 docs と矛盾しない issue を「対象外」にしないこと。** 仕様変更や ADR を覆す知見は既存文書との矛盾として立ち上がるため拾いやすいが、矛盾しない加算的知見(ライブラリのハマり → プロジェクトスキル、プロセスの学び → CLAUDE.md)こそ**新しい住所を必要とする**。棚卸しの主目的は後者の回収にある — 落とすと次サイクルで同じ穴に落ちる。

### 宛先3(プロジェクトスキル)の集約ルール

- 事象単位(1ハマり=1スキル)ではなく**対象単位**(ライブラリ/ツール/サブシステム。例: `working-with-mediapipe`)で集約する。スキルのメタデータ(name + description)は常時コンテキストに載るため、スキル数に比例して常駐コストが増える。対象単位なら「その対象を触る瞬間に発火する」という発火条件と集約単位が一致する
- `.claude/skills/` に同一対象の既存スキルがあれば追記、なければ新規作成。新規作成は **`.claude/skills/<対象名>/SKILL.md`** の形式で置き、frontmatter に `name` と `description`(どんな作業のときに読むべきかを含む)を書く。平置きの `.md` ファイルはスキルとして発見・ロードされず、受動知識として機能しない
- 破ると環境が壊れる級の致命的な罠は、スキルではなく CLAUDE.md に書く(格上げ)。スキルの発火は確率的(undertrigger 傾向)で、確実に毎セッション読まれるのは CLAUDE.md のみ

## 2. ADR ステータス遷移

覆った ADR は**削除せず**ステータスを遷移させる(Nygard 式)。削除すると「なぜ捨てたか」が消え、次サイクルで同じ案を再採用するリスクが生じる。superseded は to-prd の「ADR を尊重せよ」に対する「もう尊重不要」の標準的な信号なので、チェーンとバッティングしない。

遷移の前に、対象 ADR の**本文を読み**、どの issue がそれを覆すのかを対応づけてから遷移する。Status 行やタイトルだけで「覆った」と判断しない。対応づく issue の無い ADR には触らない。

- 新しい判断が旧 ADR を置き換えた → 旧 ADR に `Status: Superseded by ADR-XXXX` を記し、新 ADR を起票する
- 検討の結果、不採用と確定した案 → `Status: Rejected` + 理由
- 覆った ADR に制約や注記を追記して `Status: Accepted` のまま残すのは遷移ではない。覆ったと対応づいたら Status 行を必ず書き換える(to-prd は Status を見て尊重の要否を判断するため、注記だけでは次サイクルでも尊重され続けてしまう)

## 3. CONTEXT.md の剪定

失効した用語を削除・書き換える。CONTEXT.md は現在の共有言語を表す**生きた用語集**であり、自由に剪定してよい(追記型の ADR とは扱いが異なる)。

剪定の主な駆動源は §1 の spec-change — 仕様から消えた概念(機能の廃止・一本化)は用語集からも死ぬ。PRODUCT.md 行きにした spec-change ごとに、その概念の用語が CONTEXT.md に残っていないかを照合する。残すと、次サイクルの grilling が死んだ用語を共有言語として再前提化する。

## 4. テストシナリオの更新

このサイクルで確立・変化した受け入れ条件(自然言語)を `docs/PRODUCT.md` の Testing Decisions セクションに反映する。テストコード自体は持ち越さない — 次サイクルで手動確認が追いつかなくなったら、このシナリオから再生成する。

## 5. モジュール昇格(任意・要承認)

使い捨て層の中に「次サイクルでもそのまま使いたい」モジュールがあれば、削除の例外ではなく**永続層への昇格**として扱う。該当がなければこの節はスキップする。

判断基準は完成度ではなく**仕様の収束**。昇格の要望を受けたら、以下を **AI が実際に点検して**(そのモジュールに触れる spec-change issue の検索、使い捨て層への import の確認)、点検結果を根拠として人間に提示し、明示的な承認を得る(AI は独断で昇格を実行しない)。人間の「検証済みでよく動いている」という申告はきっかけであって根拠にならない — 完成度は基準ではないため、申告をそのまま受けて昇格に応じない:

- そのモジュールに触れる `spec-change` issue が直近サイクルで出ていない
- grilling がその領域に新発見・新用語を出していない
- インターフェースが切り出せて、使い捨て層への依存が無い
- 書き直しの限界費用が例外的に高い(実世界への実行で経験的に検証されたコード — スクレイパー、外部 API アダプタ等)。**単に「よく書けている」は昇格理由にならない** — 残したいのが知見だけなら、プロジェクトスキルに蒸留して次サイクルで書き直す方が方式に沿う

承認後の手順:

1. モジュールを昇格置き場(既定 `lib/`。CLAUDE.md の層の定義が正)へ移動する。依存方向は使い捨て層 → 昇格モジュールの一方向のみ — 逆依存が残っていると §8 の削除で main が壊れる
2. テストを Testing Decisions のシナリオから整備し、**持ち越す**。テスト持ち越し禁止は使い捨て層のルールであり、昇格モジュールは以後厳格維持 — テストが品質ゲートになる
3. インターフェース契約を永続 docs に書く(例: `docs/modules/<name>.md`)。次サイクルの実装セッションはこの契約経由で使い、中身のコードは読まない(外部パッケージと同格)
4. 昇格を ADR に記録する — 「サイクルを跨いでも覆らない判断」の定義そのもの。後の grilling で仕様が覆ったら、ADR をステータス遷移させてモジュールを**降格**する(使い捨て層に戻すか削除)

この4手順は分割不可の1操作として扱い、昇格を提案・計画する時点で4つすべてを明示する。どれかを省くと、契約なしで中身のコードを読まれる(3の欠落)か、覆ったときの降格経路が無くなる(4の欠落)。移動だけ済ませた「lib/ 置きっぱなし」は昇格ではなく、削除の例外扱いが名前を変えただけになる。

昇格が数サイクル続けて発生するなら、リセット対象が縮小している = プロジェクト全体の収束シグナル。個別要望として処理せず、transition-check を回す契機として人間に伝える。

## 6. issue・マイルストーンの close

棚卸し(§1)が終わってから実行する:

```bash
# マイルストーンの open issue を全て close
gh issue list --milestone "cycle-N" --state open --limit 200 --json number -q '.[].number' \
  | xargs -I{} gh issue close {} -c "cycle-N 棚卸し済み"

# マイルストーン自体を close
MS_NUM=$(gh api "repos/{owner}/{repo}/milestones" --jq '.[] | select(.title=="cycle-N") | .number')
gh api -X PATCH "repos/{owner}/{repo}/milestones/$MS_NUM" -f state=closed
```

## 7. docs コミットとタグ

1. §1〜5 の docs・昇格の変更をコミットする(例: `docs: cycle N 棚卸し`)
2. `git tag cycle-N` を打つ。リモートがあれば `git push && git push --tags`

## 8. src/ の削除(要・人間の承認)

破壊的操作。**実行前に必ず以下を提示して、人間の明示的な承認を得る**:

1. タグの存在確認を見せる: `git tag -l 'cycle-N'`(タグがあれば `git show cycle-N:src/...` でいつでも全復元できる=実質可逆であることを伝える)
2. 削除対象の一覧: 使い捨て層(CLAUDE.md の層の定義が正。既定は `src/` 全体)、テストコード(`tests/`、`*.test.*`、`e2e/` 等)、テスト用フィクスチャ。昇格済みモジュールのテストは削除しない
3. **使い捨て層の付随成果物も削除対象として点検する**: 削除するコードの運用手順ドキュメント(起動手順、cron/launchd 設定手順)、コードのコマンドを参照するプロジェクトスキル、パイプラインの実行ログ。これらは `docs/` や `.claude/skills/` に置かれていても実質は使い捨て層で、残すと次サイクルが存在しないコマンドを前提に動く。ログの未蒸留の気づきは §1 で回収済みであること
4. 残すもの: プロジェクトルートの設定類(フォーマッター、リンター、tsconfig、CI 設定)、`.claude/`、`docs/`、`CONTEXT.md`、`CLAUDE.md`、昇格済みモジュール(`lib/`)とそのテスト
5. 判断に迷うファイル(package.json の依存など次サイクルの足場になり得るもの)は個別に確認する

承認を得てから削除し、コミットする(例: `chore: cycle N end — reset disposable layer`)。

**削除後、コミットとフックが通ることを確認する。** パッケージ定義(pyproject / package.json)やコミットフックが使い捨て層を参照していると、削除の瞬間に「main は常に起動する」だけでなく **git コミット自体が壊れる**(例: pre-commit が `uv run` 経由でパッケージをビルドし、バージョン源の `src/<pkg>/__init__.py` が無くて全コミット失敗)。壊れたら、最小の stub(バージョン定数だけのパッケージと import 確認テスト)を次サイクルの種として置き、不変条件を回復してから次へ進む。

## 9. 次へ

transition-check の収束シグナルに軽く触れつつ、次サイクル(cycle-start)に進むか、収束していれば通常開発ワークフローへの移行を提案する。

cycle-start は別セッションで開始する前提とし、その起動用の指示文(使い捨て。コミットしない)をユーザーに渡して儀式を終える。
指示文は「儀式完了の現在地(タグ `cycle-N` 済み、マイルストーン close 済み)と、次の一手 = 新セッションで /cycle-rewrite cycle-start」だけに絞る。
学びと仕様はすべて docs に蒸留済みであり、指示文に内容を重複させると docs との同期ずれの種になる。
