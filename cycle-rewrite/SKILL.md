# cycle-rewrite — サイクル型リライト開発ワークフロー

## 狙い

AI 開発ではコード生成速度が人間のレビュー・理解速度を上回り、人間の頭の中の理論とコードが乖離していく(Naur "Programming as Theory Building")。この乖離=認知負荷は、設計見直し・機能追加・並列実行・時間経過で増え続ける。本ワークフローは認知負荷の発生を防ぐのではなく、発生を前提に定期的にリセットする: サイクルごとにコードをゼロから書き直し(Brooks「捨てるつもりで作れ」— AI によりリライトの限界費用が激減したため再び成立する)、永続資産はコードではなく仕様と学びに置く。

中心原則: **永続層と使い捨て層をリポジトリ内で物理的に分離する。**

| 層 | 中身 | 扱い |
| --- | --- | --- |
| 永続層 | `docs/PRODUCT.md`、`docs/adr/`、`CONTEXT.md`、`.claude/skills/`、`CLAUDE.md` / `AGENTS.md` | 厳格に維持。サイクルを跨いで積み上げる |
| 使い捨て層 | `src/` とテストコード | 品質は「動けばOK」。サイクル末に全削除 |

**コードは雑に、ドキュメントは厳格に。** 捨てていいのはコードだけ — 学びを捨てるとサイクルが収束しない。

前提: Matt Pocock のビルドチェーン(/grill-with-docs → /to-prd → /to-issues → /implement、補助として /prototype)と GitHub(issue・マイルストーン・gh CLI)。本スキルはチェーンを再実装せず、起動タイミングの誘導と前提整備に徹する。チェーンは常に全段を踏む義務ではない — 固定なのは「grilling で仕様を詰め PRODUCT.md に反映する」までで、実装ルートは実装セッションがサイクルの性質で選ぶ([実装ルートの選択](#実装ルートの選択)参照)。

## 現在地の把握

どのモードでも、まず状態を確認する。専用の状態ファイルは持たない — git タグとマイルストーンが正であり、儀式の成果物そのものが状態になるため同期ずれが構造的に起きない:

- 現在のサイクル番号 N = `git tag -l 'cycle-*'` の最大番号 + 1(タグが無ければ N = 1)
- サイクル進行中か = マイルストーン `cycle-N` が open か、`src/` が存在するか

スコープガード: CLAUDE.md に cycle-rewrite 規約ブロックが無く、ユーザーが導入を求めてもいないプロジェクトでは、このワークフローを勝手に適用しない。方式を1〜2文で紹介し、導入の意思を確認してから init に進む。

## モード選択

| ユーザーの状況 | モード |
| --- | --- |
| プロジェクトの新規セットアップ | [init](#init) |
| サイクルを始める・仕様を詰め直す | [cycle-start](#cycle-start) |
| 実装・動作確認中に学び/バグ/仕様変更/ハマりが出た | [capture](#capture) |
| サイクルを畳む・リセットする・作り直す | [cycle-end](#cycle-end) |
| 次サイクルに行くべきか、通常開発に移るべきかの相談 | [transition-check](#transition-check) |

「リセットしたい」「作り直したい」は cycle-end(儀式を経てから次へ)。迷ったらユーザーに確認する。ただし capture は迷わない — 学びが出た瞬間が起票の瞬間。

## init

新規プロジェクト(グリーンフィールド)のセットアップ。

1. 前提確認: git リポジトリであること、`gh auth status` が通ること。Pocock チェーンの設定(`docs/agents/issue-tracker.md` 等)が無ければ、先に /setup-matt-pocock-skills の実行を促す(issue トラッカーは GitHub を選ぶ)。既存の README や構想メモがあれば、サイクル1の grilling の入力候補としてユーザーに提示し、採用・差し替え・破棄を確認する — 勝手に前提化も無視もしない
2. **`docs/adr/`・`CONTEXT.md`・`docs/PRODUCT.md` は init では作らない。** 永続層の器を空のまま先回りで用意しない — `docs/adr/` と `CONTEXT.md` は domain-modeling(/grill-with-docs 経由)が最初の ADR・用語が生まれた時点で中身と共に遅延作成し、PRODUCT.md はサイクル1の grilling の結果から合成する。空テンプレートを先に置くと grilling 前に推測で埋められ、仕様が汚染される。init が作る足場は次の 3〜5(CLAUDE.md 追記・ラベル・マイルストーン)だけ
3. CLAUDE.md にワークフロー規約ブロック(層の定義・3層自律判断・ブランチ/マージ方針・ADR 解釈ルール・学びの捕捉)を追記する。テンプレートは [references/setup-templates.md](references/setup-templates.md)
4. ラベルを作成する: `learning` / `spec-change` / `decision-log`(`bug` は GitHub 既定)。ラベル = 種別分類、マイルストーン = サイクル区分。この対応を崩さない
5. マイルストーン `cycle-1` を作成する
6. 作成・変更したファイルをコミットする。コミットはローカルに留める — このワークフローは PR を使わずローカルマージで進むため、push は init の手順に含めない(タイミングは人間の判断)
7. cycle-start に進むことを提案する

## cycle-start

サイクル N の開始。仕様を詰め、チェーンに乗せる。

1. N を導出し、マイルストーン `cycle-N` が無ければ作成する
2. **読むのは `docs/PRODUCT.md`・`CONTEXT.md`・`docs/adr/`・`CLAUDE.md` のみ。** 旧サイクルの issue やコードは読まない。issue は時系列の生ログで矛盾・失効が混在するため、インプットは蒸留済み docs に限る。旧コードの参照がどうしても必要なら `git show cycle-N:src/...` を使う
3. ガード: `src/` が存在しマイルストーン `cycle-N` に open issue が残っているなら、サイクル進行中。cycle-start ではなく実装の続行か cycle-end かをユーザーに確認する
4. /grill-with-docs で仕様を詰める。第二システム症候群(Brooks)に注意 — 作り直しは過剰設計に走りがちなので、grilling では最新要件のみに絞る。grilling は、このサイクルの**業務的な完了条件** — 「何がどう動けばこのサイクルは完成か」をドメイン語の受け入れシナリオ数件で表したもの(実装の中身には踏み込まない) — を人間と合意してから終える
5. grilling 完了後:
   - **サイクル1**: 会話から `docs/PRODUCT.md` を合成する(to-prd は issue トラッカーに発行する設計でファイルを作らないため、この合成だけは本スキルの担当)。手順は [references/product-md-synthesis.md](references/product-md-synthesis.md)
   - **サイクル2以降**: grilling で判明した変更を `docs/PRODUCT.md` に反映する(同ファイルの更新手順参照)。前サイクルで PRODUCT.md が未合成のままなら、ここで初回合成する
   - どちらの場合も、手順4で合意した業務的な完了条件を受け入れシナリオとして Testing Decisions に反映する。ここが完了条件の**正本**になり、手順8の指示文はここから転記する
6. **全ファイル棚卸し(grilling の波及反映)**: grilling で方向・仕様が変わったら、**リポジトリに残っている全ファイル**を「保持 / 書き直し / 削除」の三分類で棚卸しする(cycle-end で使い捨て層と付随成果物は削除済みの前提 — その残り全部が対象)。対象は永続層 docs(運用ポリシー、技術メモ、UI メモ、モデル図)、CLAUDE.md、CONTEXT.md、プロジェクトスキル、README、設定類(パッケージ定義、フック、CI)、データ層の資産まで。判断基準は「新方向でも真か・使われるか」。迷うものは人間に確認し、削除は git タグから復元できる旨を添える。旧方向の記述を残すと、docs だけをインプットに始まる次の実装セッションがそのまま汚染される。この段では手順2の読み取り制限を解除してよい(棚卸しは全ファイルの点検が前提。読まないのは旧 issue と旧コードのまま)
7. **実装は grilling と別セッションで始める**。仕様詰め(1〜6)を終えたら、**実装セッション起動用の指示文**(使い捨て。リポジトリにはコミットしない)をユーザーに渡してセッションを区切る。指示文は「現在地 / 正の docs のありか / capture 規律の適用 / **完了条件**」だけに絞り、仕様の中身や作業の細部を書き込まない — 細部は実装セッションが docs を読んで判断し、迷いは capture で捕捉すればよい(指示文に内容を重複させると docs との同期ずれの種になる)。実装セッションのインプットは蒸留済み docs のみとし、grilling の会話の記憶に依存させない — docs に書き漏れがあれば実装が詰まって表面化し、それ自体が capture 対象の学びになる(会話の記憶で補完できてしまうと docs の欠落に気づけない)
   - **実装ルート(チェーン / prototype / 直接実装)は cycle-start では決めない。** ルートは観測可能な挙動を変えないプロセス判断であり、タスク分割と同様に実装セッションに委ねる([実装ルートの選択](#実装ルートの選択)参照)。人間がルートに制約を付けたい場合だけ、grilling で合意して制約として指示文に載せる。cycle-start が決めるのは方法ではなく**サイクルの目的**(受け入れシナリオを満たすものを作るのか、設計上の問いに答えるのか)であり、それは完了条件の形として指示文に現れる
   - **完了条件は、実装セッションが達成まで自律で進むための停止条件。** 中核は手順4で合意した**業務的な完了条件**で、このサイクル分の受け入れシナリオを Testing Decisions から指示文に**そのまま転記**する(ドメイン語の観測可能な挙動のみ。実装の中身には踏み込まない)。この転記は「内容を書き込まない」原則の意図的な例外 — capture の規律で実装中は docs を直さないため、サイクル進行中に正本と食い違う経路がなく、指示文はサイクルと共に捨てられる。設計上の問いに答えるのが目的のサイクルでは、受け入れシナリオの代わりに「問い X に答えが出て capture 済み」を完了条件とする。「マイルストーン `cycle-N` の open issue が 0」等の機械的条件は補助ゲートとして併記してよいが、完了の定義にはしない — タスク分割も実装ルートもレビューなしの AI 一任であり、issue 全消化は欲しい状態の達成を保証しない。完了条件が無いと、実装セッションは区切りごとに人間の指示待ちで止まるか、逆に根拠なく完成を宣言する。達成前に人間へ停止してよいのは3層判断の層2・層3のエスカレーションだけで、それも解消したら完了条件まで自律継続する
8. タスク分割は AI に一任(分割レビューなし)。実装・確認中は capture の規律を常時適用する

## capture

実装・動作確認中の学びを、発見の都度 GitHub issue に起票する。issue は学びの**受信箱**(捕捉専用)であり、次サイクルのインプットには使わない — だから起票は雑でよい。ただし「雑」は形式の話であって内容の話ではない — 未決の設計選択を確定済みとして書いたり、原因を推測で断定したりしない。そして漏らさない: 起票されなかった学びは cycle-end の棚卸しに乗らず、次サイクルで同じ穴に落ちる。

- `gh issue create` で起票。ラベル(`bug` / `learning` / `spec-change` / `decision-log`)+ 現在サイクルのマイルストーンを付ける
- 対象: エッジケース、想定外挙動、暗黙の要件の発覚、ライブラリのハマり、仕様変更の申し送り、AI の内部設計判断(下記層1)
- バグを捕捉するときは、まず PRODUCT.md / CONTEXT.md にその挙動の仕様があるか照合する。無ければそれは**暗黙の要件の発覚**であり、正しい挙動そのものが未決 — issue には期待動作を1つに決め打ちして書かず、「正しい挙動は未決」としてドメイン語の選択肢を併記する(例: 重複タグは冪等に無視 / エラーで拒否)。解決は先送りしてよく、捕捉段階での同期エスカレーションは不要
- 起票して即続行。その場で docs を直したりスキルを作ったりしない — 蒸留は cycle-end の棚卸しでまとめて行う(生ログのまま溜めて境界で一括処理する方が、文脈が揃い矛盾も見つかる)

### 実装ルートの選択

実装セッションの最初の判断。ルートは cycle-start では決まっていない — 観測可能な挙動を変えないプロセス判断であり、タスク分割と同じく AI に一任される。層1 と同様に、選んだルートと理由を `decision-log` issue に記録する(過剰だった儀式・足りなかった分割が、cycle-end の棚卸しでプロセスの学びとして CLAUDE.md に還流する)。指示文に人間の制約が載っていればそれに従う。

- 仕様が固まっていて作業を分割・並列化したい → /to-prd → /to-issues → /implement。チェーンはマイルストーンを知らないため、発行された issue への `cycle-N` マイルストーン付与を忘れない(`gh issue edit <num> --milestone cycle-N`)
- 設計上の問いに答えるのが目的、または小さく作って学びたい → /prototype や直接実装で素早く回す
- 判断の軸: 儀式コストはサイクル境界に集中させ、サイクル内は最小化する。若いサイクルでは PRD/issue 分割自体が過剰な儀式になりうる。途中でのルート変更も自由(変更も decision-log に記録する)

### AI の自律判断(3層)

CLAUDE.md に init が書き込むルール。実装中は常にこれに従う:

1. **内部設計の変更**(外から見える挙動が変わらない): 自律で進めてよい。ただし判断内容を `decision-log` ラベル付き issue に記録し、確認フェーズで一括報告する(事前承認ではなく事後監査)。記録がないと、動作確認で気づけなかった乖離が学びとして残らず、次サイクルで同じ判断を繰り返す
2. **観測可能な挙動・仕様の変更**: エスカレーション必須。質問は「挙動 A と挙動 B のどちらが欲しいか」というドメイン語の二択に縛る。コード理解を要求する質問は禁止。挙動の選択として表現できない変更は、定義上 層1 に落ちる。バグ修正も現在の観測可能な挙動を変えるなら層2 — 仕様に正しい挙動が明記されていなければ「どの挙動が正しいか」自体が未決の二択であり、決め打ちせず捕捉する(capture 参照)
3. **不可逆・外部影響**(課金、外部 API 契約、データ破壊等): 常に同期エスカレーション。サイクルリセットで取り消せないため例外なし

## cycle-end

サイクル終了の儀式。詳細手順は [references/cycle-end-ceremony.md](references/cycle-end-ceremony.md) を読んでから実行する。順序が重要 — 棚卸し前に close するとルーティング漏れ、タグ前に削除すると参照手段が消える:

1. **ふりかえりの聴取と捕捉**: サイクルを畳む動機とふりかえり(何がうまくいかず、どの決定が覆ったか)を人間から聞き取り、`spec-change` issue として捕捉してから棚卸しに乗せる。方向転換の判断は「畳もうと決めた瞬間」に言語化されることが多く、issue 受信箱にまだ無いことがある — これが無いと、覆す issue との対応づけで動く ADR 遷移と、失効判定で動く CONTEXT 剪定が駆動できない。聞き取るのは**判決**(何が死んだか・何を排除するか)まででよく、次サイクルの新仕様の中身は cycle-start の grilling に送る(ここで詰め始めない)。会話や起動時の引数で既に提示されていれば改めて聞かず、そのまま捕捉する
2. **issue 棚卸し(4宛先ルーティング)**: 2段階で進める。まず open issue **全件**を4宛先(仕様→`PRODUCT.md` / 設計判断→ADR / 実装ハマり→プロジェクトスキル / プロセス→`CLAUDE.md`)または明示的 close に割り当てた**棚卸し台帳**を一括で作り、issue 件数と割当件数の一致を照合する。1件ずつに縛るべきなのは人間の認知負荷がかかる**反映の承認**であって、宛先の割当ではない。台帳ができたら、承認だけを1件ずつ grilling の流儀で取り(1件提示 → 推奨宛先+具体的な反映案 → 確認 → 反映 → 次へ)、全件一括の包括承認は求めない — 認知負荷を超え、確認ゲートが形骸化する
3. **ADR ステータス遷移**: 覆った ADR は削除せず superseded / rejected に遷移(Nygard 式)
4. **CONTEXT.md の剪定**: 失効した用語を削除・書き換え(用語集は生きたドキュメント。追記型の ADR とは扱いが異なる)
5. **テストシナリオ更新**: 受け入れ条件(自然言語)を `PRODUCT.md` の Testing Decisions に反映。テストコードは持ち越さない
6. **close**: マイルストーンの全 issue を close し、マイルストーンも close する
7. **コミット + タグ**: docs の変更をコミットし、`git tag cycle-N` を打つ
8. **src/ 削除**: 使い捨て層(`src/` とテストコード)を削除する。**破壊的操作 — 実行前に必ず、タグの存在と削除対象一覧を提示して人間の明示的な承認を得る**。ルートの設定類(フォーマッター等)は残す。**使い捨て層に付随する成果物**(削除コードの運用手順ドキュメント、コードのコマンドを参照するプロジェクトスキル、パイプラインの実行ログ)も docs/ や `.claude/skills/` に居ても実質使い捨て層 — 削除対象として点検し、ログに未蒸留の学びがあれば先に棚卸しへ乗せる。削除後は**コミットとフック(build/lint)が通ることを確認する** — ビルド設定やフックが使い捨て層(パッケージ定義等)を参照していると、ここで「main は常に起動する」と git 運用自体が壊れる。壊れたら最小の stub を置いて不変条件を守る
9. 次サイクル(cycle-start)か、収束していれば通常開発への移行(transition-check)を提案する。cycle-start は**別セッションで開始する**前提で、その起動用の指示文(使い捨て。コミットしない)をユーザーに渡して儀式を終える。指示文は「儀式完了の現在地(タグ `cycle-N` 済み)と、次の一手 = /cycle-rewrite cycle-start」だけでよい — 学びと仕様はすべて docs に蒸留済みであり、指示文に内容を重複させない

## transition-check

2つの判断を支援する。どちらも最終判断は人間 — 材料を提示する。

### A. サイクル移行(今のサイクルを畳むべきか)

いずれかに該当したら cycle-end を提案する:

- 大幅な要件・仕様・設計の見直しが必要になった
- 認知負荷が高まり AI との意思疎通が困難になった(説明を聞いても納得できない、修正指示が空振りする等)

サイクルは長引かせない。リライトの限界費用は低く、乖離を抱えて進むコストの方が高い。

### B. 収束(通常開発ワークフローへ移行すべきか)

数値の閾値は設けない(プロジェクト規模で意味が変わるため)。以下の定性シグナルは **AI の判定表ではなく、人間に提示する観点リスト**である。AI が独断で「収束した」「本番化の準備が整った」と結論しない。各項目が必要とするデータの種別に注意し、リポジトリの現在断面から読めない項目は推測で埋めず「判定不能 — ◯◯が必要」と明示して人間に差し戻す:

- [ ] 直近サイクルで `spec-change` 系 issue の比率が下がり続けている(**推移** — 複数サイクルの issue 履歴が要る。現在断面だけでトレンドを断定しない)
- [ ] grilling で新しい発見・新しい用語がほぼ出なくなった(直近 grilling の**記憶** — 人間に聞く)
- [ ] 次サイクルの動機が「見直し」ではなく「機能追加のみ」になっている(ユーザーの**意図** — 聞く)
- [ ] PRODUCT.md の Out of Scope が安定している(過去タグとの **diff** で確認できる)

あわせて、**越えようとする境界に直結する open issue** を点検し、名指しで提示する(例: 本番データ保護に関わる未解決の認可・整合性 issue)。件数やラベル比率の材料としてだけ扱わない — 境界を越える前に潰すべき障害物である。境界越えの実行(実データ投入・公開等)自体は層3(不可逆)であり、常に人間の同期承認を要する。

**ハード境界(移行の上限)**: 以下を越える「直前」が、サイクル型を続けられる上限。越えるとリライトコストがマイグレーション費・調整費に変わり激増する:

- 永続データ(本番 DB への実データ投入)
- 外部 API 契約(外部に公開・提供する API)
- 実ユーザー

ユーザーが「そろそろ本番 DB に」「公開したい」等を口にしたら、境界越えの直前である旨を指摘し、収束チェックリストの評価と通常開発への移行を提案する。移行で何が変わるかも具体的に伝える: 永続 docs(PRODUCT.md・ADR・CONTEXT.md)はそのまま資産として引き継がれる一方、**使い捨て層の扱いは反転する** — `src/` とテストコードは以後永続資産となり、サイクル末の全削除は行わない。テストは Testing Decisions のシナリオから再生成して維持体制に入り、PR レビュー等の通常の品質ゲートを復活させる。

移行の作法は2通りあり、人間に選ばせる:
- **最後のサイクルを回す(推奨)**: cycle-end で現行 `src/` を捨て、蓄積した PRODUCT.md から本命実装を書き直し、それを永続資産に昇格して移行する。「動けばOK」品質のコードを本番に持ち込まない
- **現行 `src/` をそのまま昇格**: 直近サイクルの品質が十分なら、儀式を経ずに現行コードを永続資産にしてよい(棚卸しだけは行い、学びを回収してから移行する)

## 規律(全モード共通)

- **テスト**: 若いサイクルでは省略可(人間が手動確認できる規模の間)。手動確認が追いつかなくなったら、PRODUCT.md の Testing Decisions のシナリオから AI にテストコードを再生成させる。テストコードのサイクル間流用は禁止 — 精査コストが再利用の利益を上回る
- **コンテキスト汚染防止**: 旧サイクルのコードを作業ツリーに置かない(AI が読んで勝手に流用する)。参照は `git show cycle-N:src/...` か作業ツリー外への `git worktree`
- **PR 運用はしない**: 人間レビューをコード単位で行わない本ワークフローでは PR は空のゲート=儀式コストであり、PR コメントは issue→docs に一本化した捕捉経路の外に学びを漏らす。儀式コストはサイクル境界に集中させ、サイクル内は最小化する。エージェントは短命ブランチ(worktree)で作業し、ローカルチェック(build/lint、後期サイクルはテスト)通過を条件にローカルで main にマージする。例外: クラウド側リモートエージェント併用時のみ PR を統合点として許容
- **不変条件は「main は常に起動する」のみ**
- **サイクルの区切りとしてのリポジトリ分け・ブランチ分け・サブフォルダ分けは不採用**(資産分断、マージしないブランチの履歴破壊、コンテキスト汚染のため)。単一リポジトリ+タグで区切る
