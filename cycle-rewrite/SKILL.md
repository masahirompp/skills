# cycle-rewrite — サイクル型リライト開発ワークフロー

## 狙い

AI 開発ではコード生成速度が人間のレビュー・理解速度を上回り、人間の頭の中の理論とコードが乖離していく(Naur "Programming as Theory Building")。この乖離=認知負荷は、設計見直し・機能追加・並列実行・時間経過で増え続ける。本ワークフローは認知負荷の発生を防ぐのではなく、発生を前提に定期的にリセットする: サイクルごとにコードをゼロから書き直し(Brooks「捨てるつもりで作れ」— AI によりリライトの限界費用が激減したため再び成立する)、永続資産はコードではなく仕様と学びに置く。

中心原則: **永続層と使い捨て層をリポジトリ内で物理的に分離する。**

| 層 | 中身 | 扱い |
| --- | --- | --- |
| 永続層 | `docs/PRODUCT.md`、`docs/adr/`、`CONTEXT.md`、`.claude/skills/`、`CLAUDE.md` / `AGENTS.md`、昇格済みモジュール(`lib/`) | 厳格に維持。サイクルを跨いで積み上げる |
| 使い捨て層 | `src/` とテストコード | 品質は「動けばOK」。サイクル末に全削除 |

**コードは雑に、ドキュメントは厳格に。** 捨てていいのはコードだけ — 学びを捨てるとサイクルが収束しない。

層の具体的なパスは **init で確定し、CLAUDE.md の規約ブロック「層の定義」に記録する** — 以降の全モード(特に cycle-end の削除対象)はそこが正。既定は使い捨て層 = `src/` とテストコード、昇格モジュール置き場 = `lib/` で、monorepo や `src/` を使わない構成では init で人間と合意して差し替える。本スキルで `src/`・`lib/` と書くのは、CLAUDE.md で確定したパスの略記である。

前提: Matt Pocock のビルドチェーン(/grill-with-docs → /to-prd → /to-issues → /implement、補助として /prototype)と GitHub(issue・マイルストーン・gh CLI)。本スキルはチェーンを再実装せず、起動タイミングの誘導と前提整備に徹する。チェーンは常に全段を踏む義務ではない — 固定なのは「grilling で仕様を詰め PRODUCT.md に反映する」までで、実装ルートは実装セッションがサイクルの性質で選ぶ([実装ルートの選択](#実装ルートの選択)参照)。

## 現在地の把握

どのモードでも、まず状態を確認する。専用の状態ファイルは持たない — git タグとマイルストーンが正であり、儀式の成果物そのものが状態になるため同期ずれが構造的に起きない:

- 現在のサイクル番号 N = `git tag -l 'cycle-*'` の最大番号 + 1(タグが無ければ N = 1)
- サイクル進行中か = マイルストーン `cycle-N` が open か、`src/` が存在するか

スコープガード: CLAUDE.md に cycle-rewrite 規約ブロックが無く、ユーザーが導入を求めてもいないプロジェクトでは、このワークフローを勝手に適用しない。方式を1〜2文で紹介し、導入の意思を確認してから init に進む。

## モード選択

| ユーザーの状況 | モード |
| --- | --- |
| プロジェクトの新規セットアップ | [init](#init) |
| サイクルを始める・仕様を詰め直す | [cycle-start](#cycle-start) |
| 実装・動作確認中に学び/バグ/仕様変更/ハマりが出た | [capture](#capture) |
| サイクルを畳む・リセットする・作り直す | [cycle-end](#cycle-end) |
| 次サイクルに行くべきか、通常開発に移るべきかの相談 | [transition-check](#transition-check) |

「リセットしたい」「作り直したい」は cycle-end(儀式を経てから次へ)。迷ったらユーザーに確認する。ただし capture は迷わない — 学びが出た瞬間が起票の瞬間。

## init

新規プロジェクト(グリーンフィールド)のセットアップ。

1. 前提確認: git リポジトリであること、`gh auth status` が通ること。Pocock チェーンの設定(`docs/agents/issue-tracker.md` 等)が無ければ、先に /setup-matt-pocock-skills の実行を促す(issue トラッカーは GitHub を選ぶ)。既存の README や構想メモがあれば、サイクル1の grilling の入力候補としてユーザーに提示し、採用・差し替え・破棄を確認する — 勝手に前提化も無視もしない
2. **`docs/adr/`・`CONTEXT.md`・`docs/PRODUCT.md` は init では作らない。** 永続層の器を空のまま先回りで用意しない — `docs/adr/` と `CONTEXT.md` は domain-modeling(/grill-with-docs 経由)が最初の ADR・用語が生まれた時点で中身と共に遅延作成し、PRODUCT.md はサイクル1の grilling の結果から合成する。空テンプレートを先に置くと grilling 前に推測で埋められ、仕様が汚染される。init が作る足場は次の 3〜5(CLAUDE.md 追記・ラベル・マイルストーン)だけ
3. **層のパスを確定し**、CLAUDE.md にワークフロー規約ブロック(層の定義・3層自律判断・ブランチ/マージ方針・ADR 解釈ルール・学びの捕捉)を追記する。パスの既定は使い捨て層 = `src/` とテストコード、昇格モジュール置き場 = `lib/` — 既定で足りるなら聞かずに進み、monorepo や `src/` を使わない構成など既定が合わないときだけ削除対象パスを人間と合意する(リポジトリ構成からの推測で決めうちしない)。確定したパスは規約ブロックの「層の定義」に記録する — cycle-end の削除対象はこの定義が正。テンプレートは [references/setup-templates.md](references/setup-templates.md)
4. ラベルを作成する: `learning` / `spec-change` / `decision-log`(`bug` は GitHub 既定)。ラベル = 種別分類、マイルストーン = サイクル区分。この対応を崩さない
5. マイルストーン `cycle-1` を作成する
6. 作成・変更したファイルをコミットする。コミットはローカルに留める — このワークフローは PR を使わずローカルマージで進むため、push は init の手順に含めない(タイミングは人間の判断)
7. cycle-start に進むことを提案する。完了報告には、`docs/adr/`・`CONTEXT.md`・`docs/PRODUCT.md` を**意図的に作らなかったこと**とその理由(grilling の結果から遅延作成する)を明記する — 黙って未作成のままだと、人間には作り忘れと区別がつかない

## cycle-start

サイクル N の開始。仕様を詰め、実装セッションに引き継ぐ。**手順の正は [references/cycle-start.md](references/cycle-start.md) — 読んでから実行する。** 骨子と不変条件:

1. N を導出し、マイルストーン `cycle-N` を確保する。ガード: `src/` が存在し open issue が残るならサイクル進行中 — 実装続行か cycle-end かを確認する
2. インプットは蒸留済み docs(PRODUCT.md・adr/・CONTEXT.md・CLAUDE.md)のみ。旧サイクルの issue・コードは読まない(生ログは矛盾・失効が混在する)
3. /grill-with-docs で仕様を詰める。このサイクルの**業務的な完了条件**(「何がどう動けばこのサイクルは完成か」のドメイン語の受け入れシナリオ数件)を、**grilling の最初の質問群に含めて**人間と合意する — 完了条件が先に立つと以降の質問の要否と深さが定まる
4. grilling の結果を `docs/PRODUCT.md` に反映し(サイクル1は合成 — [references/product-md-synthesis.md](references/product-md-synthesis.md))、完了条件を Testing Decisions に正本として記す。方向が変わったなら残存全ファイルの棚卸し(保持/書き直し/削除)も行う
5. **実装は別セッション** — 完了条件を Testing Decisions から転記した起動指示文を渡して区切る。指示文に仕様の中身は書かない。**実装ルート(チェーン / prototype / 直接実装)は cycle-start では決めず**、実装セッションに委ねる([実装ルートの選択](#実装ルートの選択))。実装・確認中は [capture](#capture) と[実装セッションの規律](#実装セッションの規律)を常時適用する

## capture

実装・動作確認中の学びを、発見の都度 GitHub issue に起票する。issue は学びの**受信箱**(捕捉専用)であり、次サイクルのインプットには使わない — だから起票は雑でよい。ただし「雑」は形式の話であって内容の話ではない — 未決の設計選択を確定済みとして書いたり、原因を推測で断定したりしない。そして漏らさない: 起票されなかった学びは cycle-end の棚卸しに乗らず、次サイクルで同じ穴に落ちる。

- `gh issue create` で起票。ラベル(`bug` / `learning` / `spec-change` / `decision-log`)+ 現在サイクルのマイルストーンを付ける
- 対象: エッジケース、想定外挙動、暗黙の要件の発覚、ライブラリのハマり、仕様変更の申し送り、AI の内部設計判断(下記層1)
- バグを捕捉するときは、まず PRODUCT.md / CONTEXT.md にその挙動の仕様があるか照合する。無ければそれは**暗黙の要件の発覚**であり、正しい挙動そのものが未決 — issue には期待動作を1つに決め打ちして書かず、「正しい挙動は未決」としてドメイン語の選択肢を併記する(例: 重複タグは冪等に無視 / エラーで拒否)。解決は先送りしてよく、捕捉段階での同期エスカレーションは不要
- 起票して即続行。その場で docs を直したりスキルを作ったりしない — 蒸留は cycle-end の棚卸しでまとめて行う(生ログのまま溜めて境界で一括処理する方が、文脈が揃い矛盾も見つかる)
- **起票を人間の確認の後ろに置かない**。期待動作が未決でも、選択肢を併記した issue を**まず起票してから**報告する — 起票は受信箱への記録であって要承認の操作ではない(内容が違えば直せる可逆な操作)。「どちらの挙動が正しいですか」の回答待ちで起票を保留すると、捕捉が人間の応答速度に律速され、学びが漏れ始める。解決を迫る質問は不要で、人間が答えたくなればそのとき issue に反映すればよい

## 実装セッションの規律

実装セッション(cycle-start の指示文で起動される)が従う規律。capture の起票規律と常に併用する。

### 実装ルートの選択

実装セッションの最初の判断。ルートは cycle-start では決まっていない — 観測可能な挙動を変えないプロセス判断であり、タスク分割と同じく AI に一任される。層1 と同様に、選んだルートと理由を `decision-log` issue に記録する(過剰だった儀式・足りなかった分割が、cycle-end の棚卸しでプロセスの学びとして CLAUDE.md に還流する)。指示文に人間の制約が載っていればそれに従う。

- 仕様が固まっていて作業を分割・並列化したい → /to-prd → /to-issues → /implement。チェーンはマイルストーンを知らないため、発行された issue への `cycle-N` マイルストーン付与を忘れない(`gh issue edit <num> --milestone cycle-N`)
- 設計上の問いに答えるのが目的、または小さく作って学びたい → /prototype や直接実装で素早く回す
- 判断の軸: 儀式コストはサイクル境界に集中させ、サイクル内は最小化する。若いサイクルでは PRD/issue 分割自体が過剰な儀式になりうる。途中でのルート変更も自由(変更も decision-log に記録する)

### AI の自律判断(3層)

CLAUDE.md に init が書き込むルール。実装中は常にこれに従う:

1. **内部設計の変更**(外から見える挙動が変わらない): 自律で進めてよい。ただし判断内容を `decision-log` ラベル付き issue に記録し、確認フェーズで一括報告する(事前承認ではなく事後監査)。記録がないと、動作確認で気づけなかった乖離が学びとして残らず、次サイクルで同じ判断を繰り返す
2. **観測可能な挙動・仕様の変更**: エスカレーション必須。質問は「挙動 A と挙動 B のどちらが欲しいか」というドメイン語の二択に縛る。コード理解を要求する質問は禁止。挙動の選択として表現できない変更は、定義上 層1 に落ちる。バグ修正も現在の観測可能な挙動を変えるなら層2 — 仕様に正しい挙動が明記されていなければ「どの挙動が正しいか」自体が未決の二択であり、決め打ちせず捕捉する(capture 参照)
3. **不可逆・外部影響**(課金、外部 API 契約、データ破壊等): 常に同期エスカレーション。サイクルリセットで取り消せないため例外なし

## cycle-end

サイクル終了の儀式。詳細手順は [references/cycle-end-ceremony.md](references/cycle-end-ceremony.md) を読んでから実行する。順序が重要 — 棚卸し前に close するとルーティング漏れ、タグ前に削除すると参照手段が消える:

1. **ふりかえりの聴取と捕捉**: サイクルを畳む動機とふりかえり(何がうまくいかず、どの決定が覆ったか)を人間から聞き取り、`spec-change` issue として捕捉してから棚卸しに乗せる。方向転換の判断は「畳もうと決めた瞬間」に言語化されることが多く、issue 受信箱にまだ無いことがある — これが無いと、覆す issue との対応づけで動く ADR 遷移と、失効判定で動く CONTEXT 剪定が駆動できない。聞き取るのは**判決**(何が死んだか・何を排除するか)まででよく、次サイクルの新仕様の中身は cycle-start の grilling に送る(ここで詰め始めない)。会話や起動時の引数で既に提示されていれば改めて聞かず、そのまま捕捉する
2. **issue 棚卸し(4宛先ルーティング)**: 手順・宛先表・正準ロードマップの正は儀式手順書「issue 棚卸し」節。3原則で動く — **分析は一括**(open issue 全件を4宛先または close に割り当てた台帳は承認不要の AI の分析作業。件数照合付きで、儀式を開始する最初の応答に必ず含める)/ **全体像は先に見せる**(台帳と同じ応答に、儀式手順書の正準ロードマップをそのまま転記する。正準文言は儀式手順書にのみ置き、本書には写さない)/ **承認は逐次**(反映は1件ずつ確認。台帳全体への包括承認を求めず、台帳を提示する応答は1件目の反映案とその1件だけの確認で締める)
3. **ADR ステータス遷移**: 覆った ADR は削除せず superseded / rejected に遷移(Nygard 式)
4. **CONTEXT.md の剪定**: 失効した用語を削除・書き換え(用語集は生きたドキュメント。追記型の ADR とは扱いが異なる)
5. **テストシナリオ更新**: 受け入れ条件(自然言語)を `PRODUCT.md` の Testing Decisions に反映。テストコードは持ち越さない
6. **モジュール昇格(任意・要承認)**: 「次サイクルもそのまま使いたい」モジュールがあれば、削除の例外ではなく**永続層への昇格**として扱う。基準は完成度ではなく**仕様の収束**(そのモジュールに触れる spec-change が直近サイクルで無い・grilling が新発見を出していない・使い捨て層への依存が無い・書き直しの限界費用が例外的に高い)。要望を受けたらこの基準を **AI が実際に点検**し(触れる spec-change issue の検索、使い捨て層への依存の確認)、結果を根拠として人間に提示する — 「検証済みでよく動いている」という申告はきっかけであって根拠にならない(完成度は基準ではない)。人間の承認を得て `lib/` へ移動し、テストを持ち越し、インターフェース契約を永続 docs に書き、ADR に記録する — この4点は分割不可の1操作で、どれかを省くと契約なしで中身を読まれるか、覆ったときの降格経路(ADR 遷移)が無くなる。昇格が続けて発生するなら全体収束の先行指標 — transition-check を提案する
7. **close**: マイルストーンの全 issue を close し、マイルストーンも close する
8. **コミット + タグ**: docs の変更をコミットし、`git tag cycle-N` を打つ
9. **src/ 削除**: 使い捨て層(`src/` とテストコード)を削除する。**破壊的操作 — 実行前に必ず、タグの存在と削除対象一覧を提示して人間の明示的な承認を得る**。ルートの設定類(フォーマッター等)と昇格済みモジュール(`lib/`)は残す。**使い捨て層に付随する成果物**(削除コードの運用手順ドキュメント、コードのコマンドを参照するプロジェクトスキル、パイプラインの実行ログ)も docs/ や `.claude/skills/` に居ても実質使い捨て層 — 削除対象として点検し、ログに未蒸留の学びがあれば先に棚卸しへ乗せる。削除後は**コミットとフック(build/lint)が通ることを確認する** — ビルド設定やフックが使い捨て層(パッケージ定義等)を参照していると、ここで「main は常に起動する」と git 運用自体が壊れる。壊れたら最小の stub を置いて不変条件を守る
10. 次サイクル(cycle-start)か、収束していれば通常開発への移行(transition-check)を提案する。cycle-start は**別セッションで開始する**前提で、その起動用の指示文(使い捨て。コミットしない)をユーザーに渡して儀式を終える。指示文は「儀式完了の現在地(タグ `cycle-N` 済み)と、次の一手 = /cycle-rewrite cycle-start」だけでよい — 学びと仕様はすべて docs に蒸留済みであり、指示文に内容を重複させない

## transition-check

2つの判断を支援する。どちらも最終判断は人間 — 材料を提示する。**観点リスト・応答構成の正は [references/transition-check.md](references/transition-check.md) — 読んでから応答する。** 骨子:

- **A. サイクル移行**: 大幅な要件・設計の見直しが必要になった、または認知負荷が高まり AI との意思疎通が困難になったら、cycle-end を提案する。サイクルは長引かせない — リライトの限界費用は低く、乖離を抱えて進むコストの方が高い
- **B. 収束(通常開発への移行)**: **ハード境界 = 永続データ(本番 DB への実データ投入)・外部 API 契約・実ユーザー。** この直前がサイクル型の上限で、越えるとリライト費がマイグレーション費・調整費に変わり激増する。ユーザーが「そろそろ本番 DB に」「公開したい」等を口にしたら境界越えの直前である旨を指摘し、手順書の**5点構成**(境界の指摘と機構 / 収束チェックリストの点検結果 — 断面から読める材料は AI が自ら取得し、読めない項目は判定不能として人間に差し戻す / 境界に直結する open issue の名指し / 移行の作法2通りと移行後の `src/` の反転 / 最終判断の人間への委譲)で応答する。AI が独断で「収束した」と結論しない

## 規律(全モード共通)

- **テスト**: 若いサイクルでは省略可(人間が手動確認できる規模の間)。手動確認が追いつかなくなったら、PRODUCT.md の Testing Decisions のシナリオから AI にテストコードを再生成させる。テストコードのサイクル間流用は禁止 — 精査コストが再利用の利益を上回る(これは使い捨て層のルール。昇格済みモジュールのテストは持ち越して維持する)
- **昇格済みモジュール(`lib/`)**: 依存方向は使い捨て層 → 昇格モジュールの一方向のみ(逆依存があると src/ 削除で main が壊れる)。実装セッションはインターフェース契約(永続 docs)経由で使い、中身のコードは読まない — 外部パッケージと同格に扱う
- **コンテキスト汚染防止**: 旧サイクルのコードを作業ツリーに置かない(AI が読んで勝手に流用する)。参照は `git show cycle-N:src/...` か作業ツリー外への `git worktree`
- **PR 運用はしない**: 人間レビューをコード単位で行わない本ワークフローでは PR は空のゲート=儀式コストであり、PR コメントは issue→docs に一本化した捕捉経路の外に学びを漏らす。儀式コストはサイクル境界に集中させ、サイクル内は最小化する。エージェントは短命ブランチ(worktree)で作業し、ローカルチェック(build/lint、後期サイクルはテスト)通過を条件にローカルで main にマージする。例外: クラウド側リモートエージェント併用時のみ PR を統合点として許容
- **不変条件は「main は常に起動する」のみ**
- **サイクルの区切りとしてのリポジトリ分け・ブランチ分け・サブフォルダ分けは不採用**(資産分断、マージしないブランチの履歴破壊、コンテキスト汚染のため)。単一リポジトリ+タグで区切る
